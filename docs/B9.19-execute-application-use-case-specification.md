## 1. Purpose

Define the architectural contract of the future Application Use Case `ExecuteModel`:
responsibility, inputs, dependencies, admission rule, lifecycle, result, errors,
freshness, legacy relationship, future compatibility — without implementing it.

## 2. Scope

In scope: items listed in Purpose. Out of scope: any implementation, refactor,
migration, cutover, CLI/API/DTO, multi-runtime, orchestration, GUI, fine-tuning,
tests, commit, push.

## 3. Architectural Context

B9.16 closed evaluation:

```text
capability -> availability policy -> ModelArtifactResolver.resolve
  -> B9.14 compose_and_integrate -> IntegrationResult
  -> B9.15 compose_evaluation -> StrictEvaluation
  -> EvaluateModelCompatibilityResult {evaluated | blocked}
```

B9.18 decided: the evaluation result is an audit/decision record, NOT an
execution ticket. Execution re-resolves, re-acquires, re-validates at launch.
Evaluation imports nothing from runner/execution/selection/run_service.
A separate Execute use case is required behind the ModelRunner abstraction.


Current execution path (verified in run_service/execution/selection/runner):

```text
caller (CLI run/chat, HTTP POST /v1/run, chat sessions)
  -> run_service.run_once / prepare
    -> ModelArtifactResolver.resolve -> ResolvedModelArtifact
    -> prepare: detect_hardware -> assess_model (LEGACY) -> preflight -> selection
    -> ExecutionRequest + validate_execution_request
    -> LlamaCppRunner.run -> subprocess -> ExecutionResult
```

Layer map: ModelSpec/ArtifactSpec/RuntimeCapability = value objects (domain
inputs); assess_model/preflight/selector/request-validation = domain rules;
run_service.prepare/run_once and execution_service.ModelExecutionService =
application orchestration (legacy); LlamaCppRunner/subprocess/detection =
infrastructure.

## 4. Responsibility

Future `ExecuteModel` is the single Application coordinator of real execution:

1. Resolve model_id (+ selectors) via ModelArtifactResolver (re-resolution only).
2. Acquire fresh RuntimeCapability via injected provider (default: detect).
3. Enforce the evaluation admission rule (Section 7) — policy check only.
4. Run ArtifactExecutionPreflight.validate AT execution time (Section 11).
5. Run RuntimeBackendSelector.select for the ExecutionTarget (no private logic).
6. Build + validate the ExecutionRequest (prompt, timeout, target binding).
7. Invoke the injected ModelRunner abstraction (production: LlamaCppRunner).
8. Return the outcome per Section 10.
9. Own only ordering + error mapping; no domain math, no subprocess, no probing
   beyond delegating to the existing prepare-equivalent sequence.
10. Never name LlamaCppRunner, subprocess, CLI, or HTTP.

## 5. Input Contract

| Parameter | Required | Default | Notes |
|---|---|---|---|
| model_id: str | YES | - | Canonical ModelSpec.model_id. |
| quantization: str \| None | no | None | Artifact selector for resolver. |
| filename: str \| None | no | None | Exact-filename selector. |
| prompt: str | YES | - | Non-empty after strip; execution-only. |
| timeout_seconds: float \| None | no | 600.0 (current run_once default) | Finite, > 0. |
| backend_preference: str \| None | no | None (= accept selector) | A wish, never a selected target. |
| admission | no | None (= legacy gate, transitional) | Section 7: verdict summary copy, never the result object. |

EXCLUDED (evaluation-owned, must not enter Execute): required_capabilities,
scope, registry, IntegrationResult, StrictEvaluation, the
EvaluateModelCompatibilityResult object, selected backend/ExecutionTarget,
ExecutableArtifact, filesystem paths.


## 6. Dependency Contract

All collaborators explicit + injectable; production defaults allowed, never
hard-wired. No new interface justified (ModelRunner ABC already exists):

- catalog value: tuple[ModelSpec, ...] from get_catalog (direct value).
- model store: ModelStore (direct).
- artifact resolver: ModelArtifactResolver from store+catalog (direct/factory).
- capability provider: detect_llama_capability callable (callable injection).
- admission evaluator: evaluate_model_compatibility or admission summary value.
- artifact preflight: ArtifactExecutionPreflight(store).validate (instance).
- backend selector: RuntimeBackendSelector().select (instance).
- runner: ModelRunner ABC; production LlamaCppRunner(capability) chosen at the
  composition root (ModelRunner injection).

run_service.prepare step order (compatibility -> preflight -> selection) is the
reference sequence for the future use case.

## 7. Evaluation Admission Boundary

DECIDED: Option 3 — advisory admission signal, re-validated; never authority.

```text
Evaluate (B9.16, independent, any time before)
  -> verdict summary copy (status + strict verdict + identifiers, for audit)
Execute admission policy: proceed ONLY if (a) no admission required, OR
  (b) admission.status == evaluated AND strict verdict != INCOMPATIBLE
  (INSUFFICIENT_EVIDENCE handling deferred; default MUST be deny unless a
   future block specifies otherwise with tests)
  -> Execute STILL performs unconditionally:
     fresh capability -> fresh resolve -> fresh preflight
     -> fresh selection -> validate request -> run
```

Not Option 1 (no gate): discards the only strict functional claim; leaves only
the legacy heuristic. Not Option 2 (hard require + trust): a verdict is
point-in-time and goes stale (Section 11).

Transitional Alpha rule: admission=None means the legacy prepare gate applies
(assess_model reject on INCOMPATIBLE/UNKNOWN + preflight + selection), never
no gate. A future block flips the default to strict-gate-required.

B9.16 `blocked` never authorizes execution and never maps to an Execute outcome.

## 8. CompatibilityResult Boundary

Two live types (verified):

1. app.compatibility.CompatibilityResult (LEGACY): COMPATIBLE / MARGINAL /
   INCOMPATIBLE / UNKNOWN + recommended_runtime/backend + score/warnings.
   Consumer: RuntimeBackendSelector.select, run_service.prepare,
   execution_service.ModelExecutionService. Produced by assess_model.
2. B9.x strict compatibility_domain.CompatibilityResult: COMPATIBLE /
   COMPATIBLE_WITH_CONDITIONS / INCOMPATIBLE / INSUFFICIENT_EVIDENCE +
   checks/conditions. No recommended runtime/backend. Never consumed by
   selection today.

## 9. Execution Lifecycle

```text
Input -> 1.Resolve -> 2.Capability -> 3.Admission gate
  -> 4.Preflight -> 5.Target selection -> 6.ExecutionRequest -> 7.ModelRunner
  -> ExecutionResult
```

Steps 1-3, 6-failures, admission denial = preparation failures (nothing
launched). Step 7 = execution failure (ExecutionResult success=False; raises
only for runner-contract violations). ArtifactSpec != ExecutableArtifact: only
step 4 promotes the logical descriptor to a launchable path-bound fact, valid
solely within this invocation.

## 10. Execution Result Contract

Reuse ExecutionResult (app/execution.py) DIRECTLY — no new type in B9.19:
success, exit_code, stdout, stderr, error {code, message}, warnings (merged
compat+selection+runtime), diagnostics (timing/bytes/exit), runtime_metrics
(optional, UNAVAILABLE when absent). Existing ExecutionErrorCode values already
cover the taxonomy; no new codes.

OUT of the Application surface: ExecutableArtifact.path, argv/env,
executable_path, subprocess handles, full ExecutionTarget internals.
API-safe shapes continue via the existing RunOutcome projection pattern
({model_id, output, exit_code, warnings}) — projection, not replacement; no new
DTO created here.

## 11. Error Taxonomy

Preparation (raise one Application PreparationError-style contract with message
+ preserved warnings; nothing launched): resolution errors, capability
unavailable (available=False, missing executable, invocable=False), admission
denied, ArtifactPreflightError codes (MISSING/PARTIAL/INCONSISTENT/UNSAFE/
INVALID/SIZE_MISMATCH/CHECKSUM_MISMATCH), RuntimeSelectionError codes
(INCOMPATIBLE/UNKNOWN/RUNTIME_UNAVAILABLE/RUNTIME_MISMATCH/
FORMAT_UNSUPPORTED/BACKEND_UNSUPPORTED/CPU_FALLBACK_UNAVAILABLE), invalid
request (empty prompt, bad target, bad timeout, artifact mismatch).
Execution (ExecutionResult success=False with matching code): LAUNCH_FAILED,
TIMEOUT, PROCESS_FAILED, EXECUTABLE_MISSING, PERMISSION_DENIED,
ARTIFACT_INVALID (post-validation disappearance — the TOCTOU catch).
Infrastructure-owned: spawn/wait/kill, signals, exec-bit checks, clocks.
No `blocked` in Execute: preparation denial is its own error, not B9.16 blocked.

## 12. Freshness / Preflight Rules

Plain rule: the file can change between evaluation and execution, so execution
must never trust an earlier validation. Evaluation result != execution
authority. Preflight happens at execution time: validate() runs inside every
Execute invocation, after admission, on the freshly resolved ArtifactSpec
against the live ModelStore (fd-pinned opens, symlink refusal, size/sha256).
No cached ExecutableArtifact, no forwarded path, no skipped checksum.
Capability + target likewise fresh per invocation. UX consequence: evaluate ->
(user delay) -> execute is safe by construction; drift fails closed.

## 13. Legacy Relationship

Coexistence, no migration/cutover (separate decision required):
REUSES: resolver, store/specs, RuntimeCapability + detect, preflight,
selector, ModelRunner ABC + LlamaCppRunner, ExecutionRequest + validation,
ExecutionResult + codes, prepare() step order as reference.
NOT reused as authority: assess_model semantics (transitional gate only),
RunOutcome as canonical return, ModelExecutionService wiring.
Trajectory: ExecuteModel grows beside run_service; CLI run/chat + POST /v1/run
keep calling run_service unchanged. Duplication risk acknowledged (two thin
Application coordinators over shared Domain + Infrastructure); legacy frozen
to bug-fixes once the new one lands. No shared mutable helper between them.

## 14. Future Compatibility

Blocks nothing, speculates nothing. Multi-runtime/backend/GPU = new capability
values + new ModelRunner impls + selector inputs; ExecuteModel signature
unchanged (injected). Jobs/orchestration/scheduling/clusters orchestrate
invocations; GUI/API are thin adapters over Sections 5/10 (+ admission for
approval flows). Fine-tuning/datasets/LoRA = different use cases/runners.
Absent deliberately: job envelopes, registries, retry policies, persistence,
streaming — each needs its own block.

## 15. Non-Goals

No execute_model.py, no code/test/DTO/adapter/interface, no modification of
run_service/execution_service/runner.py/selection.py/LlamaCppRunner, no CLI
(execute/run/evaluate), no HTTP API, no migration/cutover, no multi-runtime/
GPU/orchestration/GUI/fine-tuning, no installs/downloads/execution, no commit,
no push, no history rewrite.

## 16. Acceptance Criteria

Responsibility placed; inputs with required/optional/defaults + exclusions;
deps naming existing contracts only; admission Option 3 + transitional rule;
both CompatibilityResult types with consumers, crossing rules, forbidden
mappings, deferred translation; lifecycle order; result = ExecutionResult;
prep-vs-exec taxonomy on existing codes; preflight timing + TOCTOU rule;
legacy coexistence + duplication risk; future compat without abstractions;
non-goals explicit. All satisfied by Sections 4-15 above.


Rules: Execute/selector consume ONLY type 1 until a dedicated tested migration
block exists. Strict verdict enters Execute ONLY via the Section 7 summary,
never as select() input. Future type-2 bridging needs its own spec + mapping +
tests (translation in Application/adapter layer, not Domain/selector/B9.19).
FORBIDDEN: passing StrictEvaluation.result into select(); synthesizing
recommended_backend; branching on COMPATIBLE_WITH_CONDITIONS inside Execute.
