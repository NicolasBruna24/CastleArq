# B9.46.23 — Runtime Artifact Evidence Representation & Transport Audit

## 1. Executive Summary

B9.46.22 defined `runtime artifact support` as a concrete observed runtime instance consuming the evaluated physical artifact, with execution context and provenance. `RuntimeKnowledge.supports_artifact: bool | None` remains an abstract check result, not the complete evidence representation.

**Verdict: `RUNTIME-ARTIFACT-EVIDENCE-REPRESENTATION-DECIDED`.**

The representation is ephemeral, explicit and transported through the application evaluation boundary. It is not Knowledge, manifest data, artifact state, or a second compatibility engine.

## 2. Current State

```text
format = PASSED
identity = PASSED
architecture = PASSED
runtime artifact support = UNKNOWN
backend = UNKNOWN
overall = INSUFFICIENT_EVIDENCE
```

Existing information:

- `RuntimeCapability`: executable, version, availability, formats, backends, one-shot.
- `ArtifactSpec`: logical model reference, physical locator, artifact_id, format, quantization, size/checksum, state.
- `GGUFArchitectureEvidence`: raw `general.architecture` and provenance.
- `RuntimeKnowledge`: declarative lists and abstract `supports_artifact`.
- `RuntimeBackendSelector`: operational target selection.
- `LlamaCppRunner`: process and `ExecutionResult`.

No existing object represents a completed runtime-instance/artifact observation.

## 3. Evidence Contract

The evidence answers:

> Which observed runtime instance, which physical artifact, under which execution context, produced which observation, and with what provenance?

It is not a claim that the runtime supports every artifact and is not a Knowledge assertion.

## 4. Minimal Fields

```text
runtime_identity: REQUIRED
runtime_version: REQUIRED
artifact_reference: REQUIRED
artifact_format: REQUIRED
artifact_architecture: OPTIONAL
backend: OPTIONAL context
observation: REQUIRED
provenance: REQUIRED
```

- `runtime_identity`: concrete executable/runtime identity, not merely product name.
- `runtime_version`: observed version/build discriminator.
- `artifact_reference`: opaque reference to the evaluated physical artifact, preferably existing artifact_id plus physical locator where available.
- `artifact_format`: format associated with the observed artifact.
- `artifact_architecture`: existing GGUF evidence may be context, not proof.
- `backend`: observed execution context only.
- `observation`: positive, negative, unavailable/not-performed, or error category.
- `provenance`: identifies the runtime observation/inspection source.

## 5. Excluded Fields

Not part of this contract:

- model identity / `model_id`;
- `ModelArtifact.identifier`;
- manifest state (`VERIFIED`);
- arbitrary filesystem state;
- Knowledge format lists as proof;
- Knowledge architecture lists as proof;
- backend availability as proof;
- generated output text;
- tensor/tokenizer/context/quantization/model-size metadata;
- trust/confidence scores;
- cache, persistence schema, event stream or audit log.


## 6. Runtime Instance

A runtime instance is not merely the product name `llama.cpp`. The minimum is the concrete executable/runtime being evaluated with its observed version. For the local case:

```text
/home/brunapc/.local/bin/llama
llama.cpp 0.4.0-dev
```

A product name alone cannot generalize an observation from one executable/build to every installation. This does not create a new runtime registry; it records the identity supplied by the existing capability and execution boundary.

## 7. Physical Artifact Observation

The evidence must reference the concrete physical artifact evaluated by the product flow. Existing `ArtifactSpec.artifact_id` is the appropriate opaque physical reference; its locator may be retained as context.

This does not alter:

```text
ArtifactSpec.model_id -> ModelArtifact.identifier
```

Nor does it change the physical/local meaning of `artifact_id`.

The GGUF reader may supply architecture as independent physical evidence, but it does not produce runtime-consumption result.

## 8. Backend Context

Backend is optional context, not support proof. If the observation ran with CPU or Vulkan, that context may be recorded. Its presence alone never produces `PASSED`; the positive observation is the relevant result.

The backend gate remains separate. This audit does not implement pre-admission backend selection.

## 9. Owner, Producer and Consumer

```text
OWNER =
  application/evaluation physical-observation boundary

PRODUCER =
  read-only runtime/artifact observation boundary

CONSUMER =
  existing strict evaluation composition/projector
```

`RuntimeCapability` is not sufficient: it detects availability and capability, not consumption of the selected artifact. `LlamaCppRunner` can produce an execution result, but it is an execution seam and may run only after compatibility/selection; using it as evidence producer would require a deliberate pre-evaluation probe or separately approved observation boundary.

`ModelStore`, `ArtifactSpec` and `ModelArtifact` do not own this evidence. Knowledge is not the owner because the value is concrete and observed.

## 10. Transport

The evidence is ephemeral and explicit:

```text
producer
  -> application evaluation input
  -> compose_evaluation
  -> evaluate_strict
  -> runtime artifact projection
  -> _check_runtime()
```

The existing `physical_evidence` transport is a precedent, but currently carries GGUF architecture only. The future transport must be distinct enough to keep the GGUF reader separate from runtime observations, without a second pipeline.

`EvaluationContext` should not become a container for arbitrary evidence: it already carries declarative `RuntimeKnowledge` and backend context. A dedicated application-level ephemeral input is the minimal boundary.

## 11. Projection to `_check_runtime()`

```text
RuntimeArtifactEvidence
  -> tri-state result
  -> RuntimeKnowledge.supports_artifact
  -> _check_runtime()
```

Conceptual mapping:

```text
positive observation -> True -> PASSED
explicit negative observation -> False -> FAILED
no observation/unavailable/not performed -> None -> UNKNOWN
observation error -> producer/transport error, not False
```

The rich evidence must remain available to the projection layer long enough to preserve provenance. The evaluator remains pure and interprets the supplied tri-state field.


## 12. B9.46.24 Implementation Boundary

La inspección de implementación confirmó que no existe una observación positiva real antes de `evaluate_model_compatibility()`.

- `RuntimeCapability` sólo detecta executable/version/availability/formats/backends/one-shot.
- `ArtifactExecutionPreflight` valida filesystem, tamaño y checksum; no carga el artifact en llama.
- `GGUFArchitectureEvidence` sólo lee `general.architecture`; no demuestra consumo.
- `LlamaCppRunner` sí puede observar un proceso real, pero pertenece al execution path posterior a compatibility/admission/selection.

Por tanto, no existe un producer dentro de las fronteras actuales que pueda producir legítimamente `RuntimeArtifactEvidence.observation=positive` antes de la evaluación strict. Ejecutar `LlamaCppRunner` como probe previo introduciría un segundo pipeline de ejecución y una nueva responsabilidad de pre-admission; usarlo sólo por capacidad/preflight sería sobreafirmación.

La implementación queda bloqueada honestamente:

```text
RUNTIME-ARTIFACT-EVIDENCE-IMPLEMENTATION-BLOCKED
```

No se creó `RuntimeArtifactEvidence`, no se conectó un segundo producer, no se alteró `_check_runtime`, no se cambió Knowledge, admission, runner, GGUF reader, identities, persistence, backend ni selector.

## 13. Error and Purity Semantics

El futuro producer debe diferenciar:

```text
positive observation
negative observation
observation not performed
runtime unavailable
artifact unavailable
observation error
```

Un error no puede proyectarse como `False`. La evidencia seguirá siendo efímera y no persistente. El evaluator permanecerá puro, sin filesystem, subprocess ni ejecución.

## 14. Next Decision

Antes de implementar el wiring, debe decidirse una única alternativa arquitectónica:

1. un probe read-only explícito y aprobado antes de admission, reutilizando el runtime real sin ser un segundo pipeline de generación; o
2. cambiar el contrato de `runtime artifact support` para consumir evidencia de una ejecución posterior, revising el orden de gates; o
3. mantener `UNKNOWN` y no presentar una observación real como evidencia strict.

No se debe resolver implícitamente con un subprocess extra ni con `RuntimeCapability`.

## 15. Invariants Preserved

```text
ArtifactSpec.model_id -> ModelArtifact.identifier
ArtifactSpec.artifact_id -> physical/local identity
ModelSpec.architecture = "Transformer"
GGUFArchitectureEvidence remains ephemeral and non-persistent

```

## 16. Validation

No se ejecutaron tests ni E2E porque el bloque se detuvo antes de implementación al no existir un producer legítimo dentro de los boundaries permitidos. No se modificó ningún archivo de producción o tests.

## 17. Final Verdict

```text
RUNTIME-ARTIFACT-EVIDENCE-IMPLEMENTATION-BLOCKED
```

Primer bloqueo: no existe una observación runtime-artifact positiva antes de la evaluación strict que puedaproducedirse sin crear un segundo pipeline o cambiar el orden arquitectónico de gates.

The evidence may be correlated with existing facts but does not own or duplicate them.
