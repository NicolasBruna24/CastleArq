# B9.46.29 — Real E2E Acceptance Contract

## 1. Executive Summary

Para CastleArq 0.1, **Real E2E** significa que el caller de producto recibe una solicitud, resuelve un artifact local real, selecciona un runtime/backend reales, ejecuta un proceso real de `llama.cpp` sobre un GGUF real y devuelve un `ExecutionResult` observable al caller.

No se requiere telemetría adicional. La evidencia mínima es operacional: entrada real, artifact real, executable real, invocación real, proceso terminado, salida observable y resultado exitoso. `exit_code == 0` no significa por sí solo artifact loaded; combinado con stdout real y contexto de ejecución sí es suficiente para E2E operacional 0.1, sin universalizar compatibilidad.

El contrato queda resuelto siempre que la implementación cambie el tratamiento de `runtime artifact support=UNKNOWN`: no debe seguir siendo una condición determinante de admission para la primera ejecución E2E. Su significado permanece Knowledge abstracta pre-ejecución, no consumo observado.

## 2. E2E Definition

- **Unit test**: componentes aislados, con dobles o fixtures.
- **Integration test**: varias capas reales, pero runner/proceso/artifact simulados o reemplazados.
- **Runtime integration**: CastleArq invoca un runtime real, pero puede no cubrir el caller completo.
- **Real E2E**: el flujo de producto completo llega desde CLI/application hasta un runtime real y un artifact real, y retorna un resultado observable.

CastleArq 0.1 sólo declara Real E2E en el último sentido. Un `FakeModelRunner`, un subprocess mockeado, un executable inexistente o un `ExecutionResult` sintético no son Real E2E.

## 3. Current End-to-End Flow

El recorrido productivo es:

```text
User command
  -> app.main.execute_command
  -> compose_execute_model_dependencies
  -> evaluate_model_compatibility
       -> ModelArtifactResolver
       -> ModelStore/catalog
       -> GGUF architecture read
       -> strict evaluation
  -> to_admission
  -> execute_model
       -> re-resolve artifact
       -> fresh RuntimeCapability
       -> _check_admission
       -> assess_model operational compatibility
       -> ArtifactExecutionPreflight
       -> RuntimeBackendSelector
       -> ExecutionRequest validation
       -> LlamaCppRunner
       -> real llama.cpp process
       -> real GGUF artifact
       -> ExecutionResult
  -> stdout/exit-code projection by CLI
```

`execute_command` devuelve 0 sólo cuando `result.success` es true y escribe `result.stdout`; devuelve 1 para preparación/admission denied o resultado fallido. La ejecución se re-resuelve y re-valida: una evaluación anterior no es autoridad de ejecución.

## 4. Required E2E Conditions

Para declarar Real E2E deben cumplirse todas estas condiciones:

1. **CastleArq accepted the request**: CLI syntax y prompt/model id válidos; el caller alcanza `execute_model` sin error de uso.
2. **Artifact resolved**: `ModelArtifactResolver` devuelve el `ModelSpec` y `ArtifactSpec` pretendidos, con `artifact_id` real.
3. **Artifact physically available**: el `ArtifactSpec` resuelve a un path local real y `ArtifactExecutionPreflight` lo valida como archivo final no symlink, con tamaño/checksum cuando declarados.
4. **Runtime capability real**: `RuntimeCapability.executable_path` existe, es regular, ejecutable y corresponde al runtime local detectado.
5. **Target selected**: el selector devuelve un `ExecutionTarget` cuyo runtime coincide con la capability y cuyo backend está soportado.
6. **Real process invoked**: `LlamaCppRunner` construye argv con `--model` y el path real y llama al proceso real, sin fake runner ni stub de subprocess.
7. **Process completed**: el proceso termina normalmente o falla de forma observable; un launch error no es éxito.
8. **Observable output**: stdout no vacío y coherente con salida observable del comando, o el fallo conserva stderr/error verificables.
9. **Successful result**: `ExecutionResult.success=True`, `exit_code=0` y `execute_command` devuelve 0.

## 5. Real Artifact Requirement

El E2E utiliza un `ArtifactSpec` real, su `artifact_id` calculado y un archivo físico real en ModelStore. El path absoluto es necesario para el argv; `artifact_id` es la identidad física/local que debe accompany evidence package. No se permite mock artifact, fake path, synthetic `ExecutionResult`, runner fake ni nombre de archivo como sustituto de identidad.

La verificación externa puede comparar el `artifact_id` y filename declarados con el directorio de ModelStore y el archivo final observado, sin persistir RuntimeArtifactEvidence.

## 6. Real Runtime Requirement

El runtime debe ser el `llama` executable local mostrado por `RuntimeCapability.executable_path`. La evidencia es capability detectada, path existente/regular/ejecutable, nombre runtime compatible con `ExecutionTarget.runtime`, version si está disponible y proceso real publicado. La validación manual directa de llama.cpp demuestra que el binario puede funcionar, pero no sustituye la evidencia de que CastleArq lo invocó.

Un `LlamaCppRunner` con `run_process` inyectado por un fake no cumple Real E2E aunque el resto del pipeline sea real.

## 7. Observable Runtime Result

El mínimo de CastleArq 0.1 es evidencia operacional, no prueba de consumo interno. Se acepta un `ExecutionResult` exitoso con stdout no vacío como evidencia de que el proceso real produjo salida observable durante la invocación. No se requiere evento estructurado `MODEL_LOADED` ni `INFERENCE_STARTED`.

La evidencia no demuestra por sí sola que una observación estructurada de artifact load fue emitida, que todas las versiones/builds soportan el artifact ni que el resultado se repetirá para cualquier prompt/artifact.

## 8. stdout / stderr Evidence

`LlamaCppRunner` captura stdout y stderr; `execute_command` escribe stdout cuando `success=True` y stderr cuando el resultado falla. `parse_llama_human_output()` sólo extrae métricas opcionales; no convierte stdout en una afirmación estructurada de model load.

Para el E2E 0.1, stdout no vacío de un proceso real exitoso es evidencia suficiente de output observable. No se aplica heurística de contenido para afirmar corrección semántica. Stderr puede demostrar diagnóstico o fallo cuando acompaña `success=False`; por sí solo no demuestra consumo ni rechazo tipificado.

## 9. exit Code Semantics

- `exit_code == 0`: el proceso terminó con status exitoso; combinado con stdout real y contexto de ejecución es suficiente para Real E2E operacional 0.1.
- `exit_code != 0`: el proceso terminó con fallo; el E2E no es exitoso y se conservan stdout, stderr y error.
- `exit_code is None`: timeout, launch failure o proceso no completado; no es E2E exitoso.

`0` no significa universalmente `artifact loaded`, `supports_artifact=True` ni compatibilidad universal. Es éxito del proceso en esta ejecución concreta.

## 10. ExecutionResult Semantics

`ExecutionResult` es la prueba mínima del resultado del proceso: success, exit code, stdout, stderr, error, warnings, diagnostics y metrics opcionales. En el E2E debe ser producido por `LlamaCppRunner` real y devuelto, no construido por un test.

Su éxito demuestra el resultado operacional one-shot. No demuestra por sí solo carga estructurada ni Knowledge. La evidencia puede ser temporal y no requiere persistencia.

## 11. Runtime Artifact Support Boundary

`RuntimeKnowledge.supports_artifact` conserva su significado Knowledge abstracto. `True` sólo sería una assertion normativa scoped; `None` significa que no existe assertion. Ninguno se deriva del resultado E2E.

Para el E2E 0.1 se decide **D + B**: `runtime artifact support` deja de ser condición necesaria de la primera admission real y deja de representar “consumo concreto”. No se elimina el check conceptual: se conserva para Knowledge, pero no debe bloquear la ejecución E2E cuando el resto de precondiciones reales están satisfechas. La evidencia post-ejecución no se convierte automáticamente en ese check.


La calidad, corrección semántica o universalidad de la respuesta no es requisito del primer E2E. La evidencia operacional no inventa una taxonomía de calidad del modelo.


## 12. EvaluationAdmission Contract

Admission debe significar: **no existe una incompatibilidad conocida que obligue a bloquear la solicitud**; no debe demostrar que una inferencia independiente ya loadará el artifact o tendrá éxito.

El contrato mínimo es:

- evaluación y resolución terminadas sin bloqueo conocido;
- `EvaluationAdmission` no debe convertir `runtime artifact support=UNKNOWN` en `INSUFFICIENT_EVIDENCE` para esta primera ejecución;
- el gate operacional `assess_model()` puede rechazar por recursos, runtime o backend;
- preflight y selector siguen siendo obligatorios y fail-closed.

Admission no sustituye la ejecución. `EvaluationAdmission` no autoriza por sí sola; sólo la aplicación y gates posteriores hacen posible el lanzamiento. Un cambio futuro debe preservar su carácter deny-only y no exigir evidencia post-ejecución.

## 13. Failure Semantics

El E2E falla si ocurre cualquiera de estos casos:

- artifact missing, unsafe, partial, inconsistent o inválido para preflight;
- capability/runtime missing, no invocable o executable inexistente/no ejecutable;
- admission bloquea la solicitud;
- compatibilidad operacional o selector rechaza;
- launch error, permission denied o timeout;
- proceso termina con exit code distinto de cero;
- `ExecutionResult.success=False`;
- proceso termina con éxito pero no existe stdout observable para la afirmación de E2E exitoso.

`INSUFFICIENT_EVIDENCE` o `UNKNOWN` son denial/admission outcomes, no `EXECUTION_FAILED`. Un fallo de preparación antes del proceso es preparación fallida, no evidencia de que llama.cpp rechazó el artifact. Un exit code no cero después de launch sí es fallo de ejecución observado, aunque la causa exacta sea desconocida.

## 14. Minimal Evidence Package

El paquete temporal mínimo para una persona externa debe contener:

```text
1. comando/CLI de CastleArq y sus entradas identificables
2. ArtifactSpec.artifact_id y filename
3. path filesystem real validado por preflight
4. RuntimeCapability.name, executable_path y version si existe
5. ExecutionTarget.runtime y backend
6. argv real, incluyendo --model y path
7. exit code
8. stdout
9. stderr
10. ExecutionResult final proyectado por execute_command
```

No requiere hashes de contenido, metrics, token accounting, GPU utilization, profiling, timestamps adicionales, telemetry, persistencia ni un nuevo schema. La ausencia de paquetes persistentes no impide aceptar una validación E2E local.

## 15. E2E Acceptance Statement

> CastleArq E2E real se considera demostrado cuando una invocación real de la CLI/application resuelve un `ArtifactSpec` con artifact real y `artifact_id` real, valida su path físico, selecciona un `RuntimeCapability` real y backend soportado, `LlamaCppRunner` construye un argv con ese artifact e invoca el executable real, el proceso completa con `exit_code == 0`, devuelve stdout observable no vacío en `ExecutionResult.success=True`, y `execute_command` proyecta el resultado con exit code 0.

La afirmación no requiere `MODEL_LOADED`, telemetría ni Knowledge assertion positive, y no afirma soporte universal.

## 16. Minimal Implementation Required

El mínimo cambio de producción antes de ejecutar la validación es acotado:

1. Revisar el gate de admission/strict para que `runtime artifact support` deje de ser determinante bloqueante del E2E, sin cambiar su semántica Knowledge.
2. Mantener `assess_model()`, preflight, selector, `LlamaCppRunner` y `ExecutionResult` como límites existentes.
3. Añadir o ejecutar una validación opt-in local con artifact/llama.cpp reales, sin fake runner, fake subprocess o mock result.
4. Capturar temporalmente el paquete de evidencia definido arriba; no introducir persistencia ni observabilidad productiva nueva.

No se necesita modificar `RuntimeArtifactEvidence` para esta aceptación operacional: puede seguir siendo evidencia post-ejecución futura, no un requisito de E2E 0.1.

## 17. Next Block

El siguiente bloque debe ser implementación concreta y acotada del cambio mínimo de admission y de una validación E2E opt-in con runtime/artifact reales. No debe abrir otra auditoría de señales terciarias ni crear una segunda pipeline.

La implementación debe demostrar dos casos separados: E2E real exitoso y denial/preflight failure sin invocar un proceso cuando corresponda.

## 18. Verdict

REAL-E2E-ACCEPTANCE-CONTRACT-RESOLVED

CastleArq 0.1 puede declarar Real E2E con evidencia operacional mínima verificable: CLI real, artifact real, runtime executable real, invocación real, proceso exitoso, stdout observable, `ExecutionResult` exitoso y proyección CLI exitosa. `runtime artifact support=UNKNOWN` deja de bloquear esta primera aceptación y no se confunde con evidencia post-ejecución de consumo. La ausencia de `MODEL_LOADED` estructurado no bloquea el primer E2E real.
