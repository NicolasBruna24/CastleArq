# B9.8 — Evaluation Domain Adapter Design

Estado: contrato implementado como adapter puro. No integra B9.3 con
producción: no toca `ModelExecutionService`, `resolver.py`, `execution.py`,
`selection.py`, `compatibility.py` ni reemplaza el evaluador legacy.

## 1. Problema

El flujo vivo opera con `ModelSpec`/`ArtifactSpec`/`RuntimeCapability`
(`models.py`, `runtimes.py`), que mezclan datos declarativos con heurística
heredada. B9.3 exige el dominio estricto `Model`/`ModelArtifact`/`EvaluationContext`
(`model_domain.py`, `compatibility_evaluator.py`), donde `None` significa
desconocido y ningún default es un hecho. B9.8 es el adapter puro entre ambos
dominios; B9.7 ya resuelve `KnowledgeRegistry → RuntimeKnowledge`.

## 2. Frontera de dominios

- `ModelSpec` mezcla catálogo y heurística: `supported_runtimes`
  (default `"llama.cpp / llama.app"`), `supported_backends` (default
  `"Vulkan"/"CPU"`), `task`, `quantizations` (bits/quality) son
  **recomendaciones heredadas, nunca conocimiento**. `Model` solo transporta
  hechos tri-state (`None` = desconocido, jamás fabricado).
- `ModelSpec.architecture = "Unknown"` y `ArtifactSpec.format = "Unknown"` son
  **centinelas** legacy; en el dominio B9 equivalen a `None`.
- `ModelSpec.model_id` es una property con fallback `id or name` que **fabrica**
  identidad; B8.1 prohíbe fabricar: el adapter usa `spec.id` solo si existe.
- `RuntimeCapability.name` (`"llama.cpp CLI"`) es un display name;
  `compatibility_names` contiene el alias compuesto `"llama.cpp / llama.app"`.
  El KB exige canonical_id exacto: ninguno de esos strings es canonical per se;
  la resolución es por pertenencia exacta contra los canonical_ids del registry.
- `RuntimeCapability.version` es texto crudo de CLI, no un identificador
  canónico de versión (B9.5 usa valores declarados como `b5377`).

Campos que NUNCA se adaptan: `task`, `supported_runtimes`, `supported_backends`,
`quantizations` (hacia el Model), `format`/`size_bytes` del spec (hacia el
Model), `compatibility_names`/`backend_arguments` (hacia conocimiento),
`version` (hacia scope).

## 3. Contrato Model (`to_model`)

| Spec | Model | Regla |
|---|---|---|
| `name` | `identity.name` | copiar; vacío → `ValueError` |
| `id` | `identity.model_id` | solo si `spec.id` no es None; sin fallback a `name` |
| `provider` | `provenance.source` | metadata declarativa; `"Unknown"` → None |
| `architecture` | `architecture.architecture` | verbatim si explícito; `"Unknown"`/vacío → None; nunca desde el nombre |
| — | `architecture.model_type` | siempre None |
| `parameter_count_b` | `architecture.parameters` | `round(x * 1_000_000_000)` (transformación aritmética declarada) |
| — | `architecture.active_parameters` | siempre None (no se asume = parameters) |
| `context_length` | `max_context` | copiar |
| — | `capabilities` | `ModelCapabilities()` todo None; nunca desde `task` |
| `task`, `supported_runtimes`, `supported_backends`, `quantizations`, `format`, `size_bytes` | — | NO copiar |
| — | `artifacts` | siempre `()` |

## 4. Contrato Artifact (`to_artifact`)

| Spec | ModelArtifact | Regla |
|---|---|---|
| `format` | `format` | verbatim si explícito (p. ej. `"GGUF"`); `"Unknown"`/vacío → None; nunca desde la cuantización |
| `artifact_id` / `model_id` | `identifier` | **siempre None** (N-1): fabricar identidad produciría FAILED determinante espurio |
| — | `precision` | `ModelPrecision(None, None)` siempre; `"Q4_K_M"` no implica precisión (B8.1) |
| `quantization` | `quantization` | `ModelQuantization(UNKNOWN)` siempre (N-2); el label nunca decide QUANTIZED |
| `size_bytes` | `storage_size_bytes` | copiar si disponible; jamás figura de memoria |

## 5. Runtime adapter (`resolve_runtime`, `runtime_scope`)

- `resolve_runtime(registry, capability)`: candidatos = subjects RUNTIME del
  registry cuyo `canonical_id` sea **exactamente igual** a `capability.name` o
  aparezca **exactamente** en `capability.compatibility_names`. Unicidad
  obligatoria: 0 o >1 coincidencias → `ValueError`. Sin fuzzy, substring,
  case-insensitive, aliases inventados ni tablas de display names. Con el
  dataset real: `("llama.cpp / llama.app", "llama.cpp")` resuelve `llama.cpp`
  (nunca `llama.app`); una capability con `"ollama"` exacto resuelve `ollama`.
- `runtime_scope(scope=None)`: **siempre `KnowledgeScope()`** en v1 (N-3:
  `capability.version` no se transforma). Sin platform, sin backend en scope
  (el backend es entidad/object y `EvaluationContext.backend`). Un scope
  explícito se conserva tal cual, sin completarlo.

Limitación documentada: sin plataforma canónica, el conocimiento

## 6. Backend canónico (decisión N-4)

Tabla declarativa exacta y cerrada: `CPU→cpu, Vulkan→vulkan, CUDA→cuda,
ROCm→rocm, HIP→hip, SYCL→sycl`. Es identidad canónica explícita, no fuzzy:
sin `lower()`, sin substring, sin aliases dinámicos. Fuera de tabla → `None`
(UNKNOWN en B9.3, nunca UNSUPPORTED).

## 7. `build_evaluation_context`

```text
(registry, capability, backend, required_capabilities, scope)
  → resolve_runtime → project_knowledge (B9.7)
  → EvaluationContext(runtime=projection.runtime_knowledge,
                      backend=canonical|None, hardware=None,
                      required_capabilities=caller-provided)
  → (EvaluationContext, KnowledgeProjection)
```

- `required_capabilities` proviene EXCLUSIVAMENTE del caller; nunca se deriva
  de `task`, de la capability ni del runtime knowledge (B9.4 §20).
- `hardware=None` siempre. No se ejecuta `evaluate()`; no se modifica
  `CompatibilityEvaluator`.
- La capability del runtime (`unrepresentable` en B9.7) jamás se convierte en
  `ModelCapabilities` del modelo.

## 10. Pureza y determinismo

`evaluation_adapter.py` no importa `runtimes.py` (usa `TYPE_CHECKING` para el
type hint y duck-typing estructural en runtime), ni subprocess/socket/urllib/
pathlib/os-environment; no ejecuta detectores, comandos, red ni descargas; sin
`eval`/`exec`. Mismo input → mismo output; inputs inmutables; outputs frozen.

## 11. API

```python
                             ) -> tuple[EvaluationContext, KnowledgeProjection]
```

## 12. Resultado esperado con el dataset real

Con B9.6.1 en scope vacío, la evaluación honesta de un spec legacy produce
`INSUFFICIENT_EVIDENCE`: `identifier=None` (identity UNKNOWN), backend
legacy `"CPU"`→`cpu` (PASSED para llama.cpp), capabilities None, architecture
None y **formato UNKNOWN**: B9.3 compara el formato con pertenencia exacta
case-sensitive (`"GGUF" != "gguf"`) y B9.8 no normaliza cadenas (ningún
case-folding autorizado); degradar a UNKNOWN es el comportamiento honesto y
queda documentado como limitación (no como regresión). B9.8 no fuerza
compatibilidad.

## 9. Provenance

`RuntimeKnowledge` no transporta provenance (B9.4 §20); B9.8 no la inyecta ni
la falsifica. La trazabilidad completa vive en `KnowledgeProjection`, que
`build_evaluation_context` devuelve junto al contexto. `ModelProvenance`
recibe solo metadata declarada del catálogo (`provider`).

platform-scoped del dataset (Vulkan/HIP/SYCL/ROCm scoped, fila b5377) es
inalcanzable y degrada a UNKNOWN aguas abajo. Además, la capa de detección
actual solo produce una capability real de llama.cpp CLI; cuando exista una de
Ollama, sus `compatibility_names` deberán contener el exacto `"ollama"`.
