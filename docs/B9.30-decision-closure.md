# B9.30 — Decision Closure

> Cierre técnico de las decisiones identificadas en `docs/B9.30-user-level-python-packaging-specification.md`. Este documento no implementa B9.30.

## Status and Evidence

Fuentes normativas: `docs/B9.29-linux-distribution-readiness.md` y `docs/B9.30-user-level-python-packaging-specification.md`.

El código real confirma:

- `pyproject.toml` declara `castlearq`, versión `0.1.0`, `requires-python = ">=3.10"` y `setuptools.build_meta`.
- No existe `[project.scripts]`; `app/main.py` contiene `main() -> int` y `python3 -m app.main` es la entrada actual.
- `--help` existe, `--version` no existe.
- `load_config()` usa por defecto `Path("config/config.toml")` y se llama desde `app.main.print_models()`.
- `default_models_directory()` usa rutas `~`-based y no `XDG_DATA_HOME`; `ModelStore()` se construye directamente en CLI, API, wiring, planner, evaluación y ejecución.
- `_open_root(create=True)` crea la raíz; `list_artifacts()` no crea.
- `app/api.py:get_version()` lee `pyproject.toml` relativo al paquete y devuelve `unknown` si no está disponible.

No se identificó un `RuntimeContext` de runtime. `EvaluationContext` y `EnvironmentContext` son contratos de otros subsistemas y no deben reutilizarse para bootstrap.

## Decision 1

Status: CLOSED

Decision: `importlib.metadata.version("castlearq")` será la fuente primaria de versión en cualquier paquete instalado, normal o editable. La única alternativa autorizada para checkout sin metadata será un fallback de desarrollo explícito que lea la versión de `pyproject.toml`; no existirá una segunda constante de versión ni `app/_version.py`.

### Rationale

`importlib.metadata` pertenece a la biblioteca estándar de Python y está disponible en Python `>=3.10`. Lee la metadata instalada, funciona en instalación normal y editable, y evita que el runtime instalado dependa de la presencia del checkout. `pyproject.toml` permanece la única fuente de verdad de declaración porque el backend lo usa para construir la metadata. El fallback de source cubre únicamente `python3 -m app.main` o desarrollo equivalente cuando la distribución todavía no está instalada.

La función de versión debe ser un adaptador único, compartido por CLI y API. Debe distinguir metadata ausente de una versión inválida y exponer un resultado controlado. La salida de `castlearq --version` será `castlearq <version>` y tendrá exit code 0 cuando la versión pueda resolverse.

### Rejected alternatives

- **`app/_version.py`:** rechazado porque duplicaría `pyproject.toml` y exigiría sincronización manual; añade mantenimiento y riesgo de drift.
- **setuptools/PEP 621 dinámico:** rechazado para B9.30 porque no es necesario para resolver runtime, añade complexity/tooling y no mejora la consulta de metadata del paquete instalado. La metadata estática actual ya es suficiente.

### Implementation consequence

- Crear un adaptador de versión compartido, sin dependencia de `pyproject.toml` en el path normal.
- Mantener `project.version = "0.1.0"` como fuente declarativa única.
- No declarar una versión superior ni modificar el backend.
- Actualizar API y CLI para usar el mismo adaptador.
- El fallback de checkout debe ser conscious/testado; no debe ejecutarse como lectura de archivos durante `import app` si metadata no es necesaria para importar.

### Tests required

- Installed package: metadata devuelve la versión declarada.
- Editable install: metadata devuelve la versión declarada.
- Checkout/development con metadata ausente: fallback controlado y correcto.
- Metadata ausente durante `--version`: comportamiento definido y testeado, sin leer rutas relativas al cwd.
- API health/version y CLI `--version` devuelven la misma versión.
- Python 3.10 compatible, sin dependencia adicional.

## Decision 2

Status: CLOSED

Decision: la resolución se implementará en `app/main.py` como bootstrap explícito y en un resolver de rutas puro compartido por los adaptadores existentes. La CLI resolverá configuración y ModelStore antes de construir dependencias de comandos que los necesiten. `app.model_store.default_models_directory()` y `app.compatibility.load_config()` dejarán de depender implícitamente del cwd mediante APIs explícitas de resolución; `ModelStore(root)` seguirá recibiendo la raíz resuelta. No se añadirá un `RuntimeContext` general.

### Code-real analysis

1. La CLI entra por `app.main.main()`, parsea argumentos y despacha handlers.
2. `load_config()` se llama en `print_models()`; el resto de la compatibilidad usa `CompatibilityConfig` como valor, no el archivo.
3. `default_models_directory()` se invoca indirectamente desde `ModelStore()` en `main`, `api`, `application_wiring`, `downloads/planner`, `evaluate_compatibility` y `execute_model`.
4. Application recibe `ExecuteModelDependencies.model_store`; los comandos reciben `ModelStore` directamente o mediante planners/resolvers. La configuración se pasa como `CompatibilityConfig` al evaluador.
5. La creación física ocurre en `ModelStore._open_root(create=True)` mediante `mkdir(parents=True)`, y en `_open_directory(..., create=True)` mediante `os.mkdir`.
6. `import app` no debe crear rutas. `--help` y `--version` deben terminar antes de resolver ModelStore. `list` sí debe resolver ModelStore, pero debe listar sin crear.
7. `detect`, `models`/compatibilidad y otros comandos no deben inicializar ModelStore salvo que su operación realmente lo necesite. `download`, `run`, `execute` y `chat` sí necesitan acceso al store; `serve` debe usar las mismas dependencias de API que ya usa.
8. Los imports actuales son mayormente import-safe, pero el resolver debe ser puro y todo acceso a filesystem debe quedar detrás de funciones/operaciones explícitas.

### Option A — Explicit CLI bootstrap (selected)

Ventajas: muestra el orden real, permite que help/version no inicialicen recursos, centraliza precedencia y facilita tests de cwd sin tocar casos de uso. Es el menor cambio compatible porque `app.main` ya es el composition/dispatch boundary.

### Option B — Infrastructure auto-resolution (rejected)

Rechazada porque escondería la resolución detrás de `ModelStore()`/`load_config()`, dificultaría distinguir read de write, conservaría defaults cwd-dependent y podría crear side effects en rutas de API o tests. La infraestructura debe recibir `Path`/configuración resuelta, no decidir implícitamente el contexto de usuario.

### Option C — RuntimeContext object (rejected)

Rechazada como abstracción innecesaria para B9.30. No existe RuntimeContext en la arquitectura actual; un objeto con config/store/environment ampliaría el boundary más de lo necesario. La dependencia concreta puede propagarse como `Path` y valores de configuración existentes.

### Resolution contract

Configuración:

```text
CLI override → environment → user config → defaults
```

La ruta de usuario es `${XDG_CONFIG_HOME}/castlearq/config.toml`; si no está definida, `${HOME}/.config/castlearq/config.toml`. Solo se usan `XDG_CONFIG_HOME` y `HOME`; no se inventan variables adicionales. Un override explícito de ruta se expone por la API/CLI soportada o como argumento bootstrap, sin cambiar el schema TOML. Archivo ausente: defaults. Archivo inválido: error controlado, no defaults silenciosos.

ModelStore:

```text
new exists → new
new absent + legacy exists → legacy
both exist → new
neither exists → official new path, sin crear todavía
```

Official path: `$XDG_DATA_HOME/castlearq/models`, o `$HOME/.local/share/castlearq/models` sin `XDG_DATA_HOME`. Legacy: `$HOME/.local/share/localai-hub/models`. La resolución pura solo devuelve `Path`; no crea directorios. La primera escritura (manifest/download) crea físicamente la raíz seleccionada mediante `ModelStore._open_root(create=True)`. `list` resuelve y lee, pero no escribe.

### Implementation consequences

- `main()` parsea primero; help/version retornan antes de resolver config/store.
- El bootstrap resuelve rutas puras y pasa `Path` a `ModelStore` y config loader.
- `print_models()` recibe o crea un `CompatibilityConfig` desde la ruta user-level resuelta, no `load_config()` con default cwd.
- `ModelStore()` no debe depender de un path relativo; los consumidores relevantes reciben `ModelStore(root)` o una dependencia ya compuesta.
- API y wiring deben recibir el mismo root resuelto cuando sus boundaries lo permitan; no se cambia la semántica de Application, `ExecuteModel`, runner ni Product Caller.
- La creación queda en operaciones de escritura de ModelStore; imports, resolución, help, version y list no crean.
- Tests existentes que dependen de `Path("config/config.toml")` o de `ModelStore()` implícito deberán recibir dependencias explícitas o fixtures temporales, sin cambiar su contrato funcional.

## Implementation Boundary

La implementación queda limitada a:

```text
version adapter y metadata wiring
CLI/bootstrap path resolution
configuration infrastructure/adapters
ModelStore path resolution y inyección
package metadata/entry point
tests y smoke validation
```

No requiere modificar Domain, Application, Compatibility, Evaluation, Decision Policy, Runner ni Product Caller. No se rediseña `EvaluationContext` ni `EnvironmentContext`; no se añade un `RuntimeContext`.

## Tests Required

### Version

- Installed package.
- Editable install.
- Checkout/development fallback.
- Metadata unavailable.
- API y CLI coinciden.

### Configuration

- cwd repository, `/tmp`, `$HOME` y directorio arbitrario.
- user config existente, ausente e inválido.
- `XDG_CONFIG_HOME` definido y fallback a `HOME/.config`.
- CLI override sobre environment, environment sobre archivo y archivo sobre defaults.
- Ninguna resolución crea `~/.config/castlearq`.

### ModelStore

- new absent / legacy absent.
- new absent / legacy exists.
- new exists / legacy exists.
- new exists / legacy absent.
- `list` no crea raíz.
- primera escritura crea la raíz oficial seleccionada.
- rutas no dependen del cwd.

### Side effects

Verificar que:

```text
import app
castlearq --help
castlearq --version
```

no crean ModelStore ni config directories, y que `castlearq list` tampoco crea ModelStore vacío. Verificar `python3 -m app.main` y `castlearq` delegan al mismo CLI.
