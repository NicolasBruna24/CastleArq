# B9.31-A — Unified llama.cpp Runtime Discovery Contract

> B9.31-C closure specification. This document records the B9.31-A contract and the validated B9.31-B implementation; it does not introduce new runtime behavior.

## 1. Estado actual

The repository has a validated Python distribution. The official execution path is unified around `resolve_llama_runtime()`; the remaining alternate-name surfaces are diagnostic inventory only:

| Surface | Current search/probe | Meaning | Problem |
|---|---|---|---|
| `app.runtimes.detect_runtimes()` | `llama`, `llama-cli`, `llama-server`, `llama.app` via `which` | at least one name is present | reports availability without validating a launcher |
| `app.observation_probe.EnvironmentObserver.observe_runtimes()` | `llama-cli`, `llama`, `llama.app` via `which` | generic runtime observation/version/help facts | different candidate order and generic interface |
| `app.runtimes.detect_llama_capability()` | only `llama` via `which` | `llama cli --version` and `llama cli --help` | actual execution path is narrower |
| `app.gpu_setup._llama_devices_text()` | `llama`, `llama-cli`, `llama.app` | best-effort device-list probe | may inspect a different executable than execution |
| `LlamaCppRunner` | receives `RuntimeCapability`; uses its path/backend argument | builds `[executable, "cli", ...]` | correctly does not discover internally, but callers can create divergent capabilities |

`LlamaCppRunner` receives the resolved capability and does not call `shutil.which`. The implemented runtime boundary provides one productive resolution path for the official `llama` launcher; alternate-name surfaces remain diagnostic.

## 2. Fuente de verdad

CastleArq 0.1 treats `llama.cpp` as the canonical runtime. The official and only execution launcher is:

```text
llama
```

It is resolved from `PATH` and is usable only after the existing probes pass:

```text
llama cli --version
llama cli --help
```

The help probe must contain `--model` and `--prompt`; the capability must also provide the existing backend argument mapping (`none` for CPU and `Vulkan0` for Vulkan).

`llama-cli`, `llama-server`, and `llama.app` are not automatically equivalent. They are diagnostic/compatibility candidates. Supporting one as an execution launcher requires a future adapter, capability contract, command construction, and tests. This preserves the B9.29 contract.

## 3. Política de discovery

The source priority is:

1. an explicitly configured runtime path, if a future extension provides it;
2. otherwise inherited process `PATH` using `shutil.which("llama")`;
3. no silent fallback to an alternate executable.

The explicit-path extension is a future configuration point, not implemented here. It must validate the same regular-file/executable and unified-CLI contract, report found-but-unusable when validation fails, and never silently fall back to PATH after an explicit path is selected.

Current candidate classification:

| Name | Classification | 0.1 behavior |
|---|---|---|
| `llama` | official candidate and launcher | PATH discovery, validation, execution |
| `llama-cli` | diagnostic/compatibility candidate | may be reported; not an execution launcher without adapter |
| `llama.app` | diagnostic/compatibility candidate | may be reported; not an execution launcher without adapter |
| `llama-server` | diagnostic candidate only | may be reported; not a one-shot launcher |

If `llama` and an alternate both exist, `llama` wins. If only an alternate exists, CastleArq 0.1 remains unavailable for execution; it does not treat the alternate as `llama`.

## 4. Identidad del runtime

The discovery result must expose identity separately from capability. Minimum identity fields are:

```text
canonical_id = "llama.cpp"
executable_path = absolute resolved path
executable_name = basename of the resolved path
version = raw/normalized version text when a probe succeeds
build_identifier = build/commit text parsed from version when available
availability = state describing the observed result
```

B9.31-B formalized these as immutable identity/discovery types: `LlamaRuntimeIdentity`, `ResolvedLlamaRuntime`, `RuntimeAvailability`, and `resolve_llama_runtime()`. It does not duplicate version constants or infer build identity from an absent probe.

Availability states preserve provenance:

```text
NOT_FOUND
FOUND_UNUSABLE
AVAILABLE
PROBE_ERROR
UNKNOWN
```

`AVAILABLE` requires a resolved executable and successful required probes. `FOUND_UNUSABLE` means the path was resolved but failed the execution contract. `PROBE_ERROR`/`UNKNOWN` must not be presented as a definitive negative capability.

## 5. Capability semantics

`RuntimeCapability` is an execution-intent contract for a concrete resolved executable, not normative knowledge about every llama.cpp build.

- **runtime available:** the official `llama` candidate was resolved and required interface probes passed.
- **runtime compatible for CastleArq 0.1:** the capability satisfies the launcher, one-shot, format, prompt, and backend-argument requirements used by the runner.
- **runtime supports GGUF:** a positive capability claim derived from the validated CLI contract; it is not a claim that every GGUF file will load.
- **runtime supports backend X:** evidence from the validated runtime/device probe or, for CPU, the known baseline contract; it is not proof that a later execution will use X.
- **runtime supports a concrete artifact:** a separate selection/admission decision based on knowledge, format, size, backend and execution policy. It is not a discovery result.

These objects remain distinct:

```text
RuntimeKnowledge: supplied normative knowledge
RuntimeObservation: read-only observed fact
RuntimeCapability: validated concrete execution capability
RuntimeArtifactEvidence: evidence tied to a particular runtime/artifact execution
ExecutionResult: outcome of an attempted process execution
```

`RuntimeKnowledge.supports_artifact` is a tri-state compatibility input. It must never be reused as proof that a specific artifact was consumed. A negative local probe must not mutate normative knowledge.

## 6. Backend semantics

Backend handling is read-only and never installs drivers, Vulkan, CUDA, ROCm, OpenCL, or any system component. It requires no root or sudo.

The contract separates:

1. **runtime backend capability:** the resolved runtime advertises or confirms a backend/device;
2. **selected backend:** CastleArq chooses a backend for a particular execution request;
3. **used backend evidence:** a real execution reports what actually happened.

CPU is the baseline backend and may be represented as available in the capability when the validated launcher contract is present. Vulkan is a capability only when positive runtime/device evidence exists; helper command presence alone is contextual evidence, not a guarantee of functionality. Other backend names remain diagnostics until explicitly supported by a capability adapter. Backend selection must not silently fall back between GPU and CPU, and the runner must continue to consume the capability's backend argument mapping.

## 7. Failure semantics

| Situation | Discovery/identity | Capability | Reason/report |
|---|---|---|---|
| `llama` absent | `NOT_FOUND` | unavailable; no executable path | runtime not found |
| `llama-cli` exists | diagnostic candidate only | unavailable for 0.1 execution | requires future adapter |
| `llama.app` exists | diagnostic candidate only | unavailable for 0.1 execution | requires future adapter |
| `llama-server` exists | diagnostic candidate only | unavailable for 0.1 one-shot execution | requires future adapter |
| path exists but is not executable/regular | `FOUND_UNUSABLE` | unavailable | executable contract failed |
| probe fails | `FOUND_UNUSABLE` or `PROBE_ERROR` | unavailable for required launcher contract; otherwise preserve unknown | preserve failure reason |
| help lacks required options | `FOUND_UNUSABLE` | unavailable | missing launcher option |
| version detectable | identity populated | capability may be available | parse version/build when possible |
| device/backend probe fails or is absent | runtime may remain available | backend capability unknown/unavailable | preserve `UNKNOWN` |
| model unsupported | identity/capability unchanged | not a discovery failure | model/artifact admission owns this |
| execution process fails | identity/capability unchanged | execution result reports failure | not proof runtime absent |

`UNKNOWN != FAILED` and `UNKNOWN != INCOMPATIBLE`. Probe errors, timeouts, permission errors, malformed output, and missing optional tools must not be silently converted into a universal incompatibility claim.

## 8. Runner boundary

The implemented flow is:

```text
resolve_llama_runtime()
  → RuntimeCapability
  → backend selection
  → LlamaCppRunner
  → ExecutionResult
```

`LlamaCppRunner` must remain discovery-free. It validates the supplied path and backend argument at its boundary, then builds the existing argv. It must not call `which`, try alternate names, redownload, or repair the runtime. Callers may inject a capability for tests, but production composition must source it from the unified discovery component.

The implemented production path is `resolve_llama_runtime()`. `detect_llama_capability()` remains a public compatibility surface backed by that resolver. The `castlearq runtime` presentation surface also consumes the resolver directly. `compose_execute_model_dependencies()` passes the same resolved capability to selection and `LlamaCppRunner`; no productive caller maintains a second launcher search.

## 9. Contrato de B9.31

The contract has three separate decisions:

```text
candidate -> compatible/usable runtime -> runtime capability
                                      -> execution evidence
```

`llama.cpp` is canonical; `llama` is the official execution launcher; alternate names are diagnostics. Discovery and capability detection are read-only, bounded, shell-free, and require no root/sudo. They never install llama.cpp, drivers, GPU stacks, or system configuration. The runner receives the already-resolved capability and does not implement a second discovery policy.

## 10. Inputs/outputs del componente de discovery

The implemented input boundary is a resolver call with the inherited `PATH` lookup and bounded read-only probe runner. A future explicit-path extension remains outside this release:

```text
resolve_llama_runtime(which=..., run=...)
```

The implemented output boundary is:

```text
ResolvedLlamaRuntime
  identity: LlamaRuntimeIdentity
  capability: RuntimeCapability | unavailable/error result
```

The output is an immutable snapshot. One resolution performs one bounded discovery and one capability validation; it does not cache across invocations or mix later system state into the identity.

## 11. Invariantes

- Only `llama` is the CastleArq 0.1 execution launcher.
- `llama-cli`, `llama.app`, and `llama-server` are never silently substituted.
- Discovery is read-only, bounded, and does not use a shell.
- Resolved path, identity, capability, selection, and execution result are separate layers.
- No path is discovered from the current working directory implicitly.
- A probe error is not automatically a definitive incompatibility.
- A backend capability is not selected/used execution evidence.
- `RuntimeKnowledge` is not mutable local observation.
- `RuntimeArtifactEvidence` is not emitted or resolved by discovery.
- The runner does not perform discovery.
- No root, sudo, driver installation, runtime installation, or system mutation is permitted.

## 12. Matriz de casos

| Situación | Resultado esperado |
|---|---|
| `llama` no existe | runtime unavailable; identity `NOT_FOUND` |
| `llama` existe y funciona | runtime available; identity and capability populated |
| candidato alternativo existe | documentar como diagnóstico; no usarlo como launcher 0.1 |
| ejecutable no ejecutable | `FOUND_UNUSABLE` / unavailable |
| probe falla | `PROBE_ERROR`/unknown según contrato; no afirmar incompatibilidad universal |
| versión detectable | runtime identity populated |
| backend CPU | capability/context; not execution evidence |
| backend Vulkan | capability/context only with positive evidence |
| GGUF soportado | runtime capability claim; not universal artifact guarantee |
| artifact concreto ejecutado | no resolver aquí; pertenece a selección/admission/evidence |
| ejecución real | no resolver aquí; pertenece al runner/result/evidence |

## 13. Fuera de alcance

B9.31-C no implementa ni cambia:

- runtime discovery o capability code;
- `app/`, `tests/`, CLI, runner, evaluator, admission, ModelStore, GGUF reader, runtime evidence, o execution result;
- configuración XDG completa o configuración explícita de ruta del runtime;
- adapters de ejecución para `llama-cli`, `llama-server` o `llama.app`;
- ModelStore migration, auto-migración o uninstall;
- instalación automática de llama.cpp, drivers, GPU stacks o root operations;
- soporte multi-runtime, multi-GPU, GUI o nuevas abstracciones;
- B9.46 runtime artifact evidence behavior.

Estos límites ya fueron respetados por la implementación validada de B9.31-B.

## 14. Implementación validada en B9.31-B

B9.31-B implementó, sin ampliar el contrato:

1. `resolve_llama_runtime()` como resolución productiva unificada desde `PATH` usando el launcher `llama`;
2. identidad de runtime con path, nombre, versión, build identifier y availability;
3. capability derivada de las probes `llama cli --version`, `llama cli --help` y `llama cli --list-devices`;
4. `detect_llama_capability()` como compatibilidad pública respaldada por el resolver;
5. separación entre `RuntimeKnowledge`, `RuntimeCapability`, `RuntimeArtifactEvidence` y `ExecutionResult`;
6. runner discovery-free que consume la capability resuelta;
7. clasificación de candidatos alternativos exclusivamente como diagnósticos.

B9.31-B validó además la ejecución real, la identidad/capability real, la suite completa, el E2E y la regresión de packaging. B9.31-C solo documenta esos resultados.

