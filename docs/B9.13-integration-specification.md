# B9.13: INTEGRATION SPECIFICATION

## Specification Materialization (ratification)

Status: **SPEC-ONLY / NOT YET IMPLEMENTED — RATIFIED SPECIFICATION**. This document defines
the contract for the Integration block between the B9.12 Boundary Adapter and the existing
Knowledge layer. No integrator code, class, or module exists at the time of ratification, and
this document authorizes only a future, separately controlled implementation block.

Provenance: this specification was produced from the completed B9.13 Integration Discovery
Audit, drafted, reviewed by humans, and corrected by a controlled correction pass. The
corrections (all preserved here): (1) the UNMAPPED representation is identified as a **new
B9.13 contractual decision** proposed and ratified by this document, not an inherited
consequence of B9.11/B9.12; (2) `backend_evidence` was removed from the Integration output
contract — backend observation evidence remains preserved exclusively through the B9.12
`BoundaryTrace`; (3) `REJECTED` (present in the B9.12 trace vocabulary but not currently
emitted by `translate()`) has no current operational B9.13 semantics — the active path is
`unmapped identity → UNMAPPED`; (4) determinism is structural, not byte-identical
serialization (serialization remains deferred, B9.12 §23.9); (5) the zero-runtime output is
expressed consistently with the actual output contract (no `IntegrationResult.context`);
(6) open decision O-03 was removed.

---

## 1. Purpose

B9.13 defines the contract for **Integration** as the first controlled route
`Observation → Knowledge` of CastleArq: a block of **pure transport orchestration** that
composes the ratified outputs of B9.12 with the ratified contracts of Knowledge (B9.5/B9.7),
preserving the epistemology of Observation and the open world of Knowledge, without
translating, evaluating, deciding, or executing.

```text
Observation (B9.11)
    ↓
Boundary Adapter (B9.12)
    ↓
Integration (B9.13 — THIS SPECIFICATION)
    ↓
Knowledge (B9.5/B9.6/B9.7)
    ↓
Evaluation (B9.3/B9.8/B9.9)
    ↓
Decision (B9.10)
    ↓
Execution
```

## 2. Scope

B9.13 covers:

- The consumption contract for `BoundaryTranslation` (B9.12 I1).
- The calling contract for `project_knowledge(registry, runtime, scope)` per `RuntimeProjection`.
- The **UNMAPPED policy** (§14 — a new B9.13 contractual decision, ratified here).
- The output contract (§19).
- The error model (§17) and the distinctions acquisition-ERROR / UNMAPPED / UNKNOWN.
- Dependency, purity, legacy-isolation and Evaluation-boundary rules.

## 3. Non-Goals

B9.13 does **not**:

- Implement the integrator module (that is a subsequent, separately controlled block).
- Modify B9.11 (`observation_domain.py`, `observation_probe.py`), B9.12
  (`boundary_adapter.py`), Knowledge (`compatibility_knowledge.py`, `initial_knowledge.py`,
  `knowledge_bridge.py`), Evaluation (`compatibility_evaluator.py`, `evaluation_adapter.py`,
  `evaluation_pipeline.py`, `evaluation_policy.py`), Decision, Execution, or legacy
  providers (`platform.py`, `hardware.py`, `runtimes.py`, `gpu_setup.py`, and by extension
  `compatibility.py`, `selection.py`, `execution_service.py`).
- Create `KnowledgeAssertion` from observed evidence; it never fabricates knowledge
  (B9.7 transports, does not invent — Integration inherits that rule).
- Call `resolve_runtime`, construct `RuntimeCapability`, or use `compatibility_names`.
- Populate `EvaluationContext` (including `hardware`); call `evaluate`/`evaluate_strict`;
  produce `ALLOW/DENY/ESCALATE`.
- Derive `KnowledgeScope`; promote timestamps; serialize; add logging/UI/persistence of
  the trace; expose backend evidence as an output field.
- Resolve any B9.12 §23 deferred decision or the I1 audit findings B.1/B.2/B.3.

## 4. Architectural Position

```text
Observation (B9.11)          = what was observed
Boundary Adapter (B9.12)     = how Observation is translated to Knowledge vocabulary
Integration (B9.13, THIS)    = how transport/composition is orchestrated
Knowledge (B9.5/B9.6/B9.7)   = what the system's knowledge asserts
Evaluation (B9.3/B9.8/B9.9)  = how facts/knowledge are evaluated against requirements
Decision (B9.10)             = what to do with the evaluation result
Execution                    = execute
```

Integration is **downstream-only composition**. Dependency direction is strictly
`Integration → {B9.12, B9.11 (value-only), Knowledge}`. Nothing in
Knowledge/Evaluation/Decision/Execution imports Integration.

The ratified route is:

```text
EnvironmentContext
        ↓
Boundary Adapter (B9.12 translate())
        ↓
BoundaryTranslation
        ↓
B9.13 Integration
        ↓
project_knowledge()
        ↓
Knowledge
```

The prohibited route is:

```text
Observation → legacy runtime detection → resolve_runtime() → Evaluation
```

## 5. Terminology

- **Acquisition:** reading the environment → `EnvironmentContext` (impure; NOT B9.13).
- **Translation:** `EnvironmentContext → BoundaryTranslation` (B9.12, pure).
- **Integration composition:** `BoundaryTranslation + registry → Integration output`
  (B9.13, pure given its input).
- **Evaluation:** `Model/Artifact/EvaluationContext → CompatibilityResult` (B9.3; outside
  B9.13).
- **UNMAPPED:** the outcome emitted today by B9.12 I1 for an observed identity with no entry
  in the closed mapping table (§9 of B9.12). Never `UNSUPPORTED`; never acquisition `ERROR`.
- **REJECTED:** a category present in the B9.12 trace vocabulary
  (`MappingOutcome`/`TraceOutcome`) that `translate()` **does not currently emit**. It has
  **no current operational B9.13 semantics** (§11).
- **Knowledge absence:** the result of `project_knowledge` with no rows → read as `UNKNOWN`
  by B9.3 (open world).

## 6. Input Contract

- Integration **receives** an already-observed `EnvironmentContext` as an argument (value,
  immutable). It does **not** invoke `EnvironmentObserver`, does not know its injections
  (`run_cmd`, `read_file`, `which`, `get_timestamp`), and does not control acquisition.
- Conceptual signature: `integrate(context: EnvironmentContext, registry: KnowledgeRegistry)
  -> IntegrationResult`.
- Integration invokes `translate(context)` (B9.12) internally. Receiving a pre-built
  `BoundaryTranslation` is rejected: it would force the caller to know B9.12 internals and
  duplicate the "when to translate" decision.
- **OPEN DECISION O-01** (§26): who produces the production `EnvironmentContext` and with
  what lifecycle. It does not block the pure contract.

## 7. Environment Acquisition Boundary

```text
Acquisition    (impure, environment-facing)  → production caller / wiring (O-01)
Translation    (pure)                        → B9.12 translate()
Integration    (pure given its input)        → B9.13
Evaluation     (pure given its context)      → B9.3/B9.8/B9.9 (later)
```

Integration never reads files, never runs commands, never consults clocks or environment
variables. All I/O belongs to Acquisition, outside B9.13.

## 8. BoundaryTranslation Consumption

- Integration consumes `BoundaryTranslation.projections` and `BoundaryTranslation.trace`
  **verbatim, without mutation** (I-01).
- For each `RuntimeProjection`, in order of appearance, Integration calls exactly once
  `project_knowledge(registry, projection.knowledge_subject, projection.scope)`.
- Integration does **not** inspect `detected_backends`, `backends_coverage` or
  `backends_outcome` for decisions; those fields do not cross to Knowledge (§16).
- `trace` is propagated verbatim to the output (§18).

## 9. Identity Flow

```text
RuntimeObservation.canonical_id
        ↓  B9.12 map_runtime_identity (§9 table — sole owner)
RuntimeProjection.knowledge_subject   (RUNTIME, canonical_id, display_name=None, aliases=())
        ↓  B9.13: verbatim pass-through
project_knowledge(registry, subject, scope)
        ↓
KnowledgeProjection / RuntimeKnowledge
```

**Explicit prohibition:** the route `RuntimeObservation → RuntimeCapability →
resolve_runtime() → KnowledgeSubject` is forbidden. Reasons (verified in code): it would
duplicate the B9.12 §9 identity table; it would introduce the legacy vocabulary
`name`/`compatibility_names` (forbidden by B9.12 §19); it would break the contractual
ownership of the mapping. **`resolve_runtime()` is NOT the consumer of `RuntimeProjection`.**
No second identity table is created. `executable_path`, provenance, candidate strings and
backend names are never re-interpreted as Knowledge identities.

Knowledge does **not** need `display_name` or `aliases` for lookup (`knowledge_bridge.py`
selects by exact canonical_id; both are irrelevant metadata). The I1 subject is directly
consumable without a second translation. Filling display_name/aliases would be architectural
duplication: forbidden.

## 10. Knowledge Registry Binding

- The `KnowledgeRegistry` is a **mandatory parameter** of Integration. **No global default.**
- Justification: `project_knowledge` already requires an explicit `KnowledgeRegistry`;
  `INITIAL_KNOWLEDGE_REGISTRY` is a declarative dataset that the application wiring may pass,
  but fixing it as a default inside the module would couple Integration to one dataset and
  reduce testability.
- Responsibility: the **caller (wiring)** chooses the registry; Integration propagates it to
  `project_knowledge` without inspecting or mutating it (`add()` is never used).

## 11. KnowledgeScope Contract

- Integration consumes `projection.scope` **verbatim**. It does not replace, derive, or
  enrich it.
- Current contractual condition: B9.12 I1 produces **exactly `KnowledgeScope()`**
  (invariant in `RuntimeProjection.__post_init__`). In v1, every Knowledge projection produced
  via B9.13 uses the empty scope — with the ratified fail-safe consequence (B9.12 §10): only
  unqualified matching; scoped rows (`SCOPE_PLATFORM_*`, `SCOPE_LLAMACPP_B5377`) remain
  unreachable by design.
- Any non-empty scope requires resolving B9.12 §23.2 via a separate contract:
  **BLOCKED BY DEFERRED DECISION**. Scope is never derived from platform, hardware, version,
  backend, executable path, provenance, or heuristics.

## 12. project_knowledge Contract

- Called **only** with: (a) the received registry, (b) `projection.knowledge_subject`
  verbatim, (c) `projection.scope` verbatim.
- The resulting `KnowledgeProjection` is propagated **without reinterpretation**: Integration
  does not inspect `supported_*`/`unsupported_*`, does not fill lists, does not convert
  `excluded_unknown`/`unrepresentable`/`conflicts` into anything else, does not pick a winner
  on `conflicts`.
- **Empty projection** (runtime with no assertions in the scope): a valid result, propagated
  as such — it means absence, which B9.3 reads as `UNKNOWN`. Never converted into an error,
  into `UNSUPPORTED`, or into an invented state.
- Forbidden: `KnowledgeProjection result → reinterpretation → invented SUPPORTED/UNSUPPORTED`.
  Integration transports knowledge; it does not produce it.

## 13. Multiple Runtime Semantics

- Each `RuntimeProjection` is projected **independently**; one `project_knowledge` call per
  runtime; no shared state between calls.
- The output **order** follows the order of `context.runtimes` (which I1 already preserves in
  `projections`). Order is presentational, never priority.
- mapped + mapped → N projections. mapped + unmapped → entries for the mapped + unmapped
  entries for the others. unmapped-only → zero entries + unmapped entries. Zero runtimes → a
  valid output with zero entries and zero unmapped (§19).
- A mapped runtime **without assertions** → an empty `KnowledgeProjection` — valid, propagated
  (§12).
- Conceptual example:

```text
runtime A → mapped
runtime B → unmapped
runtime C → mapped
Result: entries = (A, C); unmapped = (B)
```

- **Forbidden:** ranking, selection, semantic deduplication, collapsing runtimes, deciding a
  "best runtime". An UNMAPPED runtime never prevents a mapped runtime from producing a valid
  entry.

## 14. UNMAPPED Policy (ratified B9.13 decision)

**Provenance of this decision:** the **distinction** `UNMAPPED ≠ acquisition ERROR ≠
UNSUPPORTED` is a fact **inherited** from ratified contracts (B9.11; B9.12 §14/§15). But the
operational representation of UNMAPPED inside the Integration output is **not determined by
any prior contract**: it is a **new B9.13 contractual decision, ratified by this document**
(I-24).

**Ratified policy:**

```text
unmapped identity
    ↓
UNMAPPED
    ↓
IntegrationResult.unmapped (explicit data entry; no exception)
    — no KnowledgeSubject is created
    — project_knowledge() is NOT called for that runtime
    — never converted into ERROR
    — never converted into UNSUPPORTED
    — no alternative runtime is selected
    — no heuristic fallback
```

- The absence of a projection for that runtime remains `UNKNOWN` downstream (open world
  B9.5/B9.7); the chain `UNKNOWN → INSUFFICIENT_EVIDENCE → ESCALATE` remains operable by the
  responsible layers (B9.3/B9.10); the distinction is preserved in the output/trace for
  auditability and future policy.
- **Ratified justification:** it extends the existing behavior of `project_knowledge` for a
  subject with no rows (a single "unknown" model in Knowledge); it does not duplicate the
  typed error B9.12 already recorded; it does not fabricate a `KnowledgeState.UNKNOWN`
  assertion.

## 15. REJECTED vs UNMAPPED

- B9.12 contains `REJECTED` in its trace vocabulary (`MappingOutcome`/`TraceOutcome`).
- `translate()` **does not currently emit `REJECTED`** for an unmapped identity; the actual
  current outcome is `MappingOutcome.UNMAPPED`.
- The operational B9.13 route is: `unmapped identity → UNMAPPED` (§14).
- `REJECTED` is **not** treated as a synonym of `UNMAPPED`; no additional operational
  semantics are assigned to it; no implementation support is created for it. If the name is
  retained for forward compatibility, it is stated explicitly: **REJECTED has no current
  operational B9.13 semantics.**
- Mandatory distinctions (I-14 and related):

```text
UNMAPPED (translation: identity outside the B9.12 table)
  ≠ Observation acquisition ERROR (ObservationState.ERROR, verbatim data)
  ≠ Knowledge UNKNOWN (absence of assertion / explicit state)
  ≠ Knowledge UNSUPPORTED (never derivable from absence or from UNMAPPED)
```

## 16. Backend Evidence Isolation

Critical rule: `detected_backends`, `backends_coverage`, `backends_outcome` **do not cross to
Knowledge via B9.13 and do not appear as fields of the Integration output**.

`detected_backends` represents **observed evidence**. It does NOT represent compatibility,
support, preference, ranking, recommendation, selection, or execution capability. None of
those categories may be derived from it.

```text
detected_backends  ≠  RuntimeKnowledge.supported_backends
detected_backends  ≠  RuntimeKnowledge.unsupported_backends
detected_backends  ≠  KnowledgeAssertion (no kind, no state)
detected_backends  ≠  IntegrationResult.backend_evidence   ← such a field DOES NOT exist
detected_backends  ≠  selection / ranking / preference / recommendation
```

**Sole contractual destination of observed evidence:**

```text
detected_backends
    ↓
BoundaryTrace (B9.12, ratified: CROSS_BOUNDARY as evidence)
    ↓
preserved verbatim
```

No parallel metadata channel is created. The only route from a backend to Knowledge/Evaluation
in the current model is a declarative KB assertion (BACKEND subjects) → B9.7 →
`RuntimeKnowledge`, and `EvaluationContext.backend` chosen by a later layer (B9.8); observed
evidence feeds none of those routes under B9.13.

## 17. Error Model

Four categories, without collapses:

| Category | Origin | Representation | Mechanism |
|---|---|---|---|
| Acquisition ERROR | B9.11 (`ObservationState.ERROR`, `acquisition_error`) | `ObservedValue` verbatim | Data (trace), never exception, never converted to UNSUPPORTED |
| Translation UNMAPPED | B9.12 I1 — **the only outcome emitted today** (`MappingOutcome.UNMAPPED`) | outcome + trace | Data in the output; B9.13 does not re-raise |
| Translation REJECTED | a category of the B9.12 trace vocabulary, **not emitted today by `translate()`** | — | **No current operational B9.13 semantics**; no implementation support |
| Knowledge absence/UNKNOWN | B9.5/B9.7 | empty projection / `excluded_unknown` / `KnowledgeState.UNKNOWN` | Data |
| Evaluation insufficiency | B9.3/B9.10 | `UNKNOWN → INSUFFICIENT_EVIDENCE → ESCALATE` | Outside B9.13 |

- **No new exception is created.** The only permitted exception is the rejection of an invalid
  input type (`ValueError` for a non-`EnvironmentContext`/non-`KnowledgeRegistry` parameter),
  consistent with repository convention. Semantic states travel as **data**, not as exceptions.
- Integration does not catch exceptions from lower layers to reinterpret them.

## 18. Trace Contract

The `BoundaryTrace` is propagated **verbatim and in-memory** as part of the Integration output
(the `trace` field of §19); **no consumer is designed**. No logging, persistence,
serialization, or UI is added. All observed backend evidence remains preserved exclusively
through this verbatim trace (§16). The final destination of the trace is a **future concern
(O-04 / B9.12 §23.9)** that **does not reopen the output contract**: the obligation of B9.13
is that the trace arrives complete and unrewritten. Nothing is reconstructed through a second
interpretation; nothing is lost: provenance, coverage, mapping outcomes, acquisition outcomes,
error details, backend evidence, and exclusion information all remain in the verbatim trace.

## 19. Output Contract

Semantic shape fixed (the concrete shape — dataclass vs namedtuple — is an implementation-block
decision, without altering this semantic contract):

```text
IntegrationResult (immutable; frozen; all collections are tuples)
├── entries: tuple[RuntimeIntegration, ...]        — ONE per RuntimeProjection, SAME ORDER
│     ├── observation_identity: str
│     └── knowledge: KnowledgeProjection           — verbatim result of project_knowledge
│                                                    (possibly empty: runtime with no assertions)
├── unmapped: tuple[UnmappedRuntime, ...]          — ONE per UNMAPPED runtime, SAME ORDER
│     ├── observation_identity: str
│     └── outcome: MappingOutcome.UNMAPPED
└── trace: BoundaryTrace                           — verbatim from B9.12
```

**There is no** `backend_evidence` field, no `context` field, no `EvaluationContext`, no
decisions, no derived scopes.

Mandatory cases:

| Input | Output |
|---|---|
| 0 runtimes | `entries=()`, `unmapped=()`, `trace=` the `BoundaryTrace` resulting from translating the empty context (what B9.12 already defines for that case, propagated verbatim) — valid, not an error. **No additional `context` field is added.** |
| 1 runtime mapped | 1 entry (Knowledge even if the projection is empty) |
| N runtimes mapped | N entries, observation order preserved |
| mapped + unmapped | entries (only mapped) + unmapped (only unmapped), in relative observation order |
| acquisition error in facts | the `ObservedValue`s travel verbatim in trace; never converted into Knowledge states |
| invalid context (not `EnvironmentContext`) | `ValueError` (type rejection, the only permitted exception) |
| invalid registry | `ValueError` |

Cardinality: exactly one entry per projection, exactly one unmapped-entry per unmapped
runtime; `len(entries) + len(unmapped) == len(context.runtimes)`. Verifiable invariant (I-18).

## 20. Evaluation Boundary

- **Integration ends at `KnowledgeProjection` (and its internal `RuntimeKnowledge`). NOT at
  `EvaluationContext`.**
- `build_evaluation_context` is NOT reachable by B9.13: it requires a legacy `RuntimeCapability`
  (`evaluation_adapter.py:190-207`) whose fabrication is forbidden (§9). The full composition
  toward Evaluation — `Model` + `ModelArtifact` + capability + backend + `evaluate()`/
  `evaluate_strict()` — belongs to a later block that may consume the B9.13 output through
  existing composition.
- Integration does not import `compatibility_evaluator`, `evaluation_adapter`,
  `evaluation_pipeline`, `evaluation_policy`; it does not know `EvaluationContext`; it does not
  evaluate, decide, select a backend, or produce ALLOW/DENY/ESCALATE.
- `EvaluationContext.hardware` remains explicitly **outside B9.13**; B9.12 §23.7 is not
  resolved (**BLOCKED BY DEFERRED DECISION**). B9.13 does not call `evaluate()`, does not
  create a `Decision`, and does not execute `Execution`.
- Fail-safe: UNKNOWN is represented by Knowledge (absence/explicit state); INSUFFICIENT_EVIDENCE
  is determined by Evaluation (B9.3); ESCALATE is determined by Decision (B9.10). B9.13 only
  transports the information that allows the chain to be applied — it does not apply any of
  its steps.

## 21. Legacy Isolation

Modules explicitly outside the B9.13 contract (no import, no call, no construction of their
types):

```text
app/platform.py · app/hardware.py · app/runtimes.py · app/gpu_setup.py
and by extension: app/compatibility.py · app/selection.py · app/execution_service.py
```

Forbidden to use: `RuntimeCapability`, `compatibility_names`, legacy runtime/GPU detection,
`"Unknown"` sentinels, `darwin→macos` tables. The Observation → Knowledge integration never
passes through the legacy architecture. There is no legacy refactor. Verified: Knowledge does
not depend on legacy; connecting Boundary → Knowledge via B9.13 does **not** drag legacy in
(the only legacy import in the ecosystem, `compatibility_evaluator → hardware`, is type-only
and belongs to Evaluation).

## 23. Purity and Determinism

```text
Acquisition            → impure; environment-facing; NEVER inside the B9.13 module
Translation (B9.12)    → pure (already ratified)
Integration composition→ PURE: a function of (EnvironmentContext, KnowledgeRegistry)
Application wiring     → may be impure; lives OUTSIDE the B9.13 module (O-01)
```

- **Structural determinism:** the same immutable input tuple `(EnvironmentContext,
  KnowledgeRegistry)` produces a **structurally equivalent** `IntegrationResult` (structural
  equality of frozen values). No byte-identical serialization is asserted or required:
  serialization/`schema_version` remains deferred (B9.12 §23.9) and no serialization
  requirement is introduced.
- The registry is not mutated (`KnowledgeRegistry.add()` is never used).
- No I/O, no subprocess, no filesystem, no environment reads, no clocks, no randomness, no GPU
  probing, no runtime probing, no package installation, no network access, no global mutable
  state in the module.

## 24. Test Contract

The future implementation must cover (not written now):

- **Mapped runtime:** a known `canonical_id` → a valid `KnowledgeProjection`, produced by a
  call with the exact subject.
- **Unmapped runtime:** an unknown `canonical_id` → an `IntegrationResult.unmapped` entry, and
  **no** `project_knowledge` call.
- **Mixed runtimes:** mapped + unmapped + mapped → entries (A, C) + unmapped (B), relative
  order preserved.
- **Zero runtimes:** `entries=()`, `unmapped=()`, trace preserved — no synthetic entries, no
  invented runtimes, no `context` field.
- **Backend evidence:** verified NOT converted into compatibility/selection/recommendation;
  the output contains no `backend_evidence` field; evidence remains in `BoundaryTrace`
  verbatim.
- **Scope:** the scope coming from B9.12 is preserved (observable with a sentinel registry).
- **Empty Knowledge projection:** propagated without reinterpretation.
- **Errors:** acquisition ERROR travels verbatim in trace; UNMAPPED ≠ ERROR ≠ UNKNOWN ≠
  UNSUPPORTED; `REJECTED` does not appear as an operational output; invalid input →
  `ValueError`.
- **Legacy isolation:** AST guard — the integrator module does not import `platform`,
  `hardware`, `runtimes`, `gpu_setup`, `compatibility`, `selection`, `execution_service`.
- **Evaluation isolation:** the module does not import `compatibility_evaluator`,
  `evaluation_adapter`, `evaluation_pipeline`, `evaluation_policy`; `EvaluationContext.hardware`
  is not touched; no `evaluate()` call; no Decision/Execution imports.
- **Purity:** determinism (same input → structurally equal result); no filesystem, subprocess,
  environment, clock, or randomness in the module; registry not mutated.
- **Trace:** structural preservation of `BoundaryTrace` (structural equality with the trace of
  `translate()`).
