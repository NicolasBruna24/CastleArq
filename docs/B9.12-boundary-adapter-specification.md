# B9.12: BOUNDARY ADAPTER SPECIFICATION

## 1. Purpose

Block B9.12 defines (and a future implementation block will realize) a **pure, deterministic
translation boundary** between the Observation domain (B9.11) and the Knowledge / Evaluation
layers:

```text
Host
  ↓
Observation Probes            (B9.11 — exists, committed)
  ↓
EnvironmentContext            (B9.11 — exists, committed)
  ↓
Boundary Adapter              (B9.12 — THIS SPECIFICATION; not yet implemented)
  ↓
Knowledge / Evaluation        (B9.5 / B9.6.x / B9.3 / B9.8 / B9.9 — exist, untouched)
  ↓
Decision                      (B9.10 — exists, untouched)
  ↓
Execution
```

The Boundary Adapter **TRANSLATES**. It converts observed facts (with their epistemic states,
coverage, and provenance) into data shapes consumable by Knowledge and Evaluation. It never
decides, ranks, recommends, selects, executes, or probes.

## 2. Scope

B9.12 covers:

- The contract for mapping **observed runtime identity** (`RuntimeObservation.canonical_id`,
  the fixed probing target) to **Knowledge runtime identity** via an explicit, closed,
  deterministic mapping table (contractually owned by the adapter; physical placement is an
  implementation decision — see §9, §23).
- The propagation rules for **coverage**, **provenance**, **epistemic states**, and **timestamps**
  across the boundary (see §12–§13, §15).
- The classification of every Observation fact family as CROSS_BOUNDARY / TRACE_ONLY /
  OUT_OF_SCOPE (see §11).
- The definition of what the adapter must NOT do (see §17–§18) and its isolation rules (§19).

## 3. Non-goals

B9.12 does **not**:

- Implement the adapter (that is a subsequent, separate block).
- Modify Observation contracts (`observation_domain.py`, `observation_probe.py`).
- Modify Knowledge (`compatibility_knowledge.py`, `initial_knowledge.py`, `knowledge_bridge.py`).
- Modify Evaluation (`compatibility_evaluator.py`, `evaluation_adapter.py`,
  `evaluation_pipeline.py`), Decision (`evaluation_policy.py`), or Execution.
- Create `EnvironmentContext → HardwareSnapshot` or populate
  `EvaluationContext.hardware` (see §18).
- Detect hardware, run commands, execute probes, or perform any I/O.
- Unify or replace legacy platform providers (`app/platform.py`, `app/hardware.py`,
  `app/runtimes.py`, `app/gpu_setup.py`).
- Resolve `raw_version` into version identity or activate version-scoped knowledge
  (`SCOPE_LLAMACPP_B5377` remains unreachable; see §21).
- Introduce serialization, schema versioning, or any public API for `EnvironmentContext`.

## 4. Architectural position

The adapter is a **pure, downstream-only translator**. Dependency direction:

```text
Adapter → Observation domain (reads EnvironmentContext as input)
Adapter → Knowledge contracts (produces Knowledge-compatible inputs)
```

Knowledge and Evaluation must **never** import Observation modules (I-09, I-10 currently hold
and must be preserved). The adapter is the only place where both vocabularies may meet.

## 5. Inputs

The single input is an `EnvironmentContext` produced by B9.11, containing:

- `timestamp` (snapshot timestamp).
- `platform: PlatformObservation` (os_family, os_release, architecture, distribution).
- `hardware: HardwareObservation` (meminfo-derived RAM, lspci devices, `acquisition_error`,
  per-device and per-observation `coverage: CoverageEntry`).
- `runtimes: tuple[RuntimeObservation, ...]` (per runtime: `canonical_id`,
  `executable_path`, `raw_version`, `detected_backends`, `backends_outcome`, `coverage`).
- `coverage: ObservationCoverage` (top-level, one `CoverageEntry` per `ObservationFamily`).

The adapter accepts the input as an immutable value; it must not mutate, re-probe, or enrich it.

## 6. Outputs

For B9.12 v1 the adapter produces exactly **two** conceptual outputs (concrete shapes to be
fixed at implementation time, respecting existing contracts):

1. **A Knowledge-facing projection**: only the facts that have an explicit contractual mapping
   (§9), suitable for `project_knowledge` (B9.7) and `resolve_runtime` (B9.8). Within this
   projection the scope is `KnowledgeScope()` for B9.12 v1 (§10) and the runtime identity is a
   `KnowledgeSubject`-aligned canonical id obtained through the explicit mapping table (§9).
   There is no interpretation under which the adapter may freely choose between scope, identity,
   both, or neither: the projection contains exactly the mapped facts, and each mapping defines
   what it yields.
2. **A boundary trace**: a record of everything that crossed and everything that is excluded
   (§11, §13, §6.1) — analogous in spirit to `StrictEvaluation.projection` (B9.9).

**Nothing else.** In particular: no `EvaluationDecision`, no backend/runtime selection, no
`HardwareSnapshot`, no `EvaluationContext` with hardware populated.

### 6.1 Minimum trace contract (semantic; concrete shape deferred)

No concrete trace type is decided here (dataclass, dict, protocol, etc. are deferred to the
implementation block, §23). The trace must, however, be semantically capable of representing,
as a minimum:

1. input observation identity;
2. applied identity mapping (input identity → output identity);
3. mapping outcome;
4. deliberately excluded facts/families;
5. coverage state relevant to the boundary;
6. provenance relevant to the boundary;
7. acquisition/error information relevant to the boundary.

Where applicable, the trace must distinguish:

```text
mapped          — the fact crossed via an explicit contractual mapping
excluded        — the fact/family was deliberately excluded (recorded, not projected)
unmapped        — no contractual mapping exists for the fact
rejected/error  — an explicit typed rejection or error outcome occurred
```

The concrete representation of these categories is an implementation decision (§23).

## 7. Observation identity

The primary translation input of B9.12 is the Observation-side identity:

```text
RuntimeObservation.canonical_id
        ↓
explicit mapping table (§9)
        ↓
KnowledgeSubject.canonical_id
```

Current meaning of `RuntimeObservation.canonical_id` (B9.11, committed): the **fixed probing
target declared by B9.11** (e.g. `"llama.cpp"`, `"ollama"`), documented as "not a Knowledge
canonicalization mapping — identity canonicalization belongs to later architectural blocks".
B9.12 does not redefine it: in B9.11, `RuntimeObservation.canonical_id` continues to mean
exclusively the fixed probing target.

The **observed candidate** (the binary that was actually resolved) is recorded by:

- `executable_path.value` (resolved path), and
- provenance `source` (e.g. `which:llama`, `which:llama.app`, `which:ollama`).

These are **observational evidence/provenance, not identity**:

```text
executable_path.value   ≠ Knowledge identity
ObservedValue.source    ≠ Knowledge identity
```

The existence of `which:llama`, `which:llama.app`, or `which:ollama` provenance does not
authorize the adapter to infer any additional semantic identity. In particular, the candidate
names:

```text
"llama"
"llama-cli"
"llama.app"
```

are **not** converted into Knowledge identities by inference simply because they appear as
probing candidates. If a separate observational identity for resolved candidates is ever
needed, it requires another explicit contract — not an inference rule inside B9.12.

The distinction preserved across the boundary is:

```text
Observation identity
        ≠
resolved executable candidate
        ≠
Knowledge identity
```

Translation between Observation and Knowledge occurs only through the explicit contractual
mapping (§9) — never through path inspection, provenance inspection, or inference.

**Known ambiguity (documented debt, not redefined here):** the name `canonical_id` coincides
lexically with `KnowledgeSubject.canonical_id`, and today the literal values coincide
(`"llama.cpp"`, `"ollama"`), which makes the observed→knowledge mapping accidentally the
identity function. B9.12 must make the mapping **explicit** (§9) and must not rely on the
coincidence. Renaming or restructuring the Observation field is **out of scope** for B9.12
(it would modify B9.11 contracts); if a rename is later ratified, it happens in a dedicated
contract-correction block.

## 8. Knowledge identity

Current Knowledge runtime identities (verified in the repository, `app/initial_knowledge.py`):

```python
KnowledgeSubject(kind=RUNTIME, canonical_id="llama.cpp",
                 display_name="Llama CPP", aliases=("llamacpp", "llama.app"))
KnowledgeSubject(kind=RUNTIME, canonical_id="ollama", display_name="Ollama")
```

Aliases are **metadata, never lookup keys** (`app/compatibility_knowledge.py`: "Display names
and aliases are metadata, never lookup keys"). The KB lookup is exact `canonical_id`/scope
matching (`KnowledgeRegistry`: "Exact canonical identity/scope lookup; aliases/display names
ignored").

Legacy (`app/runtimes.py`) uses a **different, legacy-only** alias vocabulary:
`compatibility_names=("llama.cpp / llama.app", "llama.cpp")`. It is consumed only by the legacy
evaluator path and must **not** be reused by the adapter (§19).

## 9. Explicit identity mapping

**Contract ownership.** The Boundary Adapter owns the identity-mapping contract. The adapter
defines the single, closed translation table:

```text
observed identity → explicit deterministic mapping → Knowledge identity
```

**Contract ownership vs physical implementation location.** The semantic ownership of the
mapping belongs to the Boundary Adapter, but this specification does **not** require the table
to live physically in `app/boundary_adapter.py`. Whether it is ultimately represented as
contract data, a constant, a dataclass, a dedicated module, or another equivalent form is an
implementation decision (§23). The ownership is architectural, not physical: the mapping
contract belongs to the Boundary Adapter regardless of where its representation ends up living.

Requirements:

- **Input identity**: the table is keyed by `RuntimeObservation.canonical_id` — the fixed
  probing target (§7) — never by `executable_path`, provenance `source`, or any resolved
  candidate name. Those are observational evidence/provenance, not mapping keys (§7).
- **Closed**: every entry is enumerated in the adapter's contract; an unknown observed target is
  an explicit error or an explicit "no mapping" outcome — never a guess.
- **Deterministic**: the same input always yields the same output; no ordering-dependent
  behavior, no timestamps, no environment reads.
- **Exact**: no fuzzy matching, no substring/similarity scoring, no "best match" selection, no
  semantic inference, no invented aliases. This mirrors the already-ratified B9.8 rule
  ("nothing is normalized, folded, substring- or similarity-matched, and no alias is ever
  invented").
- **Ambiguity-rejecting**: zero or multiple candidate mappings raise an explicit, typed failure
  (same style as `resolve_runtime`'s "zero or multiple matches raise `ValueError`").
- **Auditable**: the applied mapping (input identity → output identity) is recorded in the
  adapter's trace output.

Verification note (current repository values): Observation probing candidates are
`("llama-cli", "llama", "llama.app")` (`app/observation_probe.py`, llama discovery loop) and
`"ollama"`; Knowledge runtime identities are `"llama.cpp"` (aliases `llamacpp`, `llama.app`) and
`"ollama"`. There is no overlap conflict today, but the mapping table — not the coincidence —
is the contract.

## 10. KnowledgeScope ownership (v1 scope rule)

- `KnowledgeScope` **lives in Knowledge** (`app/compatibility_knowledge.py`); it is part of the
  knowledge-assertion contract and is matched **exactly** by the bridge (B9.7) — omitted scope
  fields are not wildcards (B9.5 / B9.6.0 §11).
- Current producers: dataset constants (`SCOPE_PLATFORM_LINUX/WINDOWS/MACOS`,
  `SCOPE_LLAMACPP_B5377` in `initial_knowledge.py`) and the v1 placeholder
  `runtime_scope()` → `KnowledgeScope()` (B9.8, N-3: the raw CLI version string is never turned
  into `runtime_version`).

**B9.12 v1 rule (ambiguity closed):**

```text
KnowledgeScope() is the only scope produced by B9.12 v1.
```

The v1 scope rule is fixed:

```text
Observation evidence
        ↓
runtime identity mapping (§9)
        ↓
KnowledgeScope()
```

The adapter must **not** derive scopes from any of the following: `os_family`, `os_release`,
distribution, architecture, `raw_version`, backend evidence, hardware, executable path, or
provenance. There is no table, rule, or discretion in v1 from which the implementation may
"freely select" a scope: `KnowledgeScope()` is the only output. If scope values such as
`SCOPE_PLATFORM_LINUX`, `SCOPE_PLATFORM_MACOS`, or `SCOPE_LLAMACPP_B5377` are ever to be
produced at the boundary, that requires a separate, explicitly ratified future contract — not
an interpretation of this specification.

- **Fail-safe consequence**: with an empty scope only unqualified assertions match, and the
  pipeline falls through to `UNKNOWN → INSUFFICIENT_EVIDENCE → ESCALATE` (B9.3/B9.10).
- **Responsibility split**: scope **semantics** remain owned by Knowledge (field meaning, exact
  matching, no widening). The adapter may only apply a scope rule that a future architecture
  has explicitly ratified; until such ratification exists, it applies none. Any future
  platform-scope derivation would additionally require canonicalizing observed `os_family`
  (e.g. `"darwin"`) to Knowledge platform vocabulary (`"macos"`); that canonicalization would
  belong to the adapter's mapping table, never to Observation, and would itself have to be
  explicit, closed, and deterministic (today it is unratified; see §21).

The Boundary Adapter **TRANSLATES**; it does not **DECIDE**.

## 11. Evidence classification

Classification of B9.11 fact families at the boundary (roles only; no new types):

**Category definitions (contractual semantics):**

- **CROSS_BOUNDARY** — the data participates in the Boundary Adapter's contractual output,
  either as a Knowledge-facing semantic fact, as epistemic metadata needed to interpret that
  fact, or as metadata needed to preserve the semantics of the projection.
- **TRACE_ONLY** — the data does not become a Knowledge semantic assertion. It is retained
  solely for traceability, auditability, explanation of exclusions, provenance, and
  diagnostics of the translation process.
- **OUT_OF_SCOPE** — the data is not part of the Boundary Adapter's semantics and must not be
  converted into Knowledge. It is recorded as a contractual exclusion where applicable.

| Fact family | Classification | Rationale |
| :--- | :--- | :--- |
| Runtime identity (`RuntimeObservation.canonical_id`) | **CROSS_BOUNDARY** | Maps to Knowledge runtime identity via the explicit §9 mapping; the resolved executable candidate is not an identity (§7) |
| Runtime backend evidence (`detected_backends`) | **CROSS_BOUNDARY** (as *observed evidence set*, never selection) | Feeds Knowledge BACKEND facts as observed evidence, never functional compatibility (§14) |
| Coverage (all families) | **CROSS_BOUNDARY** (as epistemic metadata) | Prevents NOT_OBSERVED collapse (§12) |
| Provenance (`source`, per fact) | **CROSS_BOUNDARY** (as metadata) | Preserves auditability (§13) |
| Timestamps | **TRACE_ONLY** (destination undecided; `KnowledgeProvenance.observed_at` is a declarative string today) | Deferred (§23) |
| `raw_version` (raw CLI text) | **TRACE_ONLY** | N-3 forbids turning it into `runtime_version`; version identity is unowned (§21) |
| `executable_path` | **TRACE_ONLY** | No Knowledge/Evaluation field exists for it |
| `ObservationState` values | **TRACE_ONLY** (state per fact) | Preserved as metadata |
| Platform details (`os_release` kernel, distribution, architecture-as-host) | **TRACE_ONLY** (`os_family` has no Knowledge destination in v1: no scope is derived, §10) | Kernel/distro have no Knowledge representation; platform-scope derivation is unratified |
| Hardware memory (RAM), device memory (VRAM) | **OUT_OF_SCOPE** | No B9.3 check reads hardware; capacity lives in the legacy evaluator |
| Devices (vendor/device IDs, device_type) | **OUT_OF_SCOPE** | No KnowledgeKind DEVICE/VENDOR exists |
| Device driver (name/version) | **OUT_OF_SCOPE** | Legacy diagnostic domain only |
| Acquisition errors (`acquisition_error`, `ERROR` facts) | **TRACE_ONLY** | Must never be translated into "unsupported"/absence (§15) |

Nothing crosses silently: every excluded family is recorded in the trace as deliberately
excluded. **Never fill a missing downstream representation by inventing semantics.**

## 12. Coverage propagation

The adapter must preserve the Observation epistemic dimensions verbatim:

```text
NOT_OBSERVED (coverage)      → stays "not probed"     — must NOT become UNAVAILABLE
OBSERVED + UNAVAILABLE       → stays "probed, no evidence available"
OBSERVED + ERROR             → stays "probing failed" — must NOT become UNAVAILABLE
OBSERVED + positive evidence → stays a positive fact
```

Concretely: a runtime whose backend family is `NOT_OBSERVED` must not be projected as a
`RuntimeKnowledge` with empty backend lists presented as evidence (which B9.3 would read as
`CheckStatus.UNKNOWN`); when a family was not probed, the adapter either produces no projection
for that family or an explicit "not probed" marker in its trace — never an empty list that
pretends evidence was sought. `RuntimeObservation.backends_outcome` (B9.11) is the authoritative
distinguisher for the probed-without-evidence / probing-failed cases.

## 13. Provenance propagation

- Provenance travels **verbatim**: `ObservedValue.source` strings and per-fact details are
  copied into the trace output unmodified. The adapter never rewrites, summarizes, or
  reinterprets provenance.
- The applied identity mapping (§9) is recorded as **adapter metadata** (input → output), kept
  separate from observation provenance so the two are never conflated.
- Observation timestamps are carried as-is into the trace; whether they are promoted into
  `KnowledgeProvenance.observed_at` is a deferred decision (§23).

## 14. Backend evidence semantics

Explicit rule:

```text
backend evidence ≠ selected backend
```

`detected_backends = ("vulkan", "cuda")` means: *the probe observed explicit syntactic evidence
related to Vulkan and CUDA* (per B9.11's positive-evidence-only contract, AD-01). It does NOT
mean "CastleArq should use Vulkan or CUDA", does not rank backends, and does not imply
functional compatibility (B9.11 §6: GPU presence never implies backend support).

The adapter may translate this evidence **as a set** into Knowledge-compatible backend facts
(`KnowledgeKind.BACKEND` subjects: `cpu`, `vulkan`, `cuda`, `rocm`, `hip`, `sycl` are the KB
canonical ids). The adapter must NOT: rank, prefer, recommend, evaluate, select, or apply
fallback. Any `EvaluationContext.backend` value is chosen by a later layer from model/artifact
inputs (B9.8), never by the adapter.

A second, equally binding distinction:

```text
observed backend evidence ≠ functional backend compatibility
```

The adapter does not convert B9.11's positive syntactic evidence into a functional-compatibility
assertion. For example, `detected_backends = ("vulkan", "cuda")` may produce Knowledge-facing
facts representing observed evidence (`vulkan`, `cuda`), but it must never produce statements
such as:

```text
vulkan is compatible
cuda is compatible
vulkan is preferred
cuda is preferred
vulkan should be selected
```

Compatibility evaluation belongs to later layers; it is not performed, implied, or encoded by
the adapter.

## 15. Error semantics

- `ERROR` and `UNAVAILABLE` keep their B9.11 meanings across the boundary; neither collapses
  into the other, and neither becomes "unsupported" or "absent".
- `acquisition_error` and per-fact `ERROR` details are preserved in the trace verbatim.
- The closed acquisition-error category of B9.11 (`ACQUISITION_ERRORS = (TimeoutError, OSError)`
  plus non-zero exits) is an Observation concern; the adapter performs no exception handling of
  its own and never converts failures into fabricated facts.

## 16. Determinism requirements

The adapter must be:

- **Pure**: no I/O, no clocks, no randomness, no environment reads, no command execution, no
  probing.
- **Deterministic**: same input → same output, byte-identical.
- **Total over valid inputs**: every syntactically valid `EnvironmentContext` yields either a
  defined output or a defined, typed rejection — never a partial or order-dependent result.

## 17. Forbidden inference

The adapter must not contain:

- Compatibility evaluation or scoring.
- Backend/runtime ranking, preference, recommendation, or fallback selection.
- Vendor fabrication (PCI `8086` stays `"8086"`).
- Version interpretation (no semver parsing, no `raw_version → runtime_version`).
- Fuzzy matching, similarity, substring, or "best match" heuristics.
- Semantic normalization of facts beyond the explicit mapping table (§9).
- `NOT_OBSERVED → UNAVAILABLE`, `ERROR → UNAVAILABLE`, or any state collapse (§12, §15).
- Discovery of new facts (no probing, no `--help`, no `lspci`, no file reads).

## 18. Forbidden bridges

B9.12 does not create, and its implementation must not create:

```text
EnvironmentContext → HardwareSnapshot            (AD-07; legacy type as bridge is prohibited)
Observation → EvaluationContext.hardware         (hardware stays None; legacy/pending field)
Observation → Decision                           (ALLOW/DENY/ESCALATE is downstream only)
Observation → Execution
```

## 19. Legacy isolation

- The adapter must not import, reuse, or wrap `app/platform.py`, `app/hardware.py`,
  `app/runtimes.py`, or `app/gpu_setup.py` in any way that lets legacy vocabulary
  (`compatibility_names`, `detect_platform`'s `darwin→macos` token table, `"Unknown"`
  sentinels) re-enter the strict path (AD-06 analog for the adapter; protects I-05/I-06).
- `app/platform.py` is a **well-injected but legacy-rooted provider** (it depends transitively
  on `gpu_setup → hardware/runtimes`) and is unused in production; it is a candidate for a
  future extraction block, **not** a B9.12 dependency.
- The legacy alias vocabulary (`"llama.cpp / llama.app"`) is not part of the mapping table (§9).

## 21. Known gaps / debt (documented, not solved here)

1. `canonical_id` naming ambiguity (§7) — observational target vs Knowledge identity; the
   literal-coincidence problem.
2. No ratified rule for deriving `KnowledgeScope` from evidence (§10); platform- and
   version-scoped knowledge is unreachable from the strict path today.
3. `raw_version` is raw CLI text; version identity is unowned (N-3 keeps it out by design).
4. Facts without downstream representation (executable path, device/vendor/driver facts, RAM)
   currently have no trace destination other than what B9.12's trace defines.
5. `EvaluationContext.hardware` is typed to legacy `HardwareSnapshot` (pre-existing import).
6. Platform vocabulary divergence: Observation emits `os_family.lower()` (e.g. `"darwin"`),
   Knowledge canonical platform is `"macos"`; only legacy code holds that translation today.
7. Two declarative time representations (snapshot timestamp vs `KnowledgeProvenance.observed_at`)
   with no defined relation.

## 22. Acceptance criteria

A future implementation satisfies B9.12 iff it can be shown (by tests/guards) that it:

- does not modify Observation contracts, Knowledge, Evaluation, Decision, or Execution;
- executes no probes, commands, or I/O (pure function of its input);
- performs no fuzzy matching or semantic inference;
- does not select runtimes or backends, rank, recommend, or decide;
- uses only explicit, closed, deterministic mappings, rejecting ambiguous mappings;
- preserves provenance and coverage verbatim;
- keeps `NOT_OBSERVED` / `UNAVAILABLE` / `ERROR` / positive-observation distinct end-to-end;
- introduces no `Observation → HardwareSnapshot` and no
  `Observation → EvaluationContext.hardware`;
- introduces no Evaluation/Decision/Execution dependency on Observation (direction stays
  adapter → downstream);
- does not reuse legacy `app/platform.py` / `hardware.py` / `runtimes.py` in a way that breaks
  AD-06/I-05/I-06;
- is deterministic (same input → same output);
- records a trace of everything that crossed and everything deliberately excluded,
  distinguishing mapped / excluded / unmapped / rejected outcomes where applicable (§6.1).

## 23. Deferred implementation decisions

The following are deliberately open for the implementation block, to be fixed in code review,
not by this specification:

1. The concrete output types (adapter return shape) and their module location.
2. Scope rules beyond `KnowledgeScope()`: none exist in v1 (§10 — `KnowledgeScope()` is the only
   scope B9.12 v1 produces). Any future scope derivation (e.g. platform or version scopes)
   requires a separately ratified contract; it is not a free B9.12 implementation decision.
3. The exact error/rejection type for ambiguous or unmapped identities.
4. The trace record's concrete shape and type (dataclass, dict, protocol, etc. — analogy:
   `StrictEvaluation.projection`); only the semantic minimum of §6.1 is fixed by this
   specification.
5. The physical representation/location of the mapping table (contract data, constant,
   dataclass, dedicated module — whether `app/boundary_adapter.py` or elsewhere); the identity-
   mapping contract is semantically owned by the Boundary Adapter regardless (§9).
6. Whether timestamps are promoted to `KnowledgeProvenance.observed_at` (default: no).
7. The fate of `EvaluationContext.hardware` (generic facts contract vs removal) — owned by a
   later block; B9.12 leaves it `None`.
8. Whether Observation's `canonical_id` is eventually renamed (a B9.11 contract change; not
   here).
9. Serialization / `schema_version` for any exported shape.
10. Which additional probes/families may join the boundary later.
11. Whether a separate observational identity for resolved executable candidates is ever
    introduced (§7); that would require a new explicit contract, not a B9.12 inference rule.
