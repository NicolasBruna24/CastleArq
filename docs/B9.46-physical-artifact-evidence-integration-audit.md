# B9.46.18 — Physical Artifact Evidence Integration Audit

## 1. Current flow

```text
app.main.execute_command
  -> compose_execute_model_dependencies()
  -> evaluate_model_compatibility(model_id, quantization, filename)
       -> ModelArtifactResolver.resolve()
       -> ModelStore.list_artifacts()/inspect_manifest()
       -> compose_evaluation()
            -> to_model(ModelSpec)
            -> to_artifact(ArtifactSpec)
            -> build_evaluation_context(capability, backend)
            -> evaluate(...)
  -> to_admission(evaluation_result)
  -> execute_model(admission=..., dependencies=...)
       -> resolver.resolve() nuevamente
       -> _check_admission()
       -> assess_model() operacional
       -> ArtifactExecutionPreflight.validate(artifact)
            -> obtiene path físico
       -> RuntimeBackendSelector.select()
       -> LlamaCppRunner.run()
```

`execute_model` vuelve a resolver el artifact y obtiene el path real sólo en `ArtifactExecutionPreflight.validate()` mediante `ModelStore._artifact_directory(artifact) / filename`. Ese path no se devuelve al use case de evaluación strict.

## 2. Physical artifact access point

El primer punto existente con artifact físico, path calculable y acceso read-only es `ArtifactExecutionPreflight.validate()` en `app/execution.py:216-306`.

Sus responsabilidades actuales son comprobar existencia, regularidad, symlinks, tamaño y checksum, y devolver `ExecutableArtifact(path=...)`. No lee metadata semántica del contenido.

`ArtifactFilesystemInspector` sólo devuelve estado `clean/partial/final_exists/inconsistent`; no transporta `GGUFArchitectureEvidence`. `ModelArtifactResolver` devuelve únicamente `ModelSpec` y `ArtifactSpec`.

## 3. Evaluation entry point

`_check_architecture()` (`app/compatibility_evaluator.py`) recibe `model: Model` y compara `model.architecture.architecture` contra `RuntimeKnowledge.supported_architectures` con matching exacto.

El `Model` se construye en `evaluation_adapter.to_model(ModelSpec)`. Actualmente `ModelArchitecture.architecture` procede exclusivamente de `ModelSpec.architecture`, cuyo valor productivo es `Transformer`.

`evaluate_model_compatibility()` (`app/evaluate_compatibility.py:116-213`) recibe `ModelSpec`, `ArtifactSpec`, capability, backend y demás datos, pero no recibe path físico ni `GGUFArchitectureEvidence`.

## 4. Current evidence gap

```text
resolved ArtifactSpec
  -> existe y ModelStore puede derivar un path
  -> evaluate_model_compatibility no recibe path/evidence
  -> compose_evaluation construye Model desde ModelSpec.architecture="Transformer"
  -> GGUF general.architecture nunca se lee
  -> _check_architecture permanece UNKNOWN
```

El lector B9.46.17 (`app/gguf_reader.py`) existe y devuelve `GGUFArchitectureEvidence`, pero no está conectado al flujo.

## 5. Candidate transport points

### A — ArtifactSpec

Rechazado. `ArtifactSpec` representa metadata operacional/declarada/adquisición. Añadir evidencia física derivable mezclaría semánticas, persistencia y round-trip de manifest.

### B — ModelArtifact

Rechazado. `ModelArtifact` es la variante strict y no tiene contrato para raw physical metadata/provenance. Añadir `architecture_raw` convertiría la representación strict en portadora de evidencia física.

### C — ArtifactFilesystemInspection

Rechazado. Su contrato es estado de filesystem, no contenido semántico. No debe convertirse en un contenedor general de metadata GGUF.

### D — Application evaluation boundary

Seleccionado conceptualmente. La evidencia debe entrar en la aplicación como `GGUFArchitectureEvidence` ya derivada, separada de `ModelSpec`, `ArtifactSpec` y `ModelArtifact`. El adapter permanece puro y recibe evidencia como input de composición/representación; no abre el archivo.

El punto físico puede reutilizar `ArtifactExecutionPreflight`/la inspección existente como producer, pero la evidencia debe estar disponible antes de `evaluate_model_compatibility()`.


## 6. Selected integration boundary

```text
PHYSICAL-EVIDENCE-INTEGRATION-DECISION = D
PHYSICAL-INSPECTION-POINT = ArtifactExecutionPreflight / existing read-only physical inspection
EVIDENCE-TRANSPORT = application evaluation input carrying GGUFArchitectureEvidence
EVALUATION-CONSUMER = compose_evaluation -> Model architecture projection
PERSISTENCE = NONE
MODEL_SPEC_CHANGE = NONE
IDENTITY_CHANGE = NONE
ADAPTER_FILESYSTEM_ACCESS = NO
```

La integración requiere obtener evidencia antes de `evaluate_model_compatibility`, resolver el mismo artifact de forma coherente y pasar la evidencia ya derivada al boundary de evaluación. No se autoriza que `evaluation_adapter.to_model()` haga I/O.

## 7. Rejected boundaries

* `ArtifactSpec`: mezcla metadata declarada y física.
* `ModelArtifact`: mezcla strict model domain y observación física.
* `ArtifactFilesystemInspection`: mezcla filesystem state y metadata semántica.
* `ModelStore`: no debe convertirse en servicio general de metadata.
* `evaluation_adapter`: debe continuar siendo puro.
* Runner: es demasiado tarde; strict evaluation/admission ya deben ejecutarse antes.

## 8. Lifecycle

```text
physical GGUF
  -> read-only physical inspection
  -> GGUFArchitectureEvidence
  -> transport efímero al boundary de evaluación
  -> consume durante compose_evaluation
  -> discard
```

No se persiste, serializa, cachea, convierte en state ni añade al manifest.

## 9. Identity relationship

La integración no altera:

```text
ArtifactSpec.model_id -> ModelArtifact.identifier
```

`architecture_raw=qwen2` no puede utilizarse como identidad. `ArtifactSpec.artifact_id` sigue siendo la identidad física/local usada por ModelStore, resolver, preflight y storage.

## 10. ModelSpec relationship

`ModelSpec.architecture="Transformer"` permanece intacto como metadata declarada del modelo lógico. La evidencia física `qwen2` es independiente y no lo reemplaza, no se infiere de él ni se mezcla en el mismo campo.

## 11. Adapter relationship

`evaluation_adapter.to_model()` puede permanecer puro si recibe evidencia ya derivada mediante el boundary de composición. No debe abrir paths, llamar al reader GGUF, inspeccionar filesystem, calcular checksum ni conocer ModelStore.

## 12. Error propagation

```text
GGUF reader success
  -> evidence available

metadata ausente
  -> evidence present=False; strict architecture permanece UNKNOWN

GGUF reader error / artifact unreadable
  -> error de inspección física antes de evaluación/admission según el flujo futuro

architecture value presente pero no reconocido por Knowledge
  -> evidencia existe; Knowledge/evaluator conservan UNKNOWN, no FAILED
```

Un reader error no se confunde con `architecture unknown` ni con `model incompatible`.

## 13. Next implementation block

B9.46.19 deberá:

1. elegir el punto físico existente que produce `GGUFArchitectureEvidence` antes de `evaluate_model_compatibility`;
2. transportar evidencia efímera al boundary de composición/evaluación;
3. mantener `ModelSpec.architecture` intacto;
4. añadir una proyección explícita al input strict sólo en el punto aprobado;
5. mantener el adapter sin filesystem;
6. no persistir evidencia ni modificar ModelStore ownership;
7. propagar reader errors y metadata ausente con semánticas separadas;
8. añadir tests de integración de transporte y preserving identity/adapter purity.

Knowledge debe reconocer `qwen2` sólo cuando la integración esté completamente demostrada; no se agrega como sustituto de transporte.
