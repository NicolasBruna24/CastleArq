# B9.46.26 — Runtime Artifact Support Semantic Boundary Decision

## 1. Executive Summary

El conflicto semántico es real:

```text
runtime artifact support
  participa en strict evaluation pre-admission

runtime consumption real
  sólo se observa en LlamaCppRunner después de admission
```

Si `PASSED` significa “esta instancia concreta consumió este artifact”, exigirlo antes de la ejecución es circular: la admission exige una prueba que requiere ejecutar, y la ejecución exige admission.

El repositorio demuestra el boundary, pero no decide si el check debe cambiar de significado o si debe existir otra frontera operacional.

**Verdict: `RUNTIME-ARTIFACT-SUPPORT-SEMANTIC-BOUNDARY-BLOCKED`.**

## 2. Current Runtime Flow

Código confirmado:

```text
app.main.execute_command
  -> evaluate_model_compatibility
  -> to_admission
  -> execute_model(admission=...)
       -> re-resolve ModelSpec/ArtifactSpec
       -> fresh RuntimeCapability
       -> _check_admission
       -> _compatibility / assess_model
       -> ArtifactExecutionPreflight.validate
       -> RuntimeBackendSelector.select
       -> validate ExecutionRequest
       -> ModelRunner.run
            -> LlamaCppRunner
            -> ExecutionResult
```

La primera evidencia real del runtime sobre el artifact aparece en `LlamaCppRunner.run()`, después de admission, preflight y selección de backend.

## 3. Strict Evaluation Semantics

`evaluate_model_compatibility()` coordina resolución, capability, integración y evaluación. `evaluate_strict()` adapta representations y ejecuta el evaluator puro. `evaluate()` construye checks determinantes y agrega `UNKNOWN` como `INSUFFICIENT_EVIDENCE`.

Strict evaluation representa principalmente una mezcla controlada de:

- relaciones de identidad y metadata de modelo/artifact;
- conocimiento normativo de formato, arquitectura, backend y capabilities;
- evidencia física ya observada cuando se suministra explícitamente;
- contexto de backend declarado.

No representa una observación de ejecución consumada.

## 4. Runtime Check Audit

| Check | Source of truth | Physical artifact? | Runtime instance? | Actual execution? | Known pre-execution? | Current semantics |
|---|---|---:|---:|---:|---:|---|
| identity | `ModelIdentity` / `ModelArtifact.identifier` | logical reference | no | no | yes | logical membership |
| format | `ModelArtifact.format` + Knowledge lists | no | no | no | yes | normative support |

| backend | context.backend + Knowledge | no | context | no | yes | normative support |
| capabilities | required capability + Knowledge | no | no | no | yes | normative support |

`_check_runtime()` is a Knowledge interpreter, not an execution observer.

## 5. Runtime Check Semantics

`RuntimeKnowledge.supports_artifact` is an abstract tri-state:

```text
True  -> PASSED
False -> FAILED
None  -> UNKNOWN
```

`True`/`False` can be supplied as normative assertions only if a qualified contract defines their scope. They cannot be proven as facts about this exact executable/artifact merely from runtime, format or backend presence.

`None` means no authoritative runtime-artifact assertion was supplied. It is not proof of failure. Its contribution to `INSUFFICIENT_EVIDENCE` is correct under the current determinant-check contract.

The current check does not mix execution evidence; it is under-specified/mismatched relative to the concrete scope being pursued.

## 6. Evaluation Admission Audit


## 7. assess_model() Boundary

`assess_model()` estimates operational feasibility using hardware, runtime/backend status, quantization and memory. It can return compatible, marginal, incompatible or unknown. It does not open the artifact, execute llama.cpp or observe consumption.

It is an operational heuristic gate inside `execute_model`, after admission, and is distinct from strict Knowledge evaluation. It is not a legitimate substitute for runtime execution evidence.

## 8. ArtifactExecutionPreflight Boundary

`ArtifactExecutionPreflight.validate()` proves resolved filesystem state, path safety, regular-file status, size and optional checksum. It returns an `ExecutableArtifact`.

It does not prove GGUF metadata semantics, runtime format support beyond later selector, runtime artifact consumption, successful initialization or inference.

It is a preparation/safety boundary, not the producer of runtime-artifact evidence.

## 9. LlamaCppRunner Evidence Boundary

`LlamaCppRunner` validates executable/artifact/target inputs, starts llama.cpp, captures stdout/stderr, exit code, diagnostics and optional metrics, and returns `ExecutionResult`.

These signals must be separated:

```text
process started
!= backend initialized
!= artifact accepted
!= model loaded
!= inference executed
!= successful process result
```

The strongest current evidence for “this runtime instance consumed this artifact” is a normally completed selected run with exit code 0 and captured output, interpreted according to the runner error taxonomy. It is instance/backend/request-specific and does not prove universal support.

This evidence is post-admission execution evidence.

## 10. Evidence Taxonomy

### Static/normative Knowledge

```text
llama.cpp supports GGUF
```

Authority: `KnowledgeRegistry` projected to `RuntimeKnowledge`.

### Physical artifact evidence

```text
GGUF general.architecture=qwen2
```

Authority: physical artifact reader/observation. It proves metadata, not consumption.

### Runtime execution evidence

```text
runtime instance X consumed artifact Y under backend Z
```

Authority: real runtime process observation. It currently appears in `LlamaCppRunner`.

No existing pre-admission producer supplies category three.

## 13. Decision

```text
SEMANTIC-BOUNDARY-DECISION = BLOCKED
```

The missing decision is whether CastleArq wants a pre-execution Knowledge claim or post-execution operational evidence under the name `runtime artifact support`.

The current contract cannot support both meanings simultaneously. A pre-execution gate cannot require successful consumption by the execution it is gating. A post-execution observation cannot authorize that same first execution.

## 14. Consequences

- Strict evaluation remains pre-execution and pure under either future decision.
- `RuntimeKnowledge.supports_artifact` remains the abstract Knowledge field unless redefined by a later decision.
- B9.46.23 `RuntimeArtifactEvidence` remains a valid ephemeral operational value, but it must be produced by the execution boundary if the post-execution option is selected.
- No `UNKNOWN` may be changed to PASSED from capability, format, architecture or backend alone.
- Current E2E remains blocked if `MAINTAIN-UNKNOWN` is chosen.
- Current fail-closed admission remains unchanged.

## 15. Next Architectural Block

The next block must ratify exactly one of:

1. **Pre-execution Knowledge semantics:** define the scope and source of `RuntimeKnowledge.supports_artifact` so it can remain a strict admission determinant.
2. **Post-execution operational semantics:** remove/reclassify the runtime-artifact check from strict admission and define how `RuntimeArtifactEvidence` is derived from `ExecutionResult` and consumed afterward.
3. **Separate operational readiness gate:** explicitly define a new gate, owner, input, output and placement; it must not claim successful consumption without execution.

## 16. Verdict

```text
RUNTIME-ARTIFACT-SUPPORT-SEMANTIC-BOUNDARY-BLOCKED
```

No implementation was performed. No production, tests, Knowledge, admission, runner, reader, backend, identity or persistence were changed.

This is semantically coherent: strict evaluation evaluates supplied compatibility Knowledge, while `RuntimeArtifactEvidence` describes an operational observation after execution. It would require deciding whether `runtime artifact support` remains in the strict determinant set and how `ExecutionResult` becomes or carries the observation.

Not ratified.

### 11.3 Separate Operational Gate

A separate operational gate after admission could consume capability, preflight and selected-target facts, but it still could not prove actual consumption without execution. It could validate readiness, not successful consumption. Introducing it would create a new boundary and must not be conflated with `assess_model()` or preflight.

Not ratified.

### 11.4 Maintain UNKNOWN

This is honest and fail-closed while the strict check's claim remains abstract and no qualified Knowledge assertion exists. It leaves the real E2E blocked because `to_admission()` denies `insufficient_evidence`.

This is safe but does not satisfy the real-runtime execution objective.

## 12. Semantic Definition

A valid pre-execution definition would be:

> `runtime artifact support = PASSED` means an explicitly scoped, authoritative Knowledge assertion states that the selected runtime product supports the selected artifact scope.

A valid post-execution definition would be:

> `runtime artifact support = PASSED` means a concrete runtime instance/backend observed successful consumption of the selected physical artifact.

These are not interchangeable. The current name and `bool | None` Knowledge field represent the first shape, while B9.46.22–B9.46.23 pursued the second shape.

`FAILED` requires an explicit negative assertion or an execution observation classified as runtime-artifact incompatibility. Infrastructure failure, missing evidence and unavailable observation remain errors or UNKNOWN, never automatic FAILED.

`to_admission()` projects status and strict verdict. `EvaluationAdmission` is fail-closed and cannot authorize execution by itself. `insufficient_evidence` currently denies.

A pre-admission requirement can legitimately ask whether declared Knowledge supports a runtime/artifact relationship. It cannot ask whether the not-yet-authorized execution already consumed this exact artifact.

The current strict result includes the latter-shaped name but only the former-shaped field. That mismatch is the semantic boundary problem.
