# B9.57.6 — Shared Preparation Test Hermeticity Remediation

Scope: test hermeticity remediation only. No production, workflow, dependency or
metadata file was touched.

## 1. Problem

`tests/test_shared_preparation.py::SharedPreparationTests::test_run_and_chat_both_call_prepare`
failed in GitHub Actions on every declared interpreter (3.10, 3.11, 3.12, 3.13)
with:

```
E   AssertionError: False is not true
tests/test_shared_preparation.py:196: AssertionError
```

B9.57.5 reproduced the failure locally, in both directions, and established
that the result of this single unit test depended on whether a `llama` executable
was present on the host `PATH` — an undeclared environmental dependency in a
suite whose CI contract states there is "no llama.cpp".

## 2. Root Cause

The `run_model` half of the test patched `app.main.detect_llama_capability`;
the `chat_model` half did not. `chat_model` therefore executed a real host probe
(`app.runtimes.resolve_llama_runtime` -> `shutil.which("llama")`) and, when no
runtime is present, returned 1 at `app/main.py:965-970` **before** reaching the
shared `_prepare` at `app/main.py:973`. The patched `_prepare` mock was
consequently never entered.

```
Before:
  chat_model test path depended on real detect_llama_capability()

  PATH with llama     -> invocable=True  -> _prepare called -> PASS
  PATH without llama  -> invocable=False -> early return 1 -> FAIL
```

The production shared-preparation contract was never at fault: symbol
resolution in B9.57.5 confirmed `run_model` and `chat_model` both delegate to
the same `app.main._prepare`.

## 3. Remediation

Two additive changes, both inside `tests/test_shared_preparation.py`:

1. A module-level helper `_invocable_capability()` returning a real
   `app.runtimes.RuntimeCapability` (the production type, with
   `available=True` and `supports_one_shot=True`, so `invocable` is `True`
   through the production property rather than a hand-set attribute).
   The construction follows the existing repository precedent in
   `tests/test_chat.py::make_capability`.
2. `patch("app.main.detect_llama_capability", return_value=_invocable_capability())`
   added to the `chat_model` half of
   `test_run_and_chat_both_call_prepare`.

```
After:
  detect_llama_capability() is controlled by the test

  PATH with llama     -> PASS
  PATH without llama  -> PASS
```

The helper expresses exactly one fact — "a runtime is available". It performs no
probing and reproduces no production behaviour: no `_prepare`, no model
resolution, no GPU detection, no subprocess, no real filesystem, no `PATH`
inspection, no llama.cpp, no inference. The mechanism is the same `unittest.mock.patch`
already used throughout the file.

## 4. Test Contract Preserved

Unchanged: the test still asserts that both entry points reach the shared
`_prepare` under valid conditions for those routes.

- `self.assertTrue(prepare.called)` still appears twice — once per half — with
  identical meaning.
- No assertion was relaxed, removed, replaced or reordered.
- The test was not converted into a "returns the right exit code" test; exit
  codes are still not asserted.
- The test docstring is unchanged.
- Conceptual symmetry now holds explicitly:

```
run_model   -> external preconditions controlled (resolver, capability, hardware, backends)
            -> _prepare mock -> assert prepare.called

chat_model  -> external preconditions controlled (resolver, capability)
            -> _prepare mock -> assert prepare.called
```

Non-regression evidence (temporary, out-of-tree, production never modified;
all temporary artifacts removed afterwards):

| Simulated condition | `_prepare` reached | assertion significant |
| --- | --- | --- |
| `run_model` with blank prompt (early `return 2`) | `False` | yes |
| `chat_model` with non-invocable capability (early `return 1`) | `False` | yes |

Both assertions still fail when the preparation call is not reached, so the
remediation did not buy a pass by weakening the test.

## 9. CI Implication

The previous CI failure was caused by a test depending on host-installed
llama.cpp availability. The remediation removes that undeclared host dependency
from the test. **CI does not need llama.cpp for this unit test.**

evidence of a Python incompatibility; they were the same environmental defect
observed identically on 3.10, 3.11, 3.12 and 3.13. With the host probe
controlled, the test no longer carries that variable.
