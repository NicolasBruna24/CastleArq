The separation is **correct and must be preserved**: the source commit answers
"what code was tested", the evidence commit answers "where the proof lives",
and the hashes answer "which exact files ship". Collapsing the first two would
make the release unverifiable; collapsing the hashes into the commit identity
would be false, because of §9.1.

## 8. Release identity decision

### Option A — tag `6b08922` (the built/tested commit)

Pros: the tag points at the literal tree that produced the artifacts.

Cons: at that tag the repository contains **neither** the B9.36 drill
specification **nor** the drill evidence. Anyone auditing `v0.1.0` from a
checkout of the tag would find an unevidenced release: the 24/24 proof, the
hashes, the runtime baseline and the artifact identity would all be absent, and
would only be reachable by knowing to look at a later commit.

## 9. Risks and contradictions

### 9.1 Real finding — the build is NOT byte-reproducible (governance constraint)

Measured, not assumed:

```text
build of 6b08922 (the drilled candidate)
  wheel 77e6c8a1…   sdist 16885e04…

build #1 of c21fc0c
  wheel dbbfc94f…   sdist 11aeb4a1…

build #2 of c21fc0c  (same commit, minutes later)
  wheel e74db773…   sdist ae263aa2…
```

Two builds of the **same commit** produced **different** SHA-256 values, so the
drift is build non-determinism (timestamps inside the zip/tar containers and
`RECORD` regeneration), not a source difference. Extracted *content* was
identical in every case.

**Consequence for governance (does not block tagging):**

* the recorded hashes identify the **exact files that were drilled and are to be
  published**;
* they are **not** reproducible from the tag by rebuilding — a fresh build at
  `v0.1.0` will produce a *content-equivalent but byte-different* artifact;
* therefore the release must **publish the exact artifacts whose hashes are
  recorded**, and the manifest must present the hashes as the identity of
  those files;
* any third party verifying from source must be told to verify **content**, not
  to expect the same hash from a rebuild.

Reproducible builds (pinned toolchain, `SOURCE_DATE_EPOCH`, normalized
timestamps) remain a legitimate future improvement, but are out of scope here
and are **not** a precondition for tagging.

### 9.2 No other real contradictions

* No tag exists locally or remotely; no `v0.1`-related tag to collide with.
* Version `0.1.0` is unique and consistent across `pyproject.toml`, wheel
  filename, sdist filename, `.dist-info` and the console-script output.
* No drift between the documented hashes and the artifacts on disk.
* The evidence documents contain no secrets or credentials; the only matches
  for credential-like words are the spec's own rule and the phrase "expected
  token produced" describing the `B9.36-OK` output.

| credentials / secrets | none in tracked files |
| private env vars | `pyproject.toml` contains no environment references |

The release is identifiable **solely** by Git commit + package metadata +
SHA-256 + recorded evidence. No environmental input participates.


### Option B — tag `c21fc0c` (current main, contains the evidence)

Pros: the tag ships the audit trail **with** the release; §3.1 proves the
distributable content is byte-identical to what was drilled, so the recorded
hashes remain valid evidence for the tagged state; it equals `main` and
`origin/main`, so there is no divergence between "released" and "current".

Cons: the tagged commit is not literally the commit the build command ran on.

### Recommendation — **Option B: `v0.1.0` → `c21fc0c`**

Grounds, in order of weight:

1. **Distributable equivalence is proven, not assumed** (§3.1): sdist member
   lists identical, sdist trees byte-for-byte identical, wheel trees identical
   excluding `RECORD`, `pyproject.toml` and `README.md` blob-identical, and
   `docs/` provably outside both artifacts. Nothing about the product differs
   between the two commits.
2. **Auditability dominates**: a release tag should let a third party verify
   the release from the tag alone. Option A cannot; Option B can.
3. **No divergence**: `c21fc0c` is `main` and `origin/main`, so the release
   pointer and the development head agree.
4. The only argument favouring Option A — "the tag must name the built commit" —
   is neutralised by the fact that the built *content* is identical.

The source commit `6b08922` is **not discarded**: it remains recorded in the
manifest as `source_commit`, preserving the full chain.

No tag is created by this block.
