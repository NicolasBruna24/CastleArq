# B9.44 — First PyPI Trusted Publishing Validation & Publication Evidence

> **Nature of this block:** documentary and audit only.
> No application code, `pyproject.toml`, test, workflow, tag, artifact or
> Trusted Publishing configuration was modified, rebuilt, re-tagged or
> re-published during B9.44. The only produced artifact is this document.

## 1. Executive Summary

CastleArq `0.1.0` is publicly published on PyPI. This audit re-derived, from
public and read-only sources, every element of the release chain declared for
B9.44:

```text
annotated tag v0.1.0  (commit 2ebbeb4)
    ↓
GitHub Release "CastleArq v0.1.0"  (assets = the audited artifacts)
    ↓
GitHub Actions  release.yml  (run 36168543954, workflow_dispatch, success)
    ↓  verify job: SHA-256 gate fail-closed
    ↓  publish job: duplicate guard + OIDC Trusted Publishing
PyPI  castlearq 0.1.0
    ↓
clean installation into an isolated venv outside the checkout
    ↓
console script  castlearq --version  ->  castlearq 0.1.0
```

Every step of this chain was **independently confirmed in this audit**, not
merely reported: the tag, the release assets, the workflow run, its jobs and
steps, the PyPI record, and the SHA-256 of the two files actually served by
PyPI. No discrepancy was found between the declared reference state and the
observed reality.

**Final classification: `VALIDATED — FIRST PYPI PUBLICATION`** (§11).

The publication used **Model A** of the B9.41 provenance decision: the exact
previously audited artifacts were transported and hash-verified, never rebuilt
in CI. Consequently this publication is **not** a reproducible build and must
not be described as one (§9).

## 3. Trusted Publishing Configuration

The publication identity registered on PyPI is the one declared by the project:

```text
Provider:  GitHub
Owner:     NicolasBruna24
Repository: CastleArq
Workflow:  release.yml
Environment: pypi
```

These values are encoded in the repository itself and are therefore auditable
without access to the PyPI account:

* `.github/workflows/release.yml` header — states the registered publisher.
* `jobs.publish.environment: pypi` — the environment name PyPI matches.
* `jobs.publish.permissions` — `contents: read` and `id-token: write` only.
* `jobs.publish.steps[Publish to PyPI via Trusted Publishing]` uses
  `pypa/gh-action-pypi-publish` **pinned by commit SHA**
  (`dc37677b2e1c63e2034f94d8a5b11f265b73ba33`, v1.14.2) and is invoked with
  **no inputs at all** — no `password`, no `repository-url` credentials, no
  `user`.

**Invariant:** the filename `release.yml` and the environment name `pypi` are
part of the release contract. Renaming either would silently break the
publisher while the workflow would still appear to run.

The Trusted Publishing configuration itself was **not** modified, inspected
interactively, or re-registered during B9.44. Its correctness is evidenced by
the fact that the OIDC publication step succeeded (§5) — PyPI only mints and
accepts an upload token for a publisher whose registration matches the
requesting workflow, environment and repository exactly.

## 8. Security / Credential Model

```text
PyPI Trusted Publishing
GitHub Actions
OIDC
```

Evidence that no long-lived credential was involved:

* The publish step invokes `pypa/gh-action-pypi-publish` with **no password /
  user / repository-url inputs** — the OIDC path is the only configured path.
* The workflow's `permissions` are deny-by-default at the top
  (`contents: read`); `id-token: write` is granted **only** to the `publish`
  job, and only there.
* No `secrets.*` reference and no `pypirc` usage appears anywhere in the
  workflow.
* The workflow source itself states, in the Trusted Publishing header and at
  the publication step, that no credential, token or password is configured and
  that the exchange mints a short-lived PyPI token scoped to the run.

Consequently the publication is **not** documented as — and did not use — a
personal PyPI API token, a `~/.pypirc` file, or a GitHub Secret holding a PyPI
token. No PyPI API token was created, requested, rotated or used at any point
during B9.44, and no Trusted Publishing setting was altered.

PyPI remains append-only: `0.1.0` cannot be replaced, and the workflow
performs no delete, replace or retry-on-version logic.

## 9. Relationship to B9.41 Artifact Provenance Decision

B9.41 chose between two provenance models. `0.1.0` used **Model A**.

```text
Model A  —  exact audited artifacts            <-- CastleArq v0.1.0
            publish the precise files previously audited,
            transporting them via GitHub Release and verifying
            their SHA-256 before publication

Model B  —  CI rebuild from source             <-- NOT used
            re-run python -m build inside GitHub Actions and
            publish whatever the CI produces
```

Evidence that Model B was not used:

* `release.yml` contains **no build step at all** — no `python -m build`, no
  `setuptools` invocation, no build matrix. Its steps only *download* assets
  that already exist, verify them, and publish them.
* The workflow header states the decision in prose: *"This workflow NEVER
  rebuilds the distribution. The 0.1 build is not byte-reproducible, so a
  rebuild in CI would produce artifacts equivalent in content but different in
  bytes from the ones audited in B9.36."*
* The end-to-end hash equality of §4.3 — GitHub Release assets and PyPI files
  carry the same digests recorded in the manifest committed at the tag.

### 9.1 Reproducibility statement (unchanged)

This publication **does not establish, and must not be presented as, a
reproducible build.** The prior conclusion stands:

```text
Build reproducibility for 0.1.0: NOT byte-reproducible,
i.e. NOT established.

The two SHA-256 values identify the exact artifacts validated
for this release; a third party rebuilding from source must
compare extracted content and must not expect the same hash.
```

Model A guarantees **transport integrity** — the published bytes are the
audited bytes. It deliberately does not, and cannot, guarantee that the build
process that produced them is deterministic. Making builds byte-reproducible
(pinned toolchain, `SOURCE_DATE_EPOCH`, normalized container timestamps) remains
a post-`0.1.0` improvement, recorded as a follow-up and **not** implemented
here.

## 10. Evidence Limitations

The following were **not** verifiable from outside, and are recorded as
maintainer-supplied or as inferences:

1. **Trusted Publishing registration contents.** The PyPI account page was not
   opened, so the registration entry itself was not read. Its correctness is
   demonstrated indirectly: the OIDC publication succeeded, and PyPI accepts
   such an upload only when provider, owner, repository, workflow filename and
   environment all match.
2. **Step-level log output.** Job and step *conclusions* were read from the
   GitHub API, but the raw runner logs (e.g. the literal
   `All artifact hashes match the release manifest.` line) were not retrieved,
   as step-level logs require authenticated access. Conclusions are the
   authoritative outcome record and are sufficient to establish PASS/FAIL.
3. **Run identity re-derivation detail.** The dispatch input value `v0.1.0` is
   not exposed in the public run object. It is corroborated by the executed
   steps (annotated-tag assertion, manifest read, release-matched assertion all
   succeeded) and by the fact that the run published exactly the `0.1.0`
   artifacts.
4. **The `~/Descargas` install transcript** (§7) and the `pip index versions`
   transcript (§6) come from the maintainer's recorded run. This audit
   independently confirmed the underlying fact they assert — that
   `castlearq 0.1.0` is on PyPI with those digests — by querying the public
   PyPI JSON API directly.
5. **No independent third-party install.** Verification was performed by the
   same operator who published. A download of the wheel and a `pip install`
   under a different account/OS would strengthen the evidence.
6. **Single-operator environment.** No claim is made about the integrity of
   the machine on which the artifacts were originally built; Model A carries
   forward the artifact-level verification of B9.36/B9.41 rather than
   re-deriving it.

No evidence in this document is inferred, extrapolated or invented. Where a
value was not observable, it is listed above rather than asserted.

### 11.1 Follow-ups (recorded, not implemented)

Per the B9.44 rule, these are observations only — no change is made here:

* **Byte-reproducible builds** (`SOURCE_DATE_EPOCH`, pinned toolchain,
  normalized container timestamps) would upgrade the release model from
  transport-integrity to full reproducibility.
* **A published attestation path** (PEP 740 attestations / Sigstore) would let
  consumers verify provenance directly from the index without trusting the
  GitHub Release as the carrier.
* **Per-release publication verification** could be automated: a scheduled
  check comparing PyPI digests against `docs/release/<tag>-manifest.md` at the
  tag, turning this audit into a continuous control.
* **Third-party install verification** on a non-maintainer machine/OS would
  close the last observational gap of §10.5.
