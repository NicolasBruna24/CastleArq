# B9.55 — Continuous Validation Contract Decision

> **Verdict: `DECISION RATIFIED` — Option C (documented baseline, no automation) is ratified as the minimal honest continuous-validation contract. Authority rule: validation failure outranks maintainer intent.**

---

## 1. Executive Summary

**No continuous validation contract exists today at `d9d06d4`.** HECHO: the
repository contains exactly one workflow, `.github/workflows/release.yml`, whose
triggers are `push: tags: v[0-9]+.[0-9]+.[0-9]+` (release.yml:27-30) and
`workflow_dispatch` (release.yml:44). HECHO: no step in that file invokes
`pytest`; its `verify` job checks release identity and the SHA-256 of
already-built artifacts (release.yml:63-70, 200-209), and its `publish` job
uploads them (release.yml:219-263). HECHO: there is no test workflow, no build
badge, no branch protection file, and no `conftest.py`, `tox.ini`,
`noxfile.py`, `Makefile`, `.pre-commit-config.yaml` or Dependabot/Renovate
configuration in the tracked tree (`git ls-files`).

Therefore, if nobody looked at the repository today, the only fact that would
still be true about CastleArq's code is the one recorded in documents: the
maintainer's local run (`1468 passed, 2623 subtests, 0 failed`, Python 3.14.4).
That is an *assertion in prose*, not an auditable control. Nobody outside the
maintainer's machine can check it, and the machine's state is not preserved.

Option C is ratified: the contract is **documented and enumerated in this
repository, with no automation**, and it explicitly declares what it does not
guarantee. Option B (CI) and Option D (scheduled PyPI digest verification) are
**DEFERRED**, not rejected. Option A (undeclared manual discipline) is rejected
because it leaves no artifact. Option E (self-evaluation) is rejected as
circular.

HECHO: three tests in `tests/test_api_serve_contract.py:344,367,456` assert
`git diff --name-only -- <module>` is empty. INFERENCIA: those three tests are
*vacuous on a committed tree* — they assert the working tree is clean, not that
the module is correct. This is recorded in §5 and §11 and is not fixed here.

## 3. Question reconstruction

### P1 — Does a continuous validation contract exist?

**No.** A contract requires four things: *what* is verified, *when*, *against
which baseline*, and *what happens on failure*, auditable by a third party.

| Element | Today | Evidence |
| --- | --- | --- |
| What is verified | Only release artifact identity + SHA-256, at a tag | release.yml:63-70, 200-209 |
| When | On tag push or manual dispatch only | release.yml:27-30, 44 |
| Baseline | `docs/release/v0.1.0-manifest.md` committed at the tag | docs/release/v0.1.0-manifest.md:1-20 |
| On failure | `verify` fails → `publish` never runs (`needs: verify`) | release.yml:221 |
| Code executed continuously | Nothing. No `pytest` step exists anywhere | `git ls-files` → single workflow |

The contract that exists is a **transport-integrity contract for a tag**, not a
code-execution contract for `main`. INFERENCIA: these are different objects;
`release.yml` would publish a tag whose tests had never been run by anyone.

### P2 — What is the minimum honest form?

Ratified (Option C):

```text
VALIDATION CONTRACT v1 (manual, documented)

WHAT     python3 -m pytest          (full suite, from a checkout, repo root)
WHEN     before creating any release tag
BASELINE the suite present in the commit being tagged
         (64 tracked test files; 1478 test functions at d9d06d4)
ON FAIL  no tag is created. A failing run is a release blocker.
AUTHORITY validation failure > maintainer intent (§9.2)
```

The number of tests is an **observation, not a contract**. Legitimate growth
must not break validation; a *decrease* is a signal requiring explanation. The
contract is "the suite passes", not "the suite has exactly N tests".

### P3 — Who wins when contract and reality disagree?

Ratified: **validation failure > maintainer intent.** Justification is
documentary, not personal: CastleArq's public identity is fail-closed admission
(`docs/B9.51-http-admission-contract-decision.md:157`, OPTION A — HTTP uses
strict admission). INFERENCIA: a product whose differentiator is *refusing to
act without evidence* cannot retain a published posture that says *proceed
without evidence*. The rule is asymmetric on purpose: intent may change the
code, never the result of a run. It is amendable only by an explicit,
documented, committed decision — not by an exception.

## 7. B9.44 §11.1 reconciliation

B9.44 recorded, and explicitly did not implement, the follow-up at
`docs/B9.44-first-pypi-trusted-publishing-validation-and-publication-evidence.md:475-477`:

> Per-release publication verification could be automated: a scheduled check
> comparing PyPI digests against `docs/release/<tag>-manifest.md` at the tag.

**Decision: DEFER.** Not absorbed, not rejected.

Why not absorbed into this contract:

* **Different object.** A PyPI-digest comparison is a *transport/publication*
  control. `release.yml` verifies artifacts associated with a tag
  (release.yml:200-209); a scheduled check verifies that the bytes PyPI serves
  *later* still match the manifest. Neither executes CastleArq code, so neither
  is a continuous validation of the product.
* **`release.yml` cannot cover it.** The workflow's triggers are tag push and
  manual dispatch (release.yml:27-44); it runs once per release, by design, and
  adding a schedule would give the release workflow a second, non-release
  trigger and a network-read-only job in a chain whose whole justification is
  that it never rebuilds anything (release.yml:5-11). That trade is not B9.55's
  to make.
* **It would not answer the central question.** The uncomfortable fact
  established in §1 is that *no code is ever executed automatically anywhere in
  this repository*. Adding a digest checker would create the appearance of a
  continuous control while leaving that fact untouched — the exact failure mode
  §11 exists to prevent.
* **PyPI is append-only, so divergence is not always a compromise.** A mismatch
  after publication can be an index/mirror artifact as well as a tampering
  signal; the follow-up specifies no response procedure, and a scheduled job
  that fails without an owner is a control nobody acts on.

Deferred because the underlying need is real and the cost is a second
always-on surface for a single-maintainer project, which must be weighed
against the undeclared-`pytest` debt (§10 item 2).

**Option D of §8 is this same follow-up**, not a second control: D and
B9.44 §11.1 are one deferred item, recorded once in §10 (item 7) and analysed
once here.

## 8. Options analysis

### A — No automation (undeclared manual discipline)

Coverage: nothing durable. The only record is prose. Limitations: no third party
can verify the suite ever ran; nothing prevents tagging a broken commit; the
assertion rots silently. Cost: zero. New institutionalised lie: the current
state *is* this option, and it is what makes the release posture
(`release.yml` publishes, therefore the product works) unearned. Cost for one
maintainer: none today, which is precisely why it will never be improved.

### B — GitHub Actions on push/PR

Coverage: the strongest of the options — it would make "the suite passed" a
public, timestamped, third-party-checkable fact. Without a matrix it verifies
one interpreter; with a 3.10–3.13 matrix it would simultaneously close §6, but
a matrix on a repo whose `app/` imports only the standard library is cheap in
runner minutes and non-trivial in flake-surface. Cost: a new always-on surface,
a declared `pytest` dependency, and a decision about caching and timeouts. What
it guarantees: that the *suite* passed in the CI environment. What it does
**not** guarantee: hermeticity beyond that environment, behaviour on the
maintainer's real llama.cpp/GPU machine, or anything about the ~108-second
local run. Relationship to `release.yml`: orthogonal — it validates commits,
`release.yml` validates artifacts. **No workflow was created or drafted in
B9.55.** Rejected *for now* only because implementing it is outside this
block's mandate; it is Deferred as the highest-value future item (§10 item 2).

### C — Documented baseline without automation

Coverage: the command, the timing, the baseline commit, the failure response
and the authority rule — all auditable by reading this document. It does not
*detect* a regression; it makes the absence of detection explicit and named.
Limitation, stated plainly: it records an intention, and an intention recorded
in Markdown is enforced by nothing. Cost: one document, near-zero maintenance.
Its virtue over A is that A leaves no artifact at all; its virtue over B is
that it claims nothing that has not been measured. **The test count is an
observation, not a threshold**: growth is legitimate and must not fail
validation; a *drop* is unexplained drift.

### D — Scheduled publication validation (B9.44 §11.1)

**Decision: DEFER.** This option is the B9.44 §11.1 follow-up (scheduled PyPI
digest verification); the reasoning is in §7 and is not restated as a second,
independent control.

Coverage: post-publication byte integrity of the index. Detects: index
tampering or replacement after publication. Does not detect: any code defect,
any regression, any untagged change. On divergence: nothing is specified, and
PyPI append-only means the correct response is not always "abandon". It is a
transport control.

### E — CastleArq validating its own contract

**Decision: REJECTED.**

Rejected in one sentence: a product's own tests are the same artefact the
product ships, so "CastleArq says it complies" carries strictly less evidence
than an external system demonstrating it — the tests are inputs to the product
under test, not an independent witness, and treating them as one is precisely
the self-deception a fail-closed product cannot afford. CastleArq's tests *are*
kept (they are the validation subject); what is rejected is the idea that they
constitute external validation of themselves.

### Mandatory matrix

| Option | What it covers | What it does NOT cover | New institutionalised lie | Decision required | Cost for 1 maintainer |
| --- | --- | --- | --- | --- | --- |
| A | Nothing durable; preserves today's behaviour | Everything | Yes — release posture implies validated code | No | Zero now; unbounded later |
| B | Suite execution on every push/PR, publicly auditable | Real-runtime/GPU behaviour, hermeticity beyond CI, 3.10–3.13 unless a matrix is added | No — it removes a lie | Yes, next available block | ~1 workflow + a declared dev dependency |
| C | Command, timing, baseline, failure response, authority rule | Actual detection of regressions; any execution | No — it declares its own limits | **RATIFIED** | One document |
| D | Post-publication byte integrity at PyPI (same follow-up as §7) | Any code behaviour | Moderate — looks continuous while executing nothing | No — DEFER | A second always-on surface + a response procedure |
| E | Nothing independent | External evidence | Yes — circular verification | No — REJECTED | n/a |

## 9. DECISION

**Option C is ratified.** One option only.

### 9.1 The contract established

```text
CastleArq Validation Contract v1
  1. WHAT      python3 -m pytest, full suite, from a checkout, repo root.
  2. WHEN      before creating any release tag, and before any public claim
               that cites test evidence.
  3. BASELINE  the suite as it exists in the commit being tagged.
               Observed at d9d06d4: 64 tracked test files, 1478 test
               functions, 1 previously reported run of 1468 passed /
               2623 subtests / 0 failed on Python 3.14.4.
               The counts are an OBSERVATION, not a threshold.
  4. ON FAILURE no tag. No publication. A failing run is a blocker.
  5. AUTHORITY validation failure > maintainer intent (§9.2).
  6. LIMITS    this contract executes no code by itself; it is enforced by
               nothing outside the maintainer's discipline until §10 item 2
               is delivered.
```

Clause 6 exists so the contract cannot be quoted as stronger than it is.

### 9.2 Authority rule

Where contract and reality disagree, **the validation result wins**. Justified
in §3/P3: CastleArq's public identity is fail-closed admission, and a
fail-closed product may not publish an unevidenced posture. The rule is
amendable only by an explicit committed decision that states the new rule and
its cost — never by a silent exception, and never by editing this clause alone.

### 9.3 What is lost by rejecting the other options

* **Rejecting A** costs nothing and buys an artifact: the current behaviour
  becomes stated rather than assumed. A was never a choice so much as the
  absence of one.
* **Deferring B** loses the opportunity to make execution evidence public
  *now*, and leaves §6's version gap unaddressed. This is the real cost and it
  is accepted only because B requires writing a workflow, which B9.55 forbids.
* **Deferring D** loses continuous post-publication integrity monitoring; the
  B9.44 follow-up stays open.
* **Rejecting E** loses nothing real; it removes circularity.

## 11. Claims this contract does not support

These claims **cannot** be made today. Any of them appearing in README, PyPI
metadata or a future badge is a defect, not a style issue.

1. "Continuous integration" / "CI-tested" / "tests run on every commit."
2. A build or test badge of any kind.
3. "Supported on Python 3.10, 3.11, 3.12 and 3.13" as an *evidenced* claim —
   declared in `pyproject.toml:34-37`, verified on none of them (§6).
4. "Continuously validated" or "validated by CI."
5. "Reproducible builds" — the manifest itself records
   `Build byte-reproducible | false` (docs/release/v0.1.0-manifest.md:19).
6. "Release integrity implies the product works" — `release.yml` verifies
   bytes, not behaviour.
7. Any claim that the `1468 passed` figure is reproducible by a third party
   today: `pytest` is undeclared, no environment is recorded, and no in-repo
   artifact records the run.
8. "The suite passes anywhere other than the maintainer's machine" — the
   loopback-socket and `git`-dependent tests (§5.1, §5.2) mean even *there* it
   is environment-shaped, though that is currently unmeasured.
9. Any claim derived from `tests/test_api_serve_contract.py:344,367,456` that
   those modules are "verified unmodified" — those tests assert a clean working
   tree, which is true by construction on a commit.
