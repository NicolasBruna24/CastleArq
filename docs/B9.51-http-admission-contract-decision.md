# B9.51 — HTTP Admission Contract Decision

Architectural decision block. It closes the question B9.23 §13 K-3 left open
and that B9.50 documented but did not resolve:

```text
execute → strict evaluation → admission → execution
run     → legacy execution
serve   → HTTP → legacy execution → NO strict admission
```

B9.51 is a **decision and contract** block. It does not change the HTTP
implementation; see §9.

---

## 1. Scope

In scope: the admission policy of every HTTP route that executes a model, the
status mapping, the rejection body, `run_lock` semantics, the contract tests
and the contract documentation.

Out of scope: the evaluation engine, knowledge base, new checks, ModelStore,
artifact verification, runtime discovery, the `run` → `execute` cutover,
release/PyPI/CI.

---

## 2. K-3 Reconstruction

Evidence from the repository, not from intent.

### 2.1 What B9.23 left undecided

`docs/B9.23-product-caller-vertical-slice-decision.md` §13 (K-3) and §17.2
state that the HTTP adapter block must first decide:

* which status `ExecutePreparationError` maps to (legacy separates 404
  model-not-found from 422 preparation; `execute_model` folds model-not-found
  into `ExecutePreparationError`);
* which status `ExecuteAdmissionDeniedError` maps to ("403? — absent from the
  legacy vocabulary");
* whether `ExecutionResult.success=False` maps to 503 (legacy
  `RunExecutionFailedError`) or stays 200-with-error;
* `run_lock` semantics for the evaluated route.

B9.23 §17.2 classifies it as "NON-BLOCKER here, blocking for HTTP". B9.23
§5 point 5 states the HTTP API "remains the prime candidate for the *next*
surface block, once K-3 fixes the status mapping".

* `application_wiring.compose_execute_model_dependencies`.
* `format_evaluation_report` (`app/compatibility_report.py`) — the human
  rendering of a result, used by CLI `execute` on denial.

### 2.5 Internal admission result vs HTTP response

`EvaluationAdmission` is a two-field, deny-only summary. It carries no model
identity, no checks, no evidence, no expected/observed, and it cannot
authorize execution. An HTTP response is the opposite: it must be
self-describing for a machine client (a status code plus a stable body), and
its content is governed by what may be exposed to a client. The projection
therefore needs a *rule*, not a field-by-field copy — see §5.3.

### 2.6 Status code for admission denial today

**UNDEFINED.** The code 403 is nowhere in `app/api.py`; the legacy vocabulary
is 400/404/409/422/500/503. B9.23 §3 asked "403?" as an open question and it
was never answered, so 403 is *not* an existing contract — it is a candidate.

### 2.7 `run_lock` semantics today

**UNDEFINED as a documented contract.** Observed behaviour in `_handle_run`:
acquired non-blocking after JSON parse; busy → 409; released in `finally`
after `run_once` returns or raises. It is a *whole-run mutual exclusion*, and
its scope relative to evaluation is unspecified precisely because evaluation
does not exist in this path.

### 2.8 Documented policy for the six `/v1/run` cases

| Case | Today | Documented? |
| --- | --- | --- |
| model incompatible (strict) | executes | **UNDEFINED** as policy |
| evaluation with insufficient evidence | cannot occur (no evaluation) | **UNDEFINED** |
| evaluation error | cannot occur | **UNDEFINED** |
| runtime unavailable | 422 `RunPreparationFailedError` | yes (legacy pipeline) |
| invalid artifact | 422 `RunPreparationFailedError` | yes (legacy pipeline) |
| execution rejected | 503 `RunExecutionFailedError` | yes (legacy pipeline) |

## 3. Alternatives

### A — Shared strict admission

`POST /v1/run` (and chat session open) evaluate → `to_admission` → admit or
reject → execute, reusing the existing use case.

* **Coherence with `execute`:** total. One execution guarantee, two surfaces.
* **Coherence with `run`:** none needed; `run` keeps its own historical
  policy (B9.51 does not cut it over).
* **Coherence with the admission model:** it *is* the admission model, applied
  at a second caller. B9.43 designed `to_admission` for exactly this.
* **Impact on `EvaluateModelCompatibilityResult`:** none; consumed read-only.
* **Impact on `EvaluationAdmission`:** none; reused verbatim.
* **Impact on HTTP:** adds 403 and one 500 case; extends the vocabulary
  without changing existing codes.
* **Status mapping required:** yes — ratified in §5.2.

## 4. HTTP Admission Policy Decision

```text
Decision: OPTION A — HTTP uses strict admission.
```

**Rationale.** CastleArq's product thesis is that a model should only be run
when strict evaluation admits it; that is why `execute` exists, why B9.43
created the `to_admission` seam, and why B9.48 made denial explainable. HTTP
is a *presentation* of the same product capability, not a different product.
An ungated HTTP surface makes the guarantee caller-dependent: a human typing
`castlearq execute` gets protection, while a script posting to `/v1/run` — the
surface most likely to be automated — gets none, with no way to opt in. There
is no product argument in the repository for that asymmetry; B9.50's stated
cause was the absence of the K-3 decision, which is not a reason. Option B is
therefore rejected on merit, not on cost.

**Architectural meaning.** Admission is a property of *execution*, not of a
command name or a transport. Every surface that executes a model crosses the
same gate. The gate lives in the Application layer (`execute_model` +
`to_admission`); Presentation only projects it.

**Relationship to `execute`.** Identical policy, identical error vocabulary in
the Application layer. HTTP differs only in projection: a status code and a
body instead of stderr and an exit code. There is no second admission
implementation.

**Relationship to `run`.** Unchanged. `run` remains the legacy CLI command
with its historical policy (B9.19 §13, B9.23 §5). B9.51 performs **no**
`run` → `execute` cutover; that remains a separate future decision.

**Relationship to existing evaluation/admission.** Reused, not extended.
`evaluate_model_compatibility`, `to_admission`, `EvaluationAdmission`,
`_ADMITTING_VERDICTS` and `execute_model` are consumed as they exist. No new
check, no change to `CheckStatus`, `StrictEvaluation`, knowledge, or the
evaluation pipeline. No new service, manager or policy object is created.

**Required HTTP contract.** §5.

## 5. Contract Definition (ratified)

Applies to every HTTP route that launches a model: `POST /v1/run` and
`POST /v1/chat/sessions`.

### 5.1 Admission order

```text
request validation (400)
  → acquire run_lock (409)
  → evaluate_model_compatibility(...)        # may raise
  → to_admission(result)                    # fail-closed
  → execute_model(admission=...)
  → release run_lock
```

### 5.2 Status mapping (ratified, complete)

| Situation | Status | Body kind |
| --- | --- | --- |
| malformed request (content-type, JSON, fields) | **400** | `{"error"}` (unchanged) |
| model id not in the local catalog | **404** | `{"error"}` (unchanged) |
| `run_lock` already held | **409** | `{"error"}` (unchanged) |
| **admission denied** (verdict not in `{"compatible", "compatible_with_conditions"}`, or `status="blocked"`) | **403** | admission rejection body (§5.3) |
| preparation failure (`ExecutePreparationError`: artifact invalid/missing, no selectable target, unsatisfied backend preference, resolution failure that is not "not found") | **422** | `{"error"}` + `warnings` when present (extends the legacy 422) |
| **evaluation raised** (`GGUFReadError`, resolution error, integration error, any unexpected exception during evaluation) | **500** | evaluation-failure body (§5.3) |
| runtime unavailable or the runner reported failure | **503** | `{"error"}` (unchanged) |
| success | **200** | `RunResponseDTO` (unchanged) |


### 5.3 Rejection body (ratified)

Two distinct bodies, both additions to the existing `{"error": ...}` envelope,
so existing clients that only read `error` keep working.

Admission denial (403):

```json
{
  "error": "execution refused by compatibility admission",
  "admission": {
    "status": "evaluated",
    "verdict": "incompatible"
  }
}
```

`admission` carries **only** what `EvaluationAdmission` already carries:
`status` and `verdict`. It is a faithful projection of the same object, so the
HTTP body cannot disagree with the gate. The following are deliberately
**not** exposed over HTTP: `checks`, `diagnostics`, `expected`, `observed`,
`evidence`, `conditions`, and `artifact` / `capability` internals. Rationale:
they are unbounded, they name local filesystem paths, and they already have a
sanctioned transport — `castlearq compatibility <model-id>` and
`format_evaluation_report`. Exposing the whole internal structure by default
would turn a machine contract into a debugging dump.

Evaluation failure (500):

```json
{
  "error": "compatibility evaluation failed",
  "admission": { "status": "blocked", "verdict": null }
}
```

### 5.4 `run_lock` (ratified)

* Acquired **after** request validation and **before** evaluation, because
  evaluation performs environment/GPU observation and GGUF reads against the
  same machine whose single runtime and VRAM the lock protects; running two
  evaluations concurrently with an inference is precisely what the lock
  exists to prevent.
* Acquisition is non-blocking; a held lock answers **409** (unchanged).
* Held across evaluation, admission and inference, released in `finally` on
  every path (unchanged release discipline).
* **Admission denied:** the lock is released and 403 returned; no subprocess is
  launched.
* **Evaluation error:** the lock is released and 500 returned; nothing is
  launched (fail-closed).
* **Runtime failure:** the lock is released and 503 returned; the next request
  is served normally.
* **Concurrency:** at most one of {evaluate, admit, execute} runs at a time.
  There is no queue; the second caller is told 409 rather than made to wait.
* Chat session open takes the same lock for the same reason (it launches a
  runtime); per-session turn contention keeps its existing separate
  `_ChatSessionRegistry.turn_lock` → 409 semantics.

### 5.5 Reuse (binding constraint on the implementation)

The implementation must reuse `evaluate_model_compatibility`, `to_admission`,
`EvaluationAdmission` and `execute_model`. It must **not** create
`HttpEvaluationService`, `HttpAdmissionManager`, `ApiExecutionManager`,
`ExecutionPolicyV2`, `ServePolicyEngine`, `CompatibilityManager` or any
equivalent second admission implementation. The only new code permitted is
transport-level: ordering, lock scope, and the two response projections.

## 7. Documentation obligations for the implementing block

`serve_command`'s docstring, `USAGE_FLOW` and the README `serve` section must
state, after implementation: what `serve` is; that it executes models; that
strict admission **does** apply; what 403 and 500 mean; that 500 is an
evaluation *error* and not a denial; that loopback is a network-exposure
property and not the reason admission applies; and the relationship to
`execute` (same policy) and to `run` (unchanged legacy policy). The words
"read-only", "status-only" and "inspection-only" must not describe `serve`.

## 8. Test obligations for the implementing block

* `POST /v1/run` happy path reaches 200 through evaluation → admission →
  execution.
* A strict-incompatible model is rejected with the ratified 403 and the
  admission body, and **no runner is invoked**.
* `insufficient_evidence` is denied (it is not in `_ADMITTING_VERDICTS`).
* An evaluation that raises produces 500 with the evaluation-failure body, and
  no runner is invoked.
* `run_lock`: 409 while held; lock released after a denial, after an
  evaluation error and after a runtime failure.
* A drift test that fails if `app/api.py` stops consulting
  `to_admission` / `execute_model`, or if the documented mapping and the
  implemented mapping diverge.
* A drift test that `run` remains legacy and un-cut-over.

## 9. Implementation Deferred

B9.51 ratifies the contract and does not implement it. The implementation
touches every execution route in `app/api.py`, changes the observable status
vocabulary, and requires the drift tests of §8 — a separate semantic boundary
with its own review. Forcing it here would mix a decision and a behavioural
change to a live HTTP contract in one commit.

```text
DECISION RATIFIED
IMPLEMENTATION DEFERRED TO B9.52
```

Until B9.52 lands, the code still behaves as B9.50 documented. That is now
explicitly *transitional*, not endorsed: the ratified policy is Option A and
the current behaviour is a known, documented gap.

## 10. Required B9.52 Scope

1. `app/api.py`: order `evaluation → to_admission → execute_model` inside the
   `run_lock`, for `POST /v1/run` and chat session open; add the 403 and 500
   projections of §5.3; extend 422 with `warnings`.
2. Keep the existing 400/404/409/503 behaviour byte-identical.
3. Do not touch the evaluation engine, `run_service`, `run_model`.
4. `docs/` + README + `USAGE_FLOW` + `serve_command` docstring per §7.
5. Tests per §8, plus the derating of
   `tests/test_api_serve_contract.py::ExecutionGatePolicyTests::test_serve_does_not_apply_strict_evaluation`,
   which asserts the pre-B9.51 gap and must be inverted by the block that
   closes it.


No status code previously returned changes meaning. Two previously-200
request classes change outcome; that is the point of the decision and is
announced in README and `--help` by B9.52, not silently.


No exception type, message, traceback or path is returned; the cause is logged
server-side, consistent with the existing rule "never leak details to the
client" (`app/api.py` 500 handler). `status: "blocked"` is reported
truthfully: no admission was minted, so nothing was authorized.

`warnings` continue to travel on the success path (unchanged) and on 422 where
`ExecutePreparationError.warnings` exists (new, additive).

Two mappings are load-bearing and are stated explicitly because B9.23 left
them open:

* **403 for denial, not 422.** A denied admission is not a malformed request:
  the payload is valid and the caller cannot fix it by changing the payload.
  422 is reserved for preparation failures. 403 is used here in the "the
  server understood and refuses" sense, not as an authorization concept —
  CastleArq has no identities, roles or permissions.
* **500 for an evaluation error, not 403.** B9.48 (P0-2) established that an
  evaluation that *raised* is not an evaluation that *denied*. Collapsing the
  two would re-introduce exactly that conflation over HTTP. 500 is used
  because the server failed to determine admission; the internal structure of
  `StrictEvaluation` (and any check that is `unknown` / `not_applicable`) is
  never conflated with an incompatible verdict. `to_admission(None)` still
  yields a blocked admission, so execution remains fail-closed either way —
  the 500 changes only what the client is told.

`ExecuteAdmissionDeniedError` raised from inside `execute_model` (defence in
depth; unreachable when the mapping above is honoured) maps to **403**.

* **Error body required:** yes — ratified in §5.3.
* **`run_lock`:** must be defined relative to evaluation — §5.4.
* **Compatibility with current design:** high; the pieces exist.
* **New decisions required:** mapping, body, lock scope (decided here).
* **Risk of a second execution policy:** none — it removes the second policy.

### B — Deliberate legacy/ungated HTTP execution

* **Coherence with `execute`:** none. Two execution guarantees in one product.
* **Coherence with `run`:** total, but by inheriting a path B9.19 §13 keeps
  only for historical reasons.
* **Coherence with the admission model:** admission becomes opt-in per caller,
  so a guarantee that exists for the CLI is absent for the surface most likely
  to be automated (scripts, agents, future GUI).
* **Impact on the evaluation types:** none.
* **Impact on HTTP:** none — nothing to define, which is exactly the problem:
  the policy stays implicit and unpinned.
* **Status mapping / error body / `run_lock`:** not required, and therefore
  remain UNDEFINED.
* **Compatibility with current design:** trivially high (it is the status quo).
* **New decisions required:** a *product* reason, which does not exist in the
  repository. The three candidate arguments are all rejected: "it already
  works that way" is B9.23's non-decision restated; "loopback makes it safe"
  is a network-exposure property that B9.50 §4 already documented as a
  *different* property; "it is easier to reuse" is a convenience, not a
  contract.
* **Risk of a second execution policy:** maximal — it institutionalises it.

Because B9.23 selected Candidate A (a new CLI `execute` subcommand) and
explicitly deferred Candidate B (the HTTP API) *until* those four questions
were answered. Nothing in B9.24–B9.50 answered them. B9.43 ratified the
`to_admission` converter; B9.48 ratified evaluation-error-vs-denial; B9.50
documented the resulting divergence as "deliberate" while its own RATIONALE
admits the cause was that the K-3 decision "was never ratified". That is a
record of *absence of decision*, not a product argument for legacy HTTP
execution.
