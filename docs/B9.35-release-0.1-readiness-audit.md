## 3. Definition of 0.1

For this audit:

> CastleArq 0.1 is the first publicly distributable version that lets a technical user install the package, verify the external runtime, acquire and verify an artifact, and execute a local model through documented interfaces without depending on the development checkout or internal architecture knowledge.

This definition is compatible with the current product direction and with B9.29/B9.47. It does not require feature completeness, multi-runtime support, GUI, or a hosted service.

## 7. Runtime Boundary

Discovery resolves the official `llama` executable from `PATH`. It validates executability, probes the launcher, records identity/version/build/capabilities, and presents one of:

```text
AVAILABLE
NOT_FOUND
FOUND_UNUSABLE
PROBE_ERROR
UNKNOWN
```

Current environment evidence:

```text
Executable: /home/brunapc/.local/bin/llama
Version: 0.4.0-dev (build 10909)
Availability: AVAILABLE
Capabilities: GGUF, CPU, Vulkan
Exit code: 0
```

Boundary responsibilities are aligned with the release definition:

* CastleArq discovers, probes, diagnoses, records capability, and refuses unsupported use.
* The user/environment provides Python, llama.cpp, drivers/backends, network, and storage.
* CastleArq does not install or compile llama.cpp, install drivers, configure CUDA/Vulkan/ROCm, or require `sudo`.
* `llama-cli`, `llama-server`, and `llama.app` are not automatic substitutes for the official `llama` launcher.

The boundary is clear and implemented. For a user outside the developer community, the README explains that llama.cpp is external but does not prescribe a supported installation method, tested version range, or compatibility matrix. That is a P1 onboarding gap because CastleArq's probe contract depends on a particular modern launcher interface.

## 9. Artifact Lifecycle

### Logical versus physical

* Logical model: canonical `MODEL_ID` selected from the catalog.
* Physical artifact: a concrete GGUF file identified by artifact ID, filename, quantization, size, checksum, and local storage location.

The resolver and strict adapter preserve this separation. ModelStore owns persistence and derives physical state from the filesystem and manifest expectations.

### Lifecycle evidence

* Official path: `$XDG_DATA_HOME/castlearq/models` or `~/.local/share/castlearq/models`.
* Legacy read path: `~/.local/share/localai-hub/models`.
* `list` is read-only and does not create an empty store.
* Download writes streaming `.part` data, validates expected size and SHA-256, and publishes without replacing an existing final file.
* Preflight rejects missing, partial, inconsistent, symlink, non-regular, wrong-size, and checksum-mismatched artifacts.
* Real B9.46 evidence found one 4,683,073,536-byte Qwen GGUF with manifest, SHA-256, and derived `VERIFIED` state.

Temporary publication files are unlinked as part of downloader mechanics. Dedicated cleanup operations exist, but the required user journey does not automatically delete final models. Package uninstall does not remove the external user-level ModelStore.

Artifact lifecycle is **DEMONSTRATED** with a real artifact and strongly automated; clean acquisition into a new store remains a release-drill gap.
