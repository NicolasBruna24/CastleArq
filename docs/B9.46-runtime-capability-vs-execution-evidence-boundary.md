# B9.46.27 — Runtime Capability vs Execution Evidence Boundary

## 1. Executive Summary

CastleArq mezcla dos planos en `runtime artifact support`: capability/compatibility conocida antes de ejecutar y evidencia de consumo obtenida durante o después de ejecutar. No existe aún un tipo productivo `RuntimeArtifactEvidence`; el nombre del check evoca el segundo concepto, pero su única fuente (`RuntimeKnowledge.supports_artifact`) es una assertion Knowledge abstracta. `LlamaCppRunner` es el primer punto que realmente lanza el runtime.

La admission puede exigir Knowledge y facts pre-ejecución; no puede exigir que la ejecución no autorizada ya haya consumido el artifact. La implementación queda bloqueada porque faltan un producer de observation y scope estructurado para el booleano.

## 2. Current Concepts

| Concepto | Significado real | Owner actual |
|---|---|---|
| `RuntimeKnowledge` | Facts normativos supplied: nombre, listas de formats/architectures/backends/model types y `supports_artifact` tri-estado. | `app/compatibility_evaluator.py` |
| `RuntimeCapability` | Executable detectado: path, version, availability, formats, backends, prompt modes y one-shot; lo produce `detect_llama_capability()`. | `app/runtimes.py` |
| Format/architecture/backend support | Matching exacto entre input y listas RuntimeKnowledge. | Checks strict y selección operacional |
| Runtime artifact support | Hoy, sólo tri-estado de `RuntimeKnowledge.supports_artifact`; no es observation. | Check strict |
| `RuntimeArtifactEvidence` | No existe como clase productiva; B9.46.23 sólo documentó su contrato. | Contrato documental |
| `ExecutionResult` | Resultado one-shot: success, exit code, stdout, stderr, error, warnings, diagnostics y métricas. | Runner/execution |
| `LlamaCppRunner` | Runner que construye argv con `--model` y lanza el proceso. | `app/runner.py` |

## 3. Runtime Knowledge

`RuntimeKnowledge` es dato normativo supplied, no inventario autodetectado. El evaluator es intérprete y nunca detector. Las listas expresan soporte/rechazo explícito por matching exacto; ausencia significa UNKNOWN. La proyección desde capability/registry no deriva legítimamente `supports_artifact` de formats, backends o GGUF reader; una version observada tampoco justifica por sí sola ese booleano.

## 4. Runtime Capability

Runtime Capability responde: ¿qué puede afirmar CastleArq sobre un runtime antes de ejecutar el artifact? Legítimamente puede afirmar disponibilidad, invocabilidad, versión/build, formats, backends, prompt modes y aliases expuestos por probes version/help/devices. No sustituye la prueba de que una instancia concreta consuma un artifact concreto.

`RuntimeCapability` es operacional y efímera; `execute_model()` obtiene una capability fresca por invocación. No es `RuntimeArtifactEvidence`.

## 5. Physical Artifact Evidence

`GGUFArchitectureEvidence` documenta estructura/arquitectura física mediante lectura read-only. `ArtifactExecutionPreflight` valida existencia, regularidad, symlink, tamaño y checksum y devuelve `ExecutableArtifact`. Esto demuestra qué hay en el archivo, no que un runtime lo consuma. `qwen2` no es identidad, no reemplaza `ModelSpec.architecture` y no autoriza `supports_artifact`.

## 6. Runtime Execution Evidence

La definición estricta es `runtime instance X + concrete artifact Y + execution context Z + observed consumption/loading/acceptance + provenance`.

- Proceso iniciado: launch/readiness, no consumo.
- Artifact aceptado: interacción runtime-artifact, no necesariamente inferencia.
- Artifact cargado: lectura/consumo, no estandarizado todavía.
- Inferencia ejecutada: operación runtime con artifact.
- Terminación exitosa: éxito completo, no sólo compatibilidad.

Por tanto, “runtime consumed artifact” no significa “runtime process started”. La evidencia pertenece al execution boundary, después de admission, preflight y selección.

## 7. RuntimeKnowledge.supports_artifact Audit

- `True`: assertion Knowledge runtime-level explícita proyectada como PASSED. No significa por sí sola “consume cualquier artifact” ni “consume este artifact”.
- `False`: assertion negativa explícita en el scope abstracto, proyectada como FAILED. No prueba por sí sola que un build concreto rechazara el archivo.
- `None`: no hay assertion autoritativa supplied; se proyecta UNKNOWN y, siendo determinante, produce INSUFFICIENT_EVIDENCE. No es incompatibilidad.

Un producer legítimo debe ser un registry/bridge con assertion normativa y scope/provenance. Faltan runtime identity, version/build, platform, backend, format, architecture, artifact reference y provenance. `bool | None` sólo representa un claim abstracto; no cuantificación, artifact concreto ni observation. No puede representar correctamente A/B/C/D de la pregunta de soporte.

## 8. _check_runtime Audit

`_check_runtime(knowledge)` sólo ejecuta `True -> PASSED`, `False -> FAILED`, `None -> UNKNOWN`, usando `runtime.name` y `runtime.supports_artifact`. Es un intérprete Knowledge, no un observador. PASSED significa únicamente que la assertion supplied es positiva; no significa formato, arquitectura o consumo. Es correcto sólo bajo una definición ratificada de assertion Knowledge pre-ejecución.

## 9. Strict Evaluation Audit

| Check | Clasificación | Realidad |
|---|---|---|
| identity | LOGICAL RELATION + STATIC KNOWLEDGE | Relación declarada, no ejecución. |
| format | STATIC KNOWLEDGE + LOGICAL RELATION | `artifact.format` contra RuntimeKnowledge. |
| architecture | STATIC KNOWLEDGE + PHYSICAL EVIDENCE opcional | GGUF puede aportar valor físico, no consumo. |
| runtime artifact support | RUNTIME CAPABILITY abstracto | `supports_artifact`; no execution evidence. |
| backend | RUNTIME CAPABILITY + LOGICAL RELATION | Backend contra Knowledge; GPU no implica soporte. |
| capabilities | STATIC KNOWLEDGE | Flags del modelo contra requisitos. |

Strict eval agrega categorías distintas en un claim funcional; no necesita hacerlas la misma evidencia. El problema es semántico: el nombre no indica que el check sea sólo capability.

## 10. EvaluationAdmission Audit

Flujo real: `evaluate_model_compatibility -> compose/evaluate_strict -> to_admission -> execute_model -> fresh capability -> _check_admission -> compatibility/preflight/selection -> ModelRunner.run`.

`EvaluationAdmission` sólo transporta `status` y `verdict`; es deny-by-default. Antes de ejecución puede exigir facts de artifact, capability, Knowledge de format/architecture/backend/capabilities y preflight. No puede exigir que esa ejecución ya consumió el artifact. Exigirlo produciría `Admission -> Execution -> Evidence -> Admission`, circular. La evidencia post-ejecución no debe retroalimentar la admission de la primera ejecución.

## 12. RuntimeArtifactEvidence Audit

El contrato B9.46.23 combina identity/version, artifact reference/format/architecture, backend, observation y provenance. No es Knowledge: describe una observación operacional contextualizada. Su ownership natural es Execution / Operational Evidence, producida en execution boundary y consumida post-ejecución. No existe clase, producer ni consumidor productivo actualmente; no se crea en este bloque.

## 13. ExecutionResult Audit

`ExecutionResult` representa un one-shot completado o fallido: `success`, `exit_code`, stdout/stderr, error, warnings, diagnostics y métricas. `LlamaCppRunner` lo produce después del subprocess. Es destino natural conceptual de evidence post-ejecución, pero actualmente no conserva runtime identity/version, artifact reference ni backend; no tiene por tanto el contrato B9.46.23 completo. No se agregan campos en esta auditoría.

## 14. Boundary Analysis

| Concept | Scope | Source | Available pre-execution? | Requires execution? | Persistent? |
|---|---|---|---:|---:|---:|
| Runtime Knowledge | Assertions runtime | RuntimeKnowledge/bridge | Sí | No | No en el value object |
| Runtime Capability | Executable/version/availability/formats/backends | RuntimeCapability/probes | Sí | No para detectar; probe operacional | Efímera |
| Physical Artifact Evidence | Bytes/estructura | GGUF reader/preflight | Sí | No | Efímera |
| RuntimeArtifactEvidence | Runtime+artifact+context+observation | Contrato B9.46.23, sin producer | No | Sí | No |
| ExecutionResult | Resultado one-shot | Runner | No | Sí | No |

La arquitectura `Knowledge + physical facts + capability -> Strict Evaluation -> Admission -> execution -> RuntimeArtifactEvidence -> ExecutionResult` es coherente y causalmente correcta sólo si el check permanece como assertion Knowledge con scope. Hoy no es completa: falta scope estructurado, falta producer de evidence y `ExecutionResult` no conserva toda la identidad requerida. UNKNOWN pre-ejecución debe bloquear fail-closed; UNKNOWN post-ejecución no se convierte en FAILED ni Knowledge.

## 15. Architectural Decision

1. Si `runtime artifact support` permanece en Strict Evaluation, debe significar assertion normativa pre-ejecución de soporte runtime-artifact dentro de scope explícito, no consumo observado.
2. `bool | None` no basta para un artifact concreto: faltan runtime/version/build/platform/backend/format/architecture/artifact/provenance.
3. El check debe seguir independiente de format, architecture y backend sólo si Knowledge define una assertion separada; no se fusionan por inferencia.

4. `RuntimeArtifactEvidence` debe quedar exclusivamente en ejecución/post-ejecución.
5. `ExecutionResult` es destino natural conceptual, pero su contrato actual no basta para transportar toda la evidencia.
6. Antes de admission se exigen Knowledge/facts disponibles; después se observan aceptación/carga/inferencia/éxito sólo de una ejecución concreta.
7. UNKNOWN permanece UNKNOWN; requerido pre-ejecución produce INSUFFICIENT_EVIDENCE y deny-by-default. Errores de probe no son FAILED.
8. La circularidad se elimina prohibiendo que Admission dependa de Evidence de la ejecución que autoriza.
9. La implementación queda bloqueada hasta ratificar scope/producer de Knowledge o boundary post-ejecución.

## 16. Consequences

- Mantener el nombre sin redefinirlo perpetúa la ambigüedad.
- Inferir PASSED desde format, architecture, backend o GGUF sería sobreafirmar.
- Un probe `LlamaCppRunner` pre-admission sería un segundo pipeline, no permitido aquí.
- No se persiste evidence ni se duplica `assess_model()`.
- La separación propuesta conserva evaluator puro, fail-closed y runner como único lugar natural de observación.

## 17. Next Block

Elegir y documentar una sola alternativa antes de implementar:

1. Ratificar Knowledge semantics para `supports_artifact`, con scope y producer completos.
2. Ratificar post-execution semantics, retirar/reclasificar el check de admission y definir producer/consumidor desde `ExecutionResult`.
3. Ratificar mantener UNKNOWN hasta que exista Knowledge calificada.

No implementar ninguna alternativa antes de esa ratificación.

## 18. Verdict

RUNTIME-CAPABILITY-EVIDENCE-BOUNDARY-BLOCKED

La frontera conceptual está identificada, pero faltan un `RuntimeArtifactEvidence` productivo, un producer de observation y scope estructurado para `RuntimeKnowledge.supports_artifact`. La ejecución real sólo aparece después de admission en `LlamaCppRunner`; el check actual no puede significar simultáneamente capability y evidencia concreta.
