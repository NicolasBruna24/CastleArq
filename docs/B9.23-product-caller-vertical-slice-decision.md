## 3. Product Surface Candidates

### Candidate A — existing CLI (`app/main.py`)

There is no `app/cli.py`; the CLI is `app/main.py` (argparse, 1160 lines).

- **Legacy status**: the module is Presentation, but its `run` and `chat`
  commands are legacy-coupled: `run_model` imports and orchestrates
  resolver + `run_service.prepare` + `ExecutionRequest` + `LlamaCppRunner`
  directly; module-level imports include `selection`, `runtimes`, `runner`,
  `resolver`, `hardware`, `downloads`.
- **Coupled to `run_service`?** Yes, for the existing commands: the CLI run
  path uses `run_service.prepare` (imported as `_prepare`) and duplicates
  the rest of `run_once` inline.
- **Can it call Application without an architectural hybrid?** Yes, for a
  *new* command function: Presentation → Composition Root → Application is
  the sanctioned direction. The legacy coupling of other commands in the
  same file does not infect a new function that imports only
  `application_wiring` + `execute_model`.
- **Does reuse require modifying legacy?** No, if a *new* subcommand is
  added beside `run` (Option 2, §9). Rewiring the existing `run` to
  `execute_model` would be a CUTOVER and is rejected (§5).
- **Contract compatibility**: argparse already validates `model_id`
  (positional `provider`) and `--prompt`, `--quantization`, `--filename` —
  a near 1:1 match with `execute_model()`'s inputs.

### Candidate B — existing HTTP API (`app/api.py`)

- **A real HTTP surface exists**: stdlib `http.server.ThreadingHTTPServer`,
  routes `GET /health | /v1/models | /v1/artifacts`, `POST /v1/run |
  /v1/chat/sessions | /v1/chat/...`. It never calls the CLI nor
  `subprocess` (documented and tested).
- **Currently calls Legacy**: yes — `POST /v1/run` → `run_service.run_once`
  under a global `run_lock`; chat → `open_chat_session`.
- **HTTP ↔ Application separation**: good adapter hygiene already — DTOs
  and parsers (`RunRequestDTO {model_id, prompt, quantization, filename,
  timeout}`, `RunResponseDTO {model_id, output, exit_code, warnings}`) are
  pure functions separate from transport.
- **Could it become an adapter of `execute_model()`?** Structurally yes;
  `RunRequestDTO` ≈ `execute_model()` inputs. But doing it *now* forces
  undecided decisions (K-3): which status for `ExecutePreparationError`
  (legacy distinguishes 404 model-not-found vs 422 preparation, but
  `execute_model` folds model-not-found into `ExecutePreparationError`);
  which status for `ExecuteAdmissionDeniedError` (403? — absent from the
  legacy vocabulary); whether `ExecutionResult.success=False` maps to 503
  (legacy `RunExecutionFailedError`) or stays 200-with-error; `run_lock`
  semantics for the new route. Rewiring `/v1/run` itself would migrate a
  live legacy contract (cutover — rejected).
- **Verdict**: a valid *second* candidate surface, deferred until a block
  decides K-3's HTTP status mapping.

### Candidate C — new minimal product surface

No architectural home exists for a brand-new surface: `pyproject.toml` has
no `console_scripts`, there is no `app/product/`, no packaging entry point.
A new module would either be unreachable by users (⇒ not a product surface)
or still need registration in `main()`'s command dispatch (⇒ Candidate A
with extra structure). Creating a surface package now would be anticipatory
structure (§12 violation). **Rejected** — revisit only if the CLI proved
unsuitable (it does not).

### Other Candidates

- **`app/chat.py` / chat sessions**: a real product feature, but
  session-oriented (persistent process via `open_chat_session`) and legacy —
  a different use case than one-shot `execute_model()`. Not the first
  caller.
- **`app/execution_service.py` (`ModelExecutionService`)**: legacy
  application orchestration imported only by tests/observation modules —
  not a product surface (no user entry point).
- **`app/evaluate_compatibility.py`**: an Application use case with **no
  product caller at all** (test-only) — noted for §11, not a candidate.
- **GUI**: does not exist in the repository — not a candidate.

## 5. Selected Product Surface

**Candidate A — the existing CLI (`app/main.py`), via a NEW `execute`
subcommand** coexisting with the legacy `run`/`chat` commands.

Argumentation:

1. It is the innermost user-reachable surface of the repository
   (`python3 -m app.main`); no packaging or transport must exist for it to
   work, so the slice stays minimal (§12).
2. It is the only candidate whose contract (argparse flags) already matches
   `execute_model()` without inventing a DTO or deciding status codes
   (Contract clarity, Error projection).
3. A new subcommand is additive: legacy `run`/`chat`/`POST /v1/run` keep
   calling `run_service` unchanged — Option 2 coexistence (§9), exactly the
   trajectory B9.19 §13 already sanctioned ("ExecuteModel grows beside
   run_service").
4. CLI error projection is the surface's own established convention —
   message on stderr + exit code — so K-3's HTTP questions are not
   introduced anywhere (§11 of the brief: a non-HTTP surface must not grow
   HTTP concepts).
5. The HTTP API (Candidate B) remains the prime candidate for the *next*
   surface block, once K-3 fixes the status mapping; choosing it now would
   make tests freeze decisions nobody has taken.

## 6. Product Caller Location

```text
app/main.py
  ├── execute_command(...)            ← the Product Caller (new, B9.24)
  │     imports ONLY: app.application_wiring (composition),
  │                   app.execute_model    (Application),
  │                   app.execution types if needed for projection,
  │                   sys/typing           (Presentation concerns)
  ├── main() dispatch                 ← registers "execute" (new, B9.24)
  ├── run_model(...)                  ← legacy, untouched
  └── chat_model(...)                 ← legacy, untouched
```

Why this location respects current boundaries:

- **Direction**: `main.py → application_wiring → execute_model` is
  Presentation → Composition → Application. `execute_model.py` and
  `application_wiring.py` never import `main.py`, `api.py` or any framework
  (W7 structural property, already tested in
  `tests/test_execute_model_wiring.py`).
- **application_wiring.py has zero framework dependencies**, so importing
  it from the CLI adds no reverse dependency and violates no W1–W8 wiring
  property established in B9.22.
- **No new module, no new layer**: the repository's valid location for a
  CLI caller is `main.py` — every other command function lives there
  (Candidate C rejected).

## 7. Proposed Caller Contract

### Input

```text
execute_command(
    model_id: str,           # positional (existing `provider` slot, as run/chat)
    prompt: str,             # --prompt, required, non-empty
    *,
    quantization: str | None = None,   # existing shared flag
    filename: str | None = None,       # existing shared flag
    out=None, err=None,                 # injectable streams (test seam, chat precedent)
) -> int                                  # exit code: 0 ok, 1 failure, 2 usage
```

Deliberately NOT exposed in the first slice (no concrete justification):

- `timeout_seconds` — CLI `run` never exposed it; default suffices; adding
  `--timeout` is a trivial later extension if evidence appears.
- `backend_preference` — expert knob; the selector already decides; the
  brief forbids automatically exposing every `execute_model()` parameter.
- `admission` — unused in slice 1 (§11); no evaluation surface exists.

Validation lives entirely in argparse + the caller's own usage check
(exit 2), mirroring `run_model`. No DTO: argparse *is* the request DTO for
a CLI; `api.py`'s DTOs exist only because JSON serialization is a boundary
the CLI does not have.

### Output

```text
ExecutionResult  →  CLI projection (no DTO created)
  success=True   → result.stdout → out; runner result.warnings → err
                   as "Warning: <w>"; exit 0
  success=False  → result.stderr → err; error.message → err
                   ("Execute error: <message>"); warnings → err;
                   exit 1
```

`ExecutionResult` is projected field-by-field inside `execute_command`;
no `ExecuteCommandResponse`/DTO type is created (§12: no generic DTOs).
Justification if one is ever needed: only when a second projection target
(JSON) appears — i.e. when the HTTP adapter block lands.

### Error Projection

| Application-owned signal (app/execute_model.py) | Product Caller projection (CLI) |
| --- | --- |
| `ExecutePreparationError` (message, warnings) — includes resolution failure, unavailable capability, legacy compatibility gate, preflight, selection, backend-preference, request validation | `Execute error: <message>` + `Warning: ...` lines → err; exit 1 |
| `ExecuteAdmissionDeniedError` (subclass; unreachable in slice 1 since admission is not passed) | identical path; its message carries the denial reason — no special casing |
| `ExecutionResult(success=False, error=ExecutionErrorInfo{code, message})` | stderr + `Execute error: <error.message>` → err; exit 1 |
| Missing/blank model_id or prompt | usage text → err; exit 2 (CLI convention, before composition) |
| Unexpected exception (bug) | not caught — same policy as other CLI commands; never translated by the caller |

The Application owns the taxonomy (exceptions + `ExecutionResult`); the
caller only translates to stream + exit code. No HTTP status codes appear
anywhere in this table (§11, §14).

## 10. Composition Boundary

How the caller obtains dependencies:

```python
# inside execute_command (B9.24) — once per invocation, never cached
from .application_wiring import compose_execute_model_dependencies
from .execute_model import execute_model, ExecutePreparationError

deps = compose_execute_model_dependencies()   # fresh capability snapshot
result = execute_model(
    model_id, prompt,
    quantization=quantization,
    filename=filename,
    dependencies=deps,
)
```

- One composition call per command invocation matches the B9.22 contract
  ("MUST NOT be cached between invocations" — capability is a snapshot).
- The caller reaches the composition root **without touching any
  infrastructure itself**: `main.py`'s new function must not import
  `runner`, `selection`, `resolver`, `runtimes`, `hardware`, or
  `run_service` (B9.24 test: structural AST check mirroring W7).
- No service locator, no DI framework, no container — one function call
  (§12).

## 11. Evaluation → Execution

Reminder (B9.18): `EvaluateModelCompatibilityResult` is an audit/decision
record, **not** an execution ticket. The forbidden pattern is:

```text
evaluate() → pass the whole result → execute()
```

Current facts verified in this audit:

- `evaluate_model_compatibility()` (B9.16) has **no product caller at all**
  (test-only). There is no evaluation surface to integrate yet.
- `execute_model(admission=...)` accepts an `EvaluationAdmission`
  (`{status, verdict}` — a *summary copy*, deny-only, deny-by-default).
- Nothing in `app/` constructs `EvaluationAdmission` today; only
  `tests/test_execute_model.py` does.

**Decision for the first vertical slice: Option 1 — evaluation is NOT
used.** The caller passes `admission=None`, so the transitional legacy gate
(compatibility → preflight → selection) is the only gate, exactly as
B9.19 §7 specifies ("`None` means the caller carries no evaluation signal").

- No adapter is required before the slice (closure answer **N: no**).
- Documented gap for a later block: an adapter mapping
  `EvaluateModelCompatibilityResult {status, evaluation.verdict}` →
  `EvaluationAdmission {status, verdict}` will be needed only when a
  product surface exposes evaluation *and* wants its signal to influence
  execution. That is a separate block; do not build it speculatively.

## 12. Real Execution Preconditions

Distinguishing what already exists from what B9.24 needs:

```text
Wiring validation (B9.22, done)
  real dependencies → real runner → EXECUTABLE_MISSING   (test-controlled)

Vertical slice validation (B9.24 target)
  Product Caller → execute_model() → real runner → actual executable
    → actual model artifact → actual invocation → ExecutionResult
    → exit 0 with model output
```

External preconditions the environment must satisfy BEFORE B9.24 runs
(verified as requirements by the audit; **nothing installed or configured
in B9.23**):

1. **Runtime/executable**: `detect_llama_capability()` must return
   available + `invocable=True` with a real `executable_path` (llama.cpp
   `llama-cli` or equivalent installed on PATH/configured).
2. **Model + artifact**: a model present in `get_catalog()` with its
   artifact already downloaded and verified in `ModelStore` (size/checksum
   pass `ArtifactExecutionPreflight.validate`). Download happens beforehand
   via the legacy `download` command — B9.24 performs no downloads.
3. **Backend/hardware**: a backend the `RuntimeBackendSelector` accepts
   (GPU present or CPU fallback) and the legacy compatibility gate
   (`assess_model` + `config/`) permits.
4. **Permissions/config**: store and executable readable; `config/`
   present as the project already expects.
5. **No HTTP constraints**: the slice runs in-process (CLI), so the
   `run_lock`/loopback concerns of `api.py` do not apply.

If any precondition is missing on the machine, the slice still validates
end-to-end up to a truthful preparation error (exit 1) — the *success*
path is what precondition 1–2 gate.

## 13. I-5 Warning Merge

Verified state of `app/execute_model.py` (unchanged since B9.20):

- warnings are merged (`compatibility_warnings + selection.warnings`,
  dedup) only on **exception paths** — they ride on
  `ExecutePreparationError.warnings`;
- the **success path returns `runner.run(...)` verbatim** (B9.19 §10
  requires verbatim), whose `warnings` contain only runner-produced
  warnings — compatibility/selection warnings are silently dropped;
- legacy `run_once` by contrast merges all three sources into
  `RunOutcome.warnings`.

**Classification: NON-BLOCKER.**

- Justification: I-5 does not prevent any step of the vertical slice; the
  chain executes and projects a truthful `ExecutionResult`. Its effect is
  fidelity — on success the CLI `execute` command may print fewer
  `Warning:` lines than legacy `run`.
- Why not fixable here (or in the caller): merging warnings into the
  returned `ExecutionResult` is an **Application** responsibility
  (`execute_model.py`, currently a B9.23 prohibited file); merging them in
  the Product Caller would move Application logic into Presentation and is
  forbidden. I-5 stays open as its own follow-up block.

## 14. K-3 Error Projection

Known issues in projecting `ExecutionResult` → Product Response:

1. **Dual channel**: preparation/admission failures arrive as *exceptions*
   (`ExecutePreparationError` / `ExecuteAdmissionDeniedError`) with
   warnings attached; execution failures arrive as a *value*
   (`ExecutionResult.success=False`, `error: ExecutionErrorInfo{code,
   message}`); success is the same value with `success=True`. A caller must
   handle all three — §7's table does exactly that, no Application change
   needed.
2. **`error_type`/code vocabulary**: `ExecutionErrorCode` names exist on
   the result; the CLI projects only `error.message` (codes would leak
   infrastructure vocabulary without a defined product meaning).
3. **Warnings/messages**: warnings are strings; preparation warnings reach
   the caller via the exception (handled), success-path warnings limited by
   I-5 (§13).
4. **HTTP status mapping**: **does not exist and is not created here.**
   The legacy precedent (404/422/503/200) does not transfer cleanly because
   `execute_model` folds model-not-found into `ExecutePreparationError`
   and has no admission-denied status precedent.

**Classification: NON-BLOCKER for the selected (CLI) surface; remains an
OPEN DECISION for any future HTTP adapter.** Justification: the chosen
surface has no status codes to map (§5.4), so nothing undecided is frozen
by the slice. No HTTP status mapping is implemented in B9.23.

## 15. B9.24 Exact Scope

B9.24 implements **exactly** the following (and nothing else):

1. **`app/main.py` — register the command**
   - add `"execute"` to the `choices` tuple in `main()`;
   - add `"execute": ("prompt", "quantization", "filename")` to
     `supported_flags`;
   - add the dispatch branch calling the new function (same
     exactly-one-model-id rule as `run`);

   - `execute_command(model_id, prompt, *, quantization=None,
     filename=None, out=None, err=None) -> int` exactly per §7: usage
     validation (exit 2) → `compose_execute_model_dependencies()` →
     `execute_model(...)` (admission not passed) → projection of
     `ExecutePreparationError` and `ExecutionResult` → exit 0/1;
   - imports limited to `application_wiring`, `execute_model`, and
     Presentation concerns (`sys`/typing); no `run_service`, `runner`,
     `selection`, `resolver`, `runtimes`, `hardware`.
3. **Tests (new file, e.g. `tests/test_main_execute.py`)**
   - usage/validation behavior (exit 2);
   - success projection (exit 0, stdout/warnings placement) with injected
     seams — following `test_main_chat.py` stream injection and the
     `test_execute_model_wiring.py` environment-seam pattern;
   - preparation-error projection (exit 1, message + warnings on stderr);
   - `ExecutionResult(success=False)` projection (exit 1);
   - structural AST check that `execute_command` references
     `compose_execute_model_dependencies` + `execute_model` and NOT
     `run_service`/`LlamaCppRunner` (caller-side mirror of W7);
   - one caller-level test proving the composed deps reach a real
     `execute_model` invocation (spy on `execute_model` or reuse the B9.22
     seam style).
4. **Real execution attempt**: run
   `python3 -m app.main execute <model-id> --prompt ...` on a machine
   satisfying §12 and record the outcome (exit 0 + output = slice closed;
   truthful preparation error = slice demonstrated to the environment's
   current limits).
5. **Explicitly out of B9.24**: no changes to `execute_model.py`,
   `application_wiring.py`, `run_service.py`, `execution_service.py`,
   `runner.py`, `selection.py`, `execution.py`, `compatibility.py`,
   `runtimes.py`, `api.py`, `chat.py`; no legacy `run`/`chat`/`/v1/run`
   rewiring; no HTTP endpoint, no DTO, no status mapping; no admission /
   evaluation wiring; no I-5 fix; no K-3 resolution; no commit/push
   (commit strategy stays a separate decision).
