This is deliberately smaller than the future Model Library.

## 3. Purpose

Make the existing catalog/discovery capability reachable through an **existing**
product surface, without introducing Model Library UX.

B9.86 built an application boundary and deliberately shipped it without a
production caller. B9.87 gives that boundary its first real integration. It
creates no new domain, no new provider and no new product area.

## 4. Architectural rationale

### 4.1 B9.86 readiness

B9.86 is **ALLOCATED, IMPLEMENTED, VERIFIED and CLOSED** (register §26.12,
implementation commit `6cb9e1d8ab9c6f0790210a590ef48dcc11690822`). Its realized
scope is recorded in §26.5 and matches §25.2 exactly.

### 4.2 Absence of a production caller

`castlearq/catalog_query_service.py:145` `ModelCatalogQueryService` is referenced
in production code only by `castlearq/application_wiring.py:86` and
`application_wiring.py:361` (`compose_catalog_query_service`). Every behavioural
caller is in `tests/test_b986_catalog_query_service.py`. The composition
function's own docstring records the absence as deliberate
(`application_wiring.py:374-377`).

Over `castlearq/`, `ModelDiscovery.search(...)` has exactly one production call
site: `catalog_query_service.py:174`. The **search** side of the B9.80 discovery
port — as opposed to the **inspect** side consumed by B9.85 — is therefore
unreachable from any user-facing surface.

### 4.3 Existing composition boundary

The composition seam already exists and already defaults to the real provider:
`compose_catalog_query_service(discovery_provider=None)` builds
`ModelCatalogQueryService(HuggingFaceDiscoveryProvider())`
(`application_wiring.py:384-389`). `HuggingFaceDiscoveryProvider.search()`
(`castlearq/sources/huggingface_discovery.py:298`) implements validation, opaque
cursor decoding, `Link`-header pagination and candidate construction. No new
infrastructure is required.

### 4.4 Product Vision alignment

Recorded against `docs/product-vision-adr.md` §3–§14. That ADR is authoritative
for product direction; this decision applies it and does not reinterpret it.

```text
D1  — reduce uncertainty between user intent and local runtime invocation:
      "find" is the stage at which the uncertainty is highest, and it is the
      stage CastleArq answers without requiring the user to reason about
      repositories, filenames and quantizations by hand.
D3  — discovery and model selection are part of the staged Job To Be Done.
      The JTBD begins at "find"; until search is reachable, CastleArq answers
      only from an already-known model id.
D5  — discovery belongs to the core product capability. This decision exposes
      an existing core step; it does not extend the core chain.
D6  — Model Library UX remains a separate future decision, NOT ALLOCATED and
      NOT authorized (ADR §8; register §26.12). A pass-through CLI adapter is
      explicitly not a Model Library surface.
D10 — product surfaces consume shared application capabilities. The CLI adapter
      consumes the existing application boundary and adds no domain logic.
D11 — avoid adding new user-facing surfaces while allocated core capabilities
      remain without callers. B9.86 is the one fully implemented, fully tested,
      caller-less core capability in the repository; this decision closes that
      debt using an already-existing surface rather than creating a new one.
```

D4 (multi-runtime platform thesis) and D12 (unvalidated thesis) are **not**
engaged by this decision: B9.87 makes no claim about runtimes and no claim about
market demand.

## 5. Alternatives considered

Recorded without ranking. Each is described as considered and as deferred or
outside this allocation, with the condition that would make it viable later.

### 5.1 Application-level Chat lifecycle boundary

Moving the chat session lifecycle — currently `_ChatSessionEntry` (`api.py:550`),
`_ChatSessionRegistry` (`api.py:580`), `MAX_CHAT_SESSIONS` (`api.py:225`), the
shutdown gate and the turn-slot semantics — out of the HTTP transport into an
application boundary.

**Deferred, not declined.** ADR D7 (§9) names this seam directly and states that
future Chat work should move conversation/session lifecycle toward an
application-level boundary. It is architecturally sound and testable. It is not
selected here because it produces **no new user-visible capability**: every
current chat endpoint already has a live caller and full test coverage, so the
work relocates working behaviour rather than connecting unreachable capability.
A `Conversation` abstraction is **not** invented here: none exists in the
repository, and ADR D7 forbids reconstructing one.

**Viable later when:** a second chat surface is authorized (GUI, or an
OpenAI-compatible endpoint), at which point transport-owned lifecycle becomes a
functional blocker rather than a structural debt; or when chat itself becomes the
human's next priority.

### 5.2 `run` / `execute` convergence

Making the CLI `run` path consume the shared application execution service, as
B9.85 did for `cmd_download`.

**Deferred, blocked by an unresolved policy question, not by missing code.**
`main.py:1608-1679` still builds an `ExecutionRequest` and calls the runner
directly, whereas `execute` uses the application boundary. However `run` follows
a distinct legacy admission path, and no decision analogous to B9.51/B9.52 has
been taken for `run`. Refactoring it would silently change a live user-facing
command's policy behaviour, which is a human architectural decision rather than
an implementation detail.

**Viable later when:** the project owner rules on whether `run` must adopt the
strict B9.52 admission contract. That ruling, not the refactor, is the blocker.

### 5.3 Second runtime / runtime abstraction expansion

**Premature, and deferred.** `runner.ModelRunner` (`runner.py:45`) is a genuine
ABC with a single implementation (`LlamaCppRunner`, `runner.py:57`); `runtimes.py`
is llama-specific throughout. `docs/B9.47` §15 already set the condition: a
second **real** runtime and a cross-runtime policy decision must be demonstrated
first, and another round of abstraction without that is explicitly discouraged.
ADR D5 (§7) states that runtime abstraction is architectural direction, not
current capability, and that additional runtime implementations are future work.

**Viable later when:** a concrete second runtime exists with a real,
product-motivated reason, and a cross-runtime policy is ratified. Also deferred
by D11 sequencing while an allocated core capability lacks a caller.

### 5.4 Model Library UX

**Outside this allocation and not authorized by it.** ADR D6 (§8): "Model
Library UX remains unallocated and is NOT authorized for implementation by this
ADR". Register §26.12 records `Model Library UX: NOT ALLOCATED`. Model cards,
quantization-selection UI, compatibility warnings and hardware-suitability
recommendation are all Model Library concerns and are excluded (§7.2 of this
record).

**Viable later when:** an explicit human decision authorizes it — and, per D11,
only after the catalog/query capability has a real caller, which is precisely
what B9.87 establishes.

### 5.5 GUI

**Outside this allocation and not authorized by it.** ADR D8 (§10): "GUI is NOT
authorized for implementation by this ADR." Register §26.12 records
`GUI: NOT AUTHORIZED`. It would also be the clearest D11 violation in the
current repository state.

**Viable later when:** an explicit human decision authorizes it.

### 5.6 No allocation pending external product evidence

Allocating nothing until external user feedback, usage data or experiments
validate or falsify the thesis (ADR D12, §14).

**Considered and not selected, but not rejected.** It is a legitimate option
under D12: the thesis is explicitly unvalidated and no usage evidence demands a
new capability. It is not selected because B9.87 requires no new domain, no new
provider and no new user population — it exposes capability that is already
implemented, tested and closed behind a boundary that already exists. Deferring
it does not reduce the product's exposure; it only defers the moment at which
that exposure becomes visible.

**Viable later — or now — if the project owner weighs unvalidated external
evidence more heavily than closing an already-identified integration gap.** That
is a human judgement about evidence tolerance, not an architectural fact.

## 6. Product boundary

> **B9.87 exposes an existing core capability; it does not create a new Model
> Library product surface.**

The distinction is the load-bearing invariant of this allocation and is
inherited verbatim from B9.86 §25.2 (`Application boundary != Model Library UX`,
§25.5). The CLI adapter:

* invokes one existing application use case;
* presents what that use case returns;
* interprets nothing.

It introduces no variant browsing, no quantization browsing, no suitability or
compatibility information, no ranking and no acquisition.

## 8. Architectural invariants

B9.87 MUST preserve the boundary:

```text
CLI
 ↓
Application
 ↓
Discovery port
 ↓
Discovery provider
```

The CLI must NOT directly instantiate or depend on `HuggingFaceDiscoveryProvider`
for the new search path; the provider is constructed by the application
composition root, as it already is in `application_wiring.py:388`.

The CLI must NOT:

* contain discovery logic;
* reinterpret the catalog query contract;
* rank or recommend models;
* transform the search feature into a Model Library.

The existing B9.86 `ModelCatalogQueryService` contract remains **authoritative**
and is consumed as-is. Its pass-through guarantees (candidates by identity,
`next_cursor` verbatim and opaque, exactly one `search()` call per `query()`
call, no second validation authority) are not renegotiated by B9.87.
