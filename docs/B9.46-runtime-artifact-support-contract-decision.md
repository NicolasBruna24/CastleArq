# B9.46.21 — Runtime Artifact Support Contract Decision

## 1. Executive Summary

B9.46.20 established that `runtime artifact support` is evaluated solely from `RuntimeKnowledge.supports_artifact`:

```text
True  -> PASSED
False -> FAILED
None  -> UNKNOWN
```

The current bridge intentionally projects only runtime-to-format, runtime-to-architecture and runtime-to-backend relations. It does not project a runtime-to-artifact relation, and the Knowledge model has no explicit artifact subject for this check. The observed successful execution of one local `llama.cpp 0.4.0-dev` build with one GGUF is environment evidence, not a general normative assertion.

**Verdict: `RUNTIME-ARTIFACT-SUPPORT-CONTRACT-BLOCKED`.**

## 2. Current State

```text
RuntimeKnowledge.supports_artifact = None
runtime artifact support = UNKNOWN
overall = INSUFFICIENT_EVIDENCE
```

`artifact format support = PASSED`, `model architecture support = PASSED` and `identity = PASSED` do not populate this field.

## 3. Current Contract

`app/compatibility_evaluator.py::_check_runtime(knowledge)` interprets the tri-state `RuntimeKnowledge.supports_artifact` field. The evaluator is pure and does not inspect files, probe executables, select backends or infer support from other checks.

`app/knowledge_bridge.py::project_knowledge()` explicitly documents that `supports_artifact` remains `None` unless the registry itself contains a runtime→artifact claim. The current bridge representable kinds are:

```text
FORMAT
ARCHITECTURE
BACKEND
```

There is no `ARTIFACT` knowledge kind in the current projection contract.

## 4. RuntimeKnowledge Semantics

`RuntimeKnowledge` is a declarative, caller-supplied input to the evaluator. It is not a capability detector and does not own runtime installation state.

`supports_artifact` is documented as a runtime-level claim distinct from the format claim. Its current type is a bare tri-state:

```text
bool | None
```

The type cannot express runtime version, build, platform, backend, model family, architecture, artifact format or artifact identity. It therefore cannot, by itself, express a qualified runtime-artifact relation.

The fields `supported_formats`, `supported_architectures` and `supported_backends` express separate relations. They are not combined by `_check_runtime`.

## 5. Meaning of Artifact

The current code does not define whether `artifact` means any artifact, any GGUF, one format, one model family, one architecture or one concrete artifact. `ModelArtifact` contains strict artifact facts, but the `supports_artifact` field does not reference that object and receives no artifact parameter.

The only defensible current interpretation is the broad, unqualified phrase used by the evaluator documentation. The repository does not establish a narrower contract. Treating it as “any GGUF” or “this concrete GGUF” would be an unratified semantic expansion.

## 6. Runtime Observation vs Knowledge Assertion

Observed locally:

```text
/home/brunapc/.local/bin/llama
llama.cpp 0.4.0-dev
GGUF loaded and executed
CPU and Vulkan available
```

This proves a fact about one executable/build/platform/artifact combination. It does not prove:

```text
llama.cpp supports artifact=True
```

`RuntimeCapability` is operational detection: executable, version, available, formats, backends and one-shot. It must not be silently converted into normative Knowledge.

## 7. Version / Build / Backend Dependencies

The repository does not establish that runtime artifact support is runtime-wide, version-independent or build-independent. The observed runtime is a specific `0.4.0-dev` build. The capability detector records version but the strict check does not consume it.

The contract also does not establish whether support requires CPU, Vulkan or another backend. Backend availability is a separate selector/compatibility concern. A static unconditioned assertion would overstate what is currently known.

A qualified assertion would require a contract for runtime version, build, platform and backend scope. No such projection is defined for `supports_artifact`.


## 8. Authority Analysis

| Candidate | Ownership | Authority | Decision |
|---|---|---|---|
| `RuntimeKnowledge.supports_artifact` | strict evaluation input | normative runtime claim | Correct check input, but lacks qualification |
| `KnowledgeRegistry` | declarative knowledge | authoritative facts and provenance | No current runtime→artifact representation |
| `RuntimeCapability` | environment detection | current local runtime observation | Operational source, not normative |
| `LlamaCppRunner` | execution | actual process result | Too late and artifact/backend specific |
| GGUF metadata | physical artifact | artifact structure | Does not answer runtime support |

No current authority can legitimately emit the unqualified `supports_artifact=True` requested by the strict check.

## 9. Lifecycle Analysis

`supports_artifact` is intended to be supplied Knowledge, not persisted artifact state. A static Knowledge assertion would change when the Knowledge dataset is revised, not when a process happens to run.

A dynamic claim would be environment-derived and would need a distinct evidence representation and invalidation policy. The repository has no such representation for this relation. The current field cannot safely serve both static Knowledge and dynamic probe results.

## 10. `UNKNOWN` Semantics

Current `UNKNOWN` is correct: the strict evaluator received no explicit runtime-artifact assertion.

It does not mean runtime unavailable, and it does not mean artifact format unsupported. It means the required normative runtime-artifact claim is missing from the supplied Knowledge contract. The observed runtime capability is not converted automatically into that claim.

The existing fail-closed behavior remains: `UNKNOWN` contributes to `INSUFFICIENT_EVIDENCE` and does not become `FAILED` or `ALLOW`.

## 11. Architectural Options

### A — Unconditioned static Knowledge assertion

```text
llama.cpp -> supports_artifact=True
```

Rejected as currently unjustified. It omits version, build, platform, backend and artifact scope. The local observation is insufficient to establish universal support.

### B — Qualified Knowledge assertion

A future relation could express runtime + applicable scope + artifact category/format + support state. This requires a new explicit Knowledge relation or an extension of the existing model. It is not implementable by reusing `supported_formats` without a decision about scope and identity.

### C — Runtime-derived evidence

The capability detector could report a dynamic observation such as “this build can load GGUF”. `RuntimeCapability` carries operational facts, but no qualified runtime-artifact claim. Treating it as Knowledge would violate the declarative/operational separation. This requires a separate evidence contract.

### D — Explicit runtime-artifact evidence representation

A separate ephemeral representation could express runtime, version/build, backend, artifact scope and provenance. It would be necessary if the intended claim is “this local runtime can load this artifact”, rather than static Knowledge. It is not created here.

## 12. Decision

```text
RUNTIME-ARTIFACT-SUPPORT-CONTRACT-DECISION = BLOCKED

RUNTIME-ARTIFACT-SUPPORT-AUTHORITY =
  undefined until the scope of the claim is decided

RUNTIME-ARTIFACT-SUPPORT-SOURCE =
  no current source is authoritative for a general runtime->artifact assertion

RUNTIME-ARTIFACT-SUPPORT-LIFECYCLE =
  undefined; static Knowledge and dynamic environment evidence are not interchangeable

RUNTIME-ARTIFACT-SUPPORT-PERSISTENCE = NONE
```

The current field remains the strict check input, but the repository cannot safely decide whether its value should be populated by static Knowledge, qualified Knowledge, dynamic runtime evidence or a new explicit evidence representation.

The first missing decision is the scope and authority of the word `artifact` in this check. A static `llama.cpp -> True` assertion must not be added merely because one local execution succeeded.

## 13. Implementation Boundary

A future implementation block may proceed only after ratifying one of these contracts:

1. Static Knowledge: define a qualified runtime→artifact Knowledge relation and its scope, or explicitly define the broad claim and limits.
2. Dynamic evidence: define a separate ephemeral runtime-artifact evidence value including runtime identity/version/build, artifact scope, backend and provenance.
3. Existing-field adaptation: explicitly define `supports_artifact` as dynamic and extend the bridge/capability contract; this is not currently safe because the bridge is declarative and pure.

The future block must add tri-state tests and must not infer support from format PASSED, architecture PASSED, backend detection or one successful execution.

## 14. Explicit Non-Goals

- no `llama.cpp -> supports_artifact=True` declaration;
- no backend implementation or selection;
- no changes to architecture support (`llama`, `qwen2`, `qwen3`);
- no `ModelSpec`, `ArtifactSpec` or `ModelArtifact` changes;
- no GGUF reader changes;
- no persistence changes;
- no evaluator or admission changes;
- no new service, manager, registry or evidence abstraction;
- no change to `UNKNOWN`, `FAILED` or deny-by-default semantics;
- no commit and no push.
