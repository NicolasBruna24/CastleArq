# B9.0 — Compatibility Engine Design

Estado: **decisión de diseño documentada — sin implementación.**

Este documento define el **contrato conceptual del Compatibility Engine**:
la futura capa que interpreta conjuntamente `Model`, `ModelArtifact`,
`Hardware`, `Runtime` y `Backend` para determinar qué tan viable es ejecutar
un artifact/modelo concreto en un entorno determinado.

B9.0 **no implementa** el Compatibility Engine. No crea clases Python,
módulos, tests, CLI ni lógica de ningún tipo. Es una fase exclusivamente
documental, coherente con la filosofía establecida desde B1:

```text
detect → interpret → propose → user decides → user acts → verify → re-diagnose
```

CastleArq **no modifica automáticamente el sistema del usuario**.

La implementación del motor corresponde a **B9.1**, que debe poder
construirse directamente sobre este contrato sin reinterpretar las
decisiones arquitectónicas principales.

---

## 1. Responsabilidad del Compatibility Engine

El Compatibility Engine será responsable de interpretar conjuntamente:

```text
Model
ModelArtifact
Hardware
Runtime
Backend
```

y determinar qué tan viable es ejecutar un artifact/modelo concreto en un
entorno determinado.

Conceptualmente:

```text
Model
   │
   ▼
ModelArtifact
   │
   ├──────────────┐
   ▼              ▼
Hardware        Runtime
   │              │
   └──────┬───────┘
          ▼
 Compatibility Engine
          │
          ▼
 CompatibilityResult
```

### Qué aporta cada pieza

```text
Model
    Qué es.

ModelArtifact
    Qué distribución concreta se ejecuta.

Hardware
    Qué recursos/capacidades existen.

Runtime
    Qué software puede ejecutar.

Backend
    Mediante qué tecnología concreta se ejecuta.

Compatibility Engine
    Qué significa la combinación de todos ellos.
```

- **Model** describe qué es el modelo (identidad, procedencia, arquitectura,
  capacidades). Nunca contiene conclusiones.
- **ModelArtifact** describe una distribución concreta del modelo (formato,
  precisión, cuantización, almacenamiento, contexto). Nunca contiene
  requisitos rígidos de VRAM/RAM.
- **Hardware** describe las capacidades/recursos observados de la máquina
  (GPU, VRAM, RAM, CPU, almacenamiento). Observación, no interpretación.
- **Runtime** describe el software capaz de ejecutar modelos (p. ej.
  llama.cpp) y qué formatos/capacidades soporta.
- **Backend** describe la tecnología concreta de ejecución cuando
  corresponda (p. ej. Vulkan, CPU). Un runtime puede exponer varios.
- **Compatibility Engine** interpreta estas piezas conjuntamente y produce
  un `CompatibilityResult` explicable. Es la única pieza que concluye.

## 2. Estados de compatibilidad

El motor usa exactamente estos cuatro estados conceptuales:

```text
COMPATIBLE
COMPATIBLE_WITH_CONDITIONS
INCOMPATIBLE
INSUFFICIENT_EVIDENCE
```

### COMPATIBLE

Existe evidencia suficiente para considerar compatible el escenario
evaluado bajo las condiciones conocidas. No significa "óptimo" ni "rápido"
(ver §22): significa que la evidencia disponible no revela impedimentos.

### COMPATIBLE_WITH_CONDITIONS

El escenario puede ser viable, pero requiere condiciones explícitas o
existen restricciones relevantes. Ejemplos conceptuales:

- CPU offloading;
- configuración específica;
- contexto limitado;
- determinados backends;
- recursos compartidos.

No asumir todavía condiciones concretas si no existe evidencia
suficiente: las condiciones se declaran solo cuando la evidencia las
sostiene (ver §10).

### INCOMPATIBLE

Existe evidencia suficiente de que el escenario evaluado **no puede
satisfacerse** bajo las condiciones analizadas. Debe distinguirse de
UNKNOWN: `INCOMPATIBLE` es una conclusión afirmativa de inviabilidad, no
la ausencia de información.

### INSUFFICIENT_EVIDENCE

No existe evidencia suficiente para determinar compatibilidad. Este estado
es especialmente importante para CastleArq. Nunca convertir:

```text
unknown
```

en:

```text
incompatible
```

sin evidencia explícita.

---

## 3. Principio UNKNOWN

Regla arquitectónica (continuidad de B2, B5, B7 y B8):

```text
None / unknown = información desconocida
```

No significa:

```text
false
```

ni:

```text
incompatible
```

Ejemplo:

```text
VRAM = 32 GB
runtime memory estimator = unavailable
```

El resultado correcto no sería:

```text
INCOMPATIBLE
```

sino algo equivalente a:

```text
INSUFFICIENT_EVIDENCE
```

La ausencia de un estimador de memoria es un hueco de evidencia, no una
prueba de que el modelo no cabe. El motor solo puede declarar
`INCOMPATIBLE` cuando posee evidencia afirmativa de inviabilidad
(p. ej. formato no soportado por ningún runtime disponible, o una
estimación fiable que excede los recursos observados).

---

## 4. Evidence / procedencia

El Compatibility Engine no debe ser una caja negra.

Cada check importante debe poder explicar:

```text
qué se evaluó
qué se esperaba
qué se observó
qué resultado produjo
de dónde provino la evidencia
```

Conceptualmente:

```text
CompatibilityCheck

check:
    "artifact format supported"

expected:
    GGUF

observed:
    GGUF

status:
    PASSED

evidence:
    artifact.format = "GGUF"
    runtime = "llama.cpp"
```

No es necesario definir todavía las clases Python. El contrato
conceptual es:

- un **check** tiene identidad (qué se evaluó) y resultado
  (`PASSED` / `FAILED` / `UNKNOWN`, coherente con la semántica de
  evidencia de B2/B7);
- **expected** es el requisito derivado del artifact/runtime;
- **observed** es el hecho aportado por hardware/runtime/artifact;
- **evidence** cita las fuentes concretas (atributos de dominio,
  observaciones, cálculos) que sostienen el resultado;
- el resultado global se deriva de los checks y es trazable hasta
  ellos (ver §21).

## 5. Tres niveles de conocimiento

El diseño introduce explícitamente esta distinción:

```text
OBSERVED
    ↓
CALCULATED
    ↓
INFERRED
```

### OBSERVED

Dato obtenido directamente de una fuente de observación. Ejemplo:

```text
VRAM = 32 GB
```

Es un hecho medido/detectado. Tiene la máxima autoridad epistémica del
sistema: todo lo demás se construye sobre observaciones o se declara
desconocido.

### CALCULATED

Dato derivado mediante una operación determinista a partir de datos
conocidos. Ejemplo conceptual:

```text
available_memory = total_memory - reserved_memory
```

Es reproducible: mismas entradas, mismo resultado. Debe citar las
observaciones de las que deriva.

### INFERRED

Conclusión derivada de evidencia y/o cálculos. Ejemplo:

```text
CPU offloading may be required
```

Es una interpretación con incertidumbre. Regla arquitectónica: **CastleArq
no debe presentar una inferencia como si fuera una observación**. Cada
nivel viaja etiquetado, y el resultado explica en qué nivel vive cada
afirmación.

---

## 6. Separación entre storage y runtime memory

Esta separación es OBLIGATORIA.

Un artifact puede tener:

```text
storage_size = 18 GB
```

pero eso NO significa:

```text
runtime_memory_required = 18 GB
```

No asumir:

```text
archivo = memoria de ejecución
```

La memoria de ejecución depende contextualmente de factores como:

```text
model
artifact
quantization
context
runtime
backend
offloading
configuration
```

Por eso el almacenamiento es un dato del artifact (`OBSERVED` o
declarado), mientras que la memoria de ejecución es siempre un producto
`CALCULATED`/`INFERRED` del Memory Estimator (ver §7) bajo una
configuración concreta — nunca una propiedad fija del modelo.

---

## 7. Memory Estimator

El Memory Estimator se diseña conceptualmente como una pieza **separada**
del Compatibility Engine:

```text
Compatibility Engine
       │
       ├── Functional checks
       ├── Format checks
       ├── Runtime checks
       ├── Capability checks
       │
       └── Resource compatibility
                  │
                  └── Memory Estimator
```

El Memory Estimator será una capacidad futura. En B9.0:

- NO implementar fórmulas;
- NO implementar estimaciones;
- NO inventar constantes;
- NO inventar overheads;
- NO afirmar requisitos de VRAM basados únicamente en el tamaño del
  archivo.

Factores que deberá considerar posteriormente (sin fórmulas exactas
todavía). Como mínimo, conceptualmente:

- model weights;
- quantization;
- KV cache;
- context length;
- runtime overhead;
- activations;
- CPU/GPU offloading;
- configuración de ejecución.

Regla de honestidad: si el estimador no puede calcular (p. ej. parámetros
desconocidos, cuantización desconocida, overhead no modelado), debe
declarar la estimación como desconocida — lo que normalmente conduce a
`INSUFFICIENT_EVIDENCE` en la rama de recursos (§3), nunca a un número
inventado.

---

## 8. Functional compatibility

El documento diferencia compatibilidad funcional de compatibilidad de
recursos.

Functional compatibility puede considerar posteriormente:

```text
Model architecture
Artifact format
Runtime
Backend
Capabilities
```

Ejemplo conceptual:

```text
GGUF
+
llama.cpp
+
Vulkan
```

puede ser funcionalmente compatible.

Pero:

```text
functional compatibility
```

NO implica automáticamente:

```text
resource compatibility
```

Un modelo puede ser ejecutable por el runtime pero no tener recursos
suficientes para una configuración determinada. Por eso el resultado
global distingue ambas dimensiones: lo funcional responde "¿puede este
software procesar este artifact?", lo resource responde "¿cabe en esta
máquina bajo esta configuración?". Ambas deben resolverse para declarar
`COMPATIBLE`.

---

## 9. Resource compatibility

Los recursos pueden incluir conceptualmente:

```text
VRAM
RAM
storage
context-related memory
CPU
```

Pero no convertirlos todavía en requisitos rígidos del Model domain.
Recordar:

- Hardware describe los recursos disponibles.
- ModelArtifact describe el artifact.
- Runtime describe el entorno de ejecución.
- Compatibility Engine interpreta la relación.

Cada dimensión de recurso produce su propio veredicto parcial
(`PASSED` / `FAILED` / `UNKNOWN` por check, §4); un recurso desconocido
no veta el escenario, lo deja en `INSUFFICIENT_EVIDENCE` salvo que otra
dimensión aporte evidencia afirmativa de inviabilidad. Ninguna dimensión
puede "compensarse" silenciosamente con otra: si la VRAM no alcanza pero
el offloading a CPU es viable, eso se expresa como
`COMPATIBLE_WITH_CONDITIONS` con la condición explícita (§10), no como
`COMPATIBLE` a secas.

---

## 10. Conditions

El resultado puede contener condiciones. Ejemplo conceptual:

```text
COMPATIBLE_WITH_CONDITIONS

Conditions:
- CPU offloading may be required.
- Context may need to be limited.
```

Pero una condición NO es una acción ejecutable. Distinguir claramente:

```text
Condition:
    "CPU offloading may be required"

Action:
    "configure llama.cpp with X"
```

El Compatibility Engine puede producir la primera. No debe ejecutar ni
producir directamente acciones de modificación del sistema. Las acciones
pertenecen a una capa posterior de recomendación/remediación (el mismo
corte que B5/B7 ya practican: proponer datos, nunca ejecutar).

Reglas de condiciones:

- cada condición cita la evidencia que la motiva (§4);
- ninguna condición puede contradecir un check `FAILED` (un escenario
  inviable no se "condiciona" hasta volverlo viable);
- las condiciones son declarativas e inspeccionables, nunca comandos.

---

## 11. Warnings

Los warnings son información relevante que no necesariamente cambia el
estado principal. Ejemplo:

```text
Runtime memory estimation unavailable.
```

No convertir automáticamente un warning en:

```text
INCOMPATIBLE
```

Un warning documenta incertidumbre o riesgo residual dentro de un veredicto
que la evidencia sí sostiene (p. ej. `COMPATIBLE` funcional con estimación
de memoria aproximada, o `COMPATIBLE_WITH_CONDITIONS` con recursos
compartidos no medidos). Si la información faltante impide concluir, el
estado correcto es `INSUFFICIENT_EVIDENCE` (§3), no un warning añadido a
un veredicto afirmativo.

---

## 12. Purity y seguridad

El Compatibility Engine es conceptualmente una capa pura de
interpretación. NO debe:

```text
subprocess
filesystem writes
network access
downloads
installation
system modification
model execution
runtime execution
```

Puede recibir información previamente obtenida por otras capas. La
arquitectura mantiene:

```text
Observation
    ↓
Domain interpretation
    ↓
Result
```

y no:

```text
Compatibility Engine
    ↓
executes commands
    ↓
changes system
```

Esto mantiene la filosofía de CastleArq: observar, interpretar y proponer;
el usuario decide y actúa.

## 13. API conceptual

No implementar código, pero documentar una API conceptual equivalente a:

```python
result = compatibility_engine.evaluate(
    model=model,
    artifact=artifact,
    hardware=hardware,
    runtime=runtime,
)
```

Resultado conceptual:

```python
CompatibilityResult(
    status=...,
    checks=(...),
    conditions=(...),
    warnings=(...),
    evidence=(...),
)
```

No convertir esto en código real durante B9.0. Notas de contrato:

- `evaluate` es pura: mismos insumos, mismo resultado; no realiza I/O.
- `status` es uno de los cuatro estados de §2.
- `checks` es la lista de `CompatibilityCheck` (§4) que sostiene el
  veredicto; vacía solo si el estado es `INSUFFICIENT_EVIDENCE` por falta
  total de modelo evaluable.
- `conditions` solo puede ser no vacía con
  `COMPATIBLE_WITH_CONDITIONS` (§10).
- `warnings` nunca determina `status` por sí solo (§11).
- `evidence` agrega las fuentes citadas por los checks, sin duplicar
  dominios enteros.

---

## 14. No usar booleano simple

Explicar por qué esto es insuficiente:

```text
compatible = true
```

Un booleano colapsa distinciones que el usuario necesita para decidir:

- `compatible` (evidencia suficiente, sin restricciones conocidas);
- `compatible but conditional` (viable bajo condiciones explícitas —
  informarlas cambia la decisión del usuario);
- `incompatible` (evidencia afirmativa de inviabilidad — no intentarlo);
- `insufficient evidence` (no se sabe — decidir a ciegas sería imprudente).

Además, un booleano no puede explicar *por qué*. El motor debe poder
representar estos cuatro estados **y explicar por qué** (§21): el veredicto
sin su cadena checks→evidencia es inutilizable para la filosofía
"el usuario decide".

## 15. Ejemplos conceptuales

Sin afirmar cifras de memoria inventadas en ningún ejemplo.

### Ejemplo A — suficiente evidencia

```text
Model:
    known architecture
    known parameters

Artifact:
    GGUF
    Q4_K_M

Hardware:
    32 GB VRAM
    48 GB RAM

Runtime:
    llama.cpp

Backend:
    Vulkan
```

Posible resultado: `COMPATIBLE`, si los checks funcionales pasan (formato
soportado por el runtime, backend disponible) **y** la rama de recursos
resuelve con estimaciones fiables dentro de lo observado. Si alguna
dimensión de recursos solo resuelve bajo supuestos — p. ej. el modelo cabe
en VRAM únicamente con parte de las capas en CPU — el resultado correcto
es `COMPATIBLE_WITH_CONDITIONS` con la condición explícita
("CPU offloading may be required"), no un `COMPATIBLE` silencioso.

### Ejemplo B — unknown

```text
Model:
    parameters = unknown

Artifact:
    format = unknown

Hardware:
    known

Runtime:
    known
```

Resultado:

```text
INSUFFICIENT_EVIDENCE
```

Sin arquitectura/parámetros no hay estimador que calcular; sin formato no
hay check funcional que pasar. La evidencia disponible (hardware y runtime
conocidos) no basta para ninguna conclusión afirmativa.

### Ejemplo C — funcionalmente compatible pero recursos desconocidos

```text
functional compatibility = PASSED
resource compatibility = UNKNOWN
```

Resultado:

```text
INSUFFICIENT_EVIDENCE
```

Saber que el runtime *puede* procesar el artifact no dice si *cabe*.
Un `UNKNOWN` en recursos no se compensa con un `PASSED` funcional: el
veredicto global es tan débil como su dimensión más débil sin evidencia
afirmativa en contrario.

### Ejemplo D — condición

Escenario: artifact GGUF cuantizado, runtime llama.cpp con backend Vulkan
disponible, VRAM observada suficiente solo para los pesos pero no para
pesos + KV cache al contexto máximo declarado.

Resultado conceptual:

```text
COMPATIBLE_WITH_CONDITIONS

Conditions:
- Context may need to be limited.
```

La condición nombra exactamente la restricción que vuelve viable el
escenario, con su evidencia (checks de VRAM vs estimación a contexto
completo `FAILED`, a contexto reducido `PASSED`). No es una orden de
configurar nada: es información para que el usuario decida.

## 16. Multi-GPU

El diseño futuro debe poder considerar:

```text
GPU 0
GPU 1
...
```

y eventualmente:

```text
single GPU
multi-GPU
distributed execution
```

Pero B9.0 no implementa ninguna lógica multi-GPU. No asumir que `gpus[0]`
será siempre suficiente para el Compatibility Engine futuro: la limitación
actual de B1–B7 (primera GPU) es una simplificación de observación, no una
decisión del motor. Cuando el motor evalúe recursos, deberá recibir el
conjunto completo de GPUs observadas y razonar sobre agregación como
dimensiones explícitas con su propia evidencia, no como un detalle oculto.

## 19. Relación con B8

El diseño respeta las decisiones de B8.0/B8.1:

- Model y ModelArtifact están separados.
- Un Model puede tener múltiples artifacts.
- Precision y Quantization están separadas.
- `QuantizationStatus` distingue:
  - UNKNOWN
  - NOT_QUANTIZED
  - QUANTIZED
- `nominal_bits` no representa memoria.
- `storage_size` no representa runtime memory.
- `None` representa información desconocida.
- El Model domain no contiene VRAM/RAM requirements.
- La compatibilidad es contextual.

No modificar B8 para acomodar B9. Cómo las usa el motor sin cambiarlas:

- el check funcional lee `artifact.format` tal cual; un formato
  desconocido (`None`) produce check `UNKNOWN`, nunca `FAILED`;
- `QuantizationStatus.UNKNOWN` deja la rama de pesos del estimador sin
  calcular (§7); `QUANTIZED` con `nominal_bits` conocido la habilita;
  `NOT_QUANTIZED` la habilita con la precisión declarada;
- `storage_size` alimenta checks de disco (`storage`), jamás checks de
  VRAM/RAM (§6);
- la ausencia de requirements en el dominio es precisamente lo que obliga
  al motor a calcularlos contextualmente en vez de leerlos.

No se detectó tensión conceptual que requiera cambiar B8; si B9.1
encontrara una, deberá documentarse como cuestión futura antes de tocar
el dominio.

## 20. Relación con B7

El mismo principio:

```text
diagnose
    ↓
interpret
    ↓
propose
    ↓
user decides
    ↓
user acts
    ↓
verify
```

Compatibility Engine:

```text
interpret
```

No debe saltarse hacia:

```text
user acts
```

No debe ejecutar comandos. El motor vive estrictamente en la fase
`interpret`: produce veredictos, condiciones y warnings como datos. Si un
escenario resulta `COMPATIBLE_WITH_CONDITIONS`, la aplicación de esas
condiciones pertenece al usuario (o a una futura capa de recomendación
estilo B5), y su verificación posterior al ciclo B7 — nunca a una
ejecución del propio motor.

## 21. Diseño orientado a explicación

Una de las metas futuras de CastleArq es que el usuario pueda entender:

```text
Why compatible?
Why conditional?
Why incompatible?
Why unknown?
```

La explicabilidad es requisito arquitectónico. No basta con devolver un
estado. Existe una ruta conceptual obligatoria:

```text
Result
  ↓
Checks
  ↓
Evidence
  ↓
Reasoning / interpretation
```

Cada "por qué" se responde recorriendo la ruta hacia abajo: el estado por
sus checks, cada check por su expected/observed, cada observed por su
evidencia y su nivel de conocimiento (§5). No implementar un motor de
razonamiento ni LLM en B9.0: la explicación es estructural (trazabilidad
de datos), no generativa.

---

## 22. Compatibilidad no significa rendimiento

Documentar explícitamente:

```text
compatible
```

NO significa:

```text
fast
efficient
optimal
recommended
```

Un modelo puede ser técnicamente compatible y tener mal rendimiento. El
benchmarking y la performance prediction quedan fuera de B9.0. El motor
responde "¿puede ejecutarse bajo estas condiciones?", nunca "¿merece la
pena ejecutarlo?" — esa es una decisión del usuario con información que
CastleArq hoy no produce.

---

## 23. Compatibilidad no significa seguridad

También distinguir:

```text
compatibility
```

de:

```text
trust
security
provenance
```

El hecho de que un artifact sea compatible no significa que sea confiable
o seguro. Estas áreas pertenecen a futuras capas (provenance avanzada en
B9+ según B8.0 §3.2). El motor nunca debe presentar un veredicto de
compatibilidad como aval de confianza, ni degradar compatibilidad por
sospechas no evidenciadas: son dimensiones ortogonales con sus propios
estados y su propia evidencia.
