Status: **COMPLETE**

## 1. Executive Summary

`tests/test_shared_preparation.py::SharedPreparationTests::test_run_and_chat_both_call_prepare`
fails in CI on 3.10/3.11/3.12/3.13 with `AssertionError: False is not true` on
`self.assertTrue(prepare.called)` at line 196 (the `chat_model` assertion).

OBSERVED / REPRODUCED root cause: **the test's `chat_model` half does not patch
`app.main.detect_llama_capability`.** `chat_model` performs a real runtime probe
(`detect_llama_capability()`) and returns early with exit code 1 when
`capability.invocable` is false — *before* reaching `_prepare`. On the
maintainer's machine a real `llama` binary exists on `PATH`
(`/home/brunapc/.local/bin/llama`), so the probe succeeds and `_prepare` is
reached. On GitHub Actions runners no `llama` binary exists, so the probe fails,
`chat_model` returns 1 at `app/main.py:965-970`, and the patched `_prepare` is
never called.

REPRODUCED locally by removing `llama` from `PATH`:

```
# with llama on PATH -> 1 passed
# PATH=/usr/bin:/bin -> 1 failed, identical assertion at tests/test_shared_preparation.py:196
```

Classification: **TEST DEFECT** (non-hermetic test that depends on host
`PATH`/runtime availability), with a secondary **PATCH/INTERCEPTION DEFECT**
character (the `run_model` half patches `detect_llama_capability`, the
`chat_model` half does not — an asymmetry inside the same test). The production
behaviour is correct: `run_model` and `chat_model` *do* both delegate to the
same `app.main._prepare`.

## 3. Test Contract

The test claims: "run_model and chat_model must both delegate to the shared `_prepare`".

OBSERVED details requested by the block:

1. **Mock creation:** `unittest.mock.Mock()` for `exe`, `capability`,
   `preflight`, `selector`, `model_store`, `runner`, `session`; `patch(...)`
   used for `app.main.ModelArtifactResolver`, `app.main._prepare`,
   `app.main.LlamaCppRunner`, `app.main.detect_hardware`,
   `app.main.detect_llama_capability`, `app.main.detect_backends`,
   `app.main.start_chat_session`.
2. **Patched symbol:** `app.main._prepare`, `return_value=preparation`
   (a `SimpleNamespace` with `executable_artifact`, `target`,
   `compatibility_warnings=()`, `selection_warnings=()`).
3. **Namespace:** `app.main` (module-global, i.e. the alias created at
   `app/main.py:30`).
4. **Patch installation:** inside two separate `with` blocks — first around
   `run_model`, second around `chat_model`. Each block creates a *fresh*
   `prepare` mock, so the second assertion is independent of the first.
5. **`run_model` execution:** inside the first `with` block, under
   `redirect_stdout`/`redirect_stderr`.
6. **`chat_model` execution:** inside the second `with` block, with explicit
   `out=StringIO()`, `err=StringIO()`, `input_fn=lambda: "/exit"`.
7. **Input conditions:** `model_id` non-empty (so the usage guard passes), no
   quantization/filename; `input_fn` returns `/exit` on the first iteration.
8. **Session state:** `session` is a `Mock` with
   `state = SimpleNamespace(value="closed")` and a canned `send` return value.
   The state value is irrelevant to whether `_prepare` runs — the session is
   created *after* `_prepare`.
9. **Assertions:** `self.assertTrue(prepare.called)` twice (line ~178 for
   run, line 196 for chat). No exit-code assertion, no output assertion.
10. **Mock state:** no `reset_mock()`, no `side_effect`, no `return_value` on
    the `_prepare` mock other than the shared `preparation` namespace. The
    `prepare` mock is a *new* object in the second `with` block.

**Meaning of `prepare.called == False`:** the patched `app.main._prepare` was
never entered. This does **not** by itself prove the `_prepare` body was never
reached via another reference, nor that the caller did not exit before the call
site. Both were checked below.

## 4. Production Control Flow

OBSERVED in `app/main.py`:

```
run_model(model_id, prompt, ...)                       # line 868
  |- usage guard (model_id / prompt)                   -> return 2
  |- ModelStore(); ModelArtifactResolver(...).resolve()
  |- capability = detect_llama_capability()            # line 890  (NO invocable guard)
  |- preparation = _prepare(resolved.model, resolved.artifact,
  |                        capability, model_store)    # line 892
  |- ExecutionRequest(...); LlamaCppRunner(capability).run(...)
  |- return 0 / 1

chat_model(model_id, ..., input_fn, out, err)          # line 933
  |- usage guard (model_id)                            -> return 2
  |- ModelStore(); ModelArtifactResolver(...).resolve()
  |- capability = detect_llama_capability()            # line 964
  |- if not capability.invocable:                      # line 965  <<< EARLY RETURN
  |      print("Chat error: no invocable runtime is available", file=err)
  |      return 1                                       # line 970
  |- preparation = _prepare(resolved.model, resolved.artifact,
  |                        capability, model_store)    # line 973
  |- session = start_chat_session(capability, preparation.executable_artifact,
  |                               preparation.target, chunk_callback=stream)
  |- REPL loop (prompt.strip() == "/exit" -> break; EOF/KeyboardInterrupt -> break)
  |- finally: session.close()
  |- return 0
```

The asymmetry is explicit and intentional in production: `chat_model` requires
an *invocable* one-shot runtime because it drives a persistent multi-turn
process; `run_model` does not.

## 10. Hypothesis Analysis

- **H1 — `chat_model` does not call `_prepare`:** REFUTED. OBSERVED at
  `app/main.py:973`; the call is present and the patch target is identical
  (`app.main._prepare`).
- **H2 — different reference:** REFUTED. Section 5 — one symbol, one namespace,
  direct module-global lookup, no aliasing or wrapper.
- **H3 — early exit:** **CONFIRMED.** `app/main.py:965-970`,
  `if not capability.invocable: return 1`, executed before line 973. The
  condition is the value of the un-patched real `detect_llama_capability()`
  result.
- **H4 — mock/test defect (patch mechanism does not intercept):** **CONFIRMED
  in a different sense.** The patch mechanism works correctly; the *defect is in
  the test's mock setup*: the chat half omits
  `patch("app.main.detect_llama_capability")`, letting a real host probe run.
  So the mock is misconfigured, not mis-intercepting.
- **H5 — environmental condition:** **CONFIRMED and narrowed to one concrete
  variable:** host `PATH` contents (`llama` present/absent). No other
  environmental factor is supported by evidence. This is not "CI differs, so
  environment" hand-waving: the specific variable is identified and the failure
  flips with it in both directions.
- **H6 — other cause:** none. The five other tests in the file pass in both
  environments, isolating the defect to this one test's chat half.

Interaction note: H3 is the mechanism, H4 the authoring defect, H5 the trigger
condition. All three are consistent and jointly sufficient.

## 11. Root Cause Classification

**TEST DEFECT** (primary), with a **PATCH/INTERCEPTION DEFECT** character in the
mock setup.

Not a PRODUCTION BEHAVIOR DEFECT: `run_model` and `chat_model` share the same
`_prepare` as the test intends to prove; the test's assertion about sharing is
correct. The `invocable` guard in `chat_model` is deliberate, documented
production behaviour, not a regression.

Not ENVIRONMENT-DEPENDENT BEHAVIOUR of the *product*: the product's behaviour
here is deterministic. The test is environment-dependent because it leaks a
host probe into a hermetic suite.

Not TIMING-SENSITIVE and not UNKNOWN: the failure was reproduced and reversed
in both directions on a single host in under a second.

## 14. Required Remediation

Not implemented here, by block rules. For the record, the remediation surface is
**the test only**:

- make the `chat_model` half hermetic by patching
  `app.main.detect_llama_capability` (and, for symmetry, the same collaborators
  the `run_model` half patches), so no host probe influences the result; or
- enforce the `PATH`/runtime boundary suite-wide (e.g. test-level isolation of
  `shutil.which`) if the project's hermeticity contract is to be systemic.

Explicitly NOT required and NOT recommended: any change to `app/main.py`, to the
`invocable` guard, to `pyproject.toml`, to `requirements.txt`, to the workflows,
to the Python support contract, or any skip/xfail/retry/timeout change.

Final answer to the block's closing question: `run_model` records
`prepare.called == True` because its half of the test patches
`app.main.detect_llama_capability`, so `capability` is a `Mock` and control
reaches `_prepare` at line 892 unconditionally. `chat_model` leaves
`prepare.called == False` because its half does not patch that symbol, so the
real `detect_llama_capability()` probes `PATH` for a `llama` binary; in the
failing environment none exists, `capability.invocable` is false, and
`chat_model` returns 1 at `app/main.py:965-970` before ever reaching `_prepare`
at line 973. The shared-preparation contract asserted by the test is actually
held by production code.
