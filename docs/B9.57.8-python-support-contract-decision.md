## 1. Executive Summary

**Selected option: B — raise the Python minimum to `>=3.11`.**

The decision rests on three observed facts and no preference:

1. The declared range `>=3.10` has **never** been satisfiable. `app/version.py`
   imports `tomllib` unconditionally, and `39f5f66` (the commit that introduced
   it) is an ancestor of `v0.1.0`. No successful execution on Python 3.10 has
   ever existed in this repository's history.
2. The only declared versions with green evidence are 3.11, 3.12 and 3.13
   (CI run `36212861723`, plus the local reproductions of B9.57.3).
3. CastleArq's runtime is a **documented standard-library-only** property
   (`requirements.txt`, and the `pyproject.toml` comment "CastleArq's runtime
   remains standard library only"). Option B is the only option that leaves
   that property intact.

Option B makes the declaration match reality. Option A would make reality match
a declaration that has been false since publication, at the cost of overturning
a documented dependency property and adding a runtime dependency to a package
whose premise is evidence-based refusal.

## 7. tomllib Usage Analysis

OBSERVED (`grep -R "tomllib" -n app tests`): **4 import sites, 5 call sites.**

| File | Line | Role |
| --- | --- | --- |
| `app/version.py` | 6 (import), 17 (`tomllib.loads`) | **production** |
| `tests/test_public_surface.py` | 16 (import), 235 (`tomllib.loads`) | test |
| `tests/test_api.py` | 36 (import), 156 (`tomllib.loads`) | test |
| `tests/test_b930_packaging.py` | 9 (import), 23 and 79 (`tomllib.loads`) | test |

Facts:

- The **only** API used anywhere is `tomllib.loads`. No `tomllib.load`,
  no `TOMLDecodeError`, no writer.
- There is exactly **one** production call site: `app/version.py:17`.
- All four call sites read the *same file*: CastleArq's own `pyproject.toml`.
  No user TOML, no configuration file, no third-party data format is parsed.
- The production call is a **fallback only**:

  ```python
  try:
      return importlib.metadata.version("castlearq")
  except importlib.metadata.PackageNotFoundError:
      ... tomllib.loads(pyproject.toml) ...
  ```

  On an installed distribution — the documented usage — `tomllib` is never
  reached; `importlib.metadata` answers first.
- An alternative is **already used by the project** for the same purpose:
  `importlib.metadata`, on the first branch of the same function. The project
  needs a *version string*, not a TOML parser.
- The import is module-level and unconditional, which is why it is a hard
  blocker on 3.10 even though the code path is a fallback.

This narrows the problem precisely: the 3.10 incompatibility is one
module-level import in one file, whose only runtime purpose is to read this
project's own version out of its own `pyproject.toml` when the distribution
metadata is absent.

## 8. Option A — Python >=3.10 + tomli

Keep `requires-python = ">=3.10"` and make the import work on 3.10.

Consequences:

- `app/version.py` needs a guarded import (`try: import tomllib / except
  ImportError: import tomli as tomllib`) or a vendored equivalent.
- A **runtime** dependency is added: `dependencies = ["tomli; python_version < '3.11'"]`
  (or unconditional `tomli`). `requirements.txt` — currently a single comment
  asserting standard-library-only — would have to change, and the `pyproject.toml`
  comment "CastleArq's runtime remains standard library only (see
  requirements.txt)" would become false.
- The four test call sites would need the same guard, or the tests would keep
  importing `tomllib` unguarded.
- **Feasibility is already measured, not assumed**: B9.57.2 shimmed `tomllib`
  to `tomli` on real CPython 3.10.21 and got `1468 passed, 2624 subtests`.
  Option A is known to work.
- CI keeps four matrix entries; the 3.10 job would be expected to go green
  after the change, but that is a prediction, not observed.
- `v0.1.0` metadata is unchanged and remains historically wrong on 3.10 until a
  new release ships the fix.
- Ongoing cost: a third-party package in the runtime closure of a project whose
  identity is "no dependencies", plus a conditional import to maintain.

## 9. Option B — Python >=3.11

Raise the floor so the declaration matches observed, validated reality.

Consequences:

- `requires-python = ">=3.11"`.
- Remove the `Programming Language :: Python :: 3.10` classifier; keep 3.11,
  3.12, 3.13.
- CI matrix becomes `['3.11', '3.12', '3.13']`.
- `README.md:96` ("Python 3.10 or newer") and `README.md:684` ("across Python
  3.10, 3.11, 3.12 and 3.13") become inaccurate and must change.
- `app/version.py` needs **no change**: `tomllib` is standard library on every
  supported version, and the import is already correct.
- `requirements.txt` needs **no change**: the standard-library-only property
  survives intact.
- No new dependency. No conditional import. No runtime behaviour change.
- CI cost: one fewer matrix entry — strictly less, not more.
- `v0.1.0` on PyPI keeps its `>=3.10` metadata as an immutable historical
  record; the new floor applies to the next release. The discrepancy is
  documented rather than silently rewritten (see §13).
- Every version left in the declared range has green CI evidence at the
  current commit.

## 10. Option C — Python >=3.10 Without Runtime Dependency

Keep 3.10 and remove the `tomllib` need entirely.

Two shapes, both evaluated:

- **C1 — read the version without a TOML parser.** The single production need
  is `project.version` from this repository's own `pyproject.toml`, used only
  when `importlib.metadata` fails. A narrow line scan could serve it. RISK: it
  is a bespoke parser; a wrong answer is a wrong version string reported to
  users, and it is untested against the TOML grammar.
- **C2 — write a general TOML parser.** DISPROPORTIONATE: a correct TOML
  implementation is a large surface, and the project would own a parser whose
  only inputs are its own `pyproject.toml` and three test files.

Consequences:

- Removes the 3.10 blocker without a dependency, preserving
  standard-library-only.
- But it trades one measured, already-reproduced failure for **new, unmeasured
  code** whose correctness would itself need evidence.
- The four test call sites read `pyproject.toml` for contract assertions
  (`test_public_surface`, `test_b930_packaging`, `test_api`); C1 does not
  remove those, so tests would still need `tomllib` on 3.10 — meaning C1
  alone does not make the *suite* run on 3.10 unless the tests are also
  changed. That expands the change surface beyond the one production line.
- No CI evidence exists for C in any form.

## 11. Option D — Defer

Is there an objective reason not to decide now? Evaluated honestly: **no.**

- Missing information: the exact 3.10 traceback of run `36212861723`. But that
  is **not** needed — B9.57.2 already reproduced the 3.10 failure on a real
  CPython 3.10.21 interpreter and located the cause in source
  (`app/version.py:6`). The missing traceback would restate a known cause.
- Missing experiment: whether `tomli` fixes 3.10. Already performed
  (B9.57.2 shim → `1468 passed`).
- Blocked decision: none. Every input needed to choose is in hand.
- Cost of maintaining the current state: the repository continues to publish a
  metadata claim (`>=3.10`) that is false, keeps a permanently red CI entry,
  and keeps a known-broken declared version in its own support contract. That
  cost is paid on every future run and every future release.

Deferral would therefore be a preference, not an evidence-driven position.

## 15. Decision

```
Selected option: B
```

**CastleArq's Python support contract becomes `>=3.11`.**

One decision, not a combination. The justification is drawn only from evidence
recorded in this repository:

1. **The declared floor has never been real.** `39f5f66` introduced
   `import tomllib` into `app/version.py`, and that commit is an ancestor of
   the `v0.1.0` tag whose `pyproject.toml` declares `>=3.10`. Reproduced on real
   CPython 3.10.21: the suite aborts at collection with zero tests run. There
   is no working 3.10 configuration to preserve, so Option B removes a claim
   rather than a capability.

2. **Every version Option B keeps has green CI evidence.** Run `36212861723`
   at SHA `6429ec9`: 3.11, 3.12 and 3.13 all pass the full suite. Option B
   leaves a contract in which each declared version is validated. Option A
   would keep a version whose CI outcome is a *prediction*; Option C has no
   evidence in any form; Option D keeps a version known to be broken.

3. **Option B requires no change to runtime code and no dependency.** The
   `tomllib` usage is one module-level import whose only runtime role is a
   fallback that reads this project's own `pyproject.toml`; `tomllib` is
   standard library on 3.11+. `requirements.txt` states CastleArq "currently
   uses only the Python standard library", and the `pyproject.toml` comment
   repeats it. Option B is the only option that leaves that documented property
   true without qualification. Option A would overturn it; Option C would
   preserve it only by adding code whose correctness is unevidenced.

Arguments explicitly **not** used, per the block's rules: that 3.10 is old,
that most users are on 3.11, that `tomli` is small, that 3.11 is more modern,
or any appeal to popularity or convenience. None of those appear above, and
none would have been admissible.

The trade-off accepted knowingly: a user on Python 3.10 who installs CastleArq
will be refused by `requires-python` at install time instead of failing later
with an obscure `ModuleNotFoundError`. That is a clearer failure, and it is the
correct behaviour for a package that refuses what it cannot justify.

Note on what this decision does **not** rest on: the missing 3.10 traceback
from run `36212861723` is immaterial. The 3.10 failure was already reproduced
on a real interpreter and localized to source in B9.57.2, so the traceback
would restate a known cause rather than inform the choice.
