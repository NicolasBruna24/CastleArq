# B9.29 — Linux Install Contract and Packaging Readiness Specification

> Audit basis: commit `f5b06ed` (`feat: consolidate CastleArq execution and evaluation architecture`). This document is normative for the CastleArq 0.1 Linux installation boundary and records implementation work; it does not implement that work.

## 1. Executive Summary

CastleArq at `f5b06ed` is **developer-valid and packaging-partially ready**. The repository already declares a setuptools Python distribution, discovers `app*`, and exposes `castlearq = app.main:main`; all imports in `app/` resolve to the Python standard library. User configuration and model-store roots already honor XDG variables and the checkout is no longer required for their default resolution. A `python3 -m app.main` interface and a llama.cpp execution path also exist.

The repository is not yet declared externally distributable. An ignored local wheel and sdist exist in this working directory, but B9.29 did not create, rebuild, install, or validate them and they are not part of commit `f5b06ed`. There has been no clean-machine installation test. Runtime candidate handling is inconsistent, no complete configuration-precedence layer exists, no `evaluate` command exists, and uninstall/publishing behavior has not been validated as a complete user journey.

The resolved 0.1 contract is:

```text
Python >=3.10
  -> install the CastleArq Python package (`pip install .` in a venv/user environment)
  -> official command `castlearq`
  -> optional compatibility/development command `python3 -m app.main`
  -> XDG user config and data
  -> externally supplied llama.cpp CLI
  -> explicitly acquired model artifact
  -> evaluate and execute
```

No model or llama.cpp binary is bundled. CastleArq does not require root and does not install system software or drivers.

## 2. Current Installation Reality

### 2.1 Verified repository baseline

- `git status --short` was empty before the audit.
- `git log -1 --oneline` reported `f5b06ed (HEAD -> main) feat: consolidate CastleArq execution and evaluation architecture`.
- `pyproject.toml` declares package `castlearq` 0.1.0, Apache-2.0, `requires-python = ">=3.10"`, `setuptools>=61`, and `setuptools.build_meta`.
- `[project.scripts]` contains `castlearq = "app.main:main"`.
- setuptools discovery includes `app*` and excludes `config*`; `app`, `app.downloads`, and `app.sources` have `__init__.py` files.
- `requirements.txt` says the project uses only the standard library. Static AST inspection found no non-standard-library import in `app/`.
- `python3 -m app.main --help` and `--version` are implemented through the module guard in `app/main.py`.
- version resolution prefers `importlib.metadata.version("castlearq")`, with a source checkout fallback.
- ignored generated `dist/castlearq-0.1.0-py3-none-any.whl` and `dist/castlearq-0.1.0.tar.gz` are present locally. Their presence is not evidence of this audit or of a clean installation.

### 2.2 Runtime command reality

The same `app.main:main` function is exposed by both the metadata console script and `python3 -m app.main`. Therefore the internally implemented commands and the installed console-script surface are structurally the same for a correctly installed wheel:

`detect`, `diagnose`, `verify`, `models`, `list`, `source`, `plan`, `download`, `run`, `execute`, `chat`, and `serve`.

There is **no** `evaluate` command. Compatibility evaluation exists internally, including `evaluate_model_compatibility`, and `execute` performs an internal evaluation-admission step, but those facts must not be represented as a `castlearq evaluate` command. There is also no separate `runtime`/`runtime-discovery` command; discovery is exposed through existing diagnostic/detection surfaces.

### 2.3 Configuration and data reality

- `app.compatibility.default_config_path()` resolves `$XDG_CONFIG_HOME/castlearq/config.toml`, falling back to `~/.config/castlearq/config.toml`; it does not create the path.
- missing configuration returns built-in `CompatibilityConfig` defaults.
### 2.4 Runtime reality

Runtime behavior is split across modules:

- `app.runtimes.detect_runtimes()` marks llama.cpp installed if **any** of `llama`, `llama-cli`, `llama-server`, or `llama.app` is found, but does not establish a validated executable capability.
- `app.runtimes.detect_llama_capability()`, used to create the execution `RuntimeCapability`, searches **only** `llama` in `PATH` and requires successful `llama cli --version` and `llama cli --help`, including `--model` and `--prompt`.
- `app.observation_probe` searches, in order, `llama-cli`, `llama`, and `llama.app` (not `llama-server`) and probes generic `--version`/`--help` syntax.
- `app.gpu_setup` uses a candidate tuple for device probing, while the principal runner still ultimately depends on the validated `llama` path/capability.

Thus presence of only `llama-cli`, `llama-server`, or `llama.app` can make detection report an installation while execution remains unavailable. For 0.1 the normative runtime interface is a `llama` executable in `PATH` exposing the validated llama.cpp unified CLI subcommands and options. The other names are compatibility/diagnostic candidates only, not four interchangeable guaranteed launchers.

## 3. Linux Install Contract

CastleArq 0.1 shall be distributed as a standard Python source/wheel package using the existing `pyproject.toml` setuptools backend. The first reproducible installation mechanism is:

```bash
python3 -m venv <venv>
. <venv>/bin/activate
pip install .
castlearq --version
```

A user-level or venv installation is normative because it is sufficient, normal, and avoids conflating packaging ownership with operating-system ownership. `pip install .` is a packaging mechanism, not a privileged application action. Publication to PyPI, an internal index, or native repositories is not decided by this contract.

A valid installation must:

1. include the top-level `app` package and its `downloads` and `sources` subpackages;
2. import without source checkout, `PYTHONPATH`, or cwd-dependent files;
3. create the `castlearq` console script;
4. work as a normal user;
5. keep configuration and model data outside the installation prefix;
6. discover but not install llama.cpp;
7. contain no model artifacts;
8. fail cleanly when runtime or model is absent;
9. report its installed distribution version.

`python3 -m app.main` remains supported as a development and internal compatibility surface when the installed Python environment exposes the `app` module. It is not the official installed command.

## 4. Python Contract

- Minimum Python remains `>=3.10`; B9.29 does not change it.
- Packaging build dependency: `setuptools>=61` in the isolated build environment.
- Runtime Python dependencies: none beyond the standard library. The empty `[project].dependencies` state is consistent with the import audit.
- Development/test dependencies: no explicit optional or development dependency group is declared. Tests use the standard library `unittest`; pytest configuration is present, and local cache artifacts show pytest was used, but pytest is not declared as a project dependency. That is tooling debt, not a missing runtime dependency.
- Optional Python dependencies: none declared.
- External executable required for execution: a compatible llama.cpp CLI.
- Optional diagnostic executables: `vulkaninfo`, `clinfo`, `sycl-ls`, `nvidia-smi`, and `rocminfo`; absence means less evidence, not installation failure.

No undeclared non-standard-library runtime dependency was found. The reproducibility gap concerns the external runtime/model/tooling chain, not hidden Python libraries.

## 6. Configuration Contract

The normative precedence is:

```text
explicit CLI arguments
  > supported environment variables
  > user configuration
  > built-in defaults
```

The normative user file is:

```text
$XDG_CONFIG_HOME/castlearq/config.toml
```

or, when `XDG_CONFIG_HOME` is unset:

```text
~/.config/castlearq/config.toml
```

This precedence is compatible with the current direction but not fully implemented. Today XDG selects a root, TOML values override built-in compatibility defaults, and command-specific CLI values such as artifact selection override execution inputs. There is no general environment-value merge and not every internal path loads the user file. The next implementation must centralize effective configuration so every relevant command observes the same precedence, while treating XDG variables as path selectors rather than general setting overrides.

Resolution and read-only commands must not create config directories. Invalid user values must produce a clear user-facing configuration error rather than traceback or silent fallback. A future explicit CastleArq environment override must be named and tested; B9.29 does not invent one beyond the already used XDG variables.

## 7. Model Store Contract

The normative model store is:

```text
$XDG_DATA_HOME/castlearq/models
```

or, when `XDG_DATA_HOME` is unset:

```text
~/.local/share/castlearq/models
```

The existing `~/.local/share/localai-hub/models` path is retained only as a read-compatible legacy fallback, never as the normative path for new installations. Current behavior is appropriate for non-breaking compatibility: select the normative default when it exists; otherwise select an existing legacy store. It does not merge stores and it does not migrate or copy artifacts. New writes should continue to the normative store; the fallback lets existing installations keep seeing existing artifacts.

An explicit configured `[models].directory` has higher authority than the legacy fallback. The source `config/config.toml` is a repository default/template, not a writable package-owned user configuration. The implementation must verify that this distinction and the chosen override variable/schema are consistently propagated to all ModelStore consumers before release.

## 8. External Runtime Contract

CastleArq 0.1 assumes llama.cpp is an external dependency. It searches the user's inherited `PATH` without a CastleArq-specific executable override in the current code. For execution, the normative candidate is:

```text
llama
```

CastleArq validates the resolved executable and its `cli --version`/`cli --help` capabilities before considering it invocable. `llama-cli`, `llama.app`, and `llama-server` may be observed as compatibility candidates, but current execution is not guaranteed from those names alone. This is a concrete implementation constraint, not a claim that all names are supported launchers.

A missing/incompatible runtime must fail cleanly and diagnostically; CastleArq must not download, build, or install it. The future implementation should unify discovery and capability semantics so `detect` and execute cannot contradict each other, while preserving the actual `llama` unified-CLI requirement unless adapters for other executable forms are explicitly implemented and tested.

## 9. GPU and Driver Boundary

CastleArq may inspect hardware, report detected software, probe available backend evidence, and provide declarative remediation guidance. Current GPU probes are read-only and recipes do not execute install commands. The codebase contains no `sudo`, package-manager execution, `os.system`, `shell=True`, driver installation, or system configuration mutation in `app/`.

CastleArq must not install GPU/kernel drivers, CUDA, ROCm, Vulkan, OpenCL, runtime libraries, or devices; must not use root; and must not alter global configuration. GPU availability is evidence, not a guarantee. The 0.1 baseline is CPU-capable llama.cpp; accelerated backends are reported only when externally available and supported by the selected runtime.

## 10. Model Acquisition Contract

The Python package includes no model. Models are large, separately licensed/downloaded artifacts and are acquired explicitly through the existing flow:

```text
install CastleArq
  -> install/provide compatible llama.cpp externally
  -> `castlearq models` (discover model IDs)
  -> `castlearq download MODEL_ID`
  -> artifact and manifest stored in ModelStore
  -> `castlearq list`
  -> internal compatibility evaluation / `castlearq execute`
  -> real output
```

`castlearq evaluate` is not part of 0.1 because it does not exist. `execute` performs evaluation admission internally. Model download may require network and source availability; installation alone must not imply network access. Acquisition records source, repository, filename, expected size, and checksum where available, and publication is tied to the selected artifact rather than a bundled asset.

## 12. Privilege Contract

Normal installation and application runtime require no root, `sudo`, system-wide configuration, or writes outside the user's venv/user data locations. A venv is recommended for predictable packaging; a user-level install is acceptable when the user's Python/pip environment permits it. Whether pip may use its own implementation detail is independent of whether CastleArq itself requires privilege: CastleArq never escalates privileges.

Network access, writable XDG data roots, and an executable in `PATH` are normal runtime preconditions for acquisition/execution. They are not privileges.

## 13. Reproducibility Contract

A reproducible CastleArq 0.1 installation means an external Linux user can, from declared inputs:

1. use Linux with Python 3.10 or later;
2. install the Python distribution into an isolated/user environment;
3. invoke `castlearq` without checkout knowledge, `PYTHONPATH`, or cwd assumptions;
4. obtain a compatible external llama.cpp runtime;
5. acquire an explicit model artifact;
6. observe model state, runtime state, evaluation admission, and real execution output;
7. keep configuration/models across package update and uninstall;
8. do all application work as a normal user.

Reproducibility does not mean CastleArq pins or vendors the llama.cpp build, GPU stack, model source, or model checksum policy. Reproducibility requires these external inputs to be identified and their versions/URLs/checksums recorded by the user or acquisition flow. The missing evidence is a reproducible clean-room artifact/install test and a unified external-runtime discovery contract, not a missing Python dependency declaration.

## 14. Clean-Machine Validation Contract

B9.29 does not perform a clean-machine installation. A later block may execute this scenario only after packaging behavior is implemented and frozen for the test:

```text
clean Linux user environment
  -> install Python >=3.10
  -> install CastleArq package
  -> run `castlearq --help` and `--version` outside checkout
  -> run discovery/detect without llama.cpp
  -> provide external llama.cpp and verify discovery
  -> acquire a permitted model
  -> list artifact
  -> evaluate through the existing internal admission flow
  -> execute and capture real output
  -> inspect exit codes and error output
  -> update package and verify user data persists
  -> uninstall package and verify user data persists
```

Preconditions include: a defined artifact/checksum, supported Python, a documented compatible llama.cpp build/interface, a small permitted test model, an isolated HOME/XDG environment, no inherited `PYTHONPATH`, no project cwd during installed invocation, and a normal user account. The test must separately record missing-runtime and missing-model behavior. GPU success is not a release gate for the CPU-first milestone; GPU claims require separate evidence.

## 16. Decisions Resolved

1. **Install method:** standard Python package; `pip install .` in a venv or permitted user environment is the first milestone method. Publication channel is open.
2. **Python minimum:** `>=3.10`, unchanged.
3. **Official CLI:** `castlearq <command> [arguments]`, installed through `app.main:main`.
4. **Module command:** retain `python3 -m app.main <command> [arguments]` for development/internal compatibility.
5. **Configuration precedence:** CLI > supported environment > user config > defaults.
6. **Config path:** `$XDG_CONFIG_HOME/castlearq/config.toml`, else `~/.config/castlearq/config.toml`.
7. **Data/model path:** `$XDG_DATA_HOME/castlearq/models`, else `~/.local/share/castlearq/models`.
8. **Legacy path:** retain `~/.local/share/localai-hub/models` only as a read-compatible fallback; no new normative writes or automatic migration.
9. **llama.cpp discovery:** resolve through inherited `PATH`; execution requires a validated `llama` unified CLI in current code. Other names remain diagnostic/compatibility candidates until executable adapters exist.
10. **Installer responsibilities:** install Python package metadata/code/launcher only; do not install llama.cpp, models, drivers, GPU stacks, or system configuration.
11. **Bundled models:** no.
12. **Models at uninstall:** preserved; deletion requires a future explicit user action.
13. **Privileges:** none for application operation; normal user only.
14. **Distribution blockers:** clean artifact build/install, coherent runtime discovery, unified effective configuration, clean-machine model/runtime execution, and uninstall persistence validation.
15. **Next implementation block:** a focused Linux user-level packaging/readiness implementation and clean-room smoke validation block, starting from the current metadata rather than redesigning Domain/Application. It should not expand into GUI, native packages, or new runtimes.

## 18. Non-Goals

- modify packaging metadata, code, tests, runtime, CLI, ModelStore, or configuration;
- create/install/validate a new wheel or sdist;
- choose PyPI publication, signing, release channels, or native `.deb`/RPM packages;
- add Docker, AppImage, Flatpak, or Snap;
- bundle or install llama.cpp, drivers, CUDA, ROCm, Vulkan, or GPU libraries;

- add `castlearq evaluate` or invent commands;

- delete or migrate user data;
