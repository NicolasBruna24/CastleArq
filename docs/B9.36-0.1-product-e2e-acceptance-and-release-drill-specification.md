## 3. The single acceptance question

> Can a technical user install the CastleArq 0.1 release candidate **outside
> the checkout**, use a compatible external `llama`, start from an **empty
> ModelStore**, explicitly acquire a model, verify it, and execute the model
> **twice**, demonstrating that the second execution reuses the existing
> artifact without downloading it again?

The answer must rest on **observable evidence** (command output, exit codes,
filesystem state, artifact identity, timestamps), never on the test suite.

## 4. Official drill flow

```text
Release candidate commit
    ↓
Build wheel + sdist
    ↓
Inspect package contents
    ↓
Verify LICENSE inclusion
    ↓
Compute SHA-256
    ↓
Create fresh venv outside checkout
    ↓
Install candidate artifact
    ↓
Verify PYTHONPATH empty/unset
    ↓
Verify castlearq --version
    ↓
Verify external llama runtime
    ↓
Prepare empty official ModelStore
    ↓
catalog / models
    ↓
Explicit network download
    ↓
list / local verification
    ↓
execute #1
    ↓
execute #2
    ↓
Verify artifact reuse
    ↓
Preserve transcript + exit codes + artifact identity
```

The procedure keeps five concerns strictly separated:

1. **Distribution artifact construction** (§5) — builds the candidate.
2. **Product installation** (§6) — installs the candidate, outside the checkout.
3. **External llama.cpp provisioning** (§7) — *pre-existing*, never installed by CastleArq.
4. **Model acquisition** (§9) — explicit download only.
5. **Product execution** (§10, §11) — `execute` twice.

CastleArq never installs, updates, vendors or modifies llama.cpp. The drill
must not `sudo`, must not install drivers, and must not modify global system
configuration.

## 5. Packaging acceptance

### 5.1 Wheel

Build a **new** wheel from the release-candidate commit and validate:

* filename encodes the expected distribution name and version (`0.1.0`);
* `app` and its subpackages are present (package discovery `app*`, `config*` excluded);
* the console script entry point is declared;
* the files required for execution are present;
* `LICENSE` is included;
* no test-only or development-only material is shipped unnecessarily.

### 5.2 Source distribution

Build a **new** sdist and validate:

* filename encodes the expected distribution name and version;
* the full source tree required to rebuild is present;
* `LICENSE` is included;
* no packaging regression relative to the previously demonstrated state.

### 5.3 Checksums

```text
sha256(dist/*.whl)
sha256(dist/*.tar.gz)
```

The hashes are **evidence of the exact candidate that was drilled** and must be
recorded. Artifacts must not be modified after hashing; if they are, the
hashes must be recomputed and the rebuild re-drilled.

## 6. Installation acceptance

The install must happen:

* in a **new** virtualenv;
* **outside** the checkout directory;
* with **`PYTHONPATH` empty/unset**;
* using **only** the freshly built artifact;
* without importing `app` from the repository.

Mandatory recorded evidence:

```bash
echo "${PYTHONPATH:-}"
which castlearq
castlearq --version
python -c "import app, sys; print(app.__file__)"
```

The `app.__file__` probe (or equivalent) must resolve inside the venv's
`site-packages`, **not** to the repository checkout — that is the proof that
Python is importing CastleArq from the installed distribution.

If both wheel and sdist are exercised, results are recorded **separately**;
a failure in one does not silently pass because the other succeeded.

## 7. External llama.cpp acceptance

The drill uses the pre-existing external runtime:

```text
PATH
  → shutil.which("llama")
  → validation
  → version
  → help
  → list-devices
  → RuntimeCapability
```

Record:

* executable path;
* version;
* build identifier;
* availability state;
* observed capabilities (formats, backends, one-shot support);
* the backend/target actually used during the drill.

`castlearq runtime` output is part of the recorded evidence.

The runtime is a **precondition** of the drill, never an output of it. If no
compatible `llama` is available, the drill is `BLOCKED` on the environment and
must be reported as such — CastleArq must not be modified or taught to install
one.

## 8. Empty ModelStore acceptance

Before acquisition, an **empty** official ModelStore must exist for the drill
environment, and the drill must prove the model was not already present.

Record:

* resolved ModelStore location;
* initial state (directory contents / absence of the artifact);
* absence of the artifact before download;
* state after download.

The store path is resolved by the existing contract:
`$XDG_DATA_HOME/castlearq/models`, else `~/.local/share/castlearq/models`,
with `~/.local/share/localai-hub/models` as legacy-only fallback.

**Reusing a pre-existing artifact silently is a drill failure.** If the drill
isolates the store via a temporary `XDG_DATA_HOME`, that isolation must be
documented explicitly — what was set, for which steps, and why it still honors

## 9. Model acquisition acceptance

Acquisition is explicit:

```text
catalog (castlearq models)
    ↓
castlearq download MODEL_ID
```

No implicit download may occur during `list`, `execute #1` or `execute #2`.

Record:

* `MODEL_ID`;
* artifact identity;
* format;
* size;
* available checksum / identity;
* verification state;
* final path;
* acquisition command and its exit code.

The evidence must let the drill show that the artifact used by `execute` is the
**same** artifact acquired during the drill.

## 10. First execution acceptance

```bash
castlearq execute MODEL_ID "<short deterministic prompt>"
```

Record: command, exit code, stdout, stderr, success, artifact used, runtime
used, selected backend/target, and evidence of real execution.

`execute` is the product acceptance path. The legacy `run` flow must **not** be
used as a substitute.

## 11. Repeat execution and artifact reuse

Run the same `execute` command again. The second run must use the already
acquired artifact:

```text
download explícito
        ↓
artifact persistido
        ↓
execute #1
        ↓
artifact reutilizado
        ↓
execute #2
```

The drill must distinguish **download** / **local reuse** / **execution** with
sufficient evidence. The **absence of a download message alone is not
sufficient proof**; the conclusion must rest on the transcript, ModelStore
state, timestamps, and artifact identity observed before and after.

## 12. Artifact identity

An unambiguous artifact identity is preserved, at minimum:

* `MODEL_ID`;
* `artifact_id`;
* format;
* size;
* final path;
* verification state;
* physical checksum when available.

Identity must remain **consistent** across:

```text
download → list → execute #1 → execute #2
```

## 13. Exit-code matrix

Every step's exit code is preserved:

| Step | Artifact/tool | Exit |
|---|---|---|
| build wheel | build backend | ☐ |
| build sdist | build backend | ☐ |
| install wheel | venv | ☐ |
| install sdist | venv | ☐ |
| `castlearq --version` | console script | ☐ |
| `castlearq runtime` | console script | ☐ |
| catalog / `castlearq models` | console script | ☐ |
| `castlearq download` | console script | ☐ |
| `castlearq list` | console script | ☐ |
| `execute` #1 | console script | ☐ |
| `execute` #2 | console script | ☐ |

Errors must never be converted into success, stderr must never be hidden, and
a run is not valid merely because the Python process terminated.

## 14. Transcript

The drill must preserve a transcript sufficient to reconstruct it, containing
at least:

* date/time;
* tested commit;
* version;
* Python system/platform;
* installed distribution identity;
* SHA-256 of each artifact;
* runtime (path, version, build, backend);
* artifact (identity, size, verification state);
* every command and its exit code;
* first and second execution results.

## 16. llama.cpp compatibility baseline

Record, as a factual statement about the tested environment:

* llama.cpp version;
* build identifier;
* launcher used;
* backend used;
* platform;
* any other observable relevant requirement.

This is **not** a commitment to support all llama.cpp versions. The baseline
means only: *the external llama.cpp version with which the CastleArq 0.1 path
was validated.*

the official resolution contract. Any configuration or environment manipulation
is a property of the *drill environment*, not a product change.

## 17. Acceptance criteria

B9.36 is `PASS` only if **all** of the following hold:

1. wheel built from the candidate;
2. sdist built from the candidate;
3. contents inspected;
4. `LICENSE` present in both;
5. SHA-256 recorded;
6. installed outside the checkout;
7. `PYTHONPATH` empty/unused;
8. `castlearq` console script operational;
9. external `llama` discovered and usable;
10. ModelStore initially empty;
11. catalog accessible;
12. explicit download successful;
13. artifact verified;
14. `execute` #1 successful;
15. real execution demonstrated;
16. `execute` #2 successful;
17. artifact reuse demonstrated;
18. artifact identity consistent across all steps;
19. exit codes preserved;
20. complete transcript preserved;
21. tested commit identified;
22. llama.cpp baseline recorded;
23. no `sudo`, no driver installation, no system modification;
24. no architectural change made to make the drill pass.

Any failure ⇒ the drill is not `PASS`. If it exposes a real product defect,
**stop and report before changing code**.

## 18. Scope of the later execution block

Permitted there:

* generate `dist/`;
* create temporary virtualenvs;
* install wheel/sdist;
* run CastleArq;
* use the network to download the model;
* produce evidence and a B9.36 evidence document.

Not permitted there:

* change architecture;
* change admission;
* change runtime discovery;
* introduce new domain models;
* modify the ModelStore contract;
* install llama.cpp or drivers;
* create `v0.1.0`;
* publish a release;
* push.
