## 1. Decision

```text
B9.88 is allocated to route the existing CLI `chat` command through the
already-established application boundary `run_service.open_chat_session`,
replacing the CLI's duplicated resolver -> admission -> preparation ->
runtime-session pipeline with the shared application service.
```

**Decision status:** `HUMAN-RATIFIED`.

Ratified here means **decided and binding on future work**. It does not mean
implemented, verified, scheduled or released. Those are four different statuses
and this record keeps them apart.

```text
DECISION:                 HUMAN-RATIFIED
NUMBER:                   ALLOCATED — B9.88 (NAR: register section 29)
IMPLEMENTATION:           NOT STARTED
VERIFICATION:             NONE — NOT VERIFIED
CLOSURE:                  NONE — NOT CLOSED
```

The decision is specifically about **boundary ownership and caller
convergence**. It is not about creating new Chat functionality, and it is not a
feature launch.

## 3. Purpose

Make the CLI consume the application boundary that the HTTP API already
consumes, so that one Chat use case has one owner.

This is an **architectural boundary-consolidation** block. It creates no new
domain, no new provider, no new product area and no new user-facing surface.

## 4. Architectural evidence

### 4.1 The application boundary already exists

`castlearq/run_service.py:395` defines:

```text
open_chat_session(model_id, *, quantization=None, filename=None,
                  dependencies=None, admission=None) -> ChatSessionOpened
```

It is exported in `run_service.py:72` (`__all__`), accepts an already-minted
`EvaluationAdmission`, raises `ModelNotFoundError`, `RunPreparationFailedError`
and `ChatLaunchFailedError`, prints nothing and never touches the CLI.

### 4.2 It is already production-called by the API

`castlearq/api.py:151` imports it and `castlearq/api.py:1234` calls it inside
`POST /v1/chat/sessions`, forwarding the admission the handler already minted.

### 4.3 The CLI duplicates the same pipeline inline

`castlearq/main.py:1813` `chat_model` performs the equivalent sequence itself
and never calls the application boundary:

```text
main.py:1834  ModelStore()
main.py:1835  ModelArtifactResolver(model_store)
main.py:1836  resolver.resolve(...)
main.py:1845  detect_llama_capability()
main.py:1853  _admit_for_preparation(...)
main.py:1861  _prepare(...)
main.py:1883  start_chat_session(...)
```

Two surfaces therefore implement one use case, and only one of them goes
through the boundary.

### 4.4 The module states the intended separation

`run_service.py:26-30`:

> "Block 3.1 adds `open_chat_session`, the session-opening counterpart of
> `run_once`: same resolver -> `prepare` sequence, but the final step launches a
> persistent interactive session via `castlearq.chat` instead of a one-shot
> runner. The HTTP layer calls this service; it never touches the resolver,
> preflight, selector, argv or subprocess directly."

B9.88 makes the CLI obey that same statement.

### 4.5 Product Vision D7 names this seam

`docs/product-vision-adr.md` section 9 (D7):

> "When future Chat work is undertaken, conversation/session lifecycle should be
> moved toward an appropriate application-level boundary rather than permanently
> remaining as application lifecycle logic inside the HTTP transport layer."

## 5. Decision rationale

The decision is justified by the following, all verified in the repository:

```text
1. The application boundary already exists (run_service.py:395).
2. It is already production-called by the API (api.py:1234).
3. The CLI duplicates lifecycle logic instead of consuming that boundary
   (main.py:1833-1888).
4. The module documentation explicitly expresses the intended separation
   (run_service.py:26-30).
5. ADR D7 identifies the same architectural direction.
6. B9.88 introduces no new product surface: `castlearq chat` already exists.
7. The scope can be kept narrow: CLI chat caller only.
8. The `run` / `execute` policy question remains deliberately untouched.
```

It is not characterized as a feature launch. It is an architectural
boundary-consolidation block.

## 6. Product boundary

## 8. Admission rule

B9.88 MUST NOT cause `evaluation -> admission` to happen a second time merely
because the application boundary is being consumed.

The CLI already mints one admission via `_admit_for_preparation`
(`main.py:1853`). That admission is forwarded into
`run_service.open_chat_session(..., admission=admission)` using the existing
`admission` parameter that the service already exposes (`run_service.py:401`)
and that the API already uses (`api.py:1242`).

Exactly one evaluation and exactly one admission per CLI `chat` invocation
remain the invariant. Admission is neither redesigned nor duplicated, and no
second evaluation path is created.

## 9. Architectural invariants

B9.88 MUST preserve the boundary:

```text

  ↓

  ↓

```

The implementation MUST NOT introduce:

* a second admission;

B9.88 MUST preserve:

* existing admission semantics;
* existing runtime/session semantics;

* existing user-visible warnings;

## 10. `run` versus `execute` — explicitly not resolved

> **B9.88 does NOT resolve the separate `run` versus `execute`
> architectural/policy question. That question remains deferred.**

The CLI `run` command (`main.py:1750-1789`) also duplicates the resolver and
preparation sequence inline, exactly as `chat` does. B9.88 does **not**
authorize migrating it. That remains blocked on the owner ruling recorded in
`docs/B9.87-cli-catalog-query-caller-decision.md` section 5.2: whether `run`
must adopt the strict admission contract. Refactoring it would silently change
a live user-facing command's policy behaviour, which is a human architectural
decision, not an implementation detail.

It must not be inferred that because `chat` is routed through
`run_service.open_chat_session`, `run_model` must also be migrated. If a future
block addresses `run` / `execute`, it requires its own architectural decision
and its own record.

## 15. AMENDMENT A — human-approved implementation clarification

> **Status: HUMAN-RATIFIED CLARIFICATION.** This section was added after the B9.88
> implementation and its READ-ONLY compliance audit. It records a human decision
> and **narrows** nothing already approved; it authorizes one additive change.
> Sections 1-14 above are otherwise unchanged and are not rewritten.

### 15.1 What the audit found

The B9.88 implementation routed the CLI `chat` command through
`run_service.open_chat_session()` as allocated. A subsequent READ-ONLY compliance
audit identified one genuine behavioral regression:

```text
BEFORE B9.88 (main.py, pre-implementation):
    preparation = prepare(...)
    ...
    for warning in preparation.selection_warnings:
        print(f"Warning: {warning}", file=err)      # successful path, exit 0
    session = start_chat_session(...)

AFTER B9.88:
    opened = open_chat_session(...)
    session = opened.session
    # preparation.selection_warnings is computed INSIDE open_chat_session
    # and is not part of its return value -> the warning is not printed
```

`selection_warnings` is emitted by `RuntimeBackendSelector.select()` only when
the legacy compatibility verdict is `MARGINAL` (`selection.py:90-97`), a
reachable, non-blocking state (imported artifacts with unknown memory, per
`execute_model.py:155-165`). Before B9.88 that advisory line was user-visible on
stderr for a successful chat run.

This violated the already-ratified warning-preservation requirement in section
7.1 item 4 and in the section 9 invariants ("existing user-visible warnings"),
restated by the NAR at 29.5.

### 15.2 The human decision

The owner ruled:

> **B9.88 is authorized to add an additive, defaulted
> `warnings: tuple[str, ...] = ()` field to `ChatSessionOpened`, populated
> exclusively from the already-computed `preparation.selection_warnings`, so the
> CLI can preserve the pre-B9.88 successful-path warning behavior.**

### 15.3 The authorized change, precisely

```text
ChatSessionOpened
    session: Any
    model_id: str
    warnings: tuple[str, ...] = ()      # ADDED, defaulted, additive

open_chat_session(...) returns
    ChatSessionOpened(
        session=session,
        model_id=resolved.model.model_id,
        warnings=preparation.selection_warnings,
    )
```

The CLI then prints, before the successful chat banner and in the pre-B9.88
order and format:

```python
for warning in opened.warnings:
    print(f"Warning: {warning}", file=err)
```

### 15.4 What this amendment explicitly does NOT authorize

```text
- No other redesign of open_chat_session().
- No change to preparation, capability detection, admission validation, runtime
  startup or session creation.
- No new streaming contract. The chunk_callback continues to travel through the
  existing ChatDependencies.session_factory seam; chunk_callback is NOT added
  to open_chat_session().
- No second evaluation, no second admission and no second preparation. The CLI
  still calls evaluate_model_compatibility() once, to_admission() once, and the
  application boundary still prepares once.
- No recomputation of selection. The warnings come only from
  preparation.selection_warnings.
- No new warning source, no new warning class, no new abstraction.
- No change to the API contract or to api.py.
- No change to the B9.88 allocation number, scope or boundary otherwise.
```

### 15.5 Precedent for the shape of the change

This mirrors the sibling one-shot path, which already propagates exactly this
data across its boundary through `RunOutcome.warnings` (`run_service.py`) and
which `run_model` already prints on success. The chat path is brought into
consistency with it; no new concept is introduced.
