## 1. Executive Summary

The premise of this block was that 3.11, 3.12 and 3.13 fail for an unknown
reason. The investigation **falsified that premise in the version dimension**:

```text
CPython 3.11.16 -> 1468 passed, 0 failed
CPython 3.12.14 -> 1468 passed, 0 failed
CPython 3.13.15 -> 1468 passed, 0 failed
```

All on a clean clone of `83adc06`, pristine `HOME`, no undeclared plugins,
installed via `pip install ".[dev]"` — the same command CI runs. 3.11 was also
re-run with a real (non-`uv`) `pip`, matching CI's toolchain exactly, and passed.

Therefore:

* **The 3.11–3.13 CI failures are NOT caused by the Python version.** They are
  caused by something in the CI environment that is not reproduced by version
  selection.
* **The 3.10 failure IS version-caused**, and was independently re-confirmed in
  this block: 14 collection errors, `ModuleNotFoundError: tomllib` (§3).
* **The 3.11–3.13 root cause remains UNKNOWN.** GitHub returns HTTP 403 for job
  logs to non-admin tokens, and the check-run annotations contain no test output
  (§2). No traceback was obtainable, and none is fabricated here.

This is a **PARTIAL** diagnosis: the version hypothesis is eliminated with
evidence, but the actual cause is not yet identified. Eliminating a wrong
hypothesis is real progress, and it materially changes what the next step should
be.

| 3.14 | not in CI | `1468 passed` | 0 | baseline only, **not declared** |

**Differential result: 3.11/3.12/3.13 are behaviourally indistinguishable from
3.14 for this suite.** Identical counts, identical zero failures, no
version-specific failures. The smallest behavioural difference that explains
3.10 explains nothing about 3.11–3.13, because there is no such difference.

The identical CI failure across all four versions therefore points to a
**single shared cause**, not four independent version problems. If the cause
were version-specific, 3.11–3.13 would not fail identically — and more
tellingly, the suite passes on all three locally.

### 3.10 finding explicitly preserved (Phase 6)

## 8. Root Cause Classification

| Version | Classification | Confidence |
| --- | --- | --- |
| 3.10 | **IMPORT** — unconditional `tomllib` at `app/version.py:6` | CONFIRMED (reproduced) |
| 3.11 | **UNKNOWN** | Not reproduced locally in 6 controlled environments |
| 3.12 | **UNKNOWN** | Not reproduced locally |
| 3.13 | **UNKNOWN** | Not reproduced locally |

**Shared root cause across 3.11–3.13: UNKNOWN, but constrained.** It is *not*
IMPORT (all three import `app` successfully), *not* PACKAGING (install succeeds
in CI and locally), *not* DEPENDENCY (the resolved package set is identical to
the passing local runs), and *not* TYPE/ANNOTATION (no runtime annotation
problem is reachable on 3.11+, and PEP 604 was already shown to work on 3.10).

What remains genuinely open:

* **ENVIRONMENT** — a runner-image or toolchain difference not reproduced here.
* **TEST EXECUTION** — a test that passes here and fails on the runner, e.g. a
  timing-sensitive test under different I/O or CPU.
* **FILESYSTEM** — a path, permission or case-sensitivity difference.

## 9. Confirmed Facts vs Inference

### CONFIRMED (reproduced in this block)

1. CPython 3.11.16, 3.12.14 and 3.13.15 each run the full suite at `83adc06`
   with `1468 passed`, exit 0, pristine `HOME`, no undeclared plugins.
2. 3.11 also passes with real `pip`, matching CI's install path.
3. CPython 3.10.21 fails at collection with 14 `tomllib` errors.
4. The resolved dependency set on 3.11–3.13 is exactly `pytest 9.1.1` plus its
   declared transitives — nothing extra is pulled in.
5. The suite passes unchanged under 20x CPU contention (1468 passed, 2624
   subtests), so gross resource starvation is not sufficient to cause a failure.
6. The suite passes with an untracked `build/` directory present (as
   `pip install` leaves), so the three `git diff` tests are not tripped by it.
7. CI job logs are inaccessible (HTTP 403) and annotations carry no test output.

### INFERRED (reasoned, not measured)

1. Because 3.11–3.13 pass locally under CI's own commands, the CI failure is
   **environmental**, not a property of those interpreters.
2. Because the failure is identical across all four versions, it most likely has
   a **single shared cause** rather than four independent ones.
3. Because 3.10 fails for a documented, source-level reason and the other three
   do not reproduce, the four red jobs are probably **not** all instances of the
   same defect. The 3.10 job is explained; the other three are not.

### UNKNOWN

1. The actual failing test, traceback, or error message for 3.11–3.13.
2. Whether the failure is deterministic or intermittent on the runner.
3. Whether the runner image (`ubuntu-latest`, migrating to Ubuntu 26 per the
   CI notice) contributes.
4. Whether the failure is a genuine test failure at all, versus, for example, a
   collection error from a missing external tool on the runner.

## 10. Candidate Remediation Directions

**Observations only. No option is chosen, and none is implemented.**

### Direction 1 — Obtain the actual CI output (prerequisite for everything else)

*Evidence supporting it:* every other direction is speculative while the failure
text is unavailable. The 403 is a permissions boundary, not a tooling gap: a
maintainer with admin rights can download the log in seconds. Without it, no
further diagnosis is possible.

### Direction 2 — CI/environment correction

*Evidence:* the failure is not reproducible with the correct interpreter and
install command, which points at the runner rather than the project. Candidate
factors worth checking once logs are available: runner image changes (the CI
notice about Ubuntu 26), external binaries the suite may shell out to, or
filesystem differences.

### Direction 3 — Test compatibility change

*Evidence:* weak. Timing-sensitive tests do exist
(`tests/test_chat_sessions.py:903` asserts `elapsed < 5.0`; `:83-85` and
`:858-859` use monotonic deadlines; `tests/test_chat.py:167-171` likewise).
These are the only mechanisms found that could plausibly behave differently on a
slower runner. But 20x CPU contention did not reproduce a failure, so this is a
hypothesis, not a finding. **It must not be acted on by relaxing assertions.**

### Direction 4 — Separate version-specific defect remediation

*Evidence:* this is what 3.10 requires (a `tomllib` import guard or a
conditional backport). It is **not** supported for 3.11–3.13, which pass.

### Direction 5 — Dependency correction

*Evidence:* none found. The declared `pytest==9.1.1` resolves identically
locally and in CI, and installation succeeds in all four CI jobs. No drift was
observed.
