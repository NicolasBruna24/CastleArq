## 3. Auditability finding

The manifest committed at `e5213c7` — and therefore **inside** `v0.1.0` —
references three evidence documents (§6.1). Two resolve; one does not:

```bash
git show v0.1.0:docs/B9.36-…-drill-specification.md   # present
git show v0.1.0:docs/B9.36-…-drill.md                # present
git show v0.1.0:docs/B9.37-a-…-tag-specification.md
# fatal: la ruta '…' existe en disco, pero no en 'v0.1.0'
```

The `docs/` tree in the tagged commit contains 41 documents plus
`docs/release/`. B9.37-A is the **only** evidence reference the manifest makes
that is unresolvable from the tag.

Why this matters technically, not cosmetically:

1. The manifest's central claim — that `source_commit` (`6b08922`) and
   `evidence_commit` (`c21fc0c`) differ **only** documentarily and produce
   byte-identical extracted package content — is an *empirical* claim. The
   evidence for it lives **only** in B9.37-A §3.1. If B9.37-A is not in the
   tag, a third party verifying `v0.1.0` encounters an assertion with no
   resolvable proof inside the release.
2. B9.37-A is the document that **authorised** the tag target. The release
   would contain the manifest but not the reasoning that produced the release's
   own identity decision.

## 4. Option A — keep B9.37-A outside the release

Required change: the manifest would stop referencing the B9.37-A document
(i.e. **edit the manifest**).

Advantages:

* the existing tag object is never touched;
* the released manifest keeps its current identity.

Disadvantages:

* the identity decision that justified the tag target is absent from the
  audit trail of the very release it justified;
* the manifest loses historical evidence, and the empirical byte-identity claim
  becomes an unsupported assertion;
* the release is only partially self-contained;
* it requires modifying a document already committed and tagged, which is a
  *larger* mutation to released content than Option B's Git-only change;
* the dangling reference is not fixed by deletion of a line — the reasoning
  still exists outside the release.

## 5. Option B — include B9.37-A in the release

Required change: version the B9.37-A document in a new commit, then re-create
the annotated tag on that commit.

Advantages:

* every reference made by the manifest resolves **inside** the tag;
* the release audit trail becomes self-contained and independently verifiable;
* the identity decision and its empirical proof are preserved with the release;
* **the manifest requires no edit**: it identifies its own tag target indirectly
  via `git rev-parse v0.1.0^{commit}` precisely so that re-pointing the tag does
  not invalidate it. The reconciliation is therefore purely additive;
* zero impact on the distribution: `docs/` is provably never packaged.

Disadvantages:

* the existing local tag object must be deleted and re-created;
* the tag target commit changes;
* it must be an explicit, auditable operation, never a silent mutation.

## 6. Decision

```text

```

Technical justification, in order of weight:

1. **The tag is not published.** `git ls-remote --tags origin` is empty. No
   consumer, mirror, CI job or downstream user can have observed
   `122ff3e6…`. The usual objection to moving a tag — "it rewrites history
   someone already consumed" — **does not apply here**. This precondition
   expires the moment the tag is pushed, which is precisely why the decision is
   taken now and not later.
2. **The defect is real and one-sided.** The manifest is the release's entry
   document and it makes a reference that does not resolve in the release. Option
   A "fixes" it by deleting a true and useful reference; Option B fixes it by
   supplying the missing evidence. Only Option B increases verifiability.

   adds one markdown file under `docs/`. It touches no `app/`, no `tests/`, no
