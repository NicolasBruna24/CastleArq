## 2. Release scope

`v0.4.0` contains three changes relative to `v0.3.0`:

1. **Explicit model-store selection** — the store in use is selected
   deliberately and reported, instead of being inferred implicitly.
2. **Machine-readable `--json` CLI output** — a single `castlearq.cli` JSON
   envelope for the core queries.
3. **Python namespace migration** — the historical `app` namespace becomes
   `castlearq`. See §3.

## 3. Breaking change — Python namespace

**`v0.4.0` is not purely additive.** This release contains a breaking change for
consumers of the Python modules.

- `castlearq` is the public Python namespace for this release.
- The historical `app` namespace **is no longer present** in the published
  package.
- `import app` and `from app...` imports **no longer resolve**.
- Consumers importing historical `app.*` modules **must migrate** to the
  equivalent `castlearq.*` modules.
- CastleArq declares no supported Python API, so this affects only consumers
  who imported internals directly.

The `castlearq` console script is unaffected: the command name and every user
operation are unchanged.

## 4. CLI compatibility

All 17 commands remain present and behaviourally unchanged:

```text
detect  diagnose  verify  models  list  runtime  source  plan  compatibility
validate  download  import  run  execute  chat  serve  store
```

`--json` is available for the queries it covers. Exit codes are unchanged
(`0` success, `1` failure, `2` usage error).

**Python-module compatibility with `app.*` is explicitly not retained.** See §3.

## 8. Publication mechanism

```text
annotated tag v0.4.0
  -> this manifest, committed in the tagged tree
  -> GitHub Release assets
  -> SHA-256 gate (fails closed on mismatch)
  -> PyPI via Trusted Publishing
```

Intended sequence, none of which has occurred at authoring time:

1. An annotated Git tag `v0.4.0` is created on the release-preparation commit.
2. A GitHub Release `v0.4.0` is created (not a draft) with both artifacts
   attached.
3. `release.yml` re-derives the release identity from the tag, asserts the tag is
   annotated, asserts the GitHub Release matches, reads the expected SHA-256
   values from this manifest, downloads the release assets and verifies them
   (fail-closed).
4. The verified artifacts are published to PyPI through Trusted Publishing
   (OIDC). No credential or token is stored anywhere.

The workflow never rebuilds the distribution. The exact locally built artifacts
whose digests are recorded in §7 are transported, verified and published
unmodified, so rebuilding them after that point would invalidate this manifest.

At authoring time **the `v0.4.0` tag does not exist, the GitHub Release does not
exist, and `0.4.0` is not present on PyPI.**

## 9. Historical documentation

Historical documents under `docs/` reference the former `app/` paths (for
example `app/main.py`, `app/api.py`). Those references are **not rewritten**:
each records the repository state at the time its decision was taken, and
rewriting them would falsify the record they exist to preserve.

**`v0.4.0` supersedes those historical namespace references for the current
public package.** For the released artifact, the namespace is `castlearq` as
described in §3 and §5.
