# CastleArq `v0.2.0` — Publication Evidence

> **Post-publication verification.** This document records what was
> *independently observed* about the publication of `v0.2.0`, after the fact.
> It is not a changelog, not release notes, not an installation guide and not
> product documentation. The only file it produces is itself.
>
> **It is not the release identity.** `docs/release/v0.2.0-manifest.md` is the
> identity authority — it records *what* `v0.2.0` is. This document records
> *that that identity was actually published, and to what result*. See §9.

## 1. Executive Summary

CastleArq `0.2.0` is publicly published. This audit re-derived, from the
repository and from public read-only sources, every link of the release chain
declared by `docs/release/v0.2.0-manifest.md`.

```text
source commit 1359c1639055fb1481e23fe46720c6b69c0a74fb
    ↓
annotated tag v0.2.0  (tag object aba03f77fb14f665a3b0a663f8d4784067d60c49)
    ↓
GitHub Release "CastleArq v0.2.0"  (id 399526094, published 2026-09-29T21:02:51Z)
    ↓  assets = the audited artifacts, byte-identical to the manifest
release.yml run 36629776918 → verify (success) → publish (success)
    ↓  SHA-256 gate fail-closed, OIDC Trusted Publishing
PyPI  castlearq 0.2.0  (uploaded 2026-09-29T21:05:08Z / 21:05:10Z)
```

Every step above was **observed**, not assumed. The two artifact SHA-256
values were observed to agree across four independent locations: the manifest
committed at the tag, the local `dist/` files, the GitHub Release asset
digests, and the digests PyPI serves.

The release workflow's own execution was recovered: run `36629776918`,
`conclusion: success`, with both the `verify release artifacts` and
`publish to PyPI` jobs concluded `success`.

**Final classification: `VALIDATED — 0.2.0 PUBLICATION`** (§10).

Nothing in this audit modified the repository, the tags, the GitHub Release or
PyPI. Every source consulted was read-only.

## 5. Artifact Provenance

```text
castlearq-0.2.0-py3-none-any.whl
SHA-256: 784bff23e4c9c8f941a1ca38765fd05bd38e09df76156fe1c4228c98fedf1c42
size:    209970 bytes

castlearq-0.2.0.tar.gz
SHA-256: 0967b32da22b79dea0c3401d6ea70394f5b272a30a112ae928c0b8965124d8c4
size:    357802 bytes
```

### 5.1 Four-way agreement

| Location | How observed | `whl` digest | `tar.gz` digest |
| --- | --- | --- | --- |
| Manifest at the tag | `docs/release/v0.2.0-manifest.md` §2 | `784bff23…fedf1c42` | `0967b32d…6524d8c4` |
| Local build output | `sha256sum dist/*` | `784bff23…fedf1c42` | `0967b32d…6524d8c4` |
| GitHub Release assets | API `assets[].digest` | `sha256:784bff23…` | `sha256:0967b32d…` |
| Files PyPI serves | PyPI JSON `urls[].digests.sha256` | `784bff23…fedf1c42` | `0967b32d…6524d8c4` |

All four agree, and the byte sizes reported by GitHub and by PyPI match each
other (209970 / 357802).

This is the Model A provenance ratified in B9.41 and carried by
`.github/workflows/release.yml`: the artifacts were **transported and
hash-verified, never rebuilt in CI**. The evidence is consistent with that
model — the published bytes are the audited bytes.

### 5.2 Reproducibility statement (unchanged)

`v0.2.0-manifest.md:61-81` records that the build is **not** byte-reproducible
(timestamps inside the zip/tar containers and `RECORD` regeneration are not
normalised), and that making it so is a post-`0.2.0` improvement rather than a
defect. This audit observed no reason to revisit that classification, and does
not restate it. A third party verifying from source must compare *extracted
content*, not expect these hashes from a fresh build.

### 6.4 `run_attempt: 2` — recorded, not explained

The publishing run reports `run_attempt: 2`. **This audit did not retrieve the
first attempt** and therefore does not state why it was re-run. Attempt 1 is
not present in the `head_sha` query above, which returns only the latest
attempt per run. No conclusion about a failure, a cancellation or an operator
action is drawn here; see §8.

### 6.5 What was NOT retrieved

**Job logs were not retrieved.** The evidence above is API metadata: run and
job `status`, `conclusion`, step names and step conclusions, job IDs and
timestamps. No pytest output line, no hash comparison output and no
Trusted Publishing token exchange was observed, and none is asserted. The
admissible evidence is the set of successful job and step conclusions bound to
the target SHA — no more, no less. This is the same evidence limit
`docs/B9.57.7-continuous-validation-rerun.md:277-287` declared for the CI
closure, applied here deliberately.

## 8. Evidence Limitations

1. **Job logs were not retrieved** (§6.5). Only run/job/step conclusions,
   names and timestamps were observed.
2. **The first attempt of the release run was not retrieved**
   (`run_attempt: 2`, §6.4). Its status and cause are unknown and are not
   speculated about.
3. **No clean-install verification was performed.** Unlike B9.44 for `0.1.0`,
   this audit did **not** install the published wheel into an isolated
   environment and observe `castlearq --version`. The claim that the published
   artifact is installable and reports `0.2.0` is therefore **not** evidenced
   here.
4. **No Trusted Publishing configuration was inspected.** The workflow file
   documents the expected publisher, but the registered PyPI Pending Publisher
   configuration itself was not queried.
5. **The GitHub Release body is empty** (`"body": ""`). No release notes were
   published, so there is no release-note text to audit.
6. **Only the latest attempt of each workflow run was observed.** Historical
   attempts are not included in these API responses.
7. **The local `dist/` files were not rebuilt or re-inspected.** Their
   *contents* were not extracted; only their digests and the manifest-declared
   metadata were compared. The manifest's own wheel/sdist content descriptions
   (§2 of that document) were not independently re-derived here.

No inference in this document is presented as an observation. Where evidence
was not obtained, it is listed above rather than filled in.
