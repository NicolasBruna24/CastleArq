**Source state.** The artifacts were built from the prepared v0.6.0 release
source state. The release-preparation commit includes this manifest and does
not exist when this document is authored, so no self-referential commit SHA is
recorded. The annotated tag identifies that exact commit; the workflow
resolves the release identity from the tag itself.

This is a distribution recovery for the intended v0.6 software state.
Fifteen files under `castlearq/` differ from the v0.5.0 source baseline.

**Functional changes — observable behavior changes (9 files).** Six are new
modules: `admitted_commands.py`, `admitted_models.py`,
`admitted_resolution.py`, `training.py`, `training_runner.py` and
`offload_evidence.py`. Three extend existing modules: `main.py`,
`runner.py` and `execution.py`. The user-visible additions are the B9.99
admitted-model journey (`admit`, `describe`, `refresh`, `reconcile`, `show`),
the bounded SFT+LoRA training prototype, and GPU offload evidence.

**Internal and integration changes — no public-contract change (6 files).**
`api.py`, `application_wiring.py`, `resolver.py`, `selection.py`,
`evaluate_compatibility.py` and `execute_model.py` change internal wiring,
projections and diagnostics only.

The HTTP contract exposed to Desktop (`/health` with `version`,
`/v1/models`, `/v1/artifacts`) is unchanged between the v0.5.1 and v0.6.0
wheels: `castlearq/api.py` is byte-identical in both (SHA-256
`94f5dee31eb147778277721480ae04ee8668a44a59068f5464095dde6c725e6b`).

The statement carried over from the v0.5.1 manifest — that no production
code or behavior changed from the v0.5.0 source baseline — was accurate for
v0.5.1, which changed no file under `castlearq/`. It does not apply to this
release.

## 4. Reproducibility of the artifacts

These builds are **not byte-reproducible**, and the distinction matters when
comparing artifacts:

- **File digests.** The SHA-256 values recorded in section 2 are digests of
  the exact files retained in `dist/`. They are authoritative and are not
  regenerable by rebuilding the package.
- **Content reproducibility.** For a given source tree, the *payload* is
  reproducible: the wheel keeps the same 82 entries in the same order with
  byte-identical contents, and the sdist's extracted tree is identical
  (`diff -rq` reports no differences). Rebuilding produces a package with the
  same content but a different file digest.
- **Container metadata.** The difference between two builds of the same
  content is confined to time stamps in the container formats: the wheel's
  ZIP `date_time` on the six `dist-info` entries, and for the sdist both the
  `mtime` of 15 tar members and the gzip header's MTIME field.

Content reproducibility therefore does not imply byte-for-byte
reproducibility, and a rebuilt artifact must never be substituted for a
recorded one. The release workflow does not rebuild: it verifies the
retained assets against the digests in section 2.

## 5. Publication contract

```text
annotated tag v0.6.0
  -> this manifest, committed in the tagged tree
  -> GitHub Release assets
  -> SHA-256 gate (fails closed on mismatch)
  -> PyPI via Trusted Publishing
```

The release workflow never rebuilds the distributions. The exact wheel and
sdist whose digests are recorded above must be retained and attached to the
GitHub Release unmodified. The workflow checks out the tagged tree, reads this
manifest, downloads both assets, and verifies their SHA-256 values before
publication. Rebuilding after recording the hashes would invalidate this
manifest because these builds are not byte-reproducible.

The tag-push workflow may run before the GitHub Release and its assets exist.
If that run fails at the release-existence check, publish the GitHub Release
with these exact artifacts, verify the asset names and digests, then use the
existing `workflow_dispatch` trigger for `v0.6.0`. Do not bypass a failed
verification gate.
