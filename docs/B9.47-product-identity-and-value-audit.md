# B9.47 — Product Identity & Value Audit

## 1. Executive Summary

CastleArq hoy no es únicamente un wrapper de llama.cpp. Existe una identidad de producto defendible: una capa local de gestión y preparación de artifacts que convierte una solicitud de usuario en una ejecución local segura, observable y explicable sobre un runtime externo.

Su valor actual está en mantener identidad lógica de modelo separada de artifact físico; administrar ModelStore con manifests y estado derivado; resolver/preflightar artifacts; evaluar factibilidad; recomendar runtime/backend; separar conocimiento, evidencia física y ejecución; y componer un flujo de usuario en vez de exponer directamente el comando de llama.cpp.

La inferencia, carga del modelo y procesamiento de la respuesta siguen delegados a llama.cpp. La visión de múltiples runtimes todavía no es capacidad actual. CastleArq es hoy un producto de gestión/orquestación local de un runtime, no una plataforma general de runtimes.

**Verdict: PRODUCT-IDENTITY-RESOLVED**

## 2. Current Product Reconstruction

El recorrido real es:

```text
user CLI/API request
  -> catalog/model identity
  -> artifact resolution and ModelStore
  -> hardware/runtime/backend detection
  -> strict/operational compatibility evaluation
  -> EvaluationAdmission when wired
  -> ArtifactExecutionPreflight
  -> RuntimeBackendSelector
  -> LlamaCppRunner
  -> real llama.cpp process
  -> ExecutionResult / stdout / exit status
```

Entradas actuales: model id, prompt, cuantización/filename opcional, backend preference, configuración/hardware detectada y artifact local. También existen catálogo, descarga, listado, run, chat y diagnóstico.

Decisiones propias: aceptar/rechazar el request; resolver modelo/artifact; mantener manifests; detectar capacidades; estimar memoria y factibilidad; recomendar cuantización/runtime/backend; bloquear antes de lanzar; validar path, symlink, tamaño y checksum; construir target; proyectar resultado.

Estado persistente: manifests y metadata de adquisición en ModelStore. El estado físico se deriva inspeccionando filesystem; no se persiste como autoridad. No hay persistencia de inferencias ni de RuntimeArtifactEvidence.

Dependencias externas: llama.cpp para la ruta principal; Hugging Face para el único flujo de descarga soportado; sistema/hardware mediante observación local. Ollama aparece en detección/recommendation, pero no como runner de inferencia completo del flujo principal.

## 3. Current User Problem

El problema concreto es la complejidad entre intención de usuario y runtime local:

> “Quiero ejecutar este modelo local de forma reproducible y segura sin conocer manualmente repositories, filenames, quantizations, manifests, filesystem safety rules, GGUF path, CPU/Vulkan suitability ni la sintaxis exacta de llama.cpp.”

CastleArq transforma ese problema en un flujo local de descubrir, descargar, localizar, evaluar, preparar y ejecutar. No resuelve scheduling empresarial, entrenamiento, multi-tenancy ni optimización de performance.

La respuesta no es simplemente “ejecutar modelos”: llama.cpp ya puede hacerlo. El valor está en reducir incertidumbre y riesgo entre intención e invocación.

## 4. Current User / Use Case

Usuario actual: desarrollador u operador Linux con un GGUF local y llama.cpp instalado. Puede consultar catálogo, descargar un artifact soportado, listar artifacts, ejecutar one-shot, mantener chat y recibir explicaciones de compatibilidad, warnings y errores.

Conocimiento requerido: model id canónico, artifact local o acceso a fuente, y runtime instalado. CastleArq elimina selección manual de archivos, paths, validación de seguridad y elección inicial de backend. Sigue expuesta la calidad del modelo, la respuesta, el espacio disponible y la configuración del sistema.

Resultado: una respuesta operacional del proceso o un error controlado, más metadata local de artifact/compatibilidad. El producto no promete calidad, entrenamiento ni ejecución multi-runtime.

## 5. Wrapper vs Orchestration Analysis

Un wrapper delega casi toda la responsabilidad funcional al runtime. CastleArq no cumple esa definición completa:

| Responsabilidad | CastleArq | llama.cpp |
|---|---|---|
| Descubrimiento y artifacts | catálogo, ModelStore, downloader, GGUF metadata | no es lifecycle owner |
| Identidad | ModelSpec, ArtifactSpec, artifact_id, manifests | consume path |
| Seguridad | preflight, symlink/type/size/checksum | no define identidad local |
| Factibilidad | memoria, VRAM/RAM, score, warnings | no recibe política de usuario |
| Runtime/backend | detección, recomendación, selector | expone opciones/flags |
| Knowledge/evaluation | dominio strict, UNKNOWN/FAILED, provenance conceptual | no conoce contrato CastleArq |
| Inferencia | request, argv, result projection | carga y ejecuta modelo |
| Persistencia | manifests/adquisición/listings | no es lifecycle owner |

## 7. Responsibility Boundary

CastleArq debería ser responsable de identidad lógica, artifact lifecycle, resolución, adquisición/listados seguros, disponibilidad, factibilidad, selección/rechazo, preflight, request reproducible, resultado y separación de knowledge/evidence/execution.

llama.cpp debería ser responsable de cargar el GGUF, inicializar backend, ejecutar inferencia, emitir output/runtime errors y códigos de salida propios.

La frontera sigue siendo válida con otro runtime sólo si ese runtime puede exponerse como una capacidad real comparable en artifact load, inferencia, output, error, timeout y target. La substitución no es trivial porque el runner actual contiene argv, options, parsing y naming de llama.cpp.

## 8. Runtime Substitution Test

**Runtime-independent:** ModelSpec/ArtifactSpec, identity, ModelStore, resolver, download lifecycle, manifests, preflight, resource estimation, knowledge separation y result projection.

**Runtime-aware:** RuntimeCapability, RuntimeStatus, RuntimeBackendSelector, format/backend support, availability, version y target model. Son conceptos generales, pero el contrato actual está diseñado alrededor de llama.cpp CLI.

**llama.cpp-specific:** `detect_llama_capability`, `query_llama_devices`, `LlamaCppRunner` argv (`cli`, `--simple-io`, `--model`, `--device`, `--single-turn`), backend mapping, `parse_llama_human_output`, aliases y assumptions GGUF one-shot.

Si llama.cpp desapareciera, CastleArq aún podría identificar y preparar artifacts, pero no tendría un segundo runtime que ejecutar. Eso demuestra valor de gestión local y también que multi-runtime aún no existe.

## 9. LLaMA-Factory Conceptual Test

Traducir un `llamafactory-cli` sería wrapper. Para ser orquestación CastleArq tendría que poseer:

```text
modelo lógico
  -> dataset y experimento
  -> artifact/input validado
  -> compatibilidad
  -> selección de herramienta/runtime
  -> ejecución LLaMA-Factory
  -> artifact/resultado de entrenamiento
  -> evaluación
  -> siguiente decisión
```

Responsabilidades que no existen: dataset identity, experiment spec, training lifecycle, checkpoint/adapter identity, dataset provenance, training compatibility, outcome evaluation, artifact promotion/rollback y comparación.

LLaMA-Factory sería una tool specialization dentro de una política de experiments, no orquestación mientras CastleArq sólo componga argumentos.

La mayor parte del flujo está por encima de llama.cpp, pero la inferencia está delegada. La clasificación honesta es runtime-specific execution manager con valor de preparación y gestión, no orquestador multi-runtime demostrado.

## 10. Overarchitecture Audit

| Finding | Clasificación | Razón |
|---|---|---|
| Model identity, ModelStore, manifests, download lifecycle | JUSTIFIED NOW | Reducen ambigüedad y gestionan artifacts que llama.cpp no posee |
| Preflight y filesystem boundary | JUSTIFIED NOW | Es una política de producto antes de delegation |
| Hardware detection y `assess_model()` | JUSTIFIED NOW | Decide factibilidad/recommendation y bloquea riesgos |
| Backend selector | JUSTIFIED NOW | Decide target real y explica errores |
| Strict evaluator + Knowledge registry | JUSTIFIED BUT NOT YET EXPOSED | Tiene valor futuro, pero el runtime-artifact check no llega al E2E actual |
| Admission wiring | JUSTIFIED BUT NOT YET EXPOSED | La frontera deny-only es razonable; su impacto depende de la política runtime-artifact |
| GGUF architecture reader/evidence | JUSTIFIED BUT NOT YET EXPOSED | Es útil para separar metadata física, no prueba load |
| RuntimeArtifactEvidence | PREMATURE como feature actual | No hay producer, consumer ni valor de usuario probado |
| `ModelRunner` abstraction | JUSTIFIED BUT NOT YET EXPOSED | Permite sustitución; hoy sólo hay un runner real |
| API/chat/diagnosis | JUSTIFIED NOW en CLI scope | Son superficies existentes |
| Segundo motor strict frente a `assess_model()` | UNCLEAR | Borders separados, pero ambos convergen en execution y mantienen dos verdict languages |
| Ollama como runtime visible | UNCLEAR/PREMATURE | Detection existe, pero no ejecuta como flujo principal |

La arquitectura está adelantada respecto al producto en observability y generalización, no necesariamente en identidad/lifecycle/preflight. No se recomienda eliminar código en esta auditoría; se recomienda no confundir arquitectura posible con valor realizado.

## 11. CastleArq 0.1 Definition

CastleArq 0.1 es útil por sí mismo si ofrece, para un usuario Linux local:

1. descubrir o recibir un model id canónico;
2. localizar o descargar un artifact GGUF real;
3. listar y validar artifact de forma segura;
4. recomendar runtime/backend y bloquear combinaciones claramente incompatibles;
5. ejecutar un prompt one-shot o chat mediante llama.cpp real;
6. mostrar output/error/exit status claramente;
7. mantener manifests y estado local suficiente para repetir la selección.

El usuario obtiene algo distinto de usar llama.cpp directamente porque no necesita reconstruir discovery, identity, storage, safety checks, compatibility policy, backend selection ni result projection.

0.1 no necesita multi-runtime, training, GUI, cluster, LoRA, GPU scheduling, telemetría ni un segundo motor de conocimiento.

## 12. Explicit Non-Goals

CastleArq 0.1 no debe ser plataforma universal de runtimes, trainer, experiment manager, cluster scheduler, LoRA manager, cloud service, GUI, observability platform, validador de calidad semántica, segundo pipeline ni registry persistente de evidencia operacional.

La visión de múltiples runtimes puede orientar boundaries, pero no se convierte en evidencia de valor actual.

## 14. Product Identity Decision

**CastleArq is not currently “just llama.cpp”.** Su identidad actual es:

> Un gestor/orquestador local de artifacts y ejecución para un runtime local, que prepara, protege, evalúa y proyecta una ejecución real de llama.cpp con una UX y una propiedad local del artifact.

La respuesta a “¿por qué debería existir?” es: para hacer segura y repetible la operación completa alrededor de un runtime, no para mejorar el modelo ni implementar inferencia propia.

La respuesta a “¿cuál es la responsabilidad por encima de los runtimes?” es: identidad, lifecycle, resolución, factibilidad, selección, seguridad, admission y proyección de resultados.

No hay evidencia actual para afirmar que CastleArq sea una plataforma general de orquestación. Esa identidad futura requiere más de un runtime/tool real y una política cross-runtime que no existe hoy.

## 15. Recommended Next Step

Cerrar el acceptance pendiente de B9.46.29 con el cambio mínimo de admission y una validación E2E opt-in real. Después, mantener 0.1 centrado en catálogo + ModelStore + preflight + factibilidad + llama.cpp execution + output.

No añadir LLaMA-Factory, nuevos runtimes, GUI ni observability. Si se decide avanzar hacia múltiples runtimes, primero debe demostrarse un segundo runtime real y una decisión cross-runtime que no sea sólo otro wrapper.

No se recomienda iniciar otro bloque de arquitectura automáticamente. La decisión siguiente debe ser de producto: mantener CastleArq como producto local de un runtime o cambiar explícitamente el alcance.

## 16. Verdict

PRODUCT-IDENTITY-RESOLVED
