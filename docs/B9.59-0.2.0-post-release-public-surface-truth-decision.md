# B9.59 — 0.2.0 Post-Release Public Surface Truth

> **Nature of this block:** correction of a false published claim, plus the
> post-publication evidence record for `v0.2.0`. No product code,
> `pyproject.toml`, workflow, test other than the one named in §4, tag,
> artifact or Trusted Publishing configuration was modified, re-tagged or
> re-published. The files produced are the two `docs/` documents named in §4.

## 1. Purpose

CastleArq published `v0.2.0` on PyPI. The public surface shipped with that
release continued to describe the **pre-publication** state, and the test that
guarded the public surface actively enforced that stale description. This
block corrects the surface, replaces the temporal assertion with a standing
invariant, and records the publication evidence that `v0.2.0` actually shipped.

## 2. Problem

`README.md` opened with:

> **Version note.** The published PyPI release is `0.1.0`. This README describes
> the current `main` branch, which contains the unreleased `0.2.0` work and is
> ahead of that release.

Every part of that was true while `0.2.0` was unreleased and every part of it
became false the moment `v0.2.0` was published. Because `pyproject.toml` sets
`readme = { file = "README.md" }`, this text is the **long description rendered
on the PyPI page for `0.2.0` itself** — so a visitor to the `0.2.0` page was
told, by `0.2.0`, that the published release was `0.1.0` and that `0.2.0` did
not exist.

`tests/test_public_surface.py::test_readme_discloses_the_published_version`
compounded it. B9.53 §17 required the README not to imply a published release
already carried a surface it lacked; at authoring time that was correctly
expressed as a literal, and three assertions froze the pre-release state:

```python
self.assertIn("The published PyPI release is `0.1.0`", flat)
self.assertIn("current `main` branch", flat)
self.assertIn("ahead of that release", flat)
```

A test that guards the public surface had become the mechanism that kept the
public surface wrong. Swapping `0.1.0` for `0.2.0` would not have fixed that;
it would have re-armed the same failure for the next release.

Two contributing conditions, recorded because they are why this was not caught:

* **B9.53 and B9.54 have no document in `docs/`.** The blocks that produced
  the current public surface are evidenced only by commits and tests, so the
  intent behind the §17 literal was not recoverable from the repository.
* **B9.58 is referenced by five `B9.57.x` closure notes but has no document
  either**, so the last number with a written record was B9.57.8.

## 3. Decision

1. **Present the published version.** The README version note states the
   version that is published, and names only the two differences
   `docs/release/v0.2.0-manifest.md:55-56` distinguishes from `0.1.0`: the
   `validate` command and the `>=3.11` Python floor.
2. **Derive the expected version from `pyproject.toml`.** The test reads
   `[project] version` and asserts the README presents *that* value. The
   literal is gone, so the test needs no edit at the next release.
3. **Forbid pre-release framing, not a version string.** The defect was never
   that a version was written down; it was that the note described a
   *relationship* between the branch and the release — "unreleased", "ahead of
   that release" — which is true at exactly one point in a release cycle and
   silently false for the rest of it. A second test rejects that framing, so
   the whole class of drift is caught rather than one instance.
4. **Do not freeze a historical version in the test.** No version literal
   appears in either test, so neither becomes stale.

`pyproject.toml` remains the single source of truth. It was already the input
to the wheel, the sdist and the published metadata, and
`app/version.py:10-21` already resolves from it; no new source of truth was
introduced.

## 6. Explicit Non-Goals

* **Re-publishing PyPI `0.2.0`.** PyPI does not permit replacing the files of
  a published version. The corrected README reaches users with the next
  release; the live `0.2.0` page keeps the old text and cannot be otherwise.
* **Modifying the GitHub Release**, moving the `v0.2.0` tag, or creating any
  tag. The published release is correct and hash-verified.
* **`app/**`.** No product behaviour changes; `app/version.py` was read, not
  edited.
* **`pyproject.toml`**, including `requires-python` and the classifiers. It is
  the invariant's source of truth; editing it would edit the invariant.
* **CI or workflows.**
* **Legacy admission cutover** (`run` / `run_service` bypassing strict
  admission) — a separate block, `docs/B9.42:543-560`.
* **Lint / Ruff** — deferred by `docs/B9.56:509` to its own block.
* **Catalog expansion** beyond the current three models.
* **Multi-runtime, Ollama as a runtime, GUI, jobs, scheduling, any new
  capability** — `docs/B9.47:164,168`.
* **Roadmap restructuring.** A forward-looking roadmap register is a separate
  documentation block and is not started here.
* **Fixing the hardcoded `"0.2.0"` literals in `tests/test_b930_packaging.py`
  (lines 32, 88, 92).** Recorded as a finding: they are a latent instance of
  the same class and will drift at the next release, but they belong to the
  packaging block, not this one.
* **Back-filling the missing `B9.48`, `B9.50`, `B9.53`, `B9.54` and `B9.58`
  documents.** Named here as the root cause; not in this block's scope.
* **Any existing `docs/` record.** Historical documents are not rewritten;
  supersession is stated here instead.

is in real use — nine references across five `B9.57.x` documents, including

## 8. Verification Performed

```text
Targeted: tests/test_public_surface.py   -> 24 passed
Full:     python3 -m pytest               -> see §9
```

Test-first proof, in order:

1. The two new tests were written against the **unmodified** README and both
   **failed**: the version assertion reported
   `'The published release is `0.2.0`' not found in '**Version note.** The published PyPI release is `0.1.0`…'`,
   and the framing guard reported `'unreleased' unexpectedly found`.
2. Only then was the README corrected.
3. Re-running the same tests passed.
4. The README was temporarily reverted to the old note and the tests were
   confirmed to fail again, then restored — proving the guard is bound to the
   prose and not merely to the helper.

`test_api_serve_contract.py` was not modified and still passes: it enforces
set-equality between the README command table and the CLI's accepted commands,
which this change did not touch.
