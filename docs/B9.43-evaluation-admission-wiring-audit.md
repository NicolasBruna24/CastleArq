## 1. Executive Summary

**Observed facts.**

1. `EvaluationAdmission` is defined in `app/execute_model.py:79-88` as a
   frozen two-field dataclass `{status: str, verdict: str | None}`,
   documented as an *"Advisory evaluation signal: a summary copy, never the
   result object."* It is consumed exclusively by `_check_admission`
   (`app/execute_model.py:170-193`) at step 3 of `execute_model()`
   (:292), which is **deny-only and deny-by-default**
   (`_ADMITTING_VERDICTS = {"compatible", "compatible_with_conditions"}`,
   :69). Nothing in `app/` constructs it; only `tests/test_execute_model.py`
   does. The CLI passes `admission=None` (`app/main.py:1061`).
2. `EvaluateModelCompatibilityResult`
   (`app/evaluate_compatibility.py:55-67`) already contains everything an
   admission decision needs: `status` (`"evaluated"`/`"blocked"` — the exact
   vocabulary admission consumes) and `evaluation: StrictEvaluation | None`,
   whose `evaluation.result.status` is the strict verdict whose values
   (`compatible`, `compatible_with_conditions`, `incompatible`,
   `insufficient_evidence`) are exactly the admission verdict vocabulary.
   All other fields (`model_id`, `artifact`, `runtime`, `capability`,
   `integration`, `blocking_outcome`) are diagnostic/identity.
3. The conversion `EvaluateModelCompatibilityResult → EvaluationAdmission`
   does not exist anywhere: no `to_admission`/`admission_adapter` symbol is
   present in the repository (searched, zero hits).
4. The B9.8 `evaluation_adapter.py` is an **operational → strict domain
   adapter** (`ModelSpec/ArtifactSpec → Model/ModelArtifact`), frozen by an
   import allowlist (`tests/test_evaluation_adapter.py:18-22`). The missing
   conversion is a **strict/application result → application summary**
   projection between two Application use cases — a different direction, a
   different layer, and a different concern. It is *not* an inverse B9.8
   adapter.
5. Two frozen contracts locate the conversion outside both engines:
   `tests/test_execute_model.py::IsolationTests::test_no_evaluation_dependencies`
   forbids `execute_model` from importing any evaluation module, and B9.19
   §5 excludes `StrictEvaluation` and `EvaluateModelCompatibilityResult`
   from Execute inputs, allowing only the `admission` summary.

**Architectural interpretation.** The architecture already contains the
seam: Execute accepts a deny-only admission summary produced *by its
caller* "any time before" execution (B9.19 §7/§6), and the evaluation use
case already returns the data that summary requires. What is missing is a
single pure mapping function and a product surface that runs evaluation and
passes the summary — nothing else.

**Recommendation (not implemented).** **Option B — a dedicated narrow,
pure conversion** (e.g. a `to_admission(...)`-style function) hosted in the
evaluation Application layer (`app/evaluate_compatibility.py`), consumed by
the product caller, which then invokes
`execute_model(admission=...)`. No new service, module, layer or domain
object. `assess_model()` remains the operational gate; admission and the
legacy gate coexist sequentially (B9.19 §7). See §14–§18.

### 4.1 Definition (facts)

`app/evaluate_compatibility.py:55-67`, frozen dataclass, docstring

| Field | Type | Semantics |
|---|---|---|
| `model_id` | `str` | resolved identity (echo of resolved input) |

Success representation: `status == "evaluated"` with `evaluation` set.
Failure representation: `status == "blocked"` with `evaluation=None` and
`blocking_outcome` set (capability unavailable :109-117, resolution failure
:131-137, integration failure/type mismatch :146-163). B9.15 evaluation
failures are **not** captured — they propagate as exceptions (:167).

### 4.2 Sufficiency for an admission decision (facts + interpretation)

* Admission needs exactly `{status, verdict}` (§3.1). Mapping sources:
  * `status` → `result.status` — **identical vocabulary**
    (`"evaluated"`/`"blocked"`; `_blocked` :85 sets `"blocked"`,
    success path :185 sets `"evaluated"`).
  * `verdict` → `result.evaluation.result.status` — the strict
    `compatibility_domain.CompatibilityStatus` value. Its four values
    (`compatible`, `compatible_with_conditions`, `incompatible`,
    `insufficient_evidence` — `app/compatibility_domain.py:48-51`) are
    exactly the vocabulary `_ADMITTING_VERDICTS` and the admission tests
    use. `_normalized_verdict` accepts enums (`.value`), any case, and
    `-`/`_` variants (`execute_model.py:162-167`), so a
    `CompatibilityStatus` enum may be passed directly.
* Diagnostic-only fields (not part of the admission decision): `model_id`,
  `artifact`, `runtime`, `capability`, `integration`, `blocking_outcome`.
  They serve display/audit; B9.19 §7 wanted identifiers in the summary but
  `EvaluationAdmission` has no field for them (§3.3 defect).
* Conclusion: **the result contains enough information**; no additional
  data must flow.

### 4.3 Observed defects (documented, not fixed)

1. B9.23 §415-416 writes the mapping source as
   `evaluation.verdict` — `StrictEvaluation` has **no** `verdict` field
   (`evaluation_pipeline.py:68-83`); the real path is
   `evaluation.result.status`.
2. `evaluation` is typed `StrictEvaluation | None` but never
   runtime-validated: `evaluate_fn`'s return is forwarded verbatim
   (:164-177) and tests deliberately return `"EVAL-SENTINEL"` strings
   (`tests/test_evaluate_compatibility.py:93`). A conversion function must
   therefore either trust the declared type or guard defensively.
3. `app/evaluation_policy.py` emits `DecisionVerdict`
   (`allow`/`deny`/`escalate`, :62-67) — a vocabulary **disjoint** from
   `_ADMITTING_VERDICTS`; wiring `decide()` output as `admission.verdict`
   would make even `allow` deny (deny-by-default). The admission contract
   is aligned with the **strict status**, not with B9.10 verdicts
   (B9.19 §7 says "strict verdict").

## 6. Current Execution Flow

Trace of the production `execute` path (facts, `app/execute_model.py` +
`app/main.py`):

```text
CLI execute_command (app/main.py:1036-1063)
  → compose_execute_model_dependencies()        (application_wiring.py:228-274)
  → execute_model(model_id, prompt, admission=None, dependencies=deps)
      1. ModelArtifactResolver.resolve          (:276-286)  ← artifact resolution
      2. fresh RuntimeCapability + invocable    (:289, :196-211)
      3. _check_admission(admission)            (:292)      ← admission seam (no-op today)
      4. _legacy_compatibility → assess_model   (:297, :138-159)  ← OPERATIONAL GATE
         status ∈ {INCOMPATIBLE, UNKNOWN} → ExecutePreparationError (:299-303)
      5. ArtifactExecutionPreflight.validate    (:305-311)
      6. RuntimeBackendSelector.select          (:313-319)  ← runtime/backend selection
      7. backend preference + request validation (:325-341)
      8. runner.run(executable, target, request) (:343-344) ← actual execution begins
```

* `assess_model()` runs at step 4, on detected hardware/backends plus the
  projected `RuntimeStatus` (`_runtime_status`, :123-135). Its result:
  legacy `CompatibilityResult` (status/score/recommendations). Failure →
  `ExecutePreparationError` with compatibility warnings; execution
  prevented; the same object feeds `selector.select` at step 6 (:315).
* Artifact resolution happens at step 1 (before admission); selection at
  step 6 (after both gates); execution at step 8.
* Legacy `run`/`chat`/HTTP path is parallel: `run_service.prepare`
  (`run_service.py:187-236`) performs assess_model → preflight → selection
  with no admission parameter at all (B9.42 §6).

**Where an `EvaluationAdmission` could participate without changing
unrelated responsibilities (interpretation):** exactly where it is already
wired — step 3 of `execute_model`. The parameter, gate and error already
exist; only the *producer* of the value is missing. The caller (product
surface) is the natural producer: B9.19 §7 defines evaluation as "any time
before" execution and B9.19 §6 makes "admission evaluator" a caller-side
dependency. No step 4–8 responsibility changes; `assess_model`,
preflight, selection and the runner remain untouched. The legacy
`run_service` path has no admission seam and B9.19 §13 keeps it frozen —
it is out of scope for this wiring.

## 9. Admission Semantics

Concepts as the code defines them (facts; not collapsed):

### Functional compatibility

**Yes.** Strict evaluation answers: *"Does this model/artifact satisfy the
declared functional compatibility requirements?"* — evidence:
`app/compatibility_evaluator.py:18-24` states the claim ("the supplied
artifact can be considered functionally compatible with the supplied
runtime/backend context, given the available metadata and explicitly
supplied runtime/backend capability knowledge") and explicitly excludes
resource feasibility, performance and trust.

### Operational feasibility

**Yes.** `assess_model()` answers: *"Can the current machine/runtime
execute it?"* — evidence: it reads detected `HardwareSnapshot`,
`RuntimeStatus`, `BackendStatus` and computes memory fit
(`app/compatibility.py:112-186`); B9.42 §7.

### Admission

**Not exactly "the evaluation layer permits execution."** The code
indicates a narrower, asymmetric semantics:

* `EvaluationAdmission` is *"an advisory evaluation signal: a summary
  copy"* (`execute_model.py:80`) — **evidence of evaluation**, not a
  permission token.
* It **can only deny**; it "can never authorize [execution] on its own"
  (:84-85). Passing an admitting admission changes nothing about whether
  execution proceeds — steps 4-8 revalidate unconditionally
  (`test_admission_never_skips_revalidation`, order
  `resolve→capability→compatibility→preflight→select→run`).
* The actual semantic is: *"the evaluation layer has no objection to the
  execution path continuing (or: it objects)."* B9.19 §7 ratifies this as
  **Option 3 — advisory admission signal, re-validated; never authority**,
  explicitly rejecting both "no gate" (Option 1) and "hard require + trust"
  (Option 2) because verdicts are point-in-time and go stale (§11).
* `admission=None` does **not** mean denial — it means *the caller carries
  no evaluation signal* and the transitional legacy gate alone applies
  (B9.19 §149-151; `execute_model.py:173-179`).

### Execution eligibility

Composite, defined by control flow: eligibility = (admission not denied)
AND (legacy compatibility not `INCOMPATIBLE`/`UNKNOWN`) AND (preflight
passes) AND (selection succeeds) AND (request valid) AND (capability
invocable). No single component decides it alone.

## 10. Deny / Unknown Semantics

Table of the effective admission state machine (facts,
`execute_model.py:69, 162-193`):

| Input state | Classification | Effect |
|---|---|---|
| `admission is None` | **no signal** (not allow, not deny) | no admission gate; legacy gate only (transitional rule, B9.19 §149-151) |
| `status == "evaluated"` + `verdict ∈ {compatible, compatible_with_conditions}` | **allow** (=`"evaluation does not object"`) | proceed to legacy gate |
| `status == "evaluated"` + `verdict == incompatible` | **deny — functional** | `ExecuteAdmissionDeniedError` |
| `status == "evaluated"` + `verdict == insufficient_evidence` | **deny — functional (unknown denies)** | `ExecuteAdmissionDeniedError`; matches B9.19 §138-139 "INSUFFICIENT_EVIDENCE handling deferred; default MUST be deny"; frozen by `test_insufficient_evidence_denies_by_default` |
| `status == "evaluated"` + `verdict` missing/`None` | **deny — deny-by-default** | frozen by `test_missing_verdict_denies_by_default` |
| `status == "blocked"` (B9.16 precondition failure) | **deny — functional** | "B9.16 `blocked` never authorizes" (B9.19 §153); `test_blocked_never_authorizes` |
| any other `status` (`"pending"`, unknown, case variants) | **deny — deny-by-default** | `test_unknown_status_denies` |
| evaluation **errors** (B9.15 `ValueError` etc.) | **never reach admission** — they propagate out of `evaluate_model_compatibility` (:167) | a caller that catches them and still executes must pass `admission=None` (no signal), never a fabricated admitting admission; fabrication is prevented only by deny-by-default of *any* non-evaluated value |

Explicit distinctions required by §10:

* **Functional denial** = `ExecuteAdmissionDeniedError` raised at step 3 —
  the strict layer objects (identity/format/architecture/capabilities or
  missing evaluation evidence).
* **Operational/resource denial** remains entirely `assess_model()`'s
  responsibility (step 4, `INCOMPATIBLE`/`UNKNOWN` on memory/VRAM/runtime
  feasibility), plus preflight (artifact state) and selection
  (backend/format/capability). `EvaluationAdmission` has **no field** for
  hardware, memory or resources and must never acquire one — it is
  fabricated from evaluation results only.
* `UNKNOWN`-equivalents deny in **both** layers (strict
  `INSUFFICIENT_EVIDENCE` → admission deny; legacy `UNKNOWN` → gate deny),
  but for different reasons: missing functional evidence vs missing
  operational evidence. The semantics coincide; the responsibility does
  not merge.

## 11. Combined Execution Model

Model only — not implemented (interpretation grounded in cited facts):

```text
                        execution request
                               │
        caller (product surface) — BEFORE execute_model, "any time before"
        │                       │
  strict evaluation      operational assessment is NOT run here —
  evaluate_model_        it belongs to execute_model step 4
  compatibility()                │
        │                        │
  EvaluateModel-                 │
  CompatibilityResult            │
        │                        │
  to_admission()  ← MISSING (this audit's gap; §14 Option B)
        │                        │
  EvaluationAdmission            │
        └────────────┬───────────┘
                     │
              execute_model(admission=...)
                1 resolve → 2 capability → 3 admission gate (functional)
                → 4 assess_model gate (operational) → 5 preflight
                → 6 selection → 7 validate → 8 run
```

Answers (each tied to evidence):

1. **Are both checks necessary?** Yes — they answer different questions
   (B9.42 verdict; B9.19 keeps both: §7 admission *plus* "the legacy
   prepare gate applies" when `admission=None`, and even with admission the
   legacy gate still runs at step 4). Strict evaluation never reads
   hardware; `assess_model` never reads identity/format/architecture.
2. **Can either replace the other?** No. Admission cannot replace the
   legacy gate (it carries no memory/VRAM/recommendation data the selector
   needs; B9.19 FORBIDDEN: strict results into `select()`). The legacy gate
   cannot replace admission (it would discard "the only strict functional
   claim" — B9.19 §145).
3. **Sequential or independent?** The *activities* are independent:
   evaluation may run any time before execution (B9.19 §134) on a
   different object graph (it re-resolves its own artifact). The *checks*
   are sequential inside `execute_model`: admission (step 3) precedes the
   legacy gate (step 4) — `execute_model.py:292` < `:297`.
4. **Ordering requirement:** admission must be checked before the legacy
   gate (code order; frozen by `test_blocked_never_authorizes` →
   `compatibility_calls == []`), but after resolution and capability
   (frozen by `test_admission_denial_happens_after_resolution` → order
   `["resolve", "capability"]`). The caller must produce the admission
   before invoking `execute_model`; freshness is *not* required of it —
   B9.19 §11-§12: verdicts go stale by design and Execute revalidates
   everything ("drift fails closed").
5. **Where failures surface:** functional denial →
   `ExecuteAdmissionDeniedError` (subclass of `ExecutePreparationError`)
   at step 3; operational denial → `ExecutePreparationError` at step 4;
   artifact/backend issues → `ExecutePreparationError` at steps 5-6. All
   are preparation failures — nothing is launched (B9.19 §10 taxonomy).
6. **What execution needs:** only the *decision* carried by admission
   (`{status, verdict}`) plus the legacy `CompatibilityResult` (gate +
   selector input). The full `StrictEvaluation`/`EvaluateModelCompatibilityResult`
   are explicitly excluded from Execute (B9.19 §5) and must stay with the
   caller/evaluation side.

## 13. B9.8 Boundary Analysis

**Observed fact.** `app/evaluation_adapter.py:15-22,50-69` adapts operational
`ModelSpec`/`ArtifactSpec` to strict B9.3 `Model`/`ModelArtifact` and
`EvaluationContext`. It is a pure input projection, not a result consumer and
not a policy layer. B9.8's direction is:

```text
operational ModelSpec/ArtifactSpec
        ↓ evaluation_adapter
strict Model/ModelArtifact/evaluation inputs
```

The proposed result projection is conceptually the other direction, but is not
an inverse of the same adapter:

```text
EvaluateModelCompatibilityResult
        ↓ application projection
EvaluationAdmission
```

It does not reconstruct a strict model or translate operational facts into
strict facts. It copies only the application outcome and strict verdict needed
by Execute. The B9.8 adapter must remain untouched, including its unknown and
canonicalization policy and import allowlist.

## 14. Narrowest Valid Wiring

**Recommendation: Option B — a dedicated narrow adapter.** The evidence favors
a pure converter in the evaluation application layer, alongside
`EvaluateModelCompatibilityResult` in `app/evaluate_compatibility.py`, or an
equivalent existing application composition boundary. Its contract should be
limited to:

```text
EvaluateModelCompatibilityResult
    → EvaluationAdmission(status=result.status,
                          verdict=result.evaluation.result.status
                                  if result.evaluation is not None else None)
```

The extraction must use the existing strict result contract and must not
reinterpret operational `CompatibilityResult`. Blocked, missing, malformed, or
non-evaluated results must not manufacture a positive verdict.

Option A is not sufficient because no existing product caller currently runs
evaluation or constructs the summary. Option C is inappropriate: evaluation
composition owns strict evaluation, not execution-facing denial. Option D
would put translation in Execute, which is prohibited by the isolation
contract and would couple it to evaluation types. Option E is unnecessary
unless a later implementation finds an existing product-composition seam that
already owns both operations.

This is a wiring recommendation only; no converter, service, or product caller
was added.

## 15. New Abstraction Assessment

No new service, manager, registry, coordinator, domain object, or abstraction
layer is justified. `EvaluationAdmission` already is the boundary object and
`execute_model(admission=...)` already consumes it. The missing piece is a
data projection and a caller that deliberately invokes evaluation before
Execute. A new type would duplicate either the application result or the
admission summary and would reopen B9.19's exclusion of evaluation result
objects from Execute.

The only justified later addition is a small pure conversion function (or a
narrowly owned equivalent) plus product-surface wiring and tests. Any
orchestration must remain in the existing application caller/composition
responsibility, not inside the strict evaluator.

## 17. Architectural Decision

**B9.43 VERDICT**

1. `EvaluationAdmission` is an application boundary summary, currently defined
   as a frozen dataclass in `app/execute_model.py`, containing only `status`
   and optional `verdict`. It is not a permission token: a positive signal
   never authorizes execution independently.
2. Its producer should be a product/application caller that has deliberately
   obtained an `EvaluateModelCompatibilityResult`; the narrow converter should
   live in the evaluation application layer.
3. The only admission information required is the result's application status
   and the strict evaluation verdict. Identity, artifact, capability,
   integration, and blocking diagnostics remain with the result and are not
   admission fields.
4. `EvaluateModelCompatibilityResult` should be converted into the summary;
   passing the full result into `execute_model` would violate B9.19.
5. The conversion should not be placed in B9.8 `evaluation_adapter.py`, whose
   responsibility is operational → strict input adaptation. It is a separate
   application projection.
6. Strict functional evaluation and `assess_model()` must coexist. The former
   answers declared functional compatibility; the latter answers current
   machine/runtime operational feasibility. Evaluation denial must not replace
   operational denial, and operational checks must not claim to establish
   functional compatibility.
7. Evaluation may run before `execute_model`; Execute then checks admission
   before its compatibility provider, preflight, and selector. Within Execute,
   admission denial precedes the legacy gate; the gates are sequential, not
   interchangeable.
8. Functional incompatibility, insufficient evidence, blocked/malformed/missing
   evaluation, and evaluation failure must produce functional denial when the
   admission contract requires a fail-closed signal; errors may instead
   propagate at the product boundary if that is the chosen failure-reporting
   contract, but must never become allow.
9. Operational incompatibility/unknown remains denied by `assess_model()`;
   preflight and selector retain their existing responsibilities.
10. B9.8, B9.39 representation boundaries, B9.40 persistence, B9.41 manifest
    authority, B9.19 selector/Execute restrictions, current CLI behavior, and
    both compatibility engines must remain unchanged.
11. No new abstraction is necessary.
12. The next block should implement only the narrow result-to-admission
    projection and a deliberately selected product/application caller path,
    with deny-only defaults, tests for both functional and operational denial,
    and no direct strict-result selector input.

This verdict does not authorize implementation in this block.
