# B9.29 — Linux Distribution Readiness Contract

> **Materialización retrospectiva.** Este documento conserva el resultado de la auditoría/decisión B9.29. B9 fue principalmente una secuencia de work-blocks y la ausencia histórica de un archivo B9.29 individual no significa que el bloque no haya ocurrido.

## 1. Status

```text
B9.29 = CONTRACT READY
```

B9.29 es una auditoría y un contrato de readiness para la primera distribución de CastleArq en Linux. No es una implementación de packaging, no modifica la arquitectura de negocio y no reemplaza la validación de B9.30.

## 2. Executive Summary

```text
Developer-valid
Partially reproducible
Not yet distributable
```

El vertical slice funciona en el entorno del desarrollador, lo que demuestra viabilidad técnica en ese contexto. Todavía no existe una ruta reproducible para una persona externa al checkout/repositorio. B9.29 define el contrato necesario para cerrar esa brecha: empaquetado Python, CLI instalada, configuración y ModelStore de usuario, runtime externo y adquisición explícita de modelos.

## 3. First Distribution Scope

La primera distribución queda limitada a:

```text
Python application package
→ console script `castlearq`
→ user-level configuration
→ user-level ModelStore
→ external llama.cpp runtime
→ explicit model acquisition
→ CPU-first baseline
```

Este es el primer milestone de distribución, no una solución definitiva para todos los sistemas Linux.

## 4. Python Packaging

- `pyproject.toml` utiliza un backend compatible con setuptools: `setuptools.build_meta`.
- El mínimo actualmente declarado es `requires-python = ">=3.10"`.
- No se inventa una versión recomendada de Python adicional: el contrato solo requiere el mínimo declarado mientras no exista evidencia para otra decisión.
- `pip install .` puede utilizarse como mecanismo inicial de implementación y validación del paquete.
- `pip install .` no es el canal público definitivo de distribución. El canal público definitivo queda abierto para una decisión posterior.

## 5. CLI Entry Point

La distribución debe proporcionar el entry point instalado:

```text
castlearq
```

Debe existir y validar:

```text
castlearq --help
castlearq --version
```

La interfaz de desarrollo existente debe conservarse durante la transición:

```text
python3 -m app.main
```

No es el entry point final de distribución. La CLI instalada será un adaptador delgado hacia la aplicación existente, sin introducir lógica de negocio.

## 6. User-Level Configuration

La configuración distribuida no puede depender del current working directory. La precedencia contractual es:

```text
CLI overrides
→ environment
→ user configuration
→ defaults
```

La configuración de usuario debe ubicarse bajo el estándar XDG/HOME correspondiente. Una ruta candidata es:

```text
~/.config/castlearq/config.toml
```

o su equivalente basado en `XDG_CONFIG_HOME`. Esto no se implementa en B9.29. Tampoco se inventa todavía una lista definitiva de variables de entorno sin validación en el código actual.

## 7. ModelStore

El ModelStore oficial de la distribución debe ser independiente del checkout. La ruta objetivo es:

```text
~/.local/share/castlearq/models
```

o su equivalente basado en `XDG_DATA_HOME`.

Debe mantenerse la compatibilidad de lectura con la ruta legacy:

```text
~/.local/share/localai-hub/models
```

Reglas:

1. La ruta nueva es la oficial.
2. La ruta legacy puede actuar como fallback.
3. Si ambas existen, se prioriza la nueva.
4. B9.29 no realiza migración automática.
5. Desinstalar CastleArq no debe eliminar los modelos del usuario.

No se implementa nada de esto en B9.29.

## 8. External llama.cpp Runtime

El primer milestone no debe instalar automáticamente llama.cpp. Es una dependencia externa obligatoria para ejecución. CastleArq debe:

- detectar el runtime externo;
- validar que puede utilizarse;
- reportar claramente cuando no está disponible;
- utilizarlo si es compatible;
- fallar explícitamente si no cumple el contrato.

Los nombres observados, como evidencia y no como matriz definitiva, incluyen:

```text
llama
llama-cli
llama-server
llama.app
```

La matriz exacta de CastleArq version ↔ llama.cpp version/build ↔ modos de ejecución soportados queda para validación posterior. No se define aquí una matriz de compatibilidad inventada.

## 9. Model Acquisition

Los modelos no forman parte del paquete Python. La adquisición es explícita:

```text
castlearq download MODEL_ID
```

El flujo conceptual es:

```text
models
→ download
→ verify
→ list
→ execute
```

No se realiza auto-download durante la instalación, el primer arranque, `execute` ni las actualizaciones. El usuario debe saber qué modelo se obtiene, qué artefacto se obtiene, cuantización, tamaño, destino y estado de verificación. El mecanismo exacto de descarga y verificación podrá evolucionar posteriormente.

## 10. First-Run Scenarios

### A — llama.cpp ausente + ModelStore vacío

Debe funcionar:

```text
castlearq --help
castlearq --version
castlearq list
```

La ejecución debe fallar explícitamente indicando que el runtime requerido no está disponible.

### B — llama.cpp disponible + ModelStore vacío

La ejecución debe fallar indicando que falta el modelo y orientar al flujo de adquisición explícita.

### C — runtime + modelo disponibles

La ejecución debe poder continuar si ambos cumplen las condiciones de compatibilidad.

### D — runtime incompatible

Debe fallar antes de entrar al runner.

### E — modelo incompatible

El compatibility gate debe rechazarlo antes del runner.

## 11. Hardware Baseline

El primer milestone es `CPU-first`. La existencia de una GPU Intel en el hardware del desarrollador no es una promesa de soporte GPU.

- La detección de GPU puede existir.
- El diagnóstico puede existir.
- La ejecución GPU no queda garantizada por B9.29.
- Intel/NVIDIA/AMD pueden permanecer como capacidades experimentales/no garantizadas.

No se instalan drivers ni se modifican dispositivos y no se exigen privilegios root.

## 12. System Dependencies

Dependencias conceptuales obligatorias para ejecución:

```text
Python
llama.cpp externo
modelo compatible
```

Herramientas de diagnóstico opcionales:

```text
vulkaninfo
clinfo
sycl-ls
nvidia-smi
rocminfo
```

Herramientas de desarrollo/build:

```text
gcc/g++
cmake
```

Ninguna de estas herramientas es un requisito universal de instalación de CastleArq. CastleArq no debe instalar drivers ni modificar el sistema.

## 13. Permissions

La instalación y ejecución normal deben funcionar como usuario común. No se usan `sudo`/`root`, escrituras en `/usr`, instalación de drivers ni modificación de dispositivos. Los datos persistentes se mantienen en directorios de usuario para configuración, modelos y datos.

## 14. Update / Uninstall

Actualizar CastleArq no debe eliminar:

```text
user configuration
models
artifacts
manifests
```

Desinstalar el paquete elimina el código instalado, pero no borra automáticamente los datos del usuario. B9.29 no implementa migración automática de datos legacy; esa política queda como deuda futura.

## 15. Clean Installation Criteria

Una instalación limpia podrá validarse con:

1. Linux compatible.
2. Python `>=3.10`.
3. Usuario normal.
4. Sin checkout utilizado como dependencia de ejecución.
5. Instalación del paquete.
6. `castlearq --help`.
7. `castlearq --version`.
8. Ejecución fuera del checkout.
9. Configuración independiente del cwd.
10. ModelStore independiente del repo.
11. Comportamiento correcto cuando falta llama.cpp.
12. Comportamiento correcto cuando falta el modelo.
13. Modelo preparado/listable.
14. Ejecución real con runtime y modelo compatibles.
15. Sin sudo/root.
16. Persistencia de datos durante actualización/desinstalación.

La matriz de validación completa se ejecutará durante B9.30.

## 16. Supply Chain

La distribución futura debe poder identificar:

```text
CastleArq package
→ version
→ source/checksum

llama.cpp
→ source
→ version/build
→ checksum

model
→ source
→ model ID
→ artifact
→ quantization
→ checksum
→ license
```

B9.29 no implementa signing, publishing ni CI/CD.

## 17. Migration / Compatibility

Durante la transición se mantienen:

```text
python3 -m app.main
```

y los flujos legacy existentes cuando sea necesario. Se registra:

```text
legacy ModelStore
→ fallback
```

No se ejecuta migración automática en B9.29. La política formal de migración queda como deuda futura.

Áreas potencialmente afectadas:

```text

ModelStore path resolution
package metadata
CLI entry point
documentation

```

```text

```

El packaging debe adaptarse a la arquitectura existente; no debe modificar la arquitectura de negocio para resolver distribución.
