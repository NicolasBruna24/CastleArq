# B9.2 — Compatibility Evaluation Rules

Estado: **reglas de evaluación documentadas — sin implementación del evaluador.**

Este documento define las **reglas formales** que el futuro Compatibility
Engine seguirá para evaluar:

```text
Model + Artifact + Hardware + Runtime + Backend
                    ↓
               CompatibilityResult
```

B9.2 es una fase exclusivamente de **diseño/documentación**. No crea código,
tests, CLI, adaptadores ni estimaciones. La implementación del evaluador
corresponde a **B9.3+**, que debe poder construirse sobre estas reglas sin
reinventar la semántica fundamental.

Filosofía vigente desde B1:

```text
detect → interpret → propose → user decides → user acts → verify → re-diagnose
```

CastleArq **no modifica automáticamente el sistema del usuario**.

Relación entre bloques:

```text
B8.x
    Model / Artifact domain

B9.0
    Compatibility Engine architecture/design

B9.1
    Compatibility result domain

B9.2
    Evaluation rules (este documento)

Future B9.3+
    Evaluator implementation and integration
```

---

## 1. Objetivo de la evaluación

El evaluador evalúa **un Artifact concreto en un contexto de ejecución
concreto**:

```text
Artifact
    +
Hardware
    +
Runtime
    +
Backend
    ↓
Compatibility evaluation
```

El Model aporta el contexto conceptual (arquitectura, capacidades,
parámetros), pero la compatibilidad se decide contra el **Artifact**: dos
artefactos del mismo modelo (p. ej. `Q4_K_M` vs `BF16`) pueden producir
veredictos distintos en el mismo entorno.

El evaluador NO:

- selecciona el mejor artifact;
- ordena (rank) modelos;
- recomienda un modelo;
- compara múltiples artifacts;
- optimiza rendimiento.

La selección de artifact/modelo es una capa futura y separada. El
evaluador responde una sola pregunta por invocación: *¿es viable este
artifact, en este contexto, bajo esta afirmación de compatibilidad?*

### La afirmación evaluada (claim)

Toda evaluación declara explícitamente **qué afirmación** establece:

```text
claim = "artifact X runs on hardware H with runtime R + backend B
         at context length C with configuration K"
```

Las reglas de agregación (§3) se aplican **relativas a esa afirmación**:
un check `UNKNOWN` solo bloquea la conclusión cuando su evidencia es
necesaria para *esa* afirmación concreta, no en abstracto.

---

## 2. Requirement → Check → Evidence → Interpretation

Cuatro conceptos separados, en orden:

### Requirement

Algo que debe ser cierto para la compatibilidad. Ejemplo:

```text
The runtime must support the artifact format.
```

Un requirement es una proposición normativa del dominio ("para ejecutar
GGUF con llama.cpp, el runtime debe declarar soporte GGUF"). No contiene
datos observados; contiene la condición a satisfacer.

### Check

La evaluación concreta realizada contra ese requirement. Ejemplo:

```text
artifact.format == supported_format
```

Un check instancia el requirement con los datos del caso: el valor
esperado (`expected`, derivado del requirement) frente al valor observado
(`observed`, aportado por el contexto). Su resultado es `PASSED`,
`FAILED` o `UNKNOWN` (B9.1 `CheckStatus`).

### Evidence

La información que sustenta el resultado del check. Ejemplo:

```text
source = runtime capability registry
value = GGUF supported
kind = OBSERVED
```

Toda evidencia viaja con `source`, `value` y `kind` (`OBSERVED` /
`CALCULATED` / `INFERRED`, B9.1 `EvidenceItem`). Un check sin evidencia
citable es una opinión, no una evaluación.

### Interpretation

La conversión de checks + evidencia en el estado final de
compatibilidad. Es la única fase que concluye, y sigue las reglas de
agregación de §3 — nunca atajos ad hoc.

```text
Requirement  →  qué debe ser cierto
Check        →  evaluación concreta (expected vs observed)
Evidence     →  información que sustenta el resultado
Interpretation → conversión determinista en CompatibilityStatus
```

## 3. Reglas formales de agregación

El evaluador sigue este orden conceptual. Determinista: mismos checks,
mismo resultado.

### Regla A — Fallo determinante

Si algún check de compatibilidad **requerido** es `FAILED`:

```text
INCOMPATIBLE
```

salvo que el check sea explícitamente no-determinante para la afirmación
evaluada.

**Qué significa "requerido/determinante":** un check es determinante
cuando su requirement es necesario para la afirmación (§1). Ejemplo: para
la afirmación "ejecutar GGUF con llama.cpp", el check de soporte de
formato es determinante; un `FAILED` ahí cierra el caso. Un check es
no-determinante cuando evalúa una propiedad informativa que la afirmación
no necesita (p. ej. temperatura del driver cuando la afirmación solo cubre
viabilidad funcional + memoria): su `FAILED` se registra como evidencia
pero no veta el veredicto. La calificación determinante/no-determinante
pertenece al requirement, nunca se improvisa por check.

### Regla B — Condiciones

Si todos los checks requeridos pasan, pero subsisten una o más
**condiciones de compatibilidad respaldadas por evidencia**:

```text
COMPATIBLE_WITH_CONDITIONS
```

Las condiciones describen algo concreto que se sabe necesario (§12). NO se
crean condiciones simplemente porque algo sea desconocido: lo desconocido
necesario produce `INSUFFICIENT_EVIDENCE` (Regla D), no una condición.

### Regla C — Compatibilidad plena

Si todos los checks requeridos para establecer la afirmación pasan y no
subsisten condiciones:

```text
COMPATIBLE
```

### Regla D — Evidencia insuficiente

Si un check requerido es `UNKNOWN` y la evidencia faltante es necesaria
para establecer la afirmación:

```text
INSUFFICIENT_EVIDENCE
```

Importante:

```text
UNKNOWN ≠ FAILED
UNKNOWN ≠ INCOMPATIBLE
UNKNOWN ≠ CONDITION
```

Un desconocido solo bloquea la conclusión cuando *esa* evidencia concreta
es necesaria para *esa* afirmación. Ejemplos:

- Formato del artifact desconocido + afirmación que requiere ejecutar el
  artifact → `INSUFFICIENT_EVIDENCE` (el check funcional no puede pasar).
- Temperatura del driver desconocida + afirmación de viabilidad funcional
  y memoria → el check es no-determinante para esa afirmación; no bloquea
  nada (B9.1 §13: ningún `any(UNKNOWN)` automático).
- Capacidad `vision` desconocida + afirmación de generación de texto →
  irrelevante para la afirmación; ni bloquea ni condiciona. La misma
  capacidad desconocida + afirmación de tarea multimodal → Regla D.

Orden de aplicación: A antes que D (un `FAILED` determinante decide
aunque otros checks sean `UNKNOWN`); D antes que B/C (sin evidencia
necesaria no hay veredicto afirmativo que condicionar).

## 4. Compatibilidad funcional vs compatibilidad de recursos

Frontera obligatoria. Son dos dimensiones con preguntas distintas.

### Compatibilidad funcional

Preguntas como:

- ¿La arquitectura está soportada?
- ¿El formato del artifact está soportado?
- ¿El runtime puede manejar el tipo de modelo?
- ¿El backend está soportado para esta combinación runtime/artifact?
- ¿Las capacidades requeridas del modelo están disponibles?

Responde: *¿puede este software procesar este artifact?* Sus checks se
resuelven contra conocimiento explícito de capacidades (registros de
runtime, matrices de soporte), nunca por inferencia geográfica del
entorno (§9).

### Compatibilidad de recursos

Preguntas como:

- ¿Hay suficiente VRAM?
- ¿Hay suficiente RAM?
- ¿Cuál es la memoria esperada en ejecución?
- ¿Cuánto offloading se requiere?

Responde: *¿cabe en esta máquina bajo esta configuración?* Sus checks se
resuelven contra observaciones de hardware + resultados del futuro Memory
Estimator.

Lo funcional NO implica lo resource, ni viceversa: un artifact puede ser
perfectamente procesable y no caber; puede caber de sobra y ser de un
formato que ningún runtime disponible lee. El veredicto global exige
resolver **ambas** dimensiones para la afirmación (§3): funcional `PASSED`
+ recursos `UNKNOWN` → `INSUFFICIENT_EVIDENCE`, no `COMPATIBLE`.

**Sin estimación de recursos todavía.** El Memory Estimator sigue siendo
un componente futuro y separado (§19); B9.2 no implementa fórmulas.

## 5. Reglas Model / Artifact

```text
Model
    describes the conceptual model

Artifact
    describes a concrete distribution of that model
```

El mismo modelo puede tener múltiples artifacts con distintos formatos,
precisión, cuantización, tamaños de almacenamiento, variantes y límites
de contexto. La compatibilidad se evalúa contra el **Artifact**, no contra
el Model abstracto:

- los checks funcionales leen atributos del artifact (`format`,
  `precision`, `quantization`, `max_context`), no del modelo;
- el Model aporta arquitectura, tipo, parámetros y capacidades como
  contexto de la afirmación;
- no asumir que metadatos a nivel de modelo prueban compatibilidad a
  nivel de artifact (p. ej. "el modelo es Transformer" no prueba que *esta*
  distribución GGUF concreta la lea *este* runtime).

---

## 6. Reglas de arquitectura

Cómo tratar arquitectura / tipo de modelo:

```text
known + explicitly supported
    → PASSED

known + explicitly unsupported
    → FAILED

unknown + required for the claim
    → UNKNOWN
```

- El soporte debe ser **explícito** (matriz de soporte del runtime,
  evidencia citable). Prohibido inventar soporte.
- Prohibido asumir que arquitecturas de nombre parecido son
  intercambiables ("parecido a Llama" no es "Llama"): cada arquitectura
  se evalúa por su identidad declarada.
- Arquitectura desconocida + necesaria para la afirmación → check
  `UNKNOWN` → Regla D. Arquitectura desconocida + afirmación que no la
  necesita (p. ej. afirmación puramente de formato) → el check puede ser
  no-determinante.

---

## 7. Reglas de formato

El formato permanece distinto de cuantización y precisión. Ejemplos:

```text
format = GGUF
quantization = Q4_K_M
precision = unknown
```

No tratar:

```text
Q4
```

como si significara automáticamente:

```text
format = GGUF
```

Un método de cuantización no identifica un contenedor: `Q4_K_M` puede
viajar en GGUF hoy y en otro formato mañana; el check de formato lee
`artifact.format` y nada más.

Del mismo modo, no tratar:

```text
BF16
```

como un método de cuantización. `BF16` es precisión (B8.1); un artifact
`Safetensors + BF16 + NOT_QUANTIZED` pasa el check de formato por ser
Safetensors soportado, no por su precisión.

La semántica de `app/model_domain.py` (B8.1) es la referencia conceptual
autoritativa: `format`, `precision` y `quantization` son tres ejes
independientes y ningún check puede leer uno para concluir sobre otro.

---

## 8. Precisión y cuantización

Se preserva la distinción B8.1:

```text
Precision
    = numerical representation

Quantization
    = reduction/transformation of representation
```

Los ejemplos incluyen casos como `FP32`, `FP16`, `BF16` y `Q4_K_M` sin
mezclarlos: los tres primeros viven en el eje precisión; el último, en el
eje cuantización con `QuantizationStatus = QUANTIZED`.

Reglas:

- No extraer conclusiones de memoria en ejecución a partir del número
  nominal de bits: `nominal_bits = 4` describe la cuantización declarada,
  no el consumo real por parámetro (overheads, alineación, KV cache y
  resto de factores pertenecen al futuro estimador).
- No equiparar bits nominales con consumo real de memoria bajo ninguna
  fórmula provisional: B9.2 no autoriza ningún factor de conversión.
- `QuantizationStatus.UNKNOWN` en un eje necesario → check `UNKNOWN`;
  `NOT_QUANTIZED` + precisión conocida habilita la rama de pesos con la
  precisión declarada (sin inventar la desconocida).

## 9. Runtime y backend

Requisito estricto de evidencia. El evaluador NO debe inferir:

```text
Vulkan exists
    →
runtime supports artifact
```

ni:

```text
Linux
    →
runtime supports format
```

ni:

```text
GPU vendor
    →
backend supports model
```

La existencia de un backend, una plataforma o un vendor no prueba que un
runtime concreto soporte un artifact concreto: la compatibilidad
runtime/backend exige conocimiento o evidencia explícita (registro de
capacidades del runtime, matriz runtime×backend×formato citable como
evidencia `OBSERVED` o `CALCULATED`).

Si la capacidad runtime/backend requerida es desconocida:

```text
UNKNOWN
```

y el resultado final puede ser:

```text
INSUFFICIENT_EVIDENCE
```

si esa capacidad es necesaria para la afirmación (Regla D). En particular:
detectar "Vulkan disponible en el sistema" no sustituye a "llama.cpp
soporta GGUF-Q4_K_M sobre Vulkan"; son dos checks distintos con evidencias
distintas.

## 10. Reglas de hardware

El hardware es evidencia de lo que existe físicamente. El motor puede usar
hechos como CPU, RAM del sistema, GPU, VRAM, arquitectura y plataforma
detectada.

Pero B9.2 no calcula todavía:

```text
required VRAM
required RAM
runtime memory
offloading amount
performance
```

Esos pertenecen al trabajo futuro de recursos/modelos.

Además: el soporte de hardware no debe confundirse con el soporte de
software. Ejemplo:

```text
GPU present
    ≠
backend proven compatible
```

Que exista una GPU no prueba que el backend la aproveche para este
runtime/artifact; el check de backend exige su propia evidencia (§9).
Del mismo modo, VRAM observada abundante no prueba nada funcional: solo
alimenta la dimensión de recursos.

## 11. Capacidades

Se usa conceptualmente el modelo B8.1:

```text
text_generation
code_generation
vision
embeddings
tool_use
```

Cada capacidad puede ser `True`, `False` o `None`. Reglas:

- `None` significa desconocido. Prohibido interpretar `None → False`:
  que no se sepa si el modelo genera código no prueba que no lo haga.
- Capacidad requerida `True` + modelo `True` → `PASSED` (con evidencia
  del dominio del modelo).
- Capacidad requerida + modelo `False` → `FAILED` determinante (el
  modelo declara no tenerla) → Regla A.
- Capacidad requerida + modelo `None` → `UNKNOWN`; si la capacidad es
  necesaria para la afirmación → `INSUFFICIENT_EVIDENCE` (Regla D).
- Capacidad irrelevante para la afirmación (sea cual sea su valor) → el
  check puede ser no-determinante o simplemente no existir.

---

## 12. Condiciones

Regla estricta: una condición de compatibilidad solo existe cuando:

1. la condición es concreta;
2. la condición es relevante para la compatibilidad;
3. hay evidencia que la respalda;
4. no contiene comandos;
5. no contiene instrucciones de ejecución;
6. no es simplemente otra forma de decir "desconocido".

Buen ejemplo conceptual:

```text
"Requires a runtime configuration that enables GPU offloading."
```

solo si el evaluador posee evidencia autoritativa de que es necesario
(p. ej. checks de VRAM que solo pasan con parte de las capas en CPU).

Mal ejemplo:

```text
"Probably needs more VRAM."
```

porque es especulación: sin evidencia no hay condición; hay, como mucho,
un warning (§11 de B9.0) o un `INSUFFICIENT_EVIDENCE`.

---

## 13. Niveles de evidencia

Se usan:

```text
OBSERVED
CALCULATED
INFERRED
```

### OBSERVED

Evidencia directa, medida o declarada por su fuente (p. ej. VRAM
detectada, formato declarado del artifact, matriz de soporte del
runtime).

### CALCULATED

Evidencia derivada por cálculo determinista explícito (p. ej. memoria
disponible = total − reservada). Reproducible y con sus entradas
citadas.

### INFERRED

Conclusión derivada de evidencia/cálculos sin observación directa
(p. ej. "offloading probablemente necesario" bajo supuestos
declarados).

B9.2 establece explícitamente:

```text
Evidence kind does not automatically determine CheckStatus.
```

Por ejemplo:

```text
INFERRED evidence
```

puede sustentar un check cuando la regla de inferencia es explícita y
autoritativa (p. ej. una regla documentada "si VRAM < X y contexto = C,
offloading requerido", con X y C citados). La inferencia con regla
autoritativa es evidencia válida, no especulación.

Del mismo modo:

```text
OBSERVED evidence
```

no significa automáticamente que el check pasó: observar `format = ONNX`
frente a un requirement de `GGUF` produce un `FAILED` perfectamente
observado. El kind describe la procedencia; el status describe el
desenlace de expected vs observed.

## 14. Comportamiento unknown-safe

Principio:

```text
CastleArq should prefer uncertainty over fabricated certainty.
```

Ejemplos:

```text
unknown architecture
    → do not assume supported

unknown format support
    → do not assume supported

unknown backend support
    → do not assume supported

unknown capability
    → do not assume absent
```

El evaluador distingue:

```text
absence of evidence
```

de:

```text
evidence of absence
```

La primera conduce a `UNKNOWN` en el check (y, si es necesaria para la
afirmación, a `INSUFFICIENT_EVIDENCE` por Regla D). Solo la segunda —
evidencia afirmativa de que algo falta o es incompatible (formato
declarado no soportado, capacidad declarada `False`, estimación fiable
que excede lo observado) — puede producir `FAILED` y, por Regla A,
`INCOMPATIBLE`. Ningún default "optimista" ni "pesimista" sustituye a
esta distinción: el default es siempre `UNKNOWN`.

---

## 15. Compatibilidad no es rendimiento

Explícitamente:

```text
COMPATIBLE
```

NO significa:

- fast;
- efficient;
- optimal;
- recommended;
- lowest memory;
- best quality;
- best model;
- best runtime.

Del mismo modo:

```text
INCOMPATIBLE
```

significa incompatible según la afirmación evaluada y las reglas
disponibles, no "malo": otro artifact del mismo modelo, otra
configuración u otro backend pueden ser compatibles. El veredicto
califica la combinación evaluada, nunca el modelo en abstracto.

---

## 16. Compatibilidad no es confianza

No mezclar compatibilidad con seguridad del modelo, confianza en la
procedencia, reputación de la fuente, reputación de seguridad ni juicio
de licencias. La procedencia B8.0/B8.1 existe como dato, pero su
evaluación de confianza es una preocupación futura y separada: un
artifact puede ser `COMPATIBLE` y no confiable, o confiable e
`INCOMPATIBLE` para este entorno. Ningún check de compatibilidad lee
reputación, y ningún veredicto de compatibilidad la implica.

---

## 17. Sin puntuación de compatibilidad

No introducir:

```text
85% compatible
7.8/10
compatibility_score
```

El resultado permanece categórico y basado en evidencia. Una puntuación
fingiría una precisión que el motor no posee (¿qué significa "85%" sin
una métrica de distancia a la viabilidad?), colapsaría las cuatro
categorías en un número mudo y rompería la explicabilidad (§2: cada
estado responde una pregunta distinta del usuario). Si una capa futura
necesita ordenar candidatos, ordenará `CompatibilityResult` completos con
sus propios criterios declarados — nunca un escalar inventado por el
evaluador.

---

## 18. Multi-GPU

El diseño anticipa hardware multi-GPU futuro. El evaluador conceptual
opera contra un contexto de hardware capaz de representar múltiples GPUs,
no hardcodeando:

```text
GPU 0 only
```

B9.2 no inventa ningún algoritmo de compatibilidad multi-GPU. La
asignación/orquestación detallada multi-GPU (reparto de capas, memoria
agregada, ejecución distribuida) se marca explícitamente como trabajo
futuro. Regla para entonces: cada GPU es evidencia `OBSERVED`
independiente; cualquier agregación ("memoria combinada") es `CALCULATED`
con su fórmula citada, jamás una suma silenciosa.

---

## 19. Frontera del Memory Estimator

```text
Compatibility Engine
    = determines compatibility claims

Memory Estimator
    = estimates resource requirements
```

El Compatibility Engine puede consumir un futuro resultado de
memoria/recursos, pero B9.2 no implementa fórmulas. No estimar todavía:

```text
VRAM
RAM
KV cache
context memory
offloading
runtime overhead
```

Regla de consumo: el motor trata el resultado del estimador como
*evidencia con kind* (`CALCULATED` con entradas citadas, o `UNKNOWN` si
el estimador no puede calcular). Un estimador ausente o incapaz no
produce ceros ni defaults: produce `UNKNOWN`, y la Regla D decide. El
motor nunca reimplementa ni "completa" la estimación con heurísticas
propias (p. ej. usar `storage_size` como proxy de memoria: prohibido por
§6 de B9.0 y §6 de este documento).

---

## 20. Contrato del futuro evaluador

Contrato conceptual (sin implementar):

```text
evaluate(
    model,
    artifact,
    hardware,
    runtime,
    backend
) -> CompatibilityResult
```

El evaluador deberá ser:

- puro;
- determinista;
- libre de efectos secundarios;
- libre de acceso a red;
- libre de ejecución de comandos;
- libre de instalación/modificación;
- testeable a partir de los insumos suministrados.

"Testeable desde insumos" significa: toda evaluación es reproducible
construyendo los cinco insumos como datos (fakes deterministas en
tests), sin hardware real, sin runtimes reales y sin red. Cualquier regla
que no pueda probarse así es una regla mal definida y debe reformularse
antes de B9.3.

## 21. Ejemplos completos

### Ejemplo A — COMPATIBLE

Arquitectura conocida y explícitamente soportada + formato conocido y
soportado + soporte runtime/backend conocido:

```text
checks:
    architecture: PASSED (expected Transformer/MoE soportada,
        observed idéntica, evidence: matriz del runtime)
    format: PASSED (expected GGUF, observed GGUF)
    runtime: PASSED (llama.cpp declara GGUF)
    backend: PASSED (Vulkan disponible para la combinación)
    memory: PASSED (estimación fiable dentro de lo observado)
conditions: —
warnings: —
→ COMPATIBLE
```

### Ejemplo B — COMPATIBLE_WITH_CONDITIONS

Todos los checks requeridos pasan, pero subsiste una condición respaldada:

```text
checks: todos PASSED (funcional + recursos bajo supuesto declarado)
conditions:
    - "Requires a runtime configuration that enables GPU offloading."
      (evidence: VRAM observada vs estimación: solo pasa con capas en CPU)
→ COMPATIBLE_WITH_CONDITIONS
```

### Ejemplo C — INCOMPATIBLE

Arquitectura explícitamente no soportada:

```text
checks:
    architecture: FAILED (expected una de {…soportadas…},
        observed arquitectura X no listada, evidence: matriz del runtime)
→ INCOMPATIBLE (Regla A; el resto de checks no cambia el veredicto)
```

### Ejemplo D — INSUFFICIENT_EVIDENCE por arquitectura

Arquitectura desconocida y necesaria para la afirmación:

```text
checks:
    architecture: UNKNOWN (expected soporte declarable,
        observed None, evidence: ninguna)
→ INSUFFICIENT_EVIDENCE (Regla D)
```

### Ejemplo E — Capacidad desconocida (no automáticamente INCOMPATIBLE)

Capacidad `vision = None` + afirmación de generación de texto: la
capacidad es irrelevante para la afirmación → ni bloquea ni condiciona
(puede documentarse como check no-determinante `UNKNOWN` o simplemente no
evaluarse). La misma capacidad desconocida + afirmación multimodal →
`INSUFFICIENT_EVIDENCE` por Regla D. En ningún caso la incertidumbre
produce `INCOMPATIBLE` por sí sola.

### Ejemplo F — GPU presente pero backend desconocido

GPU observada + soporte del backend para esta combinación desconocido: la
presencia de la GPU alimenta la dimensión de recursos, pero el check de
backend queda `UNKNOWN`. Como el backend es necesario para la afirmación
→ `INSUFFICIENT_EVIDENCE`, no `COMPATIBLE` ("hay GPU, debe funcionar")
ni `INCOMPATIBLE` ("no se sabe, luego no"). La GPU sola no establece
compatibilidad (§9–§10).

responsabilidades):

- **GPU Diagnosis (B2)**: diagnostica el *software del sistema* (¿está
  Vulkan funcional?); el Compatibility Engine evalúa *escenarios de
  ejecución* (¿puede este artifact correr aquí?). B2 produce hechos que
  el motor puede citar como evidencia, pero no decide compatibilidad.
- **Remediation (B5)**: propone planes declarativos ante problemas
  confirmados; el motor no propone planes, solo veredictos con
  condiciones.
- **Remediation Verification (B7)**: verifica que una remediación
  aplicada cambió el estado; el motor no verifica nada posterior a su
  veredicto. Si una condición de compatibilidad se aplica (p. ej. el
  usuario limita el contexto), una re-evaluación con la nueva
  configuración es una *nueva* evaluación, no una "verificación" en
  sentido B7.

## 24. Requisitos de calidad del diseño

El documento es técnicamente riguroso para que otro desarrollador pueda
implementar B9.3 sin inventar la semántica fundamental. Lenguaje
permitido: `PASSED`, `FAILED`, `UNKNOWN`, `required evidence`,
`determinant check`, `non-determinant check`, `required`/`non-required`
para la afirmación. Lenguaje prohibido en reglas (salvo al hablar de
incertidumbre explícita):

```text
probably
usually
should work
likely compatible
seems supported
```

Distinción obligatoria en toda regla y ejemplo:

```text
fact            → lo que es (OBSERVED)
evidence        → información citada que sustenta (con kind)
calculation     → derivación determinista citada (CALCULATED)
inference       → conclusión interpretada (INFERRED, con regla)
interpretation  → conversión final en CompatibilityStatus (§3)
```
