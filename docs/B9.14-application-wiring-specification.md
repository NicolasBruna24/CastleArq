## 1. Purpose

Block B9.14 defines the **application wiring boundary** for the
Observation → Knowledge path:

```text
Acquisition (impure, environment-facing)  → B9.14 wiring (THIS SPECIFICATION)
Translation (pure)                        → B9.12 translate()
Integration composition (pure given input)→ B9.13 integrate()
Knowledge (declarative)                   → B9.5 / B9.6 / B9.7
```

B9.14 is responsible for:

1. Obtaining a production `EnvironmentContext` via `EnvironmentObserver`.
2. Owning / injecting the `KnowledgeRegistry` reference passed to integration.
3. Invoking B9.13 `integrate(context, registry)`.
4. Transporting / handing off the resulting `IntegrationResult` verbatim.
5. Defining coexistence with legacy detection without migrating it.
6. Defining the normative stop-line before Evaluation.

B9.14 is **orchestration / wiring, not domain transformation**. It
translates nothing, projects nothing, asserts no knowledge, evaluates
nothing, decides nothing, and executes nothing.

## 4. Architectural Position

```text

        │
        ├── EnvironmentObserver.capture_context()   (impure acquisition edge)
        │
        ↓

        ↓
B9.12 translate()                                    (pure, deterministic)
        ↓

        ↓
B9.13 integrate(context, registry)                   (pure given input)
        ↓

        │
        ↓
[future Evaluation-composition boundary — NOT B9.14]
        ↓

```

Q-1 (RATIFIED) / Q-2 (RATIFIED) / Q-3 (RATIFIED) note: B9.14 is composed from its own Application / Composition Root point on the CastleArq path above; it is NOT inserted into the legacy flow below. Every CastleArq-path invocation captures a fresh EnvironmentContext immediately before integrate() (see section 6), while the KnowledgeRegistry reference is provisioned once by that Composition Root and reused across invocations (Q-3b, §7.2). Legacy path, beside the new path (unchanged by Q-1/Q-2):

```text

  (ModelExecutionService / run_service.prepare / run_once / open_chat_session)

Dependency direction remains downstream-only:
`Wiring → {Observation (acquisition), B9.12, B9.13, Knowledge (value-only)}`.

## 5. Terminology

- **Acquisition:** impure environment reads → `EnvironmentContext` (B9.11;
  NOT B9.12/B9.13). Only this edge may perform I/O.
- **Translation:** `EnvironmentContext → BoundaryTranslation` (B9.12, pure).
- **Integration composition:** `(EnvironmentContext, KnowledgeRegistry) →
  IntegrationResult` (B9.13, pure given its input).
- **Wiring (B9.14):** impure-at-the-edge orchestration that supplies the two
  integration arguments and transports the result. No transformation.
- **Handoff:** verbatim, in-memory transfer of `IntegrationResult` to the
  future Evaluation-composition boundary. Not evaluation.
- **Legacy path:** `hardware.py / runtimes.py / compatibility.py /
  selection.py / execution_service.py / run_service.py` production chain.
- **Non-interference:** the normative property that wiring changes no legacy
  input, output, or behavior and legacy changes no new-path contract.

## 6. Acquisition Contract — O-01

### 6.1 Resolved

- R-A1. `EnvironmentObserver` remains the **acquisition owner**: probe logic,
  parsers, provenance rules, `ACQUISITION_ERRORS`, and coverage semantics stay
  in `observation_probe.py` / `observation_domain.py` per B9.11.
- R-A2. B9.14 owns only the **calling / wiring relationship**: supplying the
  four injected dependencies, triggering `capture_context()`, and forwarding
  the resulting value. It owns no observation logic.
- R-A3. `EnvironmentContext` is supplied to B9.13 **as an immutable value**
  (frozen dataclass, tuple collections). Wiring never mutates it.
- R-A4. The four observer dependencies — `CommandRunner`, `FileReader`,
  `WhichFinder`, `TimestampProvider` — MUST be **explicitly injectable** at
  the wiring boundary (constructor / argument injection). Hidden process-wide
  I/O bindings captured inside wiring are forbidden.
- R-A5. **No I/O may occur inside B9.12 or B9.13.** Acquisition occurs
  strictly outside the pure domain integration (B9.13 I-20 carries forward).
- R-A6. The real `CommandRunner` preserves B9.11 constraints: strict timeouts,
  no `shell=True`. The real `TimestampProvider` yields a non-empty ISO-8601
  string (the `EnvironmentContext.timestamp` contract).

### 6.2 Ratified decisions Q-1 / Q-2

Lifecycle models M1 (command-time), M2 (request-time), and M3 (application / service lifetime) remain documented trigger shapes a future own composition point may exhibit; M4 (import-time constant) remains viable for the registry dataset only, never for acquisition. No ranking among M1-M3 is made for acquisition: the normative rule is freshness-per-invocation wherever the Q-1 composition point is hosted. That ranking-independence is about the `EnvironmentContext` only: the registry reference itself is settled by Q-3b (RATIFIED, §7.2) at Application / Composition Root lifetime, with M4 retained as the dataset's own construction shape at import time.

- Q-1 (RATIFIED): B9.14 owns its own composition point inside the Application / Composition Root on the CastleArq path, separate from the legacy flow. The acquisition/integration sequence MUST NOT be inserted directly inside app/run_service.py prepare(), run_once(), open_chat_session(), nor inside app/execution_service.py ModelExecutionService. This placement is not a legacy refactor and not a migration of the existing flow. The concrete host module carrying this own composition point is RATIFIED by Q-9a/Q-9b (§13.1): `app/application_wiring.py`; Q-9 does not reopen Q-1.
- Q-2 (RATIFIED): every invocation of the CastleArq flow produces a FRESH EnvironmentContext: invocation -> EnvironmentObserver -> capture_context() -> integrate(context, registry) -> IntegrationResult -> STOP. B9.14 introduces NO EnvironmentContext cache, NO automatic snapshot reuse, NO global EnvironmentContext singleton, NO persistent EnvironmentContext, NO background refresh, NO import-time capture, and NO periodic refresh. KnowledgeRegistry is different: as a declarative dataset (not a dynamic environment snapshot) its reference has Application / Composition Root lifetime and is reused across invocations (Q-3b RATIFIED, §7.2). The conceptual difference stays normative: `EnvironmentContext` = ephemeral environmental snapshot; `KnowledgeRegistry` = immutable declarative knowledge.

Concrete DI bindings (which real CommandRunner / FileReader / WhichFinder / TimestampProvider values the production composition point passes) are RATIFIED by Q-9c (§13.1): `shutil.which` as WhichFinder, a local ISO-8601 UTC TimestampProvider glue, and new composition-root-local CommandRunner / FileReader adapters. The four-way injectability requirement itself (section 6.1) is unchanged.

## 7. Registry Contract

### 7.1 Carried forward from B9.13 (resolved)

Conceptual signature (unchanged):

```text
integrate(context: EnvironmentContext, registry: KnowledgeRegistry)
  -> IntegrationResult
```

- R-G1. `registry` is **mandatory**; no default argument.
- R-G2. **No global / singleton / default registry** (module global, lazy-init
  cache, default-parameter capture such as
  `def f(registry=INITIAL_KNOWLEDGE_REGISTRY)` are all forbidden).
- R-G3. Integration **never mutates** the registry (persistent-value
  semantics: `add` returns a new registry; insertion-order independent;
  determinism is structural).
- R-G4. The registry is **injected** (constructor / argument passing only).
- R-G5. `INITIAL_KNOWLEDGE_REGISTRY` (import-time immutable value,
  `initial_knowledge.py`) is the **RATIFIED dataset** of the CastleArq path
  (Q-3a, §7.2) and MUST reach integration by **explicit injection** from the
  Application / Composition Root. It is never a default argument, never a
  global, and never retrieved by import inside Observation or Integration.
- R-G6. The Composition Root may obtain the value by ordinary reference at
  composition time (the existing module-level value of `app.initial_knowledge`)
  and pass it as an argument. Module lookup, lazy initialisation, providers
  and service-locator lookups are forbidden; the reference to
  `app.initial_knowledge` lives only at the composition point, never in
  `observation_domain.py` / `observation_probe.py` / `observation_knowledge.py`.
- R-G7. No dataset IDs, registry selection, dataset switching, or
  multi-dataset orchestration are introduced (Q-3d, §7.2).

### 7.2 Ratified decisions Q-3a–Q-3d (human architectural decisions)

Recorded as RATIFIED HUMAN ARCHITECTURAL DECISIONS — not as repository
inference. The Q-3 discovery established that the repository contains no
production registry creation → injection path, and that no specification
text selects dataset, lifetime, owner or multiplicity by itself.
Q-4 is RATIFIED (§8.3), Q-5 is RATIFIED (§9.4) and Q-6 is RATIFIED (§10.3); Q-7 is RATIFIED (FORWARD, §11.3) and is not reopened
here. Q-9 (RATIFIED, §13.1) selects the concrete host module and the
production DI bindings without reopening Q-1/Q-2/Q-3.

- Q-3a (RATIFIED — dataset): `INITIAL_KNOWLEDGE_REGISTRY` is the knowledge
  dataset used by the CastleArq path defined by B9.14, supplied by explicit
  injection from the Application / Composition Root. This authorizes NO
  global, NO global singleton, NO hidden default of `integrate()`, NO
  registry retrieval by import inside `integrate()`, NO service locator,
  NO lazy global, and NO direct coupling of Observation to
  `app.initial_knowledge`. Its existence as an import-time value of
  `app.initial_knowledge` does not relax any of these restrictions. The
  decision means the concrete value used by the CastleArq path is the
  already-existing declarative registry — it does NOT mean Observation is
  responsible for knowing or importing the module that defines it.
- Q-3b (RATIFIED — lifetime): the `KnowledgeRegistry` has Application /
  Composition Root lifetime and MAY be reused across multiple CastleArq
  invocations. It is NOT rebuilt per invocation as a freshness requirement.
  Q-2 freshness continues to apply exclusively to `EnvironmentContext`:

  ```text
  invocation
    → EnvironmentObserver
    → capture_context()
    → fresh EnvironmentContext
    → integrate(context, registry)
    → IntegrationResult
    → STOP
  ```

  The registry reference may remain stable while the Application /
  Composition Root remains active. This authorizes NO global cache, NO
  global singleton, NO shared mutable state, NO persistent
  EnvironmentContext, NO EnvironmentContext reuse, NO background refresh of
  the EnvironmentContext, and NO import-time acquisition of the
  EnvironmentContext. The conceptual difference must remain explicit:
  `EnvironmentContext` = ephemeral environmental snapshot;
  `KnowledgeRegistry` = immutable declarative knowledge.
- Q-3c (RATIFIED — owner): the `KnowledgeRegistry` is the responsibility of
  the Application / Composition Root corresponding to the CastleArq path.
  That Composition Root is responsible for (1) provisioning / making the
  `INITIAL_KNOWLEDGE_REGISTRY` instance available, (2) holding the reference
  during its lifetime, and (3) supplying it by explicit injection to the
  B9.14 composition. "Owner" here means composition / provisioning /
  delivery responsibility for the dependency; it does NOT mean the owner may
  mutate the registry, which remains a persistent immutable value. The
  concrete module that materializes this responsibility was selected by
  Q-9 (RATIFIED, §13.1): `app/application_wiring.py`, the Application /
  Composition Root of the CastleArq path.
- Q-3d (RATIFIED — multiplicity): for the current CastleArq-path
  composition there is exactly one active `KnowledgeRegistry` instance per
  Application / Composition Root. This uniqueness is a property of the
  current composition, NOT a global property of the `KnowledgeRegistry`
  type, and MUST NOT be implemented as a global singleton, a mutable module
  global, a service locator, a hidden default, or dynamic registry
  selection. B9.14 introduces NO dataset IDs, NO registry selection, NO
  dataset switching and NO multi-dataset orchestration. The architecture
  must keep allowing distinct compositions to use distinct
  `KnowledgeRegistry` instances through explicit injection.

```text
one CastleArq composition
      ↓
one active KnowledgeRegistry instance

KnowledgeRegistry  ≠  global singleton
```

## 8. Invocation Contract

### 8.1 Resolved

- R-V1. Abstract sequence (normative, per Q-2):
  `invocation -> EnvironmentObserver -> capture_context()`
  `-> integrate(context, registry) -> IntegrationResult -> STOP`.
  The context passed to `integrate()` is the fresh value captured in the
  same invocation; `translate()` runs inside `integrate()`.
- R-V2. The caller MUST NOT pre-run `translate()`, construct
  `BoundaryTranslation`, duplicate identity mapping, inspect backend
  evidence to decide, reinterpret `UNMAPPED`, or construct
  `EvaluationContext`.

### 8.2 Forbidden caller-side behaviour

Pre-running translation, second identity tables or aliases, deriving
`RuntimeCapability` / `resolve_runtime` routes, or promoting timestamps.

## 9. Handoff Contract

### 9.1 Allowed (transport only)

Receive, return, retain in memory, forward verbatim — including exposing
Knowledge entries to the named future Evaluation-composition entry point
as opaque transport.

### 9.2 Forbidden

Evaluate, decide (`ALLOW` / `DENY` / `ESCALATE`, `recommend`, `select`),
execute, convert backend evidence / trace into assertions / ranking /
backend choice, convert `UNMAPPED` into `UNSUPPORTED`, construct
`EvaluationContext`. Any inspection of supported backends to decide is
Evaluation and belongs to the future block (B9.13 §30).

### 9.3 Trace rule (O-04 boundary)

- R-T1. `BoundaryTrace` is transported **inside** `IntegrationResult`,
  verbatim, in-memory only.
- R-T2. No second consumer, no out-of-band channel, no persistence,
  serialization, `schema_version`, UI, or diagnostics destination in B9.14.
  O-04 remains DEFERRED beyond this rule (B9.12 §23.9).

### 9.4 Decision: Q-5 Post-Integration Receiver Boundary (RATIFIED)

Q-5 is a HUMAN ARCHITECTURAL DECISION recorded here; it is not an
inference produced by the repository, and the evidence base does not
determine it by itself.

Q-5 (RATIFIED): the receiver of `IntegrationResult` is a
POST-INTEGRATION RECEIVER BOUNDARY — an abstract, post-stop-line
boundary that accepts the immutable B9.13 value
(`entries` / `unmapped` / `trace`, `app/observation_knowledge.py:113`)
and delivers it, verbatim, to the next boundary. The receiver is the
composition function's caller-side continuation: it accepts,
transports and delivers — it does NOT interpret.

- Location: strictly AFTER the B9.14 stop-line. B9.14 ends at
  `IntegrationResult` (§12); the receiver begins where B9.14 ends:

```text
B9.14 (ends at IntegrationResult)
    ↓
[Q-5 Post-Integration Receiver Boundary] (accept → transport → deliver)
    ↓
[next boundary — Evaluation-composition owns the Knowledge → Evaluation
transition per B9.13 §30; entry point NAMED by Q-8 = RATIFIED (Evaluation
Entry Boundary, §12); its concrete implementation stays with that future
block]
```

- Minimum responsibility (normative): accept the `IntegrationResult`
  value; transport it verbatim (including the embedded `BoundaryTrace`
  per R-T1, in-memory only per R-T2 / §9.1–§9.3); deliver it to the
  next boundary. Receive ≠ interpret.
- Prohibited responsibilities (normative): evaluate, decide (`ALLOW` /
  `DENY` / `ESCALATE`, `recommend`, `select`), rank, select or
  substitute backends, execute models, reclassify errors, set retry /
  fallback / degradation / recovery / execution policy, convert backend
  evidence or trace into assertions / ranking / backend choice,
  convert `UNMAPPED` into `UNSUPPORTED`, construct `EvaluationContext`,
  persist / serialize / log / render (CLI/UI/HTTP) / queue / publish
  the result. No persistence, logging, UI, API response, queue, event
  bus or database is invented by this decision.
- Evaluation relation: the receiver is the delivery point TOWARD the
  future Evaluation composition; it is NOT Evaluation and it does NOT
  design it. B9.14 never crosses the stop-line (I-Q9-08/I-Q9-09, §12);
  the Knowledge → Evaluation transition remains owned by the future
  Evaluation-composition block (B9.13 §30). No class, module, function,
  API, endpoint, CLI, event, queue or persistence is fixed by Q-5:
  the concrete receiver implementation is a future-block matter.
- Q-6 independence: Q-5 fixes no CLI/HTTP/endpoint/command/handler/
  framework/GUI/trigger, no coexistence, double detection, sequencing,
  source of truth, shared trigger, fallback, cutover or migration.
  Those REMAINS OPEN (§10.3). The receiver is conceptually independent
  of how CastleArq is activated.
- Q-7 independence: Q-5 decides no retry/fallback/degradation/
  recovery, no backend substitution, no error or execution policy, and
  no failure classification. It MAY receive an `IntegrationResult`
  whose entries/trace carry acquisition-error evidence (the B9.13
  contract preserves `OBSERVED` / `UNAVAILABLE` / `ERROR` end-to-end,
  §11.1) without reinterpreting it as operational policy. The full
  class-A policy is RATIFIED as FORWARD (Q-7, §11.3): such a result is
   forwarded to the receiver unchanged, keeping its failure semantics.
- No repository component is designated as the receiver: no existing
  Application/service/orchestration component is modified or claimed,
  and no new abstraction file is created by this decision. This
  section is the canonical record.
- No new invariant is introduced by Q-5: the boundary is already
  covered by I-04 (no evaluation imports), I-05 (no `EvaluationContext`),
  I-06 (trace verbatim, in-memory), I-10 (deterministic transport),
  I-Q9-08 (terminates at `IntegrationResult`) and I-Q9-09 (no
  stop-line crossing).

## 10. Legacy Coexistence / Dual Detection

### 10.1 Normative non-interference (resolved)

B9.14 MUST NOT alter `HardwareSnapshot`, `RuntimeStatus`,
`RuntimeCapability`, `CompatibilityEvaluator`, `RuntimeBackendSelector`,
or runner behaviour; MUST NOT replace, wrap, or bypass
`detect_hardware()` / `detect_runtimes()` / capability probes; MUST NOT
introduce cutover flags, fallback order, or unified detection; MUST NOT
make the new path authoritative; MUST NOT convert Observation into legacy
types. The legacy chain remains behaviourally unchanged until a later
ratified migration block changes it.

### 10.2 Dual-detection minimum (resolved rules)

- D-01. Independent execution of both paths is PERMITTED.
- D-02. One path MUST NOT implicitly trigger the other.
- D-03. Sequencing creates NO data dependency.
- D-04. Duplicated host observation is TOLERATED; deduplication deferred.
- D-05. The legacy path remains the SOLE execution authority.

Caching, deduplication, optimization, unified detection, and migration
are deferred (§15).

### 10.3 Decision: Q-6 Concrete Activation Contract (RATIFIED)

Q-6 is a HUMAN ARCHITECTURAL DECISION recorded here; it is not an
inference produced by the repository, and the evidence base does not
determine it by itself.

- Q-6 (RATIFIED — Concrete Activation Contract): the Q-4 abstract Host
  Boundary is concretized ONLY as a DIRECT-CALL boundary into the
  ratified Composition Root, and nothing more:
  - WHO activates: any external caller (test, future CLI/HTTP/GUI
    mechanism, embedded application call, or service invocation). The
    activator is NOT named, NOT fixed to a technology, and NOT created

    handler, web framework, entrypoint file, GUI toolkit, command

  - WHAT is invoked: the composition point exposed by

## 11. Failure Contract

### 11.1 Preserved epistemology (resolved)

B9.11 states preserved end-to-end: `OBSERVED` / `UNAVAILABLE` / `ERROR`,
orthogonal `NOT_OBSERVED`, coverage precedence AD-04, `value` / `detail` /
`source` rules, provenance verbatim. No new Observation state; `ERROR`
is never `UNSUPPORTED`; `NOT_OBSERVED` never collapses.

### 11.2 Two failure classes (resolved)

- Class A (expected external acquisition failures): recorded as data
  inside the returned context; the observer returns, never raises.
- Class B (programming / contract defects): propagate, never recorded.

### 11.3 Decision: Q-7 Class-A Failure Policy (RATIFIED — FORWARD)

Q-7 is a HUMAN ARCHITECTURAL DECISION recorded here; it is not an
inference produced by the repository, and the evidence base does not
determine it by itself.

- Q-7 (RATIFIED): the Class-A policy is FORWARD. A Class-A event is
  any expected external acquisition failure that B9.11 records as
  data inside the returned `EnvironmentContext` (the observer returns,
  never raises, §11.2). When such a context is captured, the wiring
  FORWARDS it into `integrate(context, registry)` and forwards the
  resulting `IntegrationResult` to the Q-5 receiver. There is NO abort
  path for Class-A: the invocation terminates normally at STOP with
  an observable `IntegrationResult` that preserves the Class-A
  evidence.
- Observable outcome: the `IntegrationResult` itself (entries /
  unmapped / trace per the B9.13 contract). It is observable by the
  Q-5 Post-Integration Receiver, which MUST preserve its semantics
  verbatim (accept / transport / deliver; no reinterpretation, §9.4).
  The outcome conserves the original cause/classification
  (`OBSERVED` / `UNAVAILABLE` / `ERROR`, orthogonal `NOT_OBSERVED`),
  the associated evidence detail, and provenance/trace end-to-end
  (§11.1, R-T1/R-T2). Forward ≠ accept/approve/success: a forwarded
  Class-A outcome keeps its failure semantics; it is data about a
  failure, not a successful observation.
- Propagation / termination: the flow continues unchanged —
  `Activation → Composition Root → capture_context() (Class-A
  recorded as data) → integrate(context, registry) →
  IntegrationResult → Q-5 Receiver → STOP`. Class-B (programming /
  contract defects) still propagates and never records (§11.2,
  unchanged). No new result type is created; `IntegrationResult`
  remains the normative contract.
- Explicit prohibitions (Q-7 introduces NONE of these): retry (no
  second capture, no context/registry/backend retry), fallback (no
  backend substitution, no CastleArq→legacy fallback, no alternative
  execution path), recovery / degradation / restart / remediation /
  circuit-breaker / backoff, backend/model selection or execution,
  `EvaluationContext` or any scoring/ranking/recommendation/decision,
  reclassification (`ERROR → UNAVAILABLE`, `ERROR → UNSUPPORTED`,
  `UNMAPPED → UNSUPPORTED`, Class-A → Class-B), context reuse /
  background refresh / snapshot reuse (Q-2 intact), registry
  switching or alternative datasets (Q-3 intact), second activation /
  second Composition Root / second Observation / second Integration
  (Q-6 intact), persistence / logging formats / HTTP codes / CLI exit
  codes / UI messages / event schemas (no transport decision is made;
  Q-7 is architectural, not transport).
- Abort is NOT ratified and MUST NOT be implemented: silently
  discarding a Class-A context would destroy origin, classification,
  evidence and provenance, contradicting §11.1–§11.2. The failure of
  an external probe is information to carry forward, not a reason to
  terminate the invocation.
- Class-B propagation is resolved (unchanged). The Q-9c adapters only
  ratify Observation-compatible error contracts; they do not add any
  policy beyond this FORWARD rule.
- I1 gating: Q-7 was the last explicit Q-gate before I1; its
  ratification does NOT execute I1 and does NOT authorize it by
  itself (at that step **I1 = NOT STARTED**); I1 is now **IMPLEMENTED** (§18). All other B9.14 gates remain in
  force (Q-9d allow-list §13, acceptance criteria §17, stop-line §12),
  and future decisions (Evaluation,
  activation technology, legacy migration, backend/model execution)
  stay outside Q-7; concrete receiver naming now belongs to Q-8
  (RATIFIED, §12), also outside Q-7.
- This section is the canonical record; no new specification file is
  created, no error-handler/retry/recovery/fallback module is created,
  and no code is written.
