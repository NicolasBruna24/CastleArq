# B9.56 — Continuous Validation Automation Decision

> **Verdict: `DECISION RATIFIED` — Option B (Basic CI) is ratified as a forward contract, with six hermeticity preconditions that must be discharged before the workflow is written. Option C (release gate) is DEFERRED to release/distribution work; Option D (lint) is DEFERRED to a separate block; Option E (broader platform matrix) is REJECTED.**

---

## 1. Executive Summary

**CastleArq does not have automated continuous validation.** OBSERVED: HEAD is
`d9d06d4`; `.github/workflows/` contains exactly one file, `release.yml`
(`.github/workflows/release.yml:1`), whose triggers are `push: tags` and
`workflow_dispatch` (release.yml:27-44); no step in it invokes `pytest`.
OBSERVED: there is no `conftest.py` anywhere in the tree, no `pytest.ini`, no
`[tool.pytest.ini_options]` beyond `pythonpath = ["."]`
(`pyproject.toml:52-53`), no markers, and no `skip`/`xfail`. OBSERVED: the
only branch is `main` plus `origin/main`. So the only execution evidence
CastleArq has ever produced is a local maintainer run on **Python 3.14.4** —
outside its own declared classifier range.

**Automation is ratified, and the matrix is the point.** The reason is not
convenience. B9.55 §6 established an asymmetry that documentation cannot fix:
everything CastleArq *declares* (3.10–3.13) is unverified, and the one
interpreter it *has* verified (3.14.4) it does not claim. A CI matrix over the
declared range is the only mechanism that converts a declaration into
evidence. Declining CI leaves that asymmetry permanent.

The minimum ratified contract is deliberately narrow: Linux only, the full
pytest suite, the declared Python range 3.10–3.13, `push` and `pull_request`
triggers, no release interaction, no lint, no runtime execution. CastleArq's
authority rule is unchanged: **validation failure > maintainer intent**.

Automation does **not** become effective at this commit. Six hermeticity
measurements recorded as PENDING in B9.55 §5.4 — none executed here — are
preconditions of the first implementation block. Ratifying the contract now and
implementing it only after those measurements is what keeps this decision from
creating false confidence.

## 3. Question reconstruction

**P1 — Existence.** Does CastleArq have automated continuous validation? No.
See §4.

**P2 — Minimum useful contract.** What is the smallest honest CI contract? See
§10: one workflow, Linux, full suite, declared Python range, two triggers, no
release coupling, no lint, no runtime execution.

**P3 — Authority.** If CI fails and the maintainer believes the change is
acceptable, CI wins. B9.55 §9.2's rule is carried forward **unchanged**; see
§9.2. No new principle is introduced.

**P4 — Release relationship.** CI failure must not be silently wired into
`release.yml` by this block. Validation contract, release transport and
publication policy are three distinct objects; see §9.4.

**P5 — Python matrix.** Is 3.10–3.13 the initial matrix? Yes — and the reason
is that the matrix must validate the *declared* claim, not the *observed* one.
See §5 and §10.3.

**P6 — pytest dependency.** Yes, pytest must become an explicit development
dependency, because a CI contract whose validator is undeclared is not
reproducible by anyone else. Implementation is a prerequisite, not a
consequence. See §9.6.

**P7 — Linting.** Not in this block. See §9.7.

**P8 — Platform matrix.** Linux only. See §9.8.

**P9 — Runtime boundary.** CI executes no real llama.cpp, no real GGUF, no
GPU/Vulkan, no external downloads. Default is no, and the evidence does not
argue otherwise. See §9.9.

**P10 — Hermeticity.** Six unresolved questions must remain preconditions.
Static inspection does not prove determinism, and this block does not claim it
does. See §9.10 and §10.7.

## 7. B9.44 reconciliation

B9.44 ratified a **transport** contract: annotated tag → manifest committed at
the tag → GitHub Release assets → SHA-256 gate → PyPI, with a fail-closed
`verify` job gating `publish` (release.yml:63-70, 200-209, 221). B9.44 also
deferred a scheduled PyPI digest check (§11.1, `:475-477`), which B9.55
deferred as its Option D.

**DECIDED: CI does not interact with the B9.44 contract in this block.** Three
objects stay separate:

* **Validation contract** — does the committed code pass the suite? Owner of
  this document.
* **Release transport** — are the published bytes the audited bytes? Owner of
  `release.yml` / B9.44.
* **Publication policy** — may this version be published at all? Owner of a
  future release/distribution decision.

INFERRED, stated explicitly because it is the tempting mistake: making CI a
`needs:` dependency of `release.yml` would look like rigor and would actually
couple two contracts that fail for unrelated reasons. It would also require
`release.yml` to check out code and run a suite on a tag-push event — a
material change to a chain whose stated justification is that it *never rebuilds
and never re-executes* anything (release.yml:5-11). A transport gate that also
executes code is no longer a transport gate. The B9.44 digest mechanism is not
revived, implemented or modified here; it stays deferred exactly as B9.55 left
it.

## 8. Automation options

### Option A — Keep B9.55 Option C (no automation)

Fits the current maturity and costs nothing, and the repository has lived with
it. Its fatal property is unchanged: the declared Python range has **zero**
execution evidence and cannot acquire any without automation, because a
maintainer's machine is not evidence about interpreters he does not run. This
option institutionalises the asymmetry B9.55 §6 identified. It is legitimate
and it is **not chosen** — not because CI is fashionable, but because it
cannot close the one gap that matters.

### Option B — Basic CI — **SELECTED**

One workflow, two triggers, full suite, declared Python range, Linux, nothing
else. It converts the declared range into evidence and makes the passing run a
public artifact instead of a recollection. Costs: one workflow file, a declared
dev dependency, and a bounded matrix. It does not touch the release chain, does
not lint, does not run llama.cpp, and does not attempt to prove anything about
hardware. Its weakness — that a green matrix is still not a runtime proof — is
handled by §10.6, not by pretending it away.

### Option C — CI + release gate

**DEFERRED to release/distribution work.** It is attractive because it sounds
strict, but it conflates the three objects in §7: it would make a *transport*
gate execute *code*, and it would make a green matrix a precondition of
publishing without ever having established that the matrix is the right gate
(it is not yet — six hermeticity questions are open). Deciding this before CI
has produced a single real run would be authoring policy against an untested
mechanism. Revisit only after §10.7 is discharged.

### Option D — CI + lint/static analysis

**DEFERRED to a separate block.** Three reasons. (i) There is no lint contract
today: no `[tool.ruff]`, no config file, no declared tool, and a locally
installed `ruff 0.16.7` that is ambient, not pinned. (ii) Adding a second gate
to a *first* CI adoption doubles the failure surface before the first gate is
trusted; if the matrix is flaky, you will not know whether lint or tests caused
it. (iii) Lint rules are a style policy decision, and folding them into a
validation-automation decision would mix two contracts. Lint belongs in its own
block, *after* CI is green and stable.

### Option E — Broader environment matrix (OS / runtime environments)

**REJECTED.** CastleArq is Linux-first by its own public statement
(`README.md:89,95,479-480`: "Linux is the exercised baseline"), its classifier
is `Operating System :: POSIX :: Linux` (`pyproject.toml:32`), and its runtime
code inspects Linux-specific surfaces (`/etc/os-release`, `/proc/meminfo`,
`platform.system() == "Linux"`, `app/hardware.py:326`). A Windows/macOS matrix
would mostly re-run mocks and would manufacture a green signal about platforms
the product explicitly does not claim — the precise false-confidence failure
this document exists to prevent. Adding GPU runners or a llama.cpp build to CI
is rejected for the same reason and additionally because it would put a heavy,
failure-prone third-party build inside the validation gate.

### Comparison against the decision criteria

*Architectural fit* — B is the only option that closes the declared-range gap
without touching a ratified contract. *Fail-closed identity* — B makes the
"refuse without evidence" posture auditable for the code, which is what the
product claims about itself. *Reproducibility* — B plus a declared `pytest`
(§9.6) is the first thing in this repository that makes the validation
reproducible by a third party. *Developer feedback* — B gives a public,
timestamped result on `main`; with one maintainer its value is evidentiary
rather than collaborative. *Maintenance cost* — B is one file; E is a
multi-OS, multi-interpreter surface that will rot. *False-confidence risk* — B's
risk is bounded by §10.6; C and E's risks are structural. *Maturity* — B fits a
0.1.x single-maintainer project; E does not. *Release compatibility* — B is
fully orthogonal to `release.yml`; C is invasive. *Validation vs runtime* — B
keeps the line crisp; E erases it. *Scope discipline* — B is the only option
that stays inside this block's mandate.

## 9. Decision

**DECISION: Option B is ratified. Options C and D are deferred; Option E is
rejected; Option A is not chosen.** The contract in §10 is the minimum, and it
becomes *implemented* only after §10.7 is discharged.

### 9.1 P1 — Existence

No automated continuous validation exists at `d9d06d4` (§4.1). B9.55's Option C
remains an accurate description of the tree; B9.56 replaces it as the target.

### 9.2 P3 — Authority

**Unchanged from B9.55 §9.2: validation failure > maintainer intent.** CI
failure is a validation failure and is governed by the same rule. A maintainer
who disagrees must not proceed silently: the only legitimate path is an
explicit, committed, documented decision that states the override and its cost.
This block does **not** propose changing the principle, so no new
architectural decision is created here. INFERRED justification, carried
forward: CastleArq's public identity is fail-closed admission; a fail-closed
product cannot exempt its own gate.

### 9.3 P2 — Minimum useful contract

Specified in §10. One workflow, one command, one matrix, one OS.

### 9.4 P4 — Release relationship

CI does **not** block tag creation or publication in this contract. The
distinction is deliberate: *validation* answers "does the code pass?", *release
transport* answers "are the published bytes the audited bytes?" (`release.yml`
/ B9.44), *publication policy* answers "may this version ship?". Only the
first is decided here. Making CI a release gate is Option C and is deferred
(§11.2). Until then the practical consequence is stated plainly: **a red matrix
does not mechanically prevent a tag** — §9.2 makes it a policy obligation on
the maintainer, and Option C is what would make it a mechanism.

### 9.5 Branch protection

Deferred with Option C (§11.2). Branch protection is meaningless until a check
exists to require; and for a single-maintainer repository with one branch,
protection against yourself has no adversarial value — its value would be purely
as a forcing function, which §9.2 already supplies as a policy.

### 9.6 P6 — pytest dependency

**DECIDED: `pytest` becomes an explicit development dependency** in the
implementation block, in a form that does not touch runtime dependencies
(`requirements.txt:1` must continue to say stdlib-only, and the runtime install
path must remain unchanged). Rationale: a validation contract whose validator is
undeclared is not reproducible by a third party — the exact defect B9.55 §4
recorded. Pinning is required for the version *and* for any plugin the contract
depends on; ambient local plugins (§4.2) must not leak into the contract by
accident. `pyproject.toml` was **not** modified in this block.

### 9.7 P7 — Linting

Deferred (§11.3), for the reasons in Option D. No lint tool is named, adopted
or configured here.

### 9.8 P8 — Platform matrix

**DECIDED: Linux only.** This matches the declared classifier
(`pyproject.toml:32`), the README baseline (`README.md:479-480`), and the
platform-specific code paths (`app/hardware.py:326`,
`app/observation_probe.py:394,457`). Broadening it is not "better"; it is a
different, unclaimed product.

### 9.9 P9 — Runtime boundary

**DECIDED: CI executes no real llama.cpp, no real GGUF model, no GPU/Vulkan, no
external model download.** The evidence supports this: the runtime paths are
mocked (`tests/test_chat_sessions.py:503-504`,
`tests/test_execution_integration.py:237`) and Vulkan probing is driven by
injected ICD lists (`tests/test_gpu_setup.py:116-137`). Real-runtime validation
remains the B9.36 drill's job, executed manually on the maintainer's machine —
a different activity from a commit-time gate, and conflating them would put a
heavy third-party build inside the gate.

### 9.10 P10 — Hermeticity

The suite is **not yet sufficiently characterised** for unconditional CI
adoption, and this document does not claim otherwise. Six measurements
(B9.55 §5.4) remain PENDING and become preconditions of the implementation
block (§10.7). Two known specifics must be handled there rather than
discovered there: the **loopback TCP listener**
(`tests/test_chat_sessions.py:270`) and the **three `git`-dependent, vacuous
tests** (`tests/test_api_serve_contract.py:344,367,456`).

## 10. Minimum ratified contract

This is a **specification for a future implementation block**. Nothing here was
implemented in B9.56.

### 10.1 Trigger

```text
on:
  push:      branches: [main]
  pull_request:
```

*DECIDED.* `main` is the only branch (`git branch -a`). Tag pushes are
explicitly **excluded**: tag-triggered test execution would blur the §9.4
separation between validation and release.

### 10.2 Platform

```text
runs-on: ubuntu-latest
```

Linux only (§9.8).

### 10.3 Python versions

```text
matrix: ["3.10", "3.11", "3.12", "3.13"]
```

The declared range exactly (§5). 3.14 is **not** added here; that is a metadata
decision (§11.1).

### 10.4 Test command and working directory

```text
working-directory: <repository root>
command: python -m pytest
```

The repository root is required because `pyproject.toml:52-53` sets
`pythonpath = ["."]`. The command is the one already documented in
`README.md:670-674`; the contract adds no new invocation.

### 10.5 Dependency installation

```text
1. install the package itself (editable or built) so `app` is importable
2. install a pinned development extra providing pytest (+ any plugin the
   contract depends on)
```

*DECIDED* per §9.6: the validator must be declared, and runtime dependencies
must remain stdlib-only.

### 10.6 Status and failure semantics

```text
status:   required
failure:  the run is red. Per §9.2, validation failure > maintainer intent.
```

The check is **required** for the validation contract to mean anything. It is
*not* wired to block publication — see §9.4.

**The contract states what CI does not prove.** A green matrix does not prove
GPU compatibility, llama.cpp compatibility, model compatibility, runtime
performance, hardware sufficiency, or behaviour on every Linux distribution.
CastleArq's runtime compatibility engine — its five-condition admission
contract — remains the only authority on those questions, and it operates at
runtime on real evidence, not in CI on mocks.

### 10.7 Preconditions of implementation (all currently PENDING)

The workflow must not be written until these are discharged by measurement:

1. Suite repeatability across repeated clean runs.
2. Order independence.
3. Environment isolation in a fresh venv with only declared dependencies.
4. Network isolation (confirm nothing needs egress; loopback is expected to
   work).
5. Interpreter matrix 3.10–3.13 — this *is* the contract's purpose.
6. Declared-validator bootstrap — the suite runs from a documented install
   command, which does not exist today because `pytest` is undeclared.

These are B9.55 §5.4 items 1–6, carried forward unchanged. None was executed
in B9.56.
