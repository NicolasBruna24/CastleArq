# B9.42 — Compatibility Engine Consolidation Audit

Status: **AUDIT ONLY — no code, tests or behavior were changed.**
Repository state at audit time: HEAD `18d15a9` (`main`), plus pre-existing
uncommitted changes from B9.39/B9.40/B9.41 (see §16).

---

## 1. Executive Summary

**Observed facts.**

1. CastleArq does contain two functionally named compatibility engines:
   * `assess_model()` — `app/compatibility.py:112-186` (legacy/operational engine).
   * `evaluate()` — `app/compatibility_evaluator.py:364-399` (strict B9.3 engine).
2. They do **not** have overlapping production authority today:
   * `assess_model()` is the **only** compatibility gate that controls real
     execution. It gates three production paths: `execute_model()`
     (`app/execute_model.py:297-303`), legacy `run_service.prepare()`
     (`app/run_service.py:201-211`, used by CLI `run`/`chat`, `POST /v1/run`,
     `POST /v1/chat/sessions`) and, via injection, the legacy
     `ModelExecutionService` (test-only construction today). It also feeds
     `RuntimeBackendSelector.select()` and the CLI `recommend` ranking.
   * The entire strict chain
     (`evaluate_model_compatibility → compose_evaluation → evaluate_strict → evaluate`)
     has **zero production callers**. No module in `app/` constructs an
     `EvaluationAdmission`; the CLI `execute` command passes
     `admission=None` (`app/main.py:1061`).
3. The rule sets barely overlap. `assess_model()` owns memory/VRAM/RAM
   feasibility, quantization choice, scoring and runtime/backend
   recommendation — none of which `evaluate()` performs. `evaluate()` owns
   identity, format, architecture, explicit runtime/backend knowledge and
   capability checks — none of which `assess_model()` performs. The only
   conceptual intersection is *runtime/backend support*, implemented twice
   over different data sources with different matching semantics.
4. Both engines operate on their own side of the ratified B9.8 boundary:
   `assess_model()` consumes operational `ModelSpec`; `evaluate()` consumes
   strict `Model`/`ModelArtifact` produced only through
   `evaluation_adapter.to_model()/to_artifact()`. A frozen test
   (`tests/test_execute_model.py::IsolationTests::test_no_evaluation_dependencies`)
   forbids the execution use case from importing any evaluation module.

**Architectural interpretation.** This is not "two engines with overlapping
authority". It is one *operational resource-feasibility gate* that is
currently authoritative, plus one *dormant, knowledge-based functional
evaluation engine* that is fully built, fully tested, and intentionally not
yet wired to any product surface. The relationship matches B9.39 §C-7's
"same catalog reasoned about twice, transititionally coexisting", but the
evidence shows **distinct responsibilities, not duplicated policy**.

**Recommendation (not implemented).** **Option A — Keep both.** Preserve the
boundary; do not merge, façade or extract shared policy. The next
implementation block should wire evaluation to execution through the
documented `EvaluateModelCompatibilityResult → EvaluationAdmission` adapter
gap (B9.23 §N), keeping `assess_model()` as the transitional gate until an
explicit cutover decision. See §13 and §14.

### 3.2 Behavior (rules implemented)

1. Runtime/backend combination selection: `_choose_runtime` requires an
   *available* runtime whose name fuzzy-matches `model.supported_runtimes`
   (`_same_name`, :284-285, substring matching both directions);
   `_choose_backend` requires an *available* backend in
   `model.supported_backends` that the runtime also supports (:258-271).
   No combination → `INCOMPATIBLE` (no runtime) or `UNKNOWN` (runtime but no
   backend) (:123-135).
2. Quantization selection: explicit `quantization` argument or
   `_best_quantization` (:136-138); none feasible → `UNKNOWN` (:139-144).
3. Memory estimation: `estimate_memory_bytes = parameter_count_b × 1e9 ×
   bits/8 × model_overhead` (:105-109); capacity from VRAM + RAM
   (:146, :239-248). Fit checks (:154-178):
   * `estimated ≤ safe_gpu` → `COMPATIBLE`;
   * else runtime supports CPU and `estimated ≤ safe_ram` → `MARGINAL`;
   * else → `INCOMPATIBLE` (or `UNKNOWN` when no capacity/runtime evidence).
4. Scoring (`_score`, :288-304) and recommendation
   (`recommended_quantization`, `recommended_runtime`,
   `recommended_backend`) — ranking policy, not present anywhere in the
   strict engine.

## 6. Execution and Evaluation Flows

### 6.1 Execution flow (actual control flow, traced)

```text
CLI execute (app/main.py:1054-1063)
  → compose_execute_model_dependencies()   (app/application_wiring.py:228-274;
                                            compatibility_provider deliberately
                                            LEFT UNSET — docstring :251-255)
  → execute_model(..., admission=None)     (app/main.py:1061)
      1. resolve ModelSpec + ArtifactSpec  (execute_model.py:276-286)
      2. fresh RuntimeCapability           (:289)
      3. _check_admission(None) → no-op    (:292)
      4. compatibility = _legacy_compatibility → assess_model (:297)
         if status ∈ {INCOMPATIBLE, UNKNOWN} → raise ExecutePreparationError
                                               (:299-303)  ← GATE
         preflight.validate(artifact)       (:305-311)
         selector.select(compatibility, ...) (:313-319)
      5. ExecutionRequest + validation → runner.run (:332-344)

CLI run/chat, POST /v1/run, POST /v1/chat/sessions
  → run_service.prepare → assess_model (run_service.py:201)
    → INCOMPATIBLE/UNKNOWN → PreparationError (:204-211)   ← GATE
    → preflight → selection → launch
```

Facts about `assess_model()` as gate:

* **It is a gate.** Execution is prevented (exception raised before
  preflight, selection and runner — frozen by
  `tests/test_execute_model.py::LegacyCompatibilityGateTests`).
* **Failure semantics:** `INCOMPATIBLE` and `UNKNOWN` reject; `COMPATIBLE`
  and `MARGINAL` proceed (`_REJECTING_COMPATIBILITY`,
  `app/execute_model.py:73-75`).
* **Result persistence:** none. The result is never written to disk, the
  manifest or any store; `warnings` are merged into the transient
  `ExecutionResult` (:321, :347-356) or raised in `PreparationError`.
* **User exposure:** warnings/reasons reach the user through CLI output,
  API errors, and the `recommend` ranking.
* **Additional policy beyond checking:** yes — scoring, quantization
  recommendation, runtime/backend recommendation (`_score`,
  `_best_quantization`, `_choose_runtime/_choose_backend`). The selector
  *depends* on `recommended_runtime`/`recommended_backend`
  (`app/selection.py:68-107`).

```text
(no production entry point today)
evaluate_model_compatibility(model_id, ...)      (app/evaluate_compatibility.py:90)
  → detect capability; capability.available is False → "blocked" (:109-117)
  → ModelArtifactResolver.resolve → failure → "blocked" (:126-137)
```

Facts about `evaluate()`:

* **It is an evaluator, not a gate.** It returns a result object; it never
  raises for "incompatible" (only `ValueError` for malformed input) and
  never prevents anything by itself.
* **Failures:** blocked preconditions are handled by the *application use
  case* (`"blocked"` status), not by `evaluate()`. B9.15 failures propagate
  unchanged (`evaluate_compatibility.py:167` comment).
* **Richer diagnostic:** yes — per-check `CompatibilityCheck` with
  expected/observed/evidence, plus conditions and warnings.
* **Authoritative for any production decision:** **no**. Zero production
  callers (§5.2). The nearest would-be consumer is the deny-only
  `EvaluationAdmission` parameter of `execute_model`, which nothing
  populates (`admission=None`, `app/main.py:1061`).

  model plausibly run, on which backend, with what recommendation?"*

  this artifact functionally compatible with this runtime context?"*
  (claim scoped by `app/compatibility_evaluator.py:18-24`: resource
  feasibility, performance and trust are explicitly **not** part of it).

## 8. Duplicated Policy Analysis

Suspected duplicates examined one by one:

| # | Rule | Location A | Location B | Equivalent? | Notes |
|---|---|---|---|---|---|
| 1 | "Backend must be supported" | `compatibility.py:258-271` (`_choose_backend`, fuzzy match, operational detection) | `compatibility_evaluator.py:308-334` (`_check_backend`, exact tri-state, declarative knowledge) | **No** — different data sources (detected statuses vs declared knowledge), different matching (substring vs exact), different outputs (`None` → status vs `FAILED/UNKNOWN` check) | Concept overlap only; error semantics differ entirely |
| 2 | "Runtime must be available/suitable" | `compatibility.py:251-255` + caller-side capability probes (`execute_model.py:201-211`) | `compatibility_evaluator.py:285-305` + `evaluate_compatibility.py:109-117` | **No** | Same concern, disjoint mechanisms |
| 3 | "Model fits in memory" | `compatibility.py:146-178` | — | not duplicated | no counterpart in `evaluate()` by design (B9.2/B9.3 scope) |
| 4 | "Format/architecture/identity/capabilities" | — | `compatibility_evaluator.py:190-361` | not duplicated | no counterpart in `assess_model()` |
| 5 | Reject on unknown/incompatible evidence | `execute_model.py:73-75, 299`; `run_service.py:204-207`; `execution_service.py:76-79`; `selection.py:109-119` (four *consumers* re-encode the reject set) | `evaluation_policy.py` D-10.1 (`INSUFFICIENT_EVIDENCE → ESCALATE`, non-authorizing) | Roughly aligned intent, different vocabularies | This is duplication **among consumers of `assess_model`**, not between the two engines; out of scope for engine consolidation and noted as an observation only |

**Shared lower-level primitive already available?** None. There is no common
rule module, predicate or value both engines call: `assess_model` uses
`RuntimeStatus/BackendStatus` + arithmetic; `evaluate` uses
`RuntimeKnowledge` tri-state checks. The only shared import universe is the
type layer (`HardwareSnapshot` appears in both but is *unread* by
`evaluate`).

**Conclusion (interpretation).** No duplicated compatibility *policy* exists
between the two engines — only a duplicated *subject* (the same catalog
entry is reasoned about twice). Rules #1/#2 are the closest to duplication
and are deliberately implemented over different evidence sources on each
side of the B9.8 boundary.

## 9. Authority Analysis

| Question | Answer (fact-based) |
|---|---|
| Can `assess_model()` reject an execution `evaluate()` would accept? | **Yes.** Example scenario A (below). |
| Can `evaluate()` reject something `assess_model()` accepts? | **Yes in isolation, but it cannot reject any production execution today** — it has no production caller. |
| Can they produce contradictory answers? | **Yes** — scenarios A and B below. Not observable in production today because the strict chain is unreachable from product surfaces. |
| Which result controls production execution? | **`assess_model()` only** (`execute_model.py:297-303`, `run_service.py:201-211`). |
| Is either result merely diagnostic? | `evaluate()`'s result is *entirely* non-controlling (test-only). `assess_model()`'s score/recommendations are diagnostic for `recommend`; its `status` is controlling for execution. |
| Any persisted compatibility decision? | **None found.** Neither engine writes its result to any store/manifest (consistent with B9.41: manifest state is not authoritative). |
| Is one engine used only as a precondition check? | `assess_model` is a precondition gate **and** a selection input **and** a ranking function. `evaluate` is currently neither — it is dormant. |

**Concrete divergence scenario A (assess rejects, evaluate would accept):**
A 70B model with unknown/low VRAM and no safe RAM fit →
`compatibility.py:167-178` yields `INCOMPATIBLE` (or `UNKNOWN` at :139-152)
→ `execute_model` raises at :299-303 → no execution. The strict engine,
given `RuntimeKnowledge` where format, architecture and backend are all
explicitly supported and the required capability is `True`, aggregates all
checks `PASSED` → `COMPATIBLE` (`compatibility_evaluator.py:393-398`) —
because it deliberately never reads hardware. Had an admission been wired,
the two answers would contradict.

**Concrete divergence scenario B (assess accepts, evaluate would reject):**
A small model whose `parameter_count_b` fits `safe_gpu` → `assess_model`
returns `COMPATIBLE` (`compatibility.py:159-162`) — it never inspects format
or architecture. If the knowledge base explicitly lists the artifact format
(or architecture) as unsupported, `_check_format`/`_check_architecture`
yields `FAILED` → strict `INCOMPATIBLE`. Today the mismatch is caught
later, partially, by the selector's format check (`selection.py:75-81`).

**Interpretation.** There is a *latent* contradiction risk, but no
*current* overlapping authority: one engine decides, the other does not run.
The architectural risk is precisely what a future admission wiring must
reconcile (which verdict wins), and B9.19 §7 already defines the answer:
admission may only *deny*; it can never authorize on its own.

## 13. Architectural Decision

```text
B9.42 VERDICT
```

1. **Are there currently two compatibility engines?** Yes — structurally
   two (`app/compatibility.py:112` and `app/compatibility_evaluator.py:364`),
   but only one (`assess_model`) has production authority.
2. **Do they contain duplicated compatibility policy?** No. The rule sets
   are disjoint except for the *concepts* of runtime and backend support,
   which are independently encoded over deliberately different evidence
   sources (detected operational statuses vs declared knowledge) with
   different matching and result semantics (§8). There is no shared policy
   primitive to extract.
3. **Do they have distinct responsibilities?** Yes. `assess_model` =
   operational resource feasibility + recommendation + ranking (includes
   policy `evaluate()` intentionally lacks: hardware/memory — B9.2/B9.3
   scope excludes resource feasibility). `evaluate` = knowledge-based
   functional compatibility interpretation with evidence-bearing checks
   (includes policy `assess_model` lacks: identity, format, architecture,
   explicit capabilities).
4. **Which component is authoritative for execution?** `assess_model()`,
   via three gates (`execute_model.py:297-303`, `run_service.py:201-211`,
   and the injectable `ModelExecutionService.execute`). The strict chain is
   authoritative for **nothing** in production today; `EvaluationAdmission`
   is a cut but unwired seam (`admission=None` at `app/main.py:1061`).
5. **Is consolidation justified?** **No — not of the engines.**
6. **If yes, what?** Not applicable for the engines. The one consolidation
   that *is* justified is at the **gate seam**, not inside either engine:
   the documented gap `EvaluateModelCompatibilityResult →
   EvaluationAdmission` (B9.23 §N, `docs/B9.23-...md:682-684`).
7. **If no, what boundary must be preserved?** Preserve: (a) the B9.8
   operational→strict adapter as the only bridge; (b) the frozen isolation
   of `execute_model` from evaluation modules; (c) the selector's exclusive
   dependency on the legacy `CompatibilityResult` shape; (d) the deny-only,
   deny-by-default semantics of `EvaluationAdmission`; (e) B9.39's two
   canonical representations.
8. **What should the next implementation block do?** See §14.
9. **What must explicitly remain untouched?** See §15.

## 14. Recommended Next Block

Recommendation only — **not implemented in this block**:

1. **Expose an evaluation product surface** (CLI/API use case) that calls
   `evaluate_model_compatibility(...)` and presents
   `EvaluateModelCompatibilityResult` (`status`, `evaluation.result`,
   checks/evidence). This closes the "evaluation unreachable from product"
   gap recorded in B9.23 §4.
2. **Implement the result→admission adapter** (the B9.23 §N documented
   gap): map `EvaluateModelCompatibilityResult` to `EvaluationAdmission`
   for callers that want the strict signal to *deny* execution through
   `execute_model(admission=...)`. Respect the vocabulary already frozen in
   `execute_model.py:69` (`compatible`, `compatible_with_conditions` admit;
   everything else denies) and the deny-only rule of B9.19 §7.
3. **Keep `assess_model()` as the transitional gate** exactly as B9.19 §7
   specifies ("admission=None means this gate is the only gate"). A
   cutover decision (making strict admission mandatory, then retiring the
   legacy gate) is a *separate future block* requiring behavior migration
   of: the selector's inputs, `recommend`, `run_service.prepare`, and the
   four reject-set consumers noted in §8 #5.
4. **Do not** merge, façade, rename, move or extract anything inside the
   two engines in the next block.
