```text
  -- proyección futura explícita -->
```

## B9.46.7 — N-1 Refinement Ratification

### Regla N-1 original

B9.8 y B9.39 redactaron originalmente la regla como:

```text
ArtifactSpec.artifact_id / ArtifactSpec.model_id
    -> ModelArtifact.identifier = None
```

La intención original era evitar fabricar una identidad estricta a partir de una identidad operacional ambigua y evitar un FAILED determinante espurio. La implementación actual conserva esa redacción y `to_artifact()` todavía deja `identifier=None`.

### Motivo del refinamiento

B9.46.6.baomidouó una diferencia semántica que la redacción original agrupaba:

* `ArtifactSpec.artifact_id` es identidad física/local de la variante;
* `ArtifactSpec.model_id` es una referencia explícita al modelo lógico;
* `ModelIdentity.model_id` es la identidad lógica evaluada.

El refinamiento no elimina la prohibición de fabricar identidad. Sólo permite transportar una referencia lógica ya existente y explícita, sin convertir la identidad física en lógica.

### Regla N-1 refinada y ratificada

```text
N-1 (refined)

artifact_id -> ModelArtifact.identifier
    PROHIBIDO

filename/path/checksum/name -> ModelArtifact.identifier
    PROHIBIDO

ArtifactSpec.model_id -> ModelArtifact.identifier
    PERMITIDO

ModelSpec.id -> ModelArtifact.identifier
    sólo indirectamente mediante ArtifactSpec.model_id
```

La proyección permitida no crea una identidad nueva: conserva en el dominio strict la referencia explícita que ya existe en `ArtifactSpec.model_id`.

La redacción antigua que decía que `model_id` también debía producir siempre `None` queda sustituida por esta regla refinada para el contrato de identidad lógica. `artifact_id` permanece siempre fuera de `ModelArtifact.identifier`.

### Identidad lógica vs identidad física/local

La identidad lógica es la relación que el strict check necesita:

```text
ModelIdentity.model_id
ModelSpec.id
ArtifactSpec.model_id
ModelArtifact.identifier
```

La identidad física/local es independiente:

```text
ArtifactSpec.artifact_id
  -> ModelStore
  -> Resolver
  -> Preflight
  -> storage paths
  -> manifest location
```

Ambas referencias puedenFFE coexistir para el mismo artifact. No deben fusionarse, renombrarse ni compararse entre sí. `ModelStore` conserva su ownership; la proyección strict no altera el manifest ni el estado derivado.

### Límites del refinamiento

El refinamiento:

* no cambia el significado de `artifact_id`;
* no convierte `artifact_id` en identidad lógica;
* no introduce fallback desde `name`;
* no infiere identidad desde filename;
* no usa checksum como identidad;
* no usa path como identidad;
* no altera ownership de `ModelStore`;
* no altera ownership de `ModelArtifact`;
* no elimina la separación `ModelSpec/ArtifactSpec` vs `Model/ModelArtifact`;
* no requiere una nueva representación;
* no requiere registry;
* no requiere manager;
* no requiere servicio adicional.

### Comportamiento ante ausencia

La referencia lógica sólo puede proyectarse si está explícitamente presente:

```text
ArtifactSpec.model_id presente
    -> ModelArtifact.identifier puede proyectarse

ArtifactSpec.model_id ausente
    -> identifier permanece ausente/unknown
```

No se permite ningún fallback:

```text
model_id missing
    -> fallback name
    -> fallback artifact_id
    -> fallback filename
    -> fallback path
    -> fallback checksum
```

### Compatibilidad con `_check_identity`

Después del refinamiento, el check representa:

> El artifact evaluado declara explícitamente el mismo `model_id` que el modelo lógico evaluado.

No representa:

* igualdad entre artifact físico y modelo;
* igualdad entre `artifact_id` y `model_id`;
* validación de checksum;
* validación de estado;
* validación de path.

El check sigue siendo:

```text
ModelIdentity.model_id == ModelArtifact.identifier
```

La diferencia es que el campo transports ahora una referencia lógica explícita, no un valor físico inventado.

### Impacto esperado de la futura implementación

La implementación futura queda limitada conceptualmente a `evaluation_adapter.to_artifact()`:

```text
ModelArtifact.identifier = spec.model_id
```

en lugar de dejar siempre `None`. No se modifica `artifact_id`, ModelStore, el resolver, preflight, el selector o el runner.

Tests futuros mínimos:

1. model_id coincidente: identity puede pasar;
2. model_id ausente: identity permanece UNKNOWN/deny según strict;
3. model_id distinto: identity mismatch;
4. `artifact_id` nunca se utiliza como identifier;
5. ownership y state preservados;
6. ALLOW y DENY permanecen separados.

Estos tests no se implementan en B9.46.7.

### Decisión

La documentación permite ratificar formalmente el refinamiento sin contradecir la separación de representaciones, ownership o arquitectura de gates. El código actual todavía requiere el cambio futuro de proyección; este bloque no lo realiza.

**VERDICT = N1-REFINEMENT-RATIFIED**

No modificar producción, tests, `evaluation_adapter.py`, `ModelSpec`, `ArtifactSpec`, `ModelArtifact`, `ModelIdentity`, `EvaluationAdmission`, `ModelStore`, `RuntimeBackendSelector`, runner, UNKNOWN, insufficient_evidence ni deny-by-default. No crear B9.46.8. No commit. No push.

## B9.46.14 — Physical Artifact Evidence Representation Decision

### Decision

A minimal representation of observed physical artifact evidence is architecturally necessary. No existing representation can carry the fact without changing its semantics. The representation is conceptual only in this block; no class, parser, field, service, registry, manager or implementation is created.

```text
VERDICT = PHYSICAL-ARTIFACT-EVIDENCE-CONTRACT-RESOLVED
```

### Source, owner, producer and consumer

```text
SOURCE =
  GGUF metadata key `general.architecture`

OWNER =
  physical artifact evidence representation

PRODUCER =
  read-only physical inspection boundary

CONSUMER =
  existing evaluation boundary that supplies strict architecture evidence
```

The producer reads the physical GGUF. The owner is the minimal evidence value itself, not ModelStore, ModelSpec, ModelArtifact or the manifest. The consumer is the existing evaluation composition path; the adapter remains a pure representation boundary and does not open files.

### Representation

The representation represents only:

```text
one observed physical-artifact fact:
  GGUF general.architecture
```

It does not represent:

* catalog/model metadata;
* filesystem state;
* artifact identity;
* logical model identity;
* compatibility conclusions;
* tokenizers, context length, tensor metadata, quantization or other GGUF fields;
* state or verification authority.

It is distinct from:

```text
ModelSpec.architecture
```

which remains declared logical/catalog metadata, and from:

```text
ModelArtifact.identifier
```

which remains the logical model reference refined by N-1.

### Minimal fields

The conceptual minimum is:

```text
architecture_raw: str | None
architecture_provenance: fixed/source marker for GGUF general.architecture
```

For this first contract, `canonical=raw` and `normalization=NONE`; a separate canonical field is not justified. The source marker must preserve the distinction between `GGUF general.architecture` and `ModelSpec.architecture`.

No filename, model name, repository, artifact id, checksum, quantization, runtime, backend or CLI value is a source.

### Provenance

The evidence must retain provenance that it came from:

```text
physical GGUF metadata: general.architecture
```

The provenance is observational and read-only. It is not a trust score, assertion, compatibility decision, or authority for the manifest.

### Lifecycle

```text
derive during physical inspection
-> consume during evaluation
-> discard after evaluation unless a future contract explicitly requires retention
```

The evidence is not persisted in the manifest and is not state. The physical GGUF remains the authority for the observed property.

### Persistence

```text
PERSISTENCE = NONE in this contract
```

A future cache would require a separate invalidation/provenance decision. Persisting the value in `ArtifactSpec` or manifest would risk making a stale observation look like current physical truth.

### ModelSpec relation

```text
ModelSpec.architecture = "Transformer"
GGUF evidence architecture_raw = "qwen2"
```

These are distinct concepts and must remain separate. The physical value must never replace or overwrite the catalog value.

### ModelArtifact relation

The physical evidence is outside `ModelArtifact` until the existing evaluation boundary explicitly maps it to the strict architecture fact required by the evaluator. `ModelArtifact` is not made a physical metadata container merely because it is a strict artifact representation. The later implementation must preserve provenance during that projection.

### Identity relation

The representation carries no identity:

```text
ArtifactSpec.model_id -> ModelArtifact.identifier
```

remains unchanged, and:

```text
ArtifactSpec.artifact_id
```

remains the physical/local identity used by ModelStore, Resolver, Preflight and storage. The evidence cannot be used as either identity.

### Evaluation transport

The conceptual flow is:

```text
physical GGUF
  -> read-only physical inspection
  -> physical artifact evidence
  -> existing evaluation composition boundary
  -> strict Model architecture evidence
  -> Knowledge / _check_architecture()
```

The evaluation adapter remains pure. It receives already-derived evidence through an existing or subsequently ratified boundary; it does not parse GGUF, inspect paths, or become a metadata loader.

### Minimality rationale

A new conceptual representation is necessary because the fact is simultaneously:

* not catalog metadata;
* not filesystem state;
* not artifact identity;
* not strict ModelArtifact metadata by existing contract;
* not manifest/acquisition metadata.

The representation is minimal because it carries only the one required observation and its provenance. It avoids a general metadata subsystem, duplicate authority, persistence schema, second pipeline and new authority.

### Explicit non-goals

No implementation, parser, class, field, method, API, service, manager, registry, manifest change, Knowledge change, evaluator change or adapter change is included. No E2E execution, commit or push is performed.


## B9.46.13 — Architecture Metadata Representation Decision

### Opción A — Extender ArtifactSpec

`ArtifactSpec` representa el artifact operacional/declarativo: identidad lógica, source/repository locator, filename, formato, quantization, URL, tamaño, checksum y state de transporte. Su semántica actual mezcla metadata de adquisición/declaración, pero no tiene provenance de inspección física ni un campo para metadata estructural del contenido.

Añadir `general.architecture` a `ArtifactSpec` no es una extensión semánticamente neutral:

* convertiría un dato leído del archivo en metadata del spec operacional;
* obligaría a decidir si se persiste o se recalcula;
* podría hacer que downloader/store presentaran una observación física como metadata de adquisición;
* affectaría el contrato round-trip de manifests y resolver, aunque `artifact_id` no incluyera el nuevo valor.

`ArtifactSpec` podría ser una representación de transporte futura, pero no es una representación existente cuya semántica ya autorice中加入 metadata GGUF derivada. No se adopta automáticamente.

### Opción B — Extender ArtifactFilesystemInspection

`ArtifactFilesystemInspection` representa exclusivamente:

```text
final_exists
partial_exists
state = clean | partial | final_exists | inconsistent
```

Su responsabilidad es seguridad y disponibilidad del filesystem. No contiene metadata de contenido ni provenance. Añadir `general.architecture` mezclaría estado de ejecución local con facts del header del artifact y no mostraría por sí solo cómo transportar el dato al boundary de evaluación.

La opción B sólo es una dirección de owner, no una representación existente resuelta. El punto físico correcto sigue siendo el inspector, pero su contrato actual no transporta metadata estructural.

### Opción C — Extender ModelArtifact / ModelArchitecture

`ModelArtifact` es la variante strict del artifact. `ModelArchitecture` es la descripción estructural del modelo lógico en el dominio B8. La implementación actual toma `ModelArchitecture.architecture` desde `ModelSpec.architecture`, no desde el artifact físico.

Añadir `qwen2` a `ModelArchitecture` o `ModelArtifact` sin una regla de provenanceAllowaría mezclar:

```text
ModelSpec.architecture="Transformer"  (catálogo/modelo lógico)
GGUF general.architecture="qwen2"       (artifact físico)
```

en un mismo campo conceptual. No se resuelve cómo conservar ambos facts ni cómo habría que conectarlos, por lo que la opción no puede adoptarse sin una decisión de dominio y un boundary de provenance.

### Opción D — Persistir `general.architecture` en manifest

B9.41 establece que el manifest conserva metadata declarada y adquisición, mientras el estado local es derivado. Persistir `general.architecture` sin una regla de cache/provenance crearía una posible segunda autoridad frente al archivo GGUF real: si el artifact se reemplaza, el manifest podría quedar desactualizado.

La persistencia sólo sería válida si se ratifica explícitamente que el campo es metadata declarada, o si se acepta una cache derivada con invalidación/provenance. El repositorio no contiene esa decisión. No se adopta.

### Pregunta crítica

Ninguna representación existente es actualmente semánticamente adecuada:

* `ArtifactSpec`: metadata operacional/declarada, no evidencia física de header;
* `ArtifactFilesystemInspection`: estado de filesystem, no metadata estructural;
* `ModelArtifact`/`ModelArchitecture`: dominio strict del modelo, no owner de observación física;
* `Manifest`: metadata declarada/adquisición, no autoridad física del contenido.

Por tanto no se puede elegir una representación existente sin redefinir su contrato.

```text
ARCHITECTURE-METADATA-OWNER =
  read-only physical artifact inspection layer

ARCHITECTURE-METADATA-REPRESENTATION =
  no existing representation is semantically adequate

ARCHITECTURE-METADATA-INSPECTION-POINT =
  an existing physical inspection point must be designated, but none currently transports metadata

ARCHITECTURE-METADATA-TRANSPORT =
  not defined without a ratified representation

ARCHITECTURE-METADATA-PERSISTENCE =
  not defined; must not default to manifest authority

ARCHITECTURE-METADATA-PROVENANCE =
  must distinguish physical GGUF observation from ModelSpec.architecture
```

### Contrato pendiente

Antes de implementar debe ratificarse una decisión sobre la representación que transportará el resultado de una inspección GGUF read-only y su provenance hacia el boundary de evaluación. Esa decisión puede reutilizar una representación existente sólo después de cambiar explícitamente su semántica; no se crea aquí una clase, método, parser, manager ni servicio.

El flujo contractual requerido es:

```text
GGUF
  -> designated physical inspection point
  -> ratified metadata representation + provenance
  -> existing evaluation boundary
  -> Model/architecture evidence
  -> strict _check_architecture()
```

### Límites preservados

No se altera:

```text
ArtifactSpec.model_id -> ModelArtifact.identifier
```

`artifact_id` sigue siendo identidad física/local. `evaluation_adapter.to_model()` sigue siendo un boundary puro, no un inspector. No se modifica Knowledge, evaluator, ModelStore, resolver, preflight, backend, admission ni runner.

### Verdict

```text
METADATA-REPRESENTATION-BLOCKED
```

Las opciones existentes son conceptually plausibles en parte, pero ninguna tiene un contrato ratified paraftyfar metadata física `general.architecture`. Se requiere ratificar una representación/provenance antes de implementar; no se modifica código ni se ejecuta E2E.


## B9.46.12 — GGUF Architecture Metadata Transport Contract

### Flujo real auditado

```text
download/acquisition
  -> Downloader publica el archivo físico
  -> ModelStore.save_manifest() persiste metadata declarada
  -> ModelStore.inspect_manifest() deriva estado desde filesystem/checksum
  -> ModelArtifactResolver selecciona ArtifactSpec
  -> evaluate_model_compatibility recibe ModelSpec + ArtifactSpec
  -> evaluation_adapter.to_model() construye Model
  -> strict _check_architecture()
```

El downloader no parsea metadata GGUF. `ModelStore` no la parsea. `ModelArtifactResolver` no lee el archivo. `ArtifactExecutionPreflight` valida existencia, regularidad, tamaño y checksum, pero no devuelve metadata de header. `evaluation_adapter` es puro y no recibe el path físico.

### Representaciones existentes

| Opción | Evaluación |
|---|---|
| ArtifactSpec | Es la representación operacional del artifact y podría ser la extensión mínima para un dato declarado/derivado, pero actualmente sólo contiene identidad, provenance, filename, format, quantization, size, checksum y state. No contiene `general.architecture`; el manifest tampoco tiene campo para él. |
| ModelArtifact | Es la representación strict consumida por el evaluator, pero sólo contiene precision, quantization, identifier, format y storage size. No tiene campo de raw architecture ni provenance de artifact. |
| Estructura existente de metadata | `ArtifactFilesystemInspection` sólo representa estados `clean/partial/final_exists/inconsistent`; no transporta metadata de contenido. `ModelProvenance` es metadata lógica declarada del modelo, no GGUF físico. No existe otra estructura reutilizable. |
| Nueva representación | No se crea en este bloque. Sería una decisión arquitectónica nueva, no una extensión existente. |

### Fuente y propietario

```text
ARCHITECTURE-METADATA-SOURCE =
  GGUF metadata: general.architecture

ARCHITECTURE-METADATA-OWNER =
  conceptually, artifact inspection/physical artifact layer

ARCHITECTURE-METADATA-INSPECTION-POINT =
  no existe todavía un punto de inspección GGUF conectado al flujo

ARCHITECTURE-METADATA-REPRESENTATION =
  no existe todavía una representación operational existente para general.architecture
```

El owner correcto es la capa que inspecciona el archivo físico, porque `ModelSpec.architecture` es metadata declarada del catálogo y `ModelArtifact` es una proyección strict, no un inspector. Sin embargo, el owner no puede cumplir el transporte mientras no exista un campo o estructura de salida existente.

### Relación con ModelSpec

`ModelSpec.architecture="Transformer"` y `GGUF general.architecture="qwen2"` son conceptos distintos:

* `ModelSpec.architecture` es metadata declarada del catálogo/modelo lógico.
* `general.architecture` es metadata estructural del artifact GGUF real.

No se reemplaza `Transformer` por `qwen2` manualmente. `Transformer` puede permanecer como clasificación del catálogo; `qwen2` debe viajar como evidencia física separada hasta que exista una decisión de representación.

### Persistencia

No se persiste `general.architecture` en el manifest actual. El modelo B9.41 define manifests como metadata declarada + adquisición, mientras el estado local es derivado. La evidencia de header debe derivarse durante una inspección read-only del artifact y no convertirse en autoridad de state. Persistirla requeriría una decisión explícita sobre si es metadata declarada, cache derivada o evidencia de inspección; el repositorio no contiene esa decisión.

### Transporte requerido

La dirección válida es:

```text
GGUF general.architecture=qwen2
  -> artifact inspection result/read-only
  -> ArtifactSpec extension OR existing artifact representation
  -> evaluation boundary that carries the fact
  -> Model architecture representation required by strict check
  -> _check_architecture()
```

El punto `evaluation_adapter.to_model()` no puede hacerlo por sí solo porque es puro y no recibe path ni artifact metadata. Tampoco puede hacerlo `ModelArtifact` sin una decisión de dominio para representar raw artifact architecture.

### Persistencia de identidad

La decisión no altera:

```text
ArtifactSpec.model_id -> ModelArtifact.identifier
```

ni el significado de:

```text
ArtifactSpec.artifact_id
```

`artifact_id` sigue siendo la identidad física/local usada por ModelStore, Resolver, Preflight y storage. La metadata `general.architecture` no se usa como identidad.

### Decisión

La dirección de owner e inspección está suficientemente clara, pero la representación y el transporte no tienen una opción existente ratified. No es correcto elegir silenciosamente entre:

* extender `ArtifactSpec` con metadata física;
* extender `ArtifactFilesystemInspection`;
* añadir un campo de ModelArchitecture/ModelArtifact;
* persistir `general.architecture` en manifest.

Cada opción cambia el contrato operational o strict y requiere una decisión arquitectónica explícita. No se implementa ninguna.

```text
VERDICT = METADATA-TRANSPORT-PARTIAL
```

La siguiente implementación debe cerrar primero la elección de representación existente y mantener `evaluation_adapter` como boundary puro. No se debe modificar Knowledge hasta que el dato real llegue correctamente al strict input.


## B9.46.11 — Architecture Contract Implementation

### Resultado de la inspección

No existe actualmente un punto de integración arquitectónicamente válido para transportar `general.architecture` al strict evaluator sin crear una nueva abstracción o ampliar unauthorised el modelo de metadata.

Evidencia:

* `ModelSpec.architecture` existe, pero es metadata de catálogo y contiene `Transformer`; no representa el artifact físico y no se deriva del GGUF.
* `ModelArchitecture.architecture` es el campo strict de salida; el adapter lo obtiene exclusivamente de `ModelSpec.architecture`.
* `ArtifactSpec` contiene identidad, provenance, filename, format, quantization, size y checksum, pero no contiene metadata GGUF ni `general.architecture`.
* `ModelArtifact` no tiene campo para raw architecture metadata ni para provenance de artifact; sus campos actuales son precision, quantization, identifier, format y size.

```text
    -> no existe punto de adapter que reciba la metadata física
    -> strict evaluator continúa recibiendo ModelSpec.architecture="Transformer"
```

El primer punto donde `qwen2` deja de estar disponible es la frontera entre la inspección física del GGUF y `ModelSpec`/`ArtifactSpec`: el repositorio no conserva ni conecta `general.architecture`.

### Opciones descartadas en este bloque

* No se reemplaza `ModelSpec.architecture` manualmente por `qwen2`; eso no probaría lectura del artifact.
* No se infiere desde filename, nombre, repositorio, quantization, runtime o backend.
* No se crea un `MetadataService`, `GGUFMetadataService`, `ArchitectureRegistry`, `ArchitectureManager`, nuevo domain object, segundo adapter ni pipeline paralelo.
* No se añade `qwen2` a Knowledge sin conectar la evidencia real.

### Verdict

```text
ARCHITECTURE-INTEGRATION-BLOCKED
```

El contrato de B9.46.10 está resuelto (`qwen2` raw y canonical, sin normalización), pero su implementación no puede realizarse dentro del alcance actual porque falta un punto existente para conservar y transportar la metadata física sin crear una abstracción nueva.

1. dónde se persistirá o transportará `general.architecture` dentro de la representación operacional existente;
2. qué componente existente realizará la lectura GGUF, sin crear un servicio paralelo;

No se modificó producción, Knowledge, tests, adapter, evaluator, ModelStore, resolver, preflight, backend, admission ni runner.

### Semántica actual de Architecture

`ModelArchitecture.architecture` representa la descripción estructural declarada del modelo. `RuntimeKnowledge.supported_architectures` contiene identidades canónicas de arquitectura física con matching exacto. No representa family comercial, nombre de modelo, runtime ni backend.


### Opciones consideradas

* **A — reconocer `qwen2` explícitamente:** preserva la identidad física primaria sin normalización. Requiere ampliar Knowledge y conectar la provenance del artifact al Model strict en un bloque posterior.
* **B — normalizar `qwen2 -> qwen3`:** rechazada. No existe contrato, fuente ni equivalencia semántica ratified; pertenecer a la familia Qwen no demuestra igualdad de architecture.

* **D — mantener UNKNOWN:** técnicamente fiel al Knowledge actual, pero no representa la mejor decisión contractual porque la metadata primaria sí declara `qwen2` y la opción A es exacta.

### Decisión

Se decide **Opción A**:

```text
ARCHITECTURE-CONTRACT-DECISION = A
ARCHITECTURE-SOURCE = GGUF metadata general.architecture
ARCHITECTURE-RAW = qwen2
ARCHITECTURE-CANONICAL = qwen2
ARCHITECTURE-NORMALIZATION = NONE
ARCHITECTURE-AUTHORITY = physical artifact metadata, with Knowledge provenance
```

La autoridad primaria es la metadata estructural del artifact. La Knowledge declara si ese valor está soportado por el runtime; no redefine ni transforma el valor. La conexión futura debe conservar `qwen2` como valor canónico exacto.

```text

  -> artifact metadata/provenance
```
