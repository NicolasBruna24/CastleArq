# B9.46.28 — Runtime Execution Evidence Production Contract

## 1. Executive Summary

La ejecución real comienza en `LlamaCppRunner.run()`. CastleArq puede demostrar que construyó un comando con un artifact path concreto, intentó lanzarlo y recibió un resultado de proceso. El código actual no expone una señal estructurada de que llama.cpp haya cargado el GGUF ni de que haya ejecutado una inferencia específica con ese archivo.

Por tanto, el contrato mínimo debe separar `INVOCATION_STARTED` de cualquier afirmación de consumo. `exit_code == 0` prueba que el proceso terminou con código cero, no por sí solo que el artifact fue cargado ni que produjo inferencia. Un assertion de consumo sólo puede rise a partir de evidencia runtime observada y clasificada; hoy esa evidencia no está disponible como campo productivo.

## 2. Execution Boundary

El flujo confirmado es:

```text
execute_model
  -> resolve model/artifact
  -> fresh RuntimeCapability
  -> _check_admission
  -> operational compatibility
  -> ArtifactExecutionPreflight
  -> RuntimeBackendSelector
  -> ExecutionRequest validation
  -> ModelRunner/LlamaCppRunner.run
  -> ExecutionResult
```

Eventos demostrables:

- **Capability**: se obtiene una capability fresca y se exige que sea invocable.
- **Admission**: se comprueba antes de cualquier validación/selección; puede negar.
- **Compatibility/preflight**: se evalúa compatibilidad operacional y se valida filesystem/tamaño/checksum.
- **Backend**: el selector produce `ExecutionTarget(runtime, backend)`.
- **Command**: `LlamaCppRunner` construye argv con executable, `cli`, `--model`, `str(executable_artifact.path)`, `--device`, prompt y `--single-turn`.
- **Process launch**: la llamada a `_run_process(argv, ...)` intenta crear/lanzar el proceso. El código distingue launch errors, timeout y resultado completado.
- **Termination/output**: después de `completed` se leen stdout, stderr y return code.
- **Result**: se construye `ExecutionResult` con success, exit code, outputs, error, diagnostics y métricas opcionales.

El código no puede afirmar por sí solo “el runtime aceptó la invocación”, “abrió el archivo”, “lo cargó” o “ejecutó inferencia”. Eso requiere una señal runtime definida y observada.

## 3. Evidence Levels

| Nivel | Evidencia mínima disponible | Qué demuestra | No demuestra |
|---|---|---|---|
| 1. Invocation | `argv` contiene `--model` y el path validado; la llamada al proceso fue intentada | Se entregó un path como input y se intentó invocar el runtime | Que el proceso arrancó, abrió o cargó el archivo |
| 2. Process acceptance | El proceso no launch-error/timeout y llegó a `completed` | El runtime的可执行 proceso completó su operación con ese argv | Que entendió el artifact o que la inferencia funcionó |
| 3. Artifact load | Señal runtime estructurada de lectura/carga del path, ausente actualmente | Carga consumada del artifact | Inferencia correcta o éxito completo |
| 4. Execution | Señal runtime de ejecución de inferencia usando el artifact, ausente actualmente | Operación de inferencia observada | Soporte universal para otros artifacts |
| 5. Successful execution | Señales de ejecución y resultado exitoso, ausente actualmente como observación estructurada | La instancia completó esa operación | Carga si no se observa, ni generalización de capability |

`ExecutionResult.success` y `returncode == 0` son resultados de proceso. No deben ser reetiquetados automáticamente como niveles 3–5.

## 4. Available Runtime Signals

| Señal | Observable | Confianza | Suficiente sola | Combinación/afirmación permitida |
|---|---:|---:|---:|---|
| `RuntimeCapability.name` | Sí | Alta como nombre supplied | No | Identidad de producto, no instancia completa |
| `executable_path` | Sí | Alta para executable local | No solo | Identifica el executable que se intentó ejecutar |
| `version` | Sí, desde capability probe | Media: es output parseado, no evidencia de esta ejecución | No | Runtime version/build esperado, si se conserva; no prueba consumo |
| `argv` | Sí | Alta como construcción local | Sí para invocación solicitada | `INVOCATION_STARTED` sólo después de可知 que se intentó lanzar |
| `artifact.path` | Sí, como `ExecutableArtifact.path` | Alta como path passed to argv | No | Referencia operacional; `artifact_id` es la identidad física correcta |
| `artifact.artifact_id` | Sí, en `ArtifactSpec` | Alta | Sí para referencia de artifact lógico/local | `artifact_reference`; no filename/path/checksum |
| backend target | Sí, en `ExecutionTarget` | Alta como contexto seleccionado | No | Backend de la observación, no prueba support universal |
| stdout | Sí | Depende de formato | No | Puede contener evidencia runtime, pero debe parsearse/validarse |
| stderr | Sí | Depende de formato | No | Puede indicar rechazo/fallo; no una taxonomía fiable por texto libre |
| exit code | Sí, salvo timeout/prelaunch | Alta para terminación | No para consumo | `success`/proceso terminado; no artefact load universal |
| duration | Sí en `ExecutionDiagnostics` | Alta para duración | No | Duración de proceso, no consumo |
| load time/metrics | Opcional desde `parse_llama_human_output` | Media y parseada | No | No sustituye señal de carga/inferencia; métricas no son evidencia de support |



## 5. Invocation vs Consumption

CastleArq debe mantener tres afirmaciones distintas: el runtime recibió `--model /path`; realmente cargó ese path; realmente ejecutó inferencia usando ese path. La primera es demostrable mediante argv y el intento de lanzamiento. La segunda y tercera no están demostradas por el contrato actual: no hay campo `loaded`, evento de apertura, progreso validado ni confirmación de inferencia asociada al artifact. Un exit code cero sólo añade que el proceso terminó con éxito.

## 6. Failure Semantics

| Caso | Comportamiento actual y evidencia justificable |
|---|---|
| A. archivo no existe | Preflight falla antes del runner, o el runner devuelve `ARTIFACT_INVALID` si desaparece; no hay evidence de ejecución runtime. |
| B. archivo inválido | Preflight/reader pueden detectar metadata o estructura inválida; si el runner falla, sólo consta fallo operacional. No se afirma `ARTIFACT_REJECTED` por texto arbitrario. |
| C. runtime no puede abrirlo | Puede producir exit code no cero y stderr; sin taxonomía estructurada sólo se registra fallo de proceso. |
| D. abre pero falla al cargar | No hay señal que lo distinga de otros fallos; no se crea `ARTIFACT_LOAD_FAILED` automáticamente. |
| E. carga pero falla backend | No hay señal estructurada; sólo proceso fallido y backend seleccionado. |
| F. inicia inferencia pero falla | Sólo se puede afirmar intento de invocación y resultado fallido, salvo parser de métricas. |
| G. inferencia termina correctamente | `success=True` y exit code cero demuestran resultado exitoso del proceso, no por sí solos artifact load. |

La taxonomía de fallos sólo puede usarse cuando exista señal explícita del runtime. El código actual no la posee.

## 7. RuntimeArtifactEvidence Fields

| Field | Source | Directo? | Derivado? | Nature |
|---|---|---:|---:|---|
| `runtime_identity` | `RuntimeCapability.name` + `executable_path` | Parcial | Sí | Capability; path identifica executable local |
| `runtime_version` | `RuntimeCapability.version` | No al ejecutar | De probe previo | Capability, no observación de esta ejecución |
| `artifact_reference` | `ArtifactSpec.artifact_id` | Sí | No reinterpretar | Identidad física/local; nunca filename, path, checksum o `model_id` |
| `artifact_format` | `ArtifactSpec.format` | Sí como metadata | No | Declarada; no prueba carga |
| `artifact_architecture` | GGUF evidence o metadata | No en runner | Sí, si ya se obtuvo | Physical evidence; no prueba consumption |
| `backend` | `ExecutionTarget.backend` | Sí | No | Contexto seleccionado; no support universal |
| `observation` | Resultado/eventos de runner | Parcial | Clasificación posterior | Ejecución/post-ejecución |
| `provenance` | Resultado del runner | Sí como contexto | Etiqueta mínima | `LlamaCppRunner execution result` |

No se exigen hardware, métricas, logs completos, timestamps, profiling o platform. `runtime_version` puede estar ausente; no se inventa.

## 8. Observation Contract

El conjunto mínimo justificable hoy es:

```text
NOT_ATTEMPTED
INVOCATION_STARTED
PROCESS_COMPLETED
EXECUTION_FAILED
EXECUTION_RESULT_SUCCEEDED
```

- `NOT_ATTEMPTED`: no hubo invocación runtime; no hay evidence runtime-artifact.
- `INVOCATION_STARTED`: se construyó argv con el artifact y se intentó lanzar el proceso; no prueba aceptación/carga.
- `PROCESS_COMPLETED`: el proceso terminó normalmente y el resultado fue recibido; no prueba load por sí solo.
- `EXECUTION_FAILED`: existe resultado, timeout o error de ejecución observable; no clasifica automáticamente la causa.
- `EXECUTION_RESULT_SUCCEEDED`: `success=True` y exit code cero; es éxito del resultado one-shot, no claim universal de consumo.

No se pueden producir legítimamente `ARTIFACT_REJECTED`, `ARTIFACT_LOAD_FAILED` o `BACKEND_INITIALIZATION_FAILED` con las señales actuales. Requieren una señal runtime ausente.


## 9. Provenance

La provenance mínima debe responder únicamente: ¿qué componente produjo esta observación? Para ejecución real: `LlamaCppRunner execution result`. Si no se intentó, la ausencia de provenance de runner debe ser explícita, no inventada. No se necesita esquema de eventos, timestamps ni confidence score.

## 10. Runtime Identity

El boundary conoce `RuntimeCapability.name`, `executable_path` y `version` opcional. `ExecutionTarget.runtime` contiene el runtime elegido. Path y version permiten identificar razonablemente la instancia local cuando están presentes; no hay hash de build, plataforma, GUID de proceso o identidad de proceso operativo expuesto. Nombre solo no basta; path o identidad concreta es obligatorio. Version puede estar ausente y no se fabrica.

## 11. Artifact Identity

Se conserva `Logical identity: ArtifactSpec.model_id -> ModelArtifact.identifier` y `Physical identity: ArtifactSpec.artifact_id -> RuntimeArtifactEvidence.artifact_reference`. El runner recibe `ExecutableArtifact.artifact`; su path es sólo locator operational. `artifact_reference` debe ser `artifact_id`, nunca filename, path, checksum, `model_id` o `ModelArtifact.identifier`.

## 12. Backend Context

El backend aparece como `ExecutionTarget.backend` y se traduce a `device` mediante `RuntimeCapability.backend_argument`. Es contexto de la ejecución observada. Una observación bajo CPU o Vulkan no prueba soporte universal del artifact bajo todos los backends.

## 13. ExecutionResult Relationship

La opción compatible es: `ExecutionResult` produce el resultado operativo y una capa de aplicación puede derivar o acompañar `RuntimeArtifactEvidence`. No debe contenerse recursivamente ni crear una relación circular. `ExecutionResult` no posee hoy el contrato completo: el runner recibe capability, target y executable artifact, pero sólo conserva outputs, status, diagnostics y métricas. No se añaden campos aquí.

```text
LlamaCppRunner -> ExecutionResult
ExecutionResult + execution context inputs -> RuntimeArtifactEvidence
```

La evidence debe conservar `artifact_id` y la identidad runtime que el runner recibió.

## 14. Evaluation Relationship

La relación causal es `EvaluationAdmission -> Execution -> RuntimeArtifactEvidence`. La evidencia es post-admission operational evidence. No debe convertirse automáticamente en la condición que autorizó la ejecución que la produjo ni cerrar `Admission -> Execution -> Evidence -> Admission` para la primera ejecución.

## 15. Knowledge Relationship

Una observación de que esta capability/version consumió el artifact X es instance-specific. No implica Knowledge universal sobre versiones, builds, backends, formats, architectures o artifacts. No se convierte automáticamente en `RuntimeKnowledge`; sólo una decisión posterior con alcance y provenance podría derivar una assertion normativa separada.

## 16. Fail-Closed Semantics

- No execution attempted: `NOT_ATTEMPTED` o ausencia; nunca `FAILED` de compatibilidad.

## 17. Minimal Evidence Contract

El mínimo sólo puede afirmar:

```text
runtime executable
+ runtime version cuando disponible
+ ArtifactSpec.artifact_id
+ artifact format declarada
+ backend seleccionado
+ observación de proceso/invocación
+ provenance = LlamaCppRunner execution result
```

Para afirmar que una instancia “consumió” el artifact se requiere una señal runtime de load/acceptance. Esa señal no existe actualmente. No se fabrica `ARTIFACT_LOADED` a partir de exit code cero, stdout arbitrario, preflight o metrics.

## 18. Architectural Decision

El producer futuro debe ejecutar y clasificar sólo observaciones demostrables por el boundary real. Puede producir evidencia limitada a invocación/proceso y asociarla al `artifact_id`, runtime capability, backend y provenance. No puede producir una afirmación estructurada de artifact load o inferencia porque faltan signals.

La implementación queda bloqueada para un producer que pretenda afirmar “consumed artifact” o `EXECUTION_SUCCEEDED` como consumption. Puede implementarse posteriormente evidencia limitada a invocation/process facts si se acepta explícitamente esa limitación; no debe añadirse al check pre-ejecución.

## 19. Next Block

B9.46.29 debe elegir una sola alternativa antes de implementar:

1. Implementar evidencia limitada a invocación/proceso, con observación que no afirme carga.
2. Definir un parser/protocolo runtime existente y verificable que exponga load/acceptance, sin crear una segunda execution pipeline, y sólo después implementar evidencia de consumo.
3. Mantener la ausencia de evidencia runtime-artifact como UNKNOWN y no producir evidence positiva.

No se implementa ninguna alternativa en este bloque.

## 20. Verdict

RUNTIME-EXECUTION-EVIDENCE-CONTRACT-BLOCKED

La evidencia mínima de invocación/proceso está definida, pero el repositorio no expone una señal estructurada que demuestre que llama.cpp cargó el artifact o ejecutó inferencia con él. Un producer de “runtime consumed artifact” aún no puede implementarse legítimamente.
