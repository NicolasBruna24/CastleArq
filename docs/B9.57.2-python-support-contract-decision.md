## 1. Executive Summary

CastleArq declares Python 3.10–3.13 and cannot run on 3.10. The entire declared
support range is currently unevidenced, and one member of it is provably broken.

The cause is narrow and now **measured, not inferred**: `app/version.py:6`
imports `tomllib`, which entered the standard library in **Python 3.11**. On
CPython 3.10.21 the suite does not run at all — it aborts during collection
with 14 `ModuleNotFoundError: No module named 'tomllib'` errors, so **zero
tests execute**. Because `app/api.py:143` imports `app/version.py`, the failure
reaches the CLI, not only the tests.

The decisive experiment: on real CPython 3.10.21, with `tomllib` shimmed to
`tomli` and **nothing else changed**, the full suite passed —
`1468 passed, 2624 subtests`. Therefore `tomllib` is the **sole** Python 3.10
incompatibility. No other 3.11+ standard-library import, no 3.11+ syntax and no
3.11+ typing construct exists in `app/**` or `tests/**`.

Two facts must not be conflated:

* **3.11, 3.12 and 3.13 currently FAIL in CI** (run `36209640363`), and that
  failure is *identical* across all four versions. The `tomllib` explanation
  covers 3.10 only. The cause of the 3.11–3.13 failures is **not established by
  this block** and remains open (§10).
* **3.14 is not declared anywhere** — not in `requires-python`, not in the
  classifiers, not in CI. It is the maintainer's local interpreter and nothing
  more. The only green suite CastleArq has ever produced ran on an undeclared
  version.

The published `0.1.0` on PyPI carries `requires-python = ">=3.10"`, so this is
also a **live public-contract defect**, not only a repository one.

## 4. tomllib Analysis

### 4.1 Every occurrence

| Location | Import | Use |
| --- | --- | --- |
| `app/version.py:6` | `import tomllib` | `tomllib.loads(...)` at `:17` |
| `tests/test_public_surface.py:16` | `import tomllib` | `tomllib.loads(...)` at `:235` |
| `tests/test_api.py:36` | `import tomllib` | `tomllib.loads(...)` at `:156` |
| `tests/test_b930_packaging.py:9` | `import tomllib` | `tomllib.loads(...)` at `:23`, `:79` |

**Exactly one API is used across the entire repository: `tomllib.loads`.**
No `tomllib.load`, no `TOMLDecodeError`, no file-handle form.

### 4.2 Why it is imported, and whether it is runtime-critical

*Production* (`app/version.py:10-21`): `get_version()` first tries
`importlib.metadata.version("castlearq")`. The TOML parse is a **fallback for
running from a source checkout where the distribution is not installed**. It
reads exactly one key: `project.version`.

*Tests*: the three test modules parse `pyproject.toml` to assert packaging
metadata and CLI/version agreement. Test-only usage, but test-blocking.

### 4.3 Coupling assessment

INFERRED from the 3.10 shim experiment, which is measurement rather than
opinion:

* The coupling is **shallow and narrow**. One function, one stdlib call, one
  key, in one production module.
* It is **not semantically tied to 3.11+** — TOML parsing has no 3.11 semantics
  at all; only the *module's location in the stdlib* is version-bound.
* It is **unavoidable at import time as written**: `import tomllib` at module
  scope in `app/version.py` makes the whole package unimportable on 3.10, even
  though the code path that needs TOML is a rare fallback. The import is
  unconditional; the *use* is conditional. That mismatch — an unconditional
  import for a conditional need — is the actual defect, and it is larger in
  scope than the version question itself.
* Because `app/api.py:143` imports `app/version.py`, this is a **product runtime
  defect**: on 3.10 the `castlearq` CLI cannot be imported, so
  `castlearq --version` cannot work regardless of installation state.

**Not implemented here:** no import was changed, no dependency added, no
alternative written.

## 5. Python 3.10 Compatibility Audit

Static audit plus one empirical discriminator. Classification is explicit.

### CONFIRMED

| Finding | Evidence |
| --- | --- |
| `tomllib` is the sole Python 3.10 import failure | 3.10.21: 14 collection errors; with a `tomli` shim and no other change: `1468 passed, 2624 subtests` |
| The failure is import-time, not call-time | 3.10.21 aborts during *collection*; no test body executes |
| The failure is a product defect, not only a test defect | `app/api.py:143` → `app/version.py:6` |

### LIKELY

| Finding | Basis |
| --- | --- |
| 3.11–3.13 fail for a reason *other* than `tomllib` | Identical 4/4 CI failure while `tomllib` exists in 3.11+; cause not isolated here |
| The 3.11–3.13 cause is environment/metadata-related rather than source-related | The identical suite passes on 3.14.4 in four different filesystem layouts |

### NO ISSUE FOUND

Checked and cleared, so that Option B is not chosen on a false premise:

| Checked construct | Result |
| --- | --- |
| 3.11+ stdlib imports in `app/**` | none — only `tomllib` |
| 3.11+ stdlib imports in `tests/**` | none — only `tomllib` |
| `except*`, `TaskGroup`, `StrEnum`, `datetime.UTC`, `hashlib.file_digest`, `typing.Self/Never/LiteralString`, `contextlib.chdir`, `itertools.batched` | **none present** |
| PEP 604 unions (`X \| None`) and builtin generics (`list[str]`, `tuple[str, ...]`) | 37 runtime annotations in the 9 modules lacking `from __future__ import annotations`; **verified working on 3.10.21** — these are 3.10 features, not 3.11 |
| `ast.parse(feature_version=(3,10))` over all `app/` + `tests/` | parses clean (static syntax evidence only) |
| `datetime.fromisoformat` on `isoformat()` output (`+00:00`) | **works on 3.10.21** — round-trip verified |
| Z-suffixed ISO strings (`"2026-09-18T12:00:00Z"`) | **cannot be parsed on 3.10.21** (verified: `ValueError`), but grep confirms they are only ever **compared as strings**, never passed to `fromisoformat`/`strptime`. No defect today; a latent trap if future code parses them |

### POSSIBLE

* Behavioural differences between 3.10 and 3.14 that no test exercises (e.g.
  `unittest` subtest reporting). The 3.10 shim run passed all 1468 tests, which
  is strong counter-evidence, but a *passing* suite is not proof of identical
  behaviour.
* Packaging on 3.11–3.13 is unmeasured. The 3.11–3.13 failure is unexplained.

**Deliberately not concluded:** that the codebase is "fully 3.10 compatible"
apart from `tomllib`. What is established is that *this test suite* passes on
3.10 once `tomllib` is resolved. Static inspection cannot prove runtime
compatibility, and this block does not claim it does.

## 6. Options A–D

### Option A — Retain `>=3.10`

Minimum change surface:

1. Replace the unconditional module-scope import in `app/version.py` with a
   guarded one (`try: import tomllib / except ImportError: ...`), or defer the
   import into the fallback branch where it is actually needed. The second is
   smaller and removes the defect for the installed case.
2. Add `tomli` as a conditional dependency for `python_version < "3.11"`.
3. Add the same guard in the three test modules, or add `tomli` to the `[dev]`
   extra for 3.10.
4. Re-run the matrix; 3.10 evidence then becomes real.

**Runtime dependency philosophy impact — this is the crux.** `requirements.txt:1`
states CastleArq uses only the standard library, and that is a documented
public claim. Option A introduces the project's **first runtime dependency**
(`tomli`, conditional on 3.10 only). Whether a conditional backport counts as
violating the stdlib-only contract is precisely the judgement this block must
not make unilaterally: it changes what a user downloads, and B9.53's classifier
discipline treats such a change as a support claim.

**Evidence that it is sufficient:** the shim experiment. A `tomli` shim made the
whole suite pass on 3.10.21, so the remaining work is mechanical.

### Option B — Raise the minimum to `>=3.11`

Exact contract changes required:

| Surface | Change |
| --- | --- |
| `pyproject.toml:9` | `requires-python = ">=3.11"` |
| `pyproject.toml:34` | remove the `3.10` classifier |
| `README.md:96` | "Python 3.11 or newer" |
| `README.md:684` | drop 3.10 from the CI sentence |
| `.github/workflows/ci.yml:63` | matrix becomes `['3.11','3.12','3.13']` |
| `pyproject.toml` comment near `:52` | the `pytest` pin rationale mentions `>=3.10`; re-verify |
| **Already-published `0.1.0` on PyPI** | **cannot be retroactively changed** — published metadata keeps `>=3.10` |
| `docs/release/v0.1.0-manifest.md:16` | records "Python minimum `>=3.10`" |

**Do 3.11–3.13 still need real CI validation after this change? Yes,
unambiguously.** Two independent reasons: (i) their current CI status is FAIL
for an unexplained reason, so removing 3.10 from the matrix would *not* make
the remaining jobs green; (ii) B9.55's core lesson is that a declared range
without execution evidence is an unevidenced claim. Removing a version from the
matrix without a green run would trade a known-broken claim for an unverified
one.

**Honest cost:** it narrows the supported range for a `0.1.x`, single-maintainer,
Linux-first developer tool, and it leaves a false claim on the already-published
PyPI release that only a new release can correct.

### Option C — Alternative stdlib-compatible implementation, no runtime dependency

Feasibility analysis (not implementation):

* The only production need is reading **one scalar**, `project.version`, from
  `pyproject.toml` when the distribution is not installed.
* A minimal, purpose-built reader for that single key is technically feasible
  with stdlib only, and would remove both the 3.10 failure and the need for any
  dependency.
* **However**, the same requirement exists in three **test** modules, which parse
  arbitrary `pyproject.toml` structure (`[project]`, classifiers,
  optional-dependencies, scripts, build-backend). A hand-rolled parser adequate
  for one scalar is **not** adequate for those.
* Hand-rolling a TOML parser is itself a correctness and security liability, and
  B9.36's real-toml evidence would need re-establishing.

INFERRED: Option C is **not attractive for the production path alone** and
would still leave the test-side dependency question open unless the tests are
also reworked. It trades a version constraint for parser risk. The evidence does
not support assuming it is clean.

### Option D — Defer

Would require choosing A, B or C later. The evidence needed is already almost
entirely in hand: the 3.10 cause is CONFIRMED and isolated, and the sufficiency
of A is CONFIRMED by the shim experiment. What is **missing** is the cause of
the 3.11–3.13 CI failures.

INFERRED: deferring past this point buys little on the 3.10 question specifically
and leaves CI red in the meantime. Deferral is defensible only if the 3.11–3.13
failure must be understood first, since it may change which option is coherent —
for example, if the 3.11–3.13 failure is itself a packaging defect, then
neither A nor B would fix it.

## 7. Decision Criteria

Qualitative trade-offs only. No scores, no ranking, no "best option".

**Compatibility truthfulness.** A leaves the declared range intact and must
earn evidence for it. B changes the declaration so it matches what the code
does, but only after the 3.11–3.13 failures are explained, or it would be
declaring a range it has never seen pass. C leaves the declaration intact and
attempts to make the code honour it.

**Runtime dependency simplicity.** A introduces the first runtime dependency
(conditional). B introduces none. C introduces none. A and C are therefore
disfavoured by the `requirements.txt:1` stdlib-only claim; B is favoured.

**Packaging simplicity.** B is a one-line metadata change plus documentation
coherence. A adds a conditional dependency and an environment marker, strictly
more machinery for a project whose only build requirement is `setuptools>=61`.

**Maintenance burden.** A and C both leave 3.10 in the matrix, so both keep
paying for a version near the end of upstream support. B reduces the tested
surface by one interpreter.

**Developer environment expectations.** INFERRED: the audience is developers
already working with local models on Linux (`README.md:89`). For that audience,
3.11 is a low bar. This weakens the practical cost of B, but it is an inference
about users, not a measurement, and not a reason on its own.

**CI complexity.** Identical across A, B and C — one workflow, `fail-fast: false`,
four or three entries. No option changes the CI design.

**Public support contract clarity.** A and C keep a range that must then be
*earned* by green runs. B states one thing and can be verified. A published
`0.1.0` already says `>=3.10`; under B, the correction ships in the next release
and users on 3.10 are told the truth only then.

**Impact on the already-published `0.1.0` contract.** A and C are
retroactively vindicated if they make the existing claim true. B retroactively
falsifies a published claim, which cannot be edited away and requires a new
release to correct — a fact that must be stated to users regardless of which
option is chosen.

**A criterion that applies to all options:** none of them makes CI green on its
own, because the 3.11–3.13 failure is still unexplained.

## 8. Historical Reconciliation

* **B9.55** recorded the asymmetry — declared 3.10–3.13, verified 3.14.4 — and
  had **no actual execution evidence for any declared version**. It could not
  have detected this defect; it only flagged that the gap existed.
* **B9.56** ratified Option B (basic CI) and named the declared range as the
  matrix, explicitly reasoning that the matrix must validate the *declared*
  claim. That reasoning is what made this defect detectable.
* **B9.57** created the first real validation mechanism and immediately exposed
  two independent defects: a test-hermeticity defect and the Python support
  defect. Both were invisible to local runs because the maintainer's interpreter
  is 3.14.4, where neither manifests.
* **B9.57.1** fixed the hermeticity defect correctly and confirmed it under
  pristine HOME; it did not and could not address the Python support defect.
* **The Python support defect remains unresolved.** `tomllib` on 3.10 remains.
  The 3.11–3.13 failure remains unexplained.
* **B9.57 therefore cannot close.** Its contract is implemented, but the
  validation it exists to perform has never produced a green result.

The uncomfortable finding: the first-ever execution of CastleArq's suite
outside a 3.14 workstation revealed that the project's only verified
interpreter was the one version it does not claim, and that the version it
advertises most prominently cannot import the package at all. Four releases of
documentation asserted a support range that no machine ever exercised.
