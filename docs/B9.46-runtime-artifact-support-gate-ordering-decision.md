# B9.46.25 — Runtime Artifact Support Gate Ordering Decision

## 1. Executive Summary

La auditoría confirma un conflicto de orden:

```text
runtime artifact support
  es un check determinant del strict evaluation pre-admission

runtime consumption real
  sólo puede observarse cuando LlamaCppRunner ejecuta el artifact
  después de admission, preflight y backend selection
```

No existe un producer existente que pueda demostrar consumo real antes de admission sin ejecutar un probe/runtime adicional. Por tanto, este bloque no elige artificialmente una opción.

**Verdict: `GATE-ORDERING-DECISION-BLOCKED`.**

## 2. Current Flow

Flujo confirmado por código:

```text
app.main.execute_command
  -> evaluate_model_compatibility()
  -> to_admission()
  -> execute_model(admission=...)
       -> re-resolve ModelSpec/ArtifactSpec
       -> fresh RuntimeCapability
       -> _check_admission()
       -> _compatibility() / assess_model()
       -> ArtifactExecutionPreflight.validate()
       -> RuntimeBackendSelector.select()
       -> validate ExecutionRequest
       -> ModelRunner.run()
            -> LlamaCppRunner subprocess
            -> ExecutionResult
```

La primera observación real del runtime sobre el artifact aparece en `LlamaCppRunner.run()`, después de admission y de la preparación operacional.

## 3. Strict Evaluation Purpose

`evaluate_model_compatibility()` y `evaluate()` realizan una evaluación pura y determinista de facts supplied. Responden:

> ¿El modelo/artifact es compatible con el contexto de runtime/conocimiento disponible?

No responden:

> ¿Esta instancia concreta del runtime acaba de consumir este artifact?

`evaluate()` construye seis checks determinantes: identity, format, architecture, runtime, backend y capabilities. Un `UNKNOWN` requerido produce `INSUFFICIENT_EVIDENCE`.

## 4. Check Audit

| Check | Source | Nature | Pre-execution | Requires execution |
|---|---|---|---|---:|
| identity | `ModelIdentity` + `ModelArtifact.identifier` | logical relation | yes | no |
| format | `artifact.format` + Knowledge lists | normative compatibility | yes | no |
| architecture | model architecture + Knowledge; physical GGUF evidence | normative plus physical input | yes | no |
| runtime artifact | `RuntimeKnowledge.supports_artifact` | abstract Knowledge field | yes in schema | real claim no |
| backend | requested backend + Knowledge lists | contextual compatibility | yes | no |
| capabilities | required capability + Knowledge | normative Knowledge | yes | no |

`_check_runtime()` reads only `knowledge.supports_artifact`; it is a Knowledge check, not an execution observation.

## 5. Three Evidence Categories

### A — Static/normative Knowledge

```text
llama.cpp supports GGUF
```

Authority: `KnowledgeRegistry` projected to `RuntimeKnowledge`.

### B — Physical artifact evidence

```text
GGUF general.architecture=qwen2
```

Authority: physical artifact reader/observation. It proves metadata, not runtime consumption.

### C — Runtime execution evidence

```text
runtime instance X consumed artifact Y
```

Authority: real runtime process observation. Currently produced by `LlamaCppRunner`.

C cannot be presented as A or B, and no existing pre-admission producer creates C.

## 6. Option A — Pre-admission probe

A probe before admission could produce a positive observation, but it would require a real runtime process and likely model initialization/inference. That is execution behavior even if named a probe.

Costs include resource consumption, latency, backend/configuration selection, side effects, cleanup, duplicated runner/command/runtime path, configuration drift and a new execution seam.

The current `LlamaCppRunner` cannot be reused safely before admission without changing gate ordering and duplicating preparation. No such probe is ratified.

**Status: not selectable in this block.**

## 7. Option B — Post-admission evidence

```text
strict compatibility
  -> admission
  -> preflight/selection
  -> execution
  -> RuntimeArtifactEvidence / ExecutionResult
```

Consequences:

- strict `runtime artifact support` remains `UNKNOWN` initially;
- `to_admission()` currently denies `insufficient_evidence`;
- execution cannot authorize the execution that produces its evidence;
- a future result is operational evidence, not pre-execution Knowledge;
- failed-process interpretation requires an error taxonomy.

This is semantically compatible with separating evaluation from execution, but requires changing which check gates admission or introducing a separate operational gate. The repository does not ratify that change.

## 8. Option C — Maintain UNKNOWN

`UNKNOWN` is honest while no authoritative pre-admission runtime-artifact assertion exists. It preserves `UNKNOWN != FAILED` and does not conflate execution with compatibility.

But `to_admission()` projects `insufficient_evidence` to deny, so the real product remains blocked before the runner. This is conservative, not a complete Alpha execution path.

## 9. Option D — Separate operational gate

A conceptual separation already exists:

```text
strict compatibility
  -> EvaluationAdmission
  -> operational compatibility/assess_model

## 10. EvaluationAdmission

`EvaluationAdmission` is a fail-closed summary projection. It carries status/verdict and can deny, but cannot authorize execution by itself.

With current `runtime artifact support=UNKNOWN`, the strict result is `INSUFFICIENT_EVIDENCE`, so `to_admission()` produces a denied admission. This is consistent with the current contract; it must not be changed in this read-only block.

## 11. assess_model and Preflight

`assess_model()` estimates feasibility using hardware, runtime status, backend status, quantization and memory. It is an operational/compatibility heuristic, not a runtime consumption observation.

`ArtifactExecutionPreflight.validate()` validates resolved artifact filesystem safety, size and checksum and returns an `ExecutableArtifact`. It does not open the model in llama.cpp.

Neither is a legitimate positive runtime-artifact producer for the selected claim.

## 12. LlamaCppRunner Evidence

`LlamaCppRunner.run()` starts the actual process with the validated executable artifact, selected target, prompt and timeout. It returns `ExecutionResult` with success, exit code, stdout/stderr, diagnostics and optional metrics.

The strongest currently available evidence is execution outcome:

- process started;
- artifact passed input validation;
- process returned normally;
- exit code 0;
- output was captured.

These facts indicate successful one-shot consumption of the selected artifact by that instance/backend. They do not prove universal runtime support. A nonzero result does not by itself distinguish unsupported artifact from bad request, timeout or runtime failure without an error taxonomy.

This evidence is produced after admission.

## 13. Consequences for B9.46.23

The B9.46.23 representation remains semantically valid as an ephemeral evidence value:

```text
runtime identity/version
+
physical artifact reference
+
context
+
observation
+
provenance
```

If the decision is post-admission:

```text
producer = execution/runner boundary
consumer = post-execution result/operational gate
```

It should not be inserted into Knowledge, manifest, ModelStore, ArtifactSpec or ModelArtifact.

## 14. Decision

```text
GATE-ORDERING-DECISION = BLOCKED
```

The missing architectural decision is fundamental:

1. Require runtime-artifact evidence before admission, requiring an approved pre-admission probe or changed execution boundary; or
2. Define it as execution-time evidence, requiring admission/strict evaluation to stop treating it as a determinant pre-execution claim; or
3. Authorize a separate operational gate with a defined owner and placement.

The current repository does not answer this question. Selecting `PRE-ADMISSION` invents a probe boundary; selecting `POST-ADMISSION` or `SEPARATE-OPERATIONAL-GATE` changes gate semantics; selecting `MAINTAIN-UNKNOWN` leaves real E2E blocked.

**VERDICT = GATE-ORDERING-DECISION-BLOCKED**

## 15. Invariants and Non-Goals

Preserved:

```text
strict evaluation remains pure
EvaluationAdmission remains fail-closed
UNKNOWN != FAILED
ModelSpec/ArtifactSpec/ModelArtifact ownership unchanged
GGUF evidence remains ephemeral
adapter remains filesystem-free
no second runner/subprocess/probe
no backend, identity, persistence or CLI change
no commit and no push
```

## 16. Validation

No tests were executed and no runtime command was run in this read-only audit. No production or test files were modified.

Only this document was created:

```text
docs/B9.46-runtime-artifact-support-gate-ordering-decision.md
```

  -> ArtifactExecutionPreflight
  -> RuntimeBackendSelector
  -> execution
  -> runtime artifact evidence
```

`assess_model()` covers hardware/runtime/backend/memory feasibility. Preflight covers filesystem safety and checksum. A separate runtime-specific gate could validate actual readiness, but no such gate exists today.

Introducing one requires a new boundary, consumption/production contract and explicit placement relative to admission. That is an architectural decision.
