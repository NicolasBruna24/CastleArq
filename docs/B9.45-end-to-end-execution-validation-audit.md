# B9.45 — Auditoría de validación de ejecución end-to-end

**Estado:** AUDITORÍA READ-ONLY. No se modificó código ni tests; el único archivo creado por este bloque es este documento.

**Pregunta auditada:** ¿puede CastleArq demostrar hoy un recorrido real desde el caller de producto `execute` hasta un resultado producido por el runtime, atravesando evaluación, admission, compatibilidad operacional, resolución/preflight del artifact y ejecución?

## 1. Executive Summary

CastleArq **no puede demostrar actualmente un recorrido end-to-end real y reproducible** desde `execute` hasta un resultado producido por `llama.cpp` con un modelo real. El flujo de aplicación está cableado y se puede demostrar con dobles, integración y composición real parcial; el primer punto donde se rompe la afirmación de E2E real es la ejecución: las pruebas disponibles no invocan un binario `llama.cpp` real sobre un artifact GGUF real hasta el caller de producto.

La arquitectura sí contiene el recorrido relevante:

```text
product caller (`app.main.execute_command`)
  -> strict evaluation (`evaluate_model_compatibility`)
  -> admission (`to_admission`)
  -> `execute_model(admission=...)`
  -> operational compatibility (`assess_model`)
  -> artifact preflight
  -> `RuntimeBackendSelector`
  -> `LlamaCppRunner`
  -> `ExecutionResult`
```

No debe confundirse esta evidencia con ejecución real:

* `tests/test_execution_integration.py::...test_real_end_to_end_pipeline_uses_fake_runner` ejecuta el pipeline con `FakeModelRunner` y verifica explícitamente que no se llama `subprocess.run`.
* `tests/test_execute_model_wiring.py` compone collaborators reales, pero su propio encabezado documenta que el ejecutable apunta a una ruta inexistente y que el flujo termina en la validación del runner.
* `tests/test_execute_model.py` usa dobles y declara que no ejecuta modelo ni hardware real.
* `tests/test_main_execute.py` prueba el caller, forwarding, proyección de admission y presentación del resultado, con seams mockeados.

**Verdict B9.45: `PARTIALLY-E2E-VALID`.** La estructura y ambos gates están validados; la afirmación de ejecución real y de retorno real al caller no lo está.

## 3. Artifact Lifecycle Verification

```text
modelo -> save_manifest -> list_artifacts -> inspect_manifest
       -> resolver -> preflight -> runner
```

* Registro: `app/model_store.py:102-182`, `save_manifest` escribe `manifest.json` de forma atómica. Persiste identidad, provenance, metadata, `size_bytes`, `sha256` y `downloaded_at`; no persiste `state` ni `verified` nuevos.
* Persistencia: `_write_manifest` usa `.part`, `fsync` y `os.replace`. `downloaded_at` es adquisición, no autoridad de estado.
* Descubrimiento: `list_artifacts` (`model_store.py:94-100`) recorre manifests y llama `inspect_manifest`.
* Estado derivado: `inspect_manifest` (`model_store.py:184-210`) cruza manifest, archivo final, `.part`, symlinks, tamaño y SHA-256. `ModelStore` es la autoridad local.
* Resolución: el resolver exige modelo del catálogo y artifact por `model_id`; rechaza downloading, failed y not-downloaded, y selecciona uno entre verified/downloaded.
* Ausencia: sin manifest o archivo devuelve `NOT_DOWNLOADED` y error de resolución; si desaparece después, preflight devuelve `MISSING_ARTIFACT`.
* Manifest inválido: JSON/esquema inválido produce entry `FAILED`; no se transforma en verificado.
* Preflight: final regular, no symlink, no `.part`; compara size/checksum y entrega path absoluto. La request no lleva path de filesystem.

El lifecycle está cubierto por store, resolver y preflight. Producto -> artifact real -> runner real no está cubierto.

## 4. Real Runtime Verification

El runtime objetivo es la CLI externa **llama.cpp**, representada por `RuntimeCapability` y ejecutada por `LlamaCppRunner`.

* `app/runtimes.py:detect_llama_capability` localiza binario/version/help y produce `executable_path` y argumentos de backend.
* `app/runner.py:88-111` construye `llama.cpp cli --simple-io --model <artifact> --device <backend> --prompt <prompt> --single-turn`, con `subprocess.run(..., shell=False)`.
* stdout/stderr, exit code, errores, diagnósticos y métricas se convierten en `ExecutionResult`, que vuelve por `execute_model` al caller.
* Se espera un GGUF local registrado y preflight-validado. `README.md` documenta que llama.cpp es externo y los modelos no vienen en el paquete.

`tests/test_main_execute.py` se identifica como B9.24 y prueba el caller, no ejecución real. `tests/test_execute_model_wiring.py` compone collaborators reales, pero usa `/test-only/llama` inexistente y documenta que no ejecuta modelo/subprocess. `tests/test_execution_integration.py` usa `FakeModelRunner`. No existe prueba automatizada con binario y GGUF reales hasta `execute_command`; no se ejecutó reproducción manual ni se alteró el entorno.

**Primer punto de ruptura:** la frontera entre el runner comprobada estructuralmente y su ejecución real.

## 5. ALLOW Path

```text
strict compatible -> admission allow -> execute_model
-> operational compatible/marginal -> resolved/preflight
-> selector -> runner -> result
```

La proyección compatible y la independencia de admission están probadas. `execute_model` vuelve a resolver y detectar capability; el request conserva artifact, prompt, target y timeout; el runner construye el argv; el resultado vuelve al producto.

Gaps: no hay artifact GGUF real + binario real + caller; wiring usa executable inexistente; integración usa contenido sintético y fake runner; no hay runtime/modelo/backend fijado por prueba reproducible.

## 6. DENY Path

```text
strict incompatible / insufficient_evidence / blocked
-> admission deny-by-default -> execute_model stops
-> compatibility, preflight, selector y runner no se invocan
```

`test_execute_model.py` cubre incompatible, insufficient evidence, verdict ausente, status desconocido, revalidación y runner sin llamadas. `test_main_execute.py` cubre excepciones de evaluación proyectadas a admission bloqueante. `_check_admission` (`app/execute_model.py:170-193`) es fail-closed.

La resolución ocurre antes de `_check_admission` porque el use case necesita el artifact. Una vez alcanzada la denial, precede a todos los pasos operacionales.

## 7. Dual-Gate Verification

```text
STRICT EVALUATION -> EvaluationAdmission -> ALLOW
 -> OPERATIONAL GATE -> ALLOW -> EXECUTION
STRICT EVALUATION -> DENY -> STOP
STRICT EVALUATION -> ALLOW -> OPERATIONAL GATE -> DENY -> STOP
```

Admission es deny-only y no autoriza por sí sola. `assess_model()` recalcula la compatibilidad operacional con facts frescos. Ambos casos tienen tests, pero no una prueba E2E real única.

## 8. Reproducibility Classification

**Global: B — Reproducible with local prerequisites**, para producto, resolución, gates y seam del runner. No es A porque no hay resultado producido por llama.cpp real. Para el objetivo estricto “modelo real -> llama.cpp real -> resultado real”, es **D — Not currently reproducible** con la evidencia actual.

Unitarios cubren adapters, admission, gates, store, resolver, preflight, selector y runner con dobles. Integración usa `FakeModelRunner` y artifact sintético. El vertical slice llega a caller/evaluation/admission/execute con seams. No hay ejecución real automatizada ni reproducción manual documentada.

## 9. Alpha Gaps

Flujo Alpha: `select model -> ensure artifact -> evaluate -> admit -> execute -> receive result`.

### Blocker

1. **Ausencia de evidencia E2E real reproducible:** falta binario llama.cpp real, GGUF real y prueba que cruce `execute_command`, selectores, admission, gates, preflight, runner y retorno de output real.
2. **No hay fixture local garantizado:** los tests crean archivos sintéticos y el repositorio no incluye modelo; una instalación nueva no puede cerrar el flujo sin un artefacto externo.

### Important

1. Prerrequisitos de runtime, modelo, backend y hardware no están empaquetados en una prueba reproducible.
2. No se prueba el retorno real a través del caller: el caller usa `execute_model` mockeado y wiring no ejecuta proceso.
3. `run_once` sigue siendo un camino legacy separado sin admission; puede confundir `execute` y `run`, aunque B9.45 no exige unificarlos.
4. La capability se detecta por máquina; una prueba real debe declarar precondiciones sin convertir偶然 del host en evidencia universal.

### Non-blocking

1. Mejoras de mensajes y experiencia CLI pueden esperar.
2. Métricas, diagnóstico o warnings adicionales pueden esperar tras el primer Alpha.
3. LoRA/QLoRA, datasets, clusters, multi-GPU, marketplace, cloud, GUI y observability avanzada quedan fuera.

## 10. Architectural Constraints

B9.45 no necesita y no autoriza un service, manager, registry, coordinator, generic execution layer, segundo compatibility engine, segundo artifact model o nueva persistence authority.

La mínima corrección futura es una prueba/fixture/documentación de validación: una integración opt-in/local con binario, GGUF y capability reales, sin descargar por defecto. Si exige red, fixture descarga o aislamiento de runtime, debe marcarse **architectural escalation / prerequisite policy**, no resolverse con una capa nueva.

Se mantiene `ModelStore` como autoridad del estado derivado. No se debe corregir usando `state` o `verified` persistidos.

## 12. B9.45 Verdict

# `PARTIALLY-E2E-VALID`

CastleArq demuestra caller, evaluación/admission, denial antes de los gates y runner, compatibilidad operacional independiente, lifecycle, preflight, selección y request. No demuestra simultáneamente un caller de producto, GGUF real, llama.cpp real y output real. El primer punto de ruptura es la frontera de ejecución real: el código existe, pero las pruebas terminan en `FakeModelRunner` o en validación de executable inexistente.
