# B9.6.0 — Initial Knowledge Specification

Estado: diseño documental (B9.6.0). **No implementa datos.** El dataset real
se construirá en B9.6.1 siguiendo este contrato. Bloques de referencia:
B9.4 (arquitectura de la Knowledge Base), B9.5 (`app/compatibility_knowledge.py`
— dominio y registry), B9.3 (evaluator funcional), B9.2 (reglas de evaluación).

## 1. Purpose

El primer dataset debe demostrar tres cosas, y solo tres:

1. que CastleArq puede **representar** conocimiento real de compatibilidad con
   el modelo de B9.5 (`KnowledgeAssertion` + subject/scope/provenance/state);
2. que el registry puede **consultarlo y detectar conflictos** de forma
   determinista, con `UNKNOWN != UNSUPPORTED`;
3. que ese conocimiento puede **alimentar** al evaluator de B9.3 vía
   `RuntimeKnowledge` (integración posterior, no en B9.6).

El dataset NO pretende ser completo ni útil como guía de compra. Es una prueba
de proceso: pocas afirmaciones, todas trazables, con casos UNKNOWN deliberados.
La calidad de cada afirmación importa más que la cantidad.

## 2. Scope

Dentro del dataset inicial: afirmaciones funcionales de compatibilidad sobre
Runtime, Backend, Format, Architecture y Capability (no todas las combinaciones,
solo las que tienen fuente verificable), con provenance y alcance explícitos.

Fuera del dataset inicial (ver Alpha Boundary, §24): todos los demás runtimes y
backends, más formatos, estimación de memoria, rendimiento, benchmarking,
trust/security, multi-GPU, selección y recomendación.

## 3. Initial Runtime Selection

Runtimes incluidos inicialmente: **llama.cpp** y **Ollama**. Ninguno más.

Justificación de por qué estos dos bastan para la primera prueba:

- **Cobertura de relación runtime/backend**: llama.cpp documenta backends de
  compilación/ejecución explícitos; Ollama expone soporte de GPU de forma
  propia. Dos runtimes permiten probar que el conocimiento de uno NO se
  traslada al otro (§16 del brief: no transitividad de conocimiento entre
  productos relacionados).
- **Diversidad de evidencia**: llama.cpp publica su matriz de backends en su
  repositorio (fuente primaria, revisable por commits); Ollama publica docs
  oficiales en su sitio/repo. Dos estilos de fuente distintos ejercitan la
  jerarquía de §10.
- **Espacio para UNKNOWN**: para Ollama, gran parte de las relaciones
  format/arquitectura no está documentada explícitamente → UNKNOWN natural.

### Decisión explícita sobre llama.app

`llama.app` puede **mencionarse** como producto/distribución/interfaz
relacionada con llama.cpp, pero **NO se le asigna status de runtime
independiente** en B9.6.0: se registra como alias/variante candidata de
llama.cpp, y su identidad definitiva queda **pendiente de verificación en
B9.6.1** con fuente oficial. No se crearán assertions dirigidas a un sujeto
`llama.app` en el dataset inicial.

## 4. Initial Backend Selection

Backends incluidos inicialmente: **CPU, Vulkan, CUDA, ROCm/HIP, SYCL**.

Criterios de selección:

- **Cobertura multiplataforma**: CPU cubre el caso base universal; Vulkan
  cubre GPU multi-vendor; CUDA (NVIDIA), ROCm/HIP (AMD) y SYCL (Intel/otro)
  cubren los tres vendors principales.
- **Relevancia IA local**: son los backends efectivamente usados para
  inferencia LLM local.
- **Capacidad de probar UNKNOWN**: al menos una relación runtime/backend
  quedará sin evidencia verificada en el primer dataset (p. ej. SYCL en
  Windows) — deliberadamente.
- **Capacidad de probar relaciones runtime/backend**: un mismo backend puede
  estar SUPPORTED para un runtime y UNKNOWN para otro.

### No colapso de entidades (obligatorio)

La KB debe preservar entidades distintas sin fusionarlas prematuramente:

```text
ROCm != HIP != AMD GPU      (plataforma/stack != API de transporte != hardware)
SYCL  != Level Zero != Intel GPU
CUDA  != NVIDIA GPU
Vulkan != "GPU compatible con Vulkan"
```

Una assertion puede hablar de una de estas entidades; jamás se sustituye por
otra sin una afirmación explícita y con fuente que conecte ambas.

## 5. Initial Format Selection

Un único formato inicial: **GGUF**.

Justificación:

- Es el formato con evidencia más trazable para los dos runtimes candidatos:
  llama.cpp lo define y consume; Ollama documenta la importación de GGUF de
  forma explícita. Un solo formato mantiene el dataset pequeño (§20) sin
  perder cobertura del eje Format.
- Permite probar las tres variantes del mismo check: soporte explícito,
  rechazo explícito si existe evidencia fiable, y UNKNOWN cuando el soporte no
  esté documentado.

Reglas asociadas:

- NO asumir que "modelo cuantizado" implica GGUF: Format, Precision y
  Quantization siguen siendo conceptos separados (B8.1, B9.2 §7).
- NO inferir arquitectura, capability ni backend a partir del formato (§18).
- El soporte de GGUF en un runtime no se traslada al otro (§17).

## 6. Initial Architecture Strategy

Conjunto mínimo con fines de prueba, NO una lista de arquitecturas:

1. **Arquitectura conocida y explícitamente soportada**: como máximo 2
   identificadores canónicos, solo con fuente primaria verificada en B9.6.1.
2. **Arquitectura conocida con soporte no documentado** → UNKNOWN deliberado.
3. **Arquitectura explícitamente NO soportada**: solo si existe evidencia
   primaria fiable que lo afirme; si no existe, se registra UNKNOWN y se anota
   en §19.

La lista candidata concreta queda **pendiente de verificación en B9.6.1**: no
se fijan identificadores aquí para no fabricar identificadores sin fuente.
Reglas: no inferir arquitectura desde el nombre del modelo (§18); no asumir
equivalencia entre arquitecturas con nombres similares (B9.2 §6).

## 7. Initial Capability Strategy

Capacidades consideradas (taxonomía B8.1): `text_generation`,
`code_generation`, `vision`, `embeddings`, `tool_use`.

- Cada afirmación runtime → SUPPORTS → capability requiere evidencia explícita;
  no basta con que una tecnología "pueda potencialmente" usarse de cierta
  manera.
- Se distinguen model capability / runtime capability / backend capability
  (B9.4 §18); ninguna se colapsa en otra.
- La cobertura NO exige UNKNOWN de un tipo en particular. Lo que debe quedar
  demostrado en el dataset es la semántica UNKNOWN (§19, §21): que CastleArq
  puede representarla, consultarla de forma determinista y distinguirla de
  UNSUPPORTED, con ejemplos reales y deliberados de cualquier tipo.
- Una assertion con evidencia explícita suficiente para SUPPORTED no puede
  conservarse como UNKNOWN para satisfacer una cobertura: una cuota no prevalece
  sobre la evidencia.

## 8. Knowledge States

Toda assertion futura se clasifica SUPPORTED / UNSUPPORTED / UNKNOWN
(B9.4 §12; ya implementado en B9.5 como `KnowledgeState`):

- **SUPPORTED**: afirmación explícita con fuente que declara soporte.
- **UNSUPPORTED**: afirmación explícita y trazable de falta de soporte. Solo se
  usa cuando la fuente primaria lo dice — nunca por ausencia de evidencia.
- **UNKNOWN**: no hay evidencia suficiente. El dataset incluirá casos UNKNOWN
  reales y deliberados (§19).

Invariantes que el dataset debe demostrar (coherentes con B9.5):
`UNKNOWN != UNSUPPORTED` y `ausencia de entrada != unsupported`.

## 9. Provenance

Cada assertion real usará los campos de `KnowledgeProvenance` (B9.5):
`source`, `source_type`, `reference`, `published_at`, `observed_at` (opcionales).

Reglas:

- Toda assertion real lleva provenance; consultar conocimiento nunca la destruye.
- `provenance != truth != confidence != trust`: no se crean scores, niveles ni
  rankings de fuentes (B9.4 §10–§11).
- Ante conflicto, ambas provenance se conservan (§22).
- `reference` apunta a documentación como **dato**: CastleArq nunca la ejecuta,
  descarga ni resuelve (§23).

## 10. Source Hierarchy

Jerarquía de fuentes preferidas para las assertions futuras:

1. Documentación oficial del proyecto.
2. Repositorio oficial del proyecto.
3. Documentación técnica oficial.
4. Matrices oficiales de soporte.
5. Documentación del fabricante cuando sea necesaria.
6. Fuentes secundarias solo si no existe fuente primaria.

Se evitan blogs, Reddit y contenido generado por usuarios como autoridad
principal para afirmaciones técnicas. Si una fuente secundaria contradice una
primaria: **no se resuelve silenciosamente**; se registra el conflicto (§22).

Estado de verificación de fuentes en B9.6.0: las fuentes candidatas quedan
identificadas (repositorio `ggml-org/llama.cpp` — documentación de build y
backends; documentación oficial de Ollama — GPU, plataformas e importación
GGUF), pero la **verificación puntual de cada enunciado** (quote, alcance,
fecha) se ejecutará assertion por assertion en B9.6.1. Ninguna afirmación se
considera verificada hasta entonces; las que no queden respaldadas permanecen
UNKNOWN.

## 11. Version Scope

Sin semver (B9.5 §17): `runtime_version` es metadata declarativa; no se
comparan strings de versión ni se resuelven rangos.

Cada assertion documenta su alcance:

- **global** (sin scope, se lee literalmente como la entidad general);
- **versión concreta** (`runtime_version` como dato);
- **plataforma** (`platform`);
- **variante** (`variant`).

Si la fuente no permite determinar el alcance: se registra la assertion con
scope desconocido y se anota; **nunca se inventa** un alcance.

## 12. Platform Scope

Plataformas consideradas: Linux, Windows, macOS.

No se crean assertions por plataforma sin evidencia explícita. Ejemplo
obligatorio de no-inferencia:

```text
NO asumir: llama.cpp + Vulkan funciona en Linux
por el simple hecho de que Vulkan exista en Linux.
```

La relación runtime+backend+plataforma debe estar respaldada por evidencia
explícita; sin ella, la assertion queda UNKNOWN o sin ese scope.

## 13. Hardware Boundary

El hardware del usuario NO se convierte en conocimiento universal. El dataset
puede contener conocimiento general con fuente (p. ej. "el backend X está
destinado a la familia de GPU Y"), pero **nunca** afirmaciones sobre la GPU del
usuario: eso pertenece a Observation + Compatibility Evaluation (B9.4 §3).

## 14. Intel Arc / Battlemage Case

El caso **Intel Arc B70 (Battlemage) + Linux + Vulkan + SYCL + llama.cpp** forma
parte del primer dataset como estudio de caso prioritario: es el hardware de
referencia del propio proyecto y ejercita la distinción central
**observación local ≠ conocimiento universal** (B9.4 §3).

Reglas para este caso:

- La existencia de la GPU **no** prueba soporte: cada relación
  (runtime→backend, backend→GPU) requiere evidencia explícita.
- Si una fuente documenta Arc B-Series pero solo verifica un modelo concreto, no
  se generaliza a toda la familia salvo que el alcance de la fuente lo permita.
- **Pendiente de verificación en B9.6.1**: el enunciado oficial de soporte SYCL
  del backend SYCL de llama.cpp (documentación de build) y cualquier enunciado
  explícito sobre Vulkan/Battlemage. Hasta quedar anclados, las assertions de
  este caso se mantienen como candidatos UNKNOWN — nunca se derivan del vendor
  (§18).

## 15. llama.cpp Knowledge Scope

Ámbito de conocimiento de llama.cpp en el dataset (con verificación puntual por
assertion en B9.6.1, según §10):

- **Backends**: la matriz oficial de backends del repositorio define qué
  backends de compilación/ejecución existen (CPU, CUDA, Vulkan, ROCm/HIP, SYCL,
  etc.). Solo entrarán como SUPPORTED las relaciones runtime→backend cuyo
  enunciado quede verificado.
- **Formato**: GGUF es el formato definido y consumido por llama.cpp
  (fuente primaria). Assertion candidata: `llamacpp → SUPPORTS → gguf`.
- **Arquitecturas**: sin lista gigante; solo las que la fuente primaria
  documente soportar (§6). Sin inferencia por nombre (§18).
- **Capabilities**: solo si existe enunciado explícito; de lo contrario
  UNKNOWN (§19).
- **Plataforma**: solo relations scoped cuando la fuente lo diga (§12).
- **llama.app**: alias/variante candidata; sin assertions propias (§3).

## 16. Ollama Knowledge Scope

- **Hardware/backend**: Ollama documenta soporte de GPU de forma propia; sus
  enunciados son la evidencia de sus assertions. **No se asume** que el
  conocimiento de llama.cpp aplica a Ollama aunque compartan componentes:
  cada relación tiene evidencia propia (sin transitividad §17).
- **Plataformas**: solo con enunciado explícito (§12).
- **Formatos**: GGUF entra solo si la documentación oficial lo especifica
  (importación de GGUF); de lo contrario UNKNOWN.
- **Capabilities**: solo con evidencia explícita; si no hay, UNKNOWN (§19).

## 17. Non-Transitivity

Regla explícita: si `A SUPPORTS B` y `B SUPPORTS C`, **no** se infiere
`A SUPPORTS C`. Ejemplos que el dataset debe poder distinguir:

```text
llamacpp SUPPORTS vulkan
vulkan SUPPORTS (evidencia de GPU)
⇒ NO se infiere: llamacpp soporta esa GPU concreta
```

```text
ollama SUPPORTS gguf (importación)
llamacpp SUPPORTS gguf (formato nativo)
⇌ NO son la misma assertion ni se derivan entre sí
```

La KB no realiza razonamiento transitivo implícito; cada relación es una
assertion independiente con su propia evidencia y alcance.

## 18. Non-Inference Rules (vendor / nombre / formato)

Tres prohibiciones estructurales que el dataset respeta y las pruebas deben
demostrar:

1. **Vendor**: `Intel GPU → SYCL`, `NVIDIA GPU → CUDA`,
   `AMD GPU → ROCm` — prohibido sin evidencia. Vendor, backend y runtime son
   conceptos distintos.
2. **Nombre**: "Qwen" no implica arquitectura; "Llama" no implica arquitectura;
   "Vision" no implica capability vision; "Coder" no implica code_generation.
   Los nombres sugieren, no constituyen evidencia.
3. **Formato**: GGUF no implica arquitectura, capability ni backend. GGUF
   solamente identifica un formato.

## 19. Deliberate UNKNOWN Cases

El dataset incluirá UNKNOWN reales y deliberados; un buen dataset sabe cuándo
no sabe. Candidatos (a confirmar/ajustar con la verificación de B9.6.1):

- Soporte de **SYCL en Windows** para llama.cpp (§4): sin evidencia verificada
  → UNKNOWN.
- Relaciones **Ollama → arquitectura** específicas: sin evidencia explícita →
  UNKNOWN (no se infiere del nombre ni del formato; véase §18).
- **tool_use** como capability soportada en el contexto runtime/backend
  inicial: sin enunciado trazable → UNKNOWN.
- Arquitectura con soporte "no documentado" (§6, caso 2) → UNKNOWN.
- Cualquier assertion cuyo alcance la fuente no determine (§11) → se registra
  sin scope inventado y puede quedar UNKNOWN.

La verificación de B9.6.1 puede falsificar cualquier candidato: si la evidencia
resulta suficiente, la relación se registra SUPPORTED y la demostración de la
semántica UNKNOWN queda cubierta por las demás relaciones deliberadas. Ninguna
cuota de cobertura obliga a almacenar un UNKNOWN cuando la evidencia es
suficiente (§7).

## 20. Initial Dataset Size

Tamaño propuesto: **~20–40 assertions reales** (dentro de la referencia
20–50 del brief). Justificación de comenzar pequeño:

- Cada assertion con verificación puntual cuesta una revisión completa de
  fuente (quote, alcance, fecha); 20–40 es lo máximo sostenible con esa
  calidad.
- Los 5 ejes (Runtime/Backend/Format/Architecture/Capability) ya se cubren con
  pocas relaciones bien elegidas; el resto es cantidad, no proceso.
- Los UNKNOWN deliberados (§19) y un conflicto-documentado-natural (§22)
  requieren espacio; un dataset grande los diluye.
- El dataset es una prueba de proceso: si funciona con 30, escala; si falla
  con 30, más datos no lo arreglan.

## 21. Coverage Requirements

Matriz conceptual que el dataset debe satisfacer (comprobable en B9.6.1):

| Requisito | Cobertura esperada |
|---|---|
| ≥ 2 runtimes | llama.cpp, Ollama |
| Varios backends | CPU, Vulkan, CUDA, ROCm/HIP, SYCL |
| ≥ 1 formato | GGUF |
| Varias relaciones | runtime→backend, runtime→format, runtime+backend→arch/capability |
| ≥ 1 capability | con evidencia explícita |
| ≥ 1 UNKNOWN | reales y deliberados (§19), de cualquier tipo; UNKNOWN ≠ UNSUPPORTED |
| ≥ 1 scope específico | versión y/o plataforma donde la fuente lo determine |
| Provenance | en toda assertion |

## 22. Conflict Policy

El dataset inicial **no introduce conflictos artificiales**. Si durante la
verificación de B9.6.1 aparece una contradicción real (p. ej. fuente primaria
vs secundaria), se documenta con `KnowledgeConflict` (B9.5): ambas assertions
con sus provenance se conservan, **sin elegir fuente ganadora**, y queda
registrado para revisión futura. Sin resolución automática (B9.5 §12).

## 23. Security

El dataset futuro contiene DATA únicamente. Nunca: comandos, shell, Python
ejecutable, URLs para ejecución, scripts, downloads, instrucciones de
instalación. Una referencia a documentación existe solo como `reference` de
provenance y **no se ejecuta** (coherente con B9.5 §22 y la filosofía general:
CastleArq no modifica el sistema).

## 24. Alpha Boundary

Fuera de la Alpha (y por tanto fuera de este dataset):

- Todos los demás runtimes, backends, formatos, modelos y fabricantes.
- Benchmarks, performance predictions, memory estimation.
- Multi-GPU avanzado, fine-tuning, clusters, orchestration profesional.
- Trust/security scoring, verificación de provenance (B9.0 §18).

B9.6 crea solo el primer núcleo de conocimiento.

## 25. B9.5 Mapping

Mapeo conceptual de cada assertion futura al dominio B9.5:

```text
afirmación                      → KnowledgeAssertion
"runtime/format/arquitectura…"  → KnowledgeSubject (kind + canonical_id)
entidad afectada                → object (kind + canonical_id)
alcance (global/versión/plataforma/variante)
                                → KnowledgeScope (todos opcionales)
fuente                          → KnowledgeProvenance
SUPPORTED/UNSUPPORTED/UNKNOWN   → KnowledgeState
```

Sin modificar B9.5: el dataset es DATA construida con esas estructuras.

## 26. B9.3 Integration Boundary

B9.6 produce conocimiento que posteriormente podrá convertirse en
`RuntimeKnowledge` (estructura de entrada del evaluator B9.3) para alimentar
`evaluate(model, artifact, context)`. **NO se hace esa integración en B9.6**:
B9.6.0/0.1 solo especifican y construyen el dataset; el puente KB→evaluator es
fase posterior (B9.7+).

## 27. Assertion Acceptance Criteria

Una assertion real solo se incorpora si:

1. tiene fuente identificable (jerarquía §10);
2. tiene alcance claro o scope deliberadamente desconocido (§11);
3. no depende de inferencia informal (§18);
4. no contradice silenciosamente otra assertion (§22);
5. usa un `canonical_id` válido del dominio B9.5;
6. puede explicarse en lenguaje humano;
7. puede revisarse posteriormente;
8. no contiene lógica ejecutable (§23).

## 28. Open Decisions

Decisiones que quedan abiertas y no bloquean B9.6.0:

1. **Verificación puntual de enunciados** (§10, §14): quote/alcance/fecha por
   assertion — trabajo de B9.6.1.
2. **Identificadores canónicos definitivos** de arquitecturas con soporte
   explícito (§6): se fijan en B9.6.1 con fuente.
3. **Resolución de aliases** (p. ej. `llama.app`): normalización explícita vs
   entrada dedicada — diseño de B9.4 §6; decidir implementación en B9.6.1.
4. **Comparación de versiones** cuando haya que aplicar scopes de versión:
   parser/matcher (B9.4 §7) — bloque posterior, sin semver en B9.6.
5. **Formato de almacenamiento del dataset** (módulo Python declarativo vs
   datos serializados): decisión de B9.6.1, siempre DATA pura.
