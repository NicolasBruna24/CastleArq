# B9.9 — Strict Evaluation Pipeline Design

Estado: pipeline puro ratificado (D-1 SÍ, D-2 NO, D-3 fuera). No integra
producción: no toca `execution_service.py`, `execution.py`, `selection.py`,
`resolver.py`, `compatibility.py`, `run_service.py` y no reemplaza el
evaluador legacy.

## 1. Problema

Tras B9.8, la cadena estricta existe por piezas (B9.8 → B9.7 → B9.3) pero
nadie la compone en una única llamada determinista con trazabilidad. El
round-trip completo vivía solo dentro de un test de B9.8.

## 2. Responsabilidad de B9.9

Componer, sin añadir conocimiento:

```text
(registry, ModelSpec, ArtifactSpec, capability, backend, required_capabilities, scope)
  → B9.8.to_model / to_artifact(+D-1) / build_evaluation_context
  → B9.7 KnowledgeProjection (dentro del contexto)
  → B9.3 evaluate(model, artifact, context)
  → StrictEvaluation(model, artifact, context, projection, result)
```

B9.9 no interpreta el resultado, no produce recomendaciones, no convierte a
`CompatibilityResult` legacy y no decide sobre ejecución: eso pertenece a un
bloque futuro (B9.10) con su propia política ratificada.

## 3. API

```python
@dataclass(frozen=True)
class StrictEvaluation:
    model: Model
    artifact: ModelArtifact
    context: EvaluationContext
    projection: KnowledgeProjection
    result: CompatibilityResult        # el del dominio estricto B9.3

def evaluate_strict(
    registry: KnowledgeRegistry,
    spec: ModelSpec,
    artifact: ArtifactSpec,
    capability: RuntimeCapability,     # type hint bajo TYPE_CHECKING (patrón B9.8)
    backend: str | None = None,
    required_capabilities: tuple[str, ...] = (),
    scope: KnowledgeScope | None = None,
) -> StrictEvaluation
```

## 4. Decisión D-1 (ratificada)

Tabla declarativa **exacta y cerrada**, definida en B9.9 (B9.8 queda congelado):

```python
CANONICAL_FORMATS = (("GGUF", "gguf"),)
```

- Se aplica **solo** al campo `format` del `ModelArtifact` adaptado por B9.8,
  mediante `dataclasses.replace` (el artifact es frozen).
- `"GGUF"` → `"gguf"`: el check de formato de B9.3 pasa de UNKNOWN a PASSED.
- Cualquier otro valor permanece **sin alterar** (no hay `lower()`, no hay
  case-folding genérico, no hay substring ni fuzzy): un formato no listado
  produce UNKNOWN aguas abajo, jamás UNSUPPORTED.
- La tabla NO debe crecer hacia un normalizador genérico sin nueva
  ratificación.

## 5. UNKNOWN

Todo lo no representado degrada a UNKNOWN: `identifier=None` (N-1) → identidad
UNKNOWN; capabilities `None` → UNKNOWN; backend fuera de la tabla N-4 → None →
UNKNOWN; formato no en CANONICAL_FORMATS → UNKNOWN. Nunca UNKNOWN/ausencia →
UNSUPPORTED. La ausencia no se inventa como assertion UNKNOWN.

## 6. Provenance

`StrictEvaluation.projection` conserva la `KnowledgeProjection` de B9.7
**intacta**: las assertions originales con su provenance, `excluded_unknown`,
`unrepresentable` y `conflicts`. No se copia provenance dentro de
`RuntimeKnowledge` ni se inyecta en el resultado B9.3.

## 7. Conflicts

Los conflictos reportados por B9.7 bajo el scope objetivo se propagan tal cual
en `projection.conflicts`, sin ganador, sin convertirlos en UNKNOWN ni
UNSUPPORTED. La política de decisión ante conflicto es de B9.10+.

## 8. Pureza y determinismo

`evaluation_pipeline.py` no importa `runtimes.py` en runtime (`TYPE_CHECKING`
+ duck-typing, patrón B9.8) ni subprocess/socket/urllib/pathlib/os-environment;
sin `eval`/`exec`; sin filesystem ni red. Mismo input → mismo output; inputs
sin mutar; outputs frozen. El orden interno es el de los bloques ya
deterministas (B9.3 checks fijos, B9.5/B9.7 orden canónico).

## 9. Límites

- Con el dataset B9.6.1 y specs legacy reales, el resultado esperado sigue
  siendo `INSUFFICIENT_EVIDENCE`: identidad UNKNOWN (`identifier=None`),
  capabilities UNKNOWN, backend/format según tablas. Es degradación honesta,
  no regresión.
- Plataforma y versión siguen sin alcance (N-3 y limitación B9.8); el
  conocimiento platform-scoped permanece fuera → UNKNOWN.
- `ModelCapabilities` permanece todo None: B9.9 no añade fuente de
  capabilities.

## 10. Aislamiento de producción

Ningún archivo de producción existente se modifica. B9.9 es aditivo; los 6
módulos de ejecución quedan bit a bit idénticos (verificado por suite y git
status).

## 11. Integración futura (B9.10, fuera de alcance)

El wiring de producción requerirá: política de decisión ante
`INSUFFICIENT_EVIDENCE` y ante conflictos, puente resultado-estricto → decisión
de ejecución (sin fabricar recomendaciones), y fuentes de observación
(plataforma, versión, identidad real de artifacts, capabilities del modelo).

## 12. Acceptance criteria

1. Solo 3 archivos nuevos; 0 existentes modificados.
2. Suite completa verde; `compileall` OK; `git diff --check` OK.
3. Pureza AST; determinismo; inmutabilidad de inputs/outputs.
4. D-1: GGUF→gguf→PASSED; formatos no listados sin alterar.
5. UNKNOWN/ausencia jamás convertidos en UNSUPPORTED; conflictos propagados.
