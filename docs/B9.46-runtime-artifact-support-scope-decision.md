# B9.46.22 — Runtime→Artifact Support Scope Decision

## 1. Executive Summary

El claim mínimo que CastleArq necesita para la ejecución real no es:

```text
llama.cpp supports GGUF
```

sino:

```text
una instancia runtime observada
    +
un artifact físico concreto
    +
evidencia de que el runtime puede consumir ese artifact
```

El claim seleccionado es **runtime instance + physical artifact evidence**. No es Knowledge estática global y no es una igualdad de identidad de artifact.

**Verdict: `RUNTIME-ARTIFACT-SUPPORT-SCOPE-DECIDED`.**

El alcance queda semánticamente decidido, aunque el `bool | None` actual de `RuntimeKnowledge.supports_artifact` sea insuficiente para representarlo. La implementación no pertenece a este bloque.

## 2. Current State

```text
format = PASSED
identity = PASSED
architecture = PASSED
runtime artifact support = UNKNOWN
backend = UNKNOWN
overall = INSUFFICIENT_EVIDENCE
```

La arquitectura física ya llega correctamente mediante:

```text
GGUF general.architecture=qwen2
```

El problema pendiente es la relación entre un runtime concreto y un artifact físico concreto.

## 3. Exact Meaning of `supports_artifact`

`supports_artifact` debe significar, para el scope decidido:

> Una instancia runtime identificada, bajo el contexto de ejecución observado, produjo evidencia positiva de que puede consumir el artifact físico evaluado.

No significa:

```text
el runtime soporta cualquier artifact
```

ni:

```text
el artifact_id es una capacidad del runtime
```

ni:

```text
el backend está disponible
```

ni:

```text
la arquitectura fue reconocida por Knowledge
```

ni:

```text
el artifact tiene checksum/manifest válido
```

La evidencia debe conservar el runtime, el artifact físico, la evidencia observada y las condiciones relevantes (versión/build/backend), sin convertir la observación en autoridad universal.

## 4. Candidate Scopes

| Scope | Decisión | Motivo |
|---|---|---|
| A — Runtime→Format | insuficiente | GGUF no identifica instancia, versión, build o artifact concreto |
| B — Runtime→Architecture | insuficiente | `qwen2` ya tiene check separado; no demuestra consumo del GGUF completo |
| C — Runtime→Format+Architecture | parcial | más preciso, pero todavía no identifica instancia/artifact ni evidencia de consumo |
| D — Runtime+Backend→Artifact | insuficiente | backend es importante, pero no identifica artifact ni demuestra carga |
| E — Runtime→Concrete artifact | correcto sólo como evidencia dinámica | debe expresa una relación runtime-instance/artifact |
| F — Runtime Capability + Physical Artifact Evidence | elegido | refleja la evidencia real y separa observación de Knowledge |


## 5. Knowledge vs Runtime Evidence

Knowledge conserva facts declarativos y normativos, por ejemplo:

```text
runtime supports format GGUF
runtime supports architecture qwen2
```

La evidencia runtime-artifact es dinámica y observada:

```text
runtime instance X loaded artifact Y
```

El claim elegido es el segundo. No se convierte en Knowledge persistente ni se deriva de `format PASSED`, `architecture PASSED` o `backend detected`.

Un check separado ya demuestra Knowledge sobre format y architecture. El nuevo claim debe responder si el runtime real pudo consumir el artifact evaluado.

## 6. Version / Build Scope

La versión y build son parte de la identidad de la evidencia dinámica:

```text
llama.cpp 0.4.0-dev + executable path/build identity
```

No son necesariamente parte de una assertion Knowledge estática, pero deben estar disponibles para no presentar como universal una observación de una build concreta.

El repositorio no demuestra que el soporte sea estable entre versiones/builds. No se introduce version matching en este bloque.

## 7. Backend Scope

El backend es una dimensión del contexto de evidencia:

```text
runtime instance + CPU/Vulkan/CUDA/... + physical artifact
```

No es la definición del claim por sí solo. `backend available` no significa `runtime supports artifact`.

El check de backend permanece separado. Si la evidencia de carga sólo se obtiene con un backend concreto, esa condición queda en la evidencia runtime-artifact y no reemplaza `RuntimeKnowledge.supported_backends`.

## 8. Artifact Format Scope

El formato forma parte de la evidencia física:

```text
artifact.format=GGUF
```

Pero el claim no se reduce a `runtime supports GGUF`. El GGUF concreto, su architecture y su instancia runtime deben quedar relacionados por la misma observación.

`format=PASSED` permanece como check Knowledge independiente. No se elimina ni se fusiona con runtime-artifact support.

## 9. Architecture Scope

`GGUF general.architecture=qwen2` permanece como evidencia física independiente y produce `architecture=PASSED`.

No se usa como sustitución del claim runtime-artifact. La evidencia puede incluir architecture como dimensión/provenance de inspección, pero no redefine `_check_architecture` ni introduce `qwen2 -> qwen3`.

## 10. Artifact Identity Scope

El claim se refiere al artifact físico observado durante la evaluación, no a una identidad lógica.

`ArtifactSpec.artifact_id` puede localizar o identificar el archivo local en la evidencia, pero no se transforma en identidad de modelo ni en nombre de capability.

Permanece separado:

```text
ArtifactSpec.model_id -> ModelArtifact.identifier
```

La evidencia no sustituye `model_id`, `artifact_id`, `ModelArtifact.identifier` ni el state derivado de `ModelStore`.

## 11. Strict Evaluation Semantics

Para el scope elegido:

```text
PASSED =
  evidencia positiva del runtime instance para el artifact físico evaluado

FAILED =
  evidencia negativa explícita y trazable para ese runtime/artifact/context

UNKNOWN =
  no existe evidencia autoritativa suficiente, o la inspección no pudo ejecutarse
```

`UNKNOWN` no se convierte en `FAILED` por ausencia de observation. Reader failure, runtime unavailable y artifact inválido conservan errores separados.

La matriz actual `bool | None` sólo expresa un resultado abstracto, no toda la evidencia necesaria para el scope decidido.

## 12. Existing Representation Sufficiency

```text
RuntimeKnowledge.supports_artifact = INSUFFICIENT
```

Es suficiente como nombre abstracto del check, pero insuficiente para representar:

```text
runtime instance
+
runtime version/build
+
backend context
+
physical artifact reference
+
format/architecture observations
+
evidence provenance
```

No se crea aquí una representación nueva. El siguiente bloque debe ratificar la forma mínima de representar o transportar esta evidencia y después decidir cómo se proyecta al check.

## 13. Decision

```text
RUNTIME-ARTIFACT-SUPPORT-SCOPE-DECISION = RUNTIME INSTANCE + PHYSICAL ARTIFACT EVIDENCE

RUNTIME-ARTIFACT-SUPPORT-SCOPE =
  a specific observed runtime instance consuming the specific evaluated artifact

RUNTIME-ARTIFACT-SUPPORT-AUTHORITY =
  runtime execution/inspection boundary producing traceable evidence

RUNTIME-ARTIFACT-SUPPORT-SOURCE =
  read-only runtime/artifact evidence; not static format, architecture or backend Knowledge

RUNTIME-ARTIFACT-SUPPORT-PERSISTENCE = NONE
```

`RuntimeKnowledge.supports_artifact` remains the strict check's abstract result, but it cannot be populated from a new authority until the evidence contract is implemented and projected.

## 14. Next Implementation Boundary

The next implementation block must only:

1. define the minimum ephemeral evidence shape for runtime instance + physical artifact observation;
2. preserve runtime identity/version/build and artifact reference;
3. preserve format/architecture and backend as separate evidence dimensions;
4. distinguish success, explicit negative and unavailable evidence;
5. transport the evidence through the existing application/evaluation boundary;
6. project the derived result to `_check_runtime()` without changing GGUF reader, Knowledge or admission semantics;
7. test that `format=PASSED`, `architecture=PASSED`, backend detection and `UNKNOWN` are not treated as runtime-artifact success;
8. keep adapter filesystem-free, evidence non-persistent, identity unchanged and no new manager/service/registry.

No implementation is performed in this block.

## 15. Non-Goals

- no backend implementation;
- no runtime selector changes;
- no runner changes;
- no GGUF reader changes;
- no architecture changes;
- no identity changes;
- no persistence;
- no Knowledge changes in this block;
- no evaluator or admission changes in this block;
- no test modifications in this block;
- no commit and no push.
