# B9.41 — Metadata Ownership Audit

> Auditoría arquitectónica **de solo lectura** sobre la propiedad y semántica de
> la metadata de artefactos locales. No se modificó código, tests ni
> documentación existente para producir este documento.
>
> Alcance de evidencia: `app/` (búsquedas globales de `state`, `verified`,
> `downloaded_at`, `save_manifest`, `inspect_manifest`, `list_artifacts`,
> `ArtifactSpec`, `ModelArtifact`) y `tests/` (contratos congelados).

---

## 1. Executive Summary

1. **`state` y `verified` no aportan información en producción.**
   `run_download()` (B9.40) persiste el `ArtifactSpec` recién creado por el
   source adapter, cuyo estado es siempre `NOT_DOWNLOADED`
   (`app/sources/huggingface.py:126`). Por tanto, **todo manifest de producción**
   registra `state="not_downloaded"` y `verified=false` aunque el archivo ya
   esté publicado y su checksum sea correcto. La anomalía observada en el probe
   vertical de B9.40 no es un caso aislado: es el único resultado posible del
   esquema actual.

2. **Nadie lee `state`/`verified` del manifest para decidir.** El planner
   (`app/downloads/planner.py:104-116`), el resolver (`app/resolver.py:79-105`),
   la CLI (`app/main.py:592`), la API (`app/api.py:735-780`), la ejecución
   (`app/execution.py:223-297`) y la evaluación (sin referencias) consumen
   exclusivamente estado **derivado** (`StoredArtifact.state`) o su propia
   re-derivación desde el filesystem. Las únicas lecturas del `state` persistido
   son: (a) su validación de esquema en `_artifact_from_payload`
   (`app/model_store.py:292-296`, un valor desconocido invalida el manifest
   entero → `FAILED`) y (b) la igualdad round-trip de **un** test de resolver.

3. **`verified` y `downloaded_at` son campos write-only en todo el repo**
   (grep `payload.get("verified")` / `["downloaded_at"]`: 0 coincidencias en
   `app/` y `tests/`). `_artifact_from_payload` no los consume; ningún DTO los
   expone; ninguna decisión los usa.

4. **El contenido realmente load-bearing del manifest es: identidad +
   locators + expectaciones declaradas (`size_bytes`, `sha256`) + timestamp de
   registro.** La única columna del write leg es `downloaded_at`
   (`app/model_store.py:138`). No existe campo `artifact_id` en el JSON (es una
   `property` y el nombre del directorio) ni campo de versión de esquema.

5. **La decisión ya está ratificada y la implementación la incumple en el
   registro.** B9.39 D-5 (`docs/B9.39-model-representation-consolidation-decision.md:458-489`)
   declara: estado derivado, nunca almacenado con autoridad; el valor persistido
   es informativo e inerte. `README.md:253-256` dice lo mismo. Pero el registro
   persistido **contradice sistemáticamente** el filesystem en cada nueva
   descarga (violación de I-3 a nivel de datos, aunque no a nivel funcional).

6. **Recomendación única: Opción C + documentación (A).** Dejar de persistir
   `state` y `verified`; conservar `downloaded_at` como marca de adquisición;
   mantener lectura tolerante de manifests legacy que sí contengan `state`;
   documentar el manifest como *registro de adquisición + expectativas*, con el
   estado siempre derivado. **Se rechaza explícitamente** el parche
   `state="verified"` (analizado en §9): reintroduciría estado almacenado con
   autoridad y sería incorrecto cuando `sha256` es `None` o si el archivo se
   corrompe después.

## 2. Current Metadata Model

### 2.1 Ciclo real y dueños por etapa

```text
discover   HuggingFaceSource.discover_artifacts
           → ArtifactSpec(frozen, state=NOT_DOWNLOADED)     dueño: source adapter
             identidad + locators + expectaciones (size/sha)

select     select_artifact (sin estado)

plan       DownloadPlanner.plan
           → valida expectaciones del spec
           → inspect_manifest(path) si existe manifest       dueño: ModelStore (derivación)
             usa StoredArtifact.state (DERIVADO), jamás manifest['state']

download   Downloader.download
           → publica archivo + verifica size/sha en tránsito  dueño: Downloader (transferencia)
           → jamás toca manifest (tests/test_downloader.py::test_manifest_is_unchanged)

publish    run_download (app/main.py:824-841)
           → ModelStore.save_manifest(artifact)              dueño: ModelStore (registro)
             payload = expectaciones + identidad + downloaded_at
             (state copiado del spec; verified = f(state))

read       list_artifacts / inspect_manifest                 dueño: ModelStore
           → estado DERIVADO = f(payload, filesystem)
             .part / existencia / tamaño / SHA-256

consume    resolver (gating), api DTO, CLI list, execution preflight
           → todos leen estado derivado o re derivan ellos mismos
```

### 2.2 Dos (y más) semánticas llamadas "state"

| Semántica | Tipo | Dónde | ¿Autoridad? |
| --- | --- | --- | --- |
| `manifest['state']` | copia persistida del spec | `model_store.py:137` | **No** (inerte; solo gate de parseo) |
| `StoredArtifact.state` | derivación por inspección | `model_store.py:159-189` | **Sí** (única respuesta expuesta) |
| `ArtifactFilesystemState` | hechos crudos de archivos | `downloads/inspection.py:29-108` | Insumo de la derivación |
| `DownloadResultStatus` | resultado de transferencia | `downloads/downloader.py` | Solo durante la descarga |
| `ExecutableArtifact.size_verified/checksum_verified` | re-verificación por ejecución | `execution.py:207-297` | Gate de arranque (in-memory) |
| `RecoveryDecision` | decisión sobre inspección | `downloads/recovery.py:42-65` | Read-only, no persiste |

### 2.3 Metadata declarada vs. observada vs. de adquisición

- **Declarada (identidad + expectaciones)**: `model_id`, `source`,
  `repository`, `filename`, `format`, `quantization`, `download_url`,
  `size_bytes`, `sha256`. Dueño: source adapter → persistida en el manifest.
  `size_bytes`/`sha256` son *expectaciones* (oráculo remoto), no observaciones:
  la observación real vive en el filesystem y siempre se recalcula.
- **Observada (estado local)**: existe/`.part`/tamaño/SHA reales. Dueño:
  `ModelStore` (derivación). **Nunca se persiste con autoridad.**
- **De adquisición (write leg)**: `downloaded_at`. Dueño: `ModelStore`
  (`_write_manifest` genera el timestamp). Auditoría pura.

| `downloaded_at` (ISO-8601 UTC) | `datetime.now()` en cada escritura | `ModelStore` (registro de adquisición) | no (es historia) | auditoría; ninguna decisión lo lee | **sí** (como marca de registro) |

Fuera del JSON:

- **`artifact_id` NO es un campo persistido.** Es `ArtifactSpec.artifact_id`
  (`app/models.py:51-56`): `sha256(source|repository|filename|quantization)`,
  materializado como nombre de directorio (`root/<model_id>/<artifact_id>/`).
  Siempre derivable; pertenece al dominio de identidad, no al registro.
- No hay campo `version`/`schema_version` (grep en `model_store.py`: 0).

### 3.1 Respuestas focalizadas (state, verified, downloaded_at, …)

- **`state`**: se escribe en `model_store.py:137`; se lee/valida en
  `model_store.py:292-296` (ausente → default `not_downloaded`; inválido →
  `ValueError` → manifest completo `FAILED` con `artifact=None`). El spec
  reconstruido lo arrastra en `StoredArtifact.artifact.state`, pero **cero
  código de producción lee ese atributo** (grep `\.artifact\.state`: solo un
  test que compara su propio fixture). Representa únicamente **información
  transportada** (el default con que se creó el spec), ni estado local, ni
  metadata declarada útil, ni estado remoto.
- **`verified`**: escrito en `model_store.py:139`; **nunca leído**. En
  producción siempre `false` (porque `state` siempre es `not_downloaded`).
- **`downloaded_at`**: generado por escritura (`model_store.py:138`);
  en producción ≈ hora de finalización de la descarga (se persiste tras
  `result.success`), en tests = hora de siembra. **Nunca se actualiza al
  verificar** (la verificación no escribe manifiests); la migración lo preserva
  (`manifest_migration.py:179-202` copia el payload salvo `model_id`). No
  participa en ninguna decisión; no es obligario para funcionar (0 lectores).
- **`artifact_id` / `model_id`**: ver arriba; `model_id` es el único campo con
  escritor de corrección posregistro (`_rewrite_manifest`, migración explícita
  e idempotente).

## 4. ArtifactSpec Semantics

### 4.1 Definición y valores

- Definido en `app/models.py:38-56` (`@dataclass(frozen=True)`), campo
  `state: ArtifactState = ArtifactState.NOT_DOWNLOADED` (`models.py:49`).
- Valores posibles (`models.py:30-35`): `not_downloaded`, `downloading`,
  `downloaded`, `verified`, `failed`.

### 4.2 Quién lo crea / modifica / lee / serializa

| Rol | Quién | Evidencia |
| --- | --- | --- |
| Crea (producción) | `HuggingFaceSource.discover_artifacts` → `state=NOT_DOWNLOADED` | `app/sources/huggingface.py:116-127` |
| Crea (producción) | `print_plan` (default del dataclass) | `app/main.py:657-665` |
| Crea (producción) | `DownloadPlanner._blocked` (spec sintético `"Unknown"`) | `app/downloads/planner.py:226-231` |
| Crea (carga) | `_artifact_from_payload` desde el manifest | `app/model_store.py:305-316` |
| Modifica | **nadie** — frozen y sin ningún `replace(..., state=...)` en `app/` | grep `dataclasses.replace`: solo `huggingface.py:225` (size/sha) |
| Escribe a disco | `_write_manifest` | `app/model_store.py:137,139` |
| Lee (decisión) | **nadie en producción** | planner/resolver/API/CLI leen `StoredArtifact.state` |
| Lee (validación) | `_artifact_from_payload` (gate de esquema) | `app/model_store.py:292-296` |
| Lee (tests) | igualdad round-trip, defaults, inmutabilidad | ver §8 |

### 4.3 ¿Tiene autoridad semántica real?

**No.** El nombre `state` es engañoso:

- No es estado local: nunca se observa el filesystem para fijarlo.
- No es estado remoto: el remoto no tiene "descargado/verificado".
- No es metadata declarada útil: en producción es una constante
  (`NOT_DOWNLOADED`) que no discrimina nada.
- Es **solo información transportada**: el valor por defecto que el spec
  arrastra desde su creación hasta (eventualmente) el payload.

Autoridad real de estado = `StoredArtifact.state` (`model_store.py:159-189`),
que además **ignora por diseño** el `state` persistido: la prueba congelada está
en `tests/test_model_store.py:216-223` (siembra `state=VERIFIED`, escribe el
archivo, la inspección devuelve `DOWNLOADED`).

`ArtifactSpec` **no** es hoy un objeto lifecycle mutable (satisface I-5): es
frozen, nadie lo muta y tests congelan esa inmutabilidad
(`test_execution_integration.py:241-247`, `test_runner.py:313-315`,
`test_download_planner.py:159-168`). El riesgo de que *llegue* a serlo lo
mantiene precisamente vivo el campo `state` en el esquema persistido.

### 4.4 Pregunta 6 — ¿múltiples fuentes de verdad para "verified/downloaded/…"?

Inventario de campos homólogos:

| Campo equivalente | Dónde | Naturaleza |
| --- | --- | --- |
| `ArtifactSpec.state` | `models.py:49` | default transportado, inerte |
| `ModelArtifact` (B8 estricto) | `model_domain.py:215-250` | **no tiene** campos lifecycle (correcto) |
| `manifest['state']`, `['verified']` | `model_store.py:137,139` | copia persistida inerte |
| `StoredArtifact.state` | `model_store.py:44-49` | derivación (autoridad expuesta) |
| resolver: gating por estado | `resolver.py:79-105` | consume la autoridad |
| `DownloadPlanStatus` + `existing` | `planner.py:38-53` | decisión de plan, no persistida |
| `ArtifactFilesystemState` | `downloads/inspection.py:29-33` | hechos crudos (insumo) |
| `DownloadResultStatus` incl. `PARTIAL_COMPLETE_UNVERIFIED` | `downloader.py:54` | transferencia, en memoria |
| `ExecutableArtifact.size_verified/checksum_verified` | `execution.py:207-213` | re-verificación por ejecución, en memoria |
| campos equivalentes en evaluación | `evaluation_adapter.py`, `evaluation_pipeline.py`, `evaluate_compatibility.py` | **ninguno** (grep `state/installed/available/local`: 0) |
| `VerificationStatus.VERIFIED` | `remediation_verification.py:72-76` | dominio distinto (remediación de compatibilidad), no lifecycle |

Conclusión: existen **tres derivaciones vivas** (store, inspector de
descargas, preflight de ejecución) más **una copia muerta** (`verified`
persistido). Las tres derivaciones leen los mismos hechos de filesystem y no
se contradicen; la copia muerta es la única fuente que puede contradecir.

## 5. ModelStore Semantics

### 5.1 `save_manifest()` (`app/model_store.py:98-157`)

- **Recibe**: un `ArtifactSpec` (identidad + locators + expectaciones + el
  `state` heredado).
- **Transforma**: solo validación de seguridad de rutas
  (`_safe_filename`, `_safe_model_id`, symlinks rechazados) y apertura
  atómica de directorios (`O_NOFOLLOW`, modo `0o700`).
- **Escribe**: el payload de §3 vía `manifest.json.part` + `fsync` +
  `os.replace` (atómico).
- **Añade timestamps**: sí — `downloaded_at = datetime.now(timezone.utc)`
  (`model_store.py:138`), **en cada escritura** (re-registro pisa la marca).
- **Normaliza valores**: no (no pliega case, no convierte defaults); solo el
  timestamp y el cómputo `verified = (state == VERIFIED)` (línea 139).
- **Persiste estado**: sí, literalmente lo copia del spec (línea 137) — sin
  observar nada.
- **¿Puede producir información que contradiga al filesystem?**: **Sí.** Es
  exactamente el hallazgo del probe de B9.40: persiste `state="not_downloaded"`
  y `verified=false` justo después de que el transfer publicó un archivo cuya
  inspección deriva `VERIFIED`. No hace ninguna inspección en el momento de
  escribir, así que *nunca* puede emitir un estado verdadero.
- **Dueño conceptual de cada campo**: ver tabla de §3.

**Clasificación (con evidencia): D — combinación ambigua.**

- (A) persistencia de metadata declarada: los campos de identidad y
  expectaciones lo son (`huggingface.py:116-127` → payload sin cambios).
- (C) registro de adquisición: el `downloaded_at` es una marca de evento que
  solo existe gracias a la escritura, y la creación de
  `root/<model_id>/<artifact_id>/` es el acto de registrar.
- (B) snapshot de estado: **no** — no inspecciona el filesystem, por lo que no
  puede ser un snapshot; los campos `state`/`verified` son un *intento*
  vestigial de snapshot que nunca observó nada.
- La mezcla sin declarar qué es qué es justamente lo que produce la
  contradicción C-1/C-2 (§7): la opción B no está dada, está *sugerida
  erróneamente* por el esquema.

### 5.2 `inspect_manifest()` (`app/model_store.py:159-189`)

Derivación exacta (Pregunta 4):

```text
manifest metadata (expectaciones + identidad)
  + filesystem facts (.part, existencia, tamaño real, SHA real)
  + comparación contra expectaciones
  = StoredArtifact.state
```

| Condición (en orden) | Estado derivado | `message` |
| --- | --- | --- |
| JSON inválido / campo requerido ausente / `state` desconocido / path unsafe / symlink | `FAILED` (`artifact=None`) | error capturado |
| existe `<filename>.part` | `DOWNLOADING` | — |
| falta el archivo final | `NOT_DOWNLOADED` | — |
| `size_bytes` declarado ≠ tamaño real | `FAILED` | "File size differs from manifest" |
| `sha256` declarado y coincide | `VERIFIED` | — |
| `sha256` declarado y no coincide | `FAILED` | "SHA-256 differs from manifest" |
| sin `sha256` y archivo presente con tamaño ok | `DOWNLOADED` | — |

**Papel del manifest en la derivación**: requisito de *localización e
identidad* + fuente de las *expectaciones* contra las que se contrasta el
filesystem. **No participa como autoridad de estado**: su campo `state` jamás
se consulta para decidir (solo para validar que el string sea un miembro
válido del enum). La autoridad del resultado son los hechos observados.

### 5.3 `list_artifacts()` (`app/model_store.py:90-96`)

- **Devuelve**: `list[StoredArtifact]` = `{artifact reconstruido (spec desde
  payload), state DERIVADO, manifest_path, message}`. No devuelve el JSON crudo.
- **Reconstruye `ArtifactSpec`**: sí, vía `_artifact_from_payload`
  (`model_store.py:287-316`) con defaults para campos ausentes
  (`state` ausente → `NOT_DOWNLOADED`; `format/quantization` ausentes →
  `"Unknown"`; `download_url` no-str → `None`).
- **Recalcula estado**: sí, en cada llamada, por `inspect_manifest`.
- **¿Puede devolver un estado distinto de `manifest['state']`?**: **Sí, es su
  comportamiento normal y congelado** (`test_model_store.py:216-223`).
- **Manifest inconsistente**: degradación granular — JSON/esquema roto →
  entrada `FAILED` con `artifact=None` (se lista en "Invalid artifacts" en la
  CLI y al final en la API); contenido roto → entrada `FAILED` con spec
  reconstruido. Nunca lanza excepción al llamador.

## 6. Derived State Rules

### 6.1 Regla de derivación

```text
manifest metadata          filesystem facts            comparación
─────────────────          ────────────────            ───────────
model_id   (identidad)     .part existe?               size real == size_bytes?
filename   (ruta)          final existe?               sha real  == sha256?
size_bytes (expectación)   size real                   ↓
sha256     (expectación)    sha real                    estado derivado
                │                 │                     NOT_DOWNLOADED / DOWNLOADING /
                └────────┬────────┘                     DOWNLOADED / VERIFIED / FAILED
                         ▼
              StoredArtifact.state  (única autoridad expuesta)
```

Reglas operativas comprobadas:

1. El estado **se recalcula en cada inspección**; nada lo cachea entre
   invocaciones (resolver/plan/list siempre llaman `list_artifacts`/`inspect_manifest`).
2. El manifest **identifica, localiza y aporta expectaciones**; nunca aporta
   el resultado del estado.
3. La ejecución re-verifica por su cuenta (`ArtifactExecutionPreflight`,
   `execution.py:223-297`) contra las *mismas* expectaciones del manifest:
   allí el manifest es **oráculo** (expected), el filesystem es **observación**
   (actual). Consistente con la regla 2.
4. Ningún campo derivable del filesystem se persiste como estado (hoy se
   incumple: `state`/`verified`).

### 6.2 Invariantes evaluados

**I-1 — El filesystem es la autoridad para determinar si el archivo existe.**
✅ **Ratificar.** Evidencia: `inspect_manifest` decide con
`file_path.exists()`/`partial_path.exists()`; el planner solo decide
`ALREADY_DOWNLOADED` cuando la *derivación* (no el manifest) lo dice;
`ArtifactCleanup` puede borrar el archivo pero **nunca** el manifest
(`cleanup.py:57-58`) → un registro puede sobrevivir sin archivo y el sistema
lo reporta `NOT_DOWNLOADED` correctamente. Adición necesaria: el manifest es
requisito de *descubrimiento* (sin él el archivo es invisible), de modo que la
autoridad de existencia es el filesystem y la de registro es el manifest; la
interacción correcta es exactamente la derivación actual.

**I-2 — El checksum/tamaño real es la autoridad para verificar.**
✅ **Ratificar con refinamiento.** La verificación es una *comparación*: la
expectación (`sha256`/`size_bytes`) vive en el manifest (declarada, remota) y
la observación en el filesystem. Ninguno basta solo: sin expectación no hay
`VERIFIED` (regla congelada: `test_model_store.py:73-79`), sin observación no
hay verificación. Autoridad del *resultado*: los bytes observados, contrastados
contra la expectación persistida.

**I-3 — El manifest identifica y registra, pero no puede contradecir hechos
derivados del filesystem.**
✅ **Ratificar — y es el invariante que viola B9.41 hoy.** La contradicción
actual (C-1/C-2) no daña decisiones porque nadie lee esos campos, pero deja en
disco un registro que miente a cualquier lector crudo (humano o futuro código)
y contradice B9.39 D-5 y `README.md:253-256`. La corrección es dejar de
persistir el estado, no sincronizarlo (un estado persistido "verdadero" hoy
volvería a mentir mañana ante cualquier corrupción).

**I-4 — `ModelStore` es el único propietario del estado local
persistido/derivado.**
⚠️ **Ratificar con precisión.** Es dueño de la *respuesta expuesta*
(`StoredArtifact.state`) y del registro persistido; nadie más escribe estado.
Pero la *lógica* de derivación está triplicada (`inspect_manifest`,
`ArtifactFilesystemInspector`, checksum del preflight de ejecución). Las tres
leen los mismos hechos → sin conflicto de verdad hoy, sí duplicación de
mantenimiento. Redactar el invariante como: *ModelStore es el único propietario
de la persistencia y de la API de estado; otras capas pueden re-derivar desde
el filesystem, pero jamás persistir ni cachear estado.*

**I-5 — `ArtifactSpec` no debe convertirse en un objeto lifecycle mutable.**
✅ **Ratificar.** Satisfecha hoy (frozen, cero mutaciones, tests que congelan
inmutabilidad: `test_execution_integration.py:241-247`,
`test_runner.py:313-315`, `test_download_planner.py:159-168`). El campo
`state` persistido es la puerta de entrada tentadora para romperla; retirarlo
del esquema reduce la superficie (el spec queda como descriptor declarativo).

**I-6 (candidata nueva) — Ningún campo derivable del filesystem debe
persistirse como estado; todo timestamp de adquisición debe ser inmutable una
vez emitido el registro inicial.**
✅ Proponer. Cubre C-1, C-2 y C-3 de una sola vez y es verificable
estáticamente (grep de escritura).

## 7. Contradictions Found

### C-1 `manifest['state']` ≠ estado derivado (sistémica)

```text
manifest:   state = "not_downloaded"   (constante de producción)
filesystem: archivo publicado + size ok + sha ok
inspección: VERIFIED
```

- **Origen**: `save_manifest` copia el spec sin inspeccionar
  (`model_store.py:137`); el spec siempre llega con `NOT_DOWNLOADED`
  (`huggingface.py:126`).
- **Impacto por consumidor**:

| Consumidor | ¿Lee `manifest['state']`? | Impacto funcional | Impacto de registro |
| --- | --- | --- | --- |
| planner | no (usa derivado) | ninguno | ninguno |
| resolver | no (usa derivado) | ninguno | ninguno |

- Gravidad: **de datos, no de comportamiento** (la suite completa pasa y el
  probe de B9.40 deriva `VERIFIED`), pero viola I-3 en cada registro nuevo.

### C-2 `manifest['verified']` = `false` ≠ resultado de checksum

Misma raíz; agravante: `verified` es **write-only** — la contradicción existe
sin ningún lector. En producción es siempre `false` (constante). Es el campo
más candidato a eliminación de todo el esquema.

### C-3 `downloaded_at` no significa "descarga verificada"

Se genera en la escritura, nunca se actualiza al verificar, la migración lo
preserva, nadie lo lee. En producción coincide con el fin de la transferencia;
en tests significa "cuándo se sembró". Semántica real: **`registered_at`**.
Ninguna decisión depende de él (Pregunta 7: es solo histórico/auditoría; no es
obligatorio).

### C-4 Salida CLI vs. estado derivado (cosmético)

`main.py:837-839` imprime `"SHA-256 verified."` y acto seguido
`"Artifact state: downloaded"` **hardcodeado**, mientras que `list` mostrará
`VERIFIED` para el mismo artefacto. Ambos valores son aceptables para el
resolver; es una inconsistencia de wording, no de semántica.

### C-5 Acoplamiento de gate de parseo al enum persistido

`_artifact_from_payload` exige que `state` sea un miembro válido del enum
(`model_store.py:292-296`): un valor desconocido (p. ej. un miembro retirado
del enum en el futuro) invalida el manifest completo → el artefacto deja de
ser resoluble. El esquema persistido queda así **cristalizado al revés**: no
por valor sino por gate. Nota importante: el lector **ya tolera la ausencia**
del campo (`payload.get("state", default)`), lo que prueba que retirarlo del
escritor es compatible de lectura (hacia adelante y hacia atrás).

### C-6 Contratos de test congelados que protegen la persistencia de `state`

- `tests/test_resolver.py:61` — `assertEqual(result.artifact, artifact)` exige
  round-trip completo del spec, **incluido** `state=VERIFIED` del fixture.
- `tests/test_manifest_migration.py:79` — `payload["state"] == "verified"`.

Estos tests congelan *incidentalmente* la persistencia que D-5 declaró inerte:
son contratos a_resolver **antes** de implementar (§11), no razones para
mantener el campo.

### C-7 `ArtifactSpec` ≠ `ModelArtifact` (duplicidad estructural)

Dos representaciones de artefacto (`models.py` vs `model_domain.py:215-250`)
— hallazgo C-1/C-5 de B9.39, fuera de alcance aquí. Ninguna contiene estado de
lifecycle; el adaptador de evaluación no copia `state`
(`evaluation_adapter.py`: 0 referencias). No hay contradicción de estado entre
ambas.

### C-8 Derivación paralela en ejecución

`ArtifactExecutionPreflight` re-verifica tamaño/SHA con su propia implementación
(`execution.py:269-291`) en lugar de reusar `inspect_manifest`. Lee los mismos
hechos → mismo resultado esperado; duplicación de mantenimiento (bajo I-4), no
conflicto de verdad. No forma parte de B9.41.

## 9. Architectural Options

Comparación basada en evidencia; ninguna se implementa aquí.

### Opción A — Solo corregir semántica/documentación del manifest

- **Qué**: declarar en docs/docstrings que `state`/`verified` son
  informativos/cache y que la autoridad es la derivación (hoy ya lo dicen
  `README.md:253-256` y B9.39 D-5).
- **A favor**: cero churn de código/tests.
- **En contra**: el registro **sigue mintiendo** en cada descarga nueva; la
  contradicción C-1/C-2 queda permanente en disco; el gate de parseo C-5
  permanece; la documentación ya dice "inerte" y el esquema lo contradice — es
  exactamente la deuda que motivó B9.41.
- **Veredicto**: insuficiente.

### Opción B — Modificar qué campos se persisten

- **Qué**: ajuste genérico del payload sin definir semántica.
- **Análisis**: es el paraguas de C con menos precisión; como categoría
  solitaria no dice *qué* ni *por qué*. Se subsume en C.

### Opción C — Eliminar campos redundantes `state` / `verified`

- **Qué**: dejar de escribir ambos; mantener lectura tolerante de manifests
  legacy que los contengan (el lector ya lo hace); documentar.
- **A favor**: elimina C-1, C-2 y C-5 de raíz; 0 consumidores de producción
  los leen (grep); 19/21 contratos de test indiferentes; coherente con D-5,
  I-3, I-5 e I-6; compatible de lectura en ambas direcciones (campo ausente →
  default, campo presente → validado).
- **En contra**: exige re-expresar T-7 (`test_resolver` igualdad) y T-9
  (`payload["state"]`); deja `ArtifactSpec.state` como default no persistido
  (ver decisión pendiente en §11).
- **Costo**: 1 archivo de producción (`app/model_store.py`) + 2 tests +
  documentación.

### Opción D — Separar metadata declarada de metadata de adquisición

- **Qué**: dos estructuras/archivos (p. ej. `spec.json` + `adquisition.json`).
- **A favor**: pureza conceptual máxima.
- **En contra**: **hoy no existe ningún segundo escritor/lector que lo
  requiera**; crearía una representación nueva (non-goal) y una abstracción
  nueva sin consumidor — justo lo que B9.39 prohíbe; el manifest único ya
  contiene los tres tipos de dato perfectamente identificables por campo
  (§2.3). La separación se justificaría si en el futuro apareciera un log de
  eventos (re-verificación, re-descarga), que hoy no existe.
- **Veredicto**: sobre-ingeniería actual; no elegir por preferencia estética.

### Opción E (variante del parche) — Persistir `manifest.state = "verified"`

- **Qué**: escribir el estado derivado/observado en el registro.
- **Por qué se rechaza con evidencia**:
  1. `save_manifest` no inspecciona: para escribir `VERIFIED` debería
     re-derivar en el momento de escribir (costo de SHA completo + carrera con
     la publicación), y si `sha256` es `None` el valor correcto sería
     `DOWNLOADED`, no `VERIFIED` (T-4).
  2. Reintroduce **estado persistido con autoridad** → viola directamente
     B9.39 D-5 y el propio enunciado de esta auditoría ("no solucionar
     automáticamente… eso sería solamente un parche").
  3. Cualquier corrupción posterior vuelve a dejar el registro mintiendo
     (todo el motivo de I-3).
  4. Enmascara en lugar de corregir la propiedad: nadie necesita ese valor.

### Opción E' — Mantener `state` y solo documentarlo como "estado declarado al registrar"

- Variante nominal de A: renombrar mentalmente el campo a "estado en el
  momento de crear el spec". En producción ese valor es la constante
  `not_downloaded`, o sea **cero información persistida**; el esquema seguiría
  engañando y el gate C-5 permanece. No supera el test de "¿qué dato real
  transporta?".

## 10. Recommended Decision

**Recomendación única: Opción C + documentación asociada (A como parte de C),
con lectura tolerante de manifests legacy.**

La decisión se sustenta en esta cadena de evidencia:

1. El único campo de adquisición real es `downloaded_at`; `state` y `verified`
   en producción son **constantes sin información** (`not_downloaded` /
   `false`) porque el spec proviene del source adapter y nadie lo muta.
2. **Cero consumidores de producción** leen `state`/`verified` del payload
   (grep de `payload.get(...)`: solo el gate de validación de `state`;
   `verified` y `downloaded_at`: 0 lectores). Planner, resolver, CLI, API,
   ejecución y evaluación funcionan con derivación.
3. La autoridad del estado ya está ratificada como **derivada** (B9.39 D-5;
   `README.md:253-256`; test T-2 congelado). Mantener en el esquema un campo
   que la derivación ignora obliga a sostener una contradicción permanente en
   disco (C-1/C-2) sin ningún beneficio.
4. El lector **ya tolera la ausencia** del campo (`model_store.py:292`
   `payload.get(...)` con default), por lo que retirarlo del escritor es
   compatible en ambas direcciones: manifests nuevos sin `state` y legacy con
   `state` siguen leyéndose.
5. El parche "escribir `verified`/`true`" (Opción E) fracasa semánticamente
   (sin `sha256` el estado correcto es `DOWNLOADED`; con corrupción futura el
   registro vuelve a mentir) y reintroduce exactamente la autoridad
   persistida que D-5 prohíbe.
6. La Opción D no tiene ningún consumidor que la justifique hoy y crearía una
   representación nueva (non-goal).

**Definición de la semántica resultante del manifest:**

```text
manifest.json  =  registro de adquisición (identidad + locators + expectaciones
                  declaradas + marca de registro downloaded_at)
estado local   =  SIEMPRE derivado por ModelStore (filesystem + expectaciones)
ArtifactSpec   =  descriptor declarativo inmutable; state es un default de
                  descubrimiento no persistido (candidato a retiro posterior)
```

**Rechazos explícitos:** escribir `state="verified"`; sincronizar el estado
persistido tras cada inspección; separar en dos ficheros; convertir `state` en
un "snapshot" observado.

## 12. Non-Goals

Queda explícitamente fuera de B9.41:

- **Nuevas representaciones** de artefacto/modelo (no crear tipos ni
  estructuras nuevas; ninguna variante de `StoredArtifact`/`ArtifactSpec`).
- **Lifecycle manager** (no introducir una máquina de estados persistida ni un
  servicio de transiciones; la derivación por inspección se mantiene).
- **Cambios de resolver no relacionados** (la política de gating
  `resolver.py:79-105` no cambia; solo su contraparte de persistencia).
- **Compatibility engine** (B9.3/B9.7/B9.8: evaluación, knowledge bridge,
  remediation — ningún archivo).
- **Ejecución** (`execution.py`, `execute_model.py`, `run_service.py`,
  runners): su re-verificación independiente se conserva tal cual.
- **Packaging** (B9.30: rutas default, distribución).
- **GUI / API surface**: no cambiar DTOs ni endpoints (el DTO `state` sigue
  siendo el derivado).
- **Remote/cloud lifecycle**: ninguna gestión remota de estados.
- **Borrado de datos existentes**: los manifests ya escritos se leen
  tolerando sus campos legacy; no hay migración forzada.
- **Commits/push**: no realizar.
