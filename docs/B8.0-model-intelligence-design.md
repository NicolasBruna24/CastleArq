# B8.0 — Model Intelligence Design

Estado: **decisión de diseño documentada — sin implementación.**

CastleArq inicia la rama **Model Intelligence**. Este documento registra
**qué información debe conocer CastleArq sobre un modelo de IA** antes de que
una futura capa (Compatibility Engine, B8.1+) pueda determinar si ese modelo
es viable para un hardware/runtime determinado.

B8.0 **no implementa** clases de dominio, I/O, APIs ni lógica de
compatibilidad. Es una fase exclusivamente documental, coherente con la
filosofía establecida desde B1:

```text
detect → interpret → propose → user decides → user acts → verify → re-diagnose
```

CastleArq **no modifica automáticamente el sistema del usuario**.

---

## 1. Objetivo de B8.0

Definir el **contrato conceptual** que describirá los modelos de IA y sus
artefactos, de forma que:

- la identidad de un modelo no se confunda con una variante distribuible;
- lo desconocido se represente explícitamente (nunca se invente);
- las conclusiones de viabilidad (compatible, VRAM necesaria, etc.) queden
  fuera del modelo de datos y pertenezcan a la capa que interpreta.

La implementación de las estructuras de dominio corresponde a **B8.1 — Model
Domain**, tras revisar este contrato.

---

## 2. Modelo lógico vs artefacto

**Decisión:** un modelo lógico y un artefacto ejecutable/distribuible son
conceptos diferentes.

```text
Qwen3-Coder-30B-A3B              ← modelo lógico (identidad)
│
├── GGUF / Q4_K_M                ← artefacto (variante concreta)
├── GGUF / Q5_K_M
├── GGUF / Q8_0
└── Safetensors / BF16
```

- El **modelo lógico** representa la identidad y características generales:
  qué es el modelo, de dónde proviene, qué arquitectura tiene y qué puede
  hacer.
- El **artefacto** representa una variante concreta que puede ser almacenada,
  distribuida o utilizada por un runtime: un formato, una cuantización, un
  tamaño de almacenamiento.

Reglas derivadas:

1. El mismo modelo lógico puede tener **múltiples artefactos**.
2. Una cuantización diferente **no constituye automáticamente un modelo
   diferente**: es otra variante del mismo modelo lógico.
3. La relación modelo↔artefacto es 1:N; el artefacto referencia a su modelo
   lógico (no al revés).

## 3. Categorías de información del modelo

### 3.1 Identity — identificar el modelo

| Campo | Significado |
|---|---|
| `name` | Nombre legible. **Conceptualmente obligatorio.** |
| `model_id` | Identificador canónico dentro de CastleArq. |
| `version` | Versión del modelo, si se conoce. |
| `variant` | Variante declarada por el autor (p. ej. instruct, base). |

`name` es el único campo conceptualmente obligatorio: un modelo sin nombre
identificable no es representable. Los demás campos pueden ser desconocidos.

### 3.2 Provenance — procedencia básica

| Campo | Ejemplo |
|---|---|
| `source` | `"huggingface"` |
| `repository` | `"Qwen/Qwen3-Coder-30B-A3B"` |
| `author` | `"Qwen"` |

**IMPORTANTE: procedencia no significa confianza.** B8.0 no implementa:

- trust scores;
- firmas;
- hashes;
- cadenas de evidencia;
- verificación de autenticidad.

El sistema avanzado de evidencia/provenance queda para **B9 o posteriores**.
Nota: la verificación de integridad ya existente en el pipeline de descarga
actual (SHA-256) es independiente de este contrato y no se modifica.

---

### 3.3 Architecture — estructura del modelo

| Campo | Ejemplo |
|---|---|
| `architecture` | `"Transformer"` |
| `model_type` | `"MoE"` |
| `parameters` | `30B` |
| `active_parameters` | `3B` |

- Todos los valores pueden ser **desconocidos**.
- **No asumir automáticamente** que `active_parameters == parameters`: en
  arquitecturas densas suelen coincidir, pero solo la evidencia lo confirma.

### 3.4 Quantization — representación

| Campo | Ejemplos |
|---|---|
| `quantization_method` / método | `Q4_K_M`, `Q5_K_M`, `Q8_0` |
| `quantization_bits` | 4, 5, 8, 16 |

Diferencia conceptual obligatoria:

```text
no cuantizado   ≠   información desconocida
```

- Un artefacto `FP16`/`BF16` **no cuantizado** es un hecho confirmado.
- Que CastleArq no sepa la cuantización es **desconocido**.

En la implementación B8.1 se usará `None` para lo desconocido. **No se creará
un enum `UNKNOWN`** salvo que una necesidad real futura lo justifique.

#### Corrección B8.1 — `Precision != Quantization != Format`

La primera revisión del dominio corrigió la representación: **la precisión
numérica no es un método de cuantización** (BF16 no es "cuantización"). El
dominio final separa tres conceptos:

```text
ModelPrecision        → precisión numérica de los pesos (F32, F16, BF16,
                        FP8, …; sin enum cerrado; name/bits pueden ser None)
ModelQuantization     → estado explícito de cuantización del artefacto
QuantizationStatus    → UNKNOWN | NOT_QUANTIZED | QUANTIZED
format (artifact)     → contenedor (GGUF, Safetensors, …), independiente
```

Semántica de `QuantizationStatus`:

- `UNKNOWN` — no hay evidencia suficiente para determinar si el artefacto
  está cuantizado.
- `NOT_QUANTIZED` — hay evidencia suficiente para afirmar que **no** está
  cuantizado (y entonces no admite método ni bits).
- `QUANTIZED` — hay evidencia suficiente para afirmar que está cuantizado;
  método y `nominal_bits` pueden ser conocidos o desconocidos.

`UNKNOWN ≠ NOT_QUANTIZED`: nunca se representan con el mismo valor ni se
convierten automáticamente el uno en el otro. Tampoco se inventa precisión
base desde la cuantización: para `GGUF + Q4_K_M` la precisión queda
desconocida (no se asume `FP4`). `nominal_bits` es una cifra declarada:
nunca el promedio real de bits por parámetro ni un insumo de memoria.

### 3.5 Format — formato del artefacto

El formato es **independiente de la cuantización**:

```text
GGUF, Safetensors, ONNX, ...
```

```text
format ≠ quantization
```

Son conceptos diferentes: `GGUF / Q4_K_M` declara formato `GGUF` y
cuantización `Q4_K_M`; el mismo formato puede contener cualquier cuantización
(incluida ninguna o desconocida).

### 3.6 Resources — recursos representables inicialmente

CastleArq representa inicialmente:

- `storage_size`: tamaño del archivo en disco.
- `max_context`: contexto máximo declarado del artefacto.

**Decisión arquitectónica:**

```text
storage_size ≠ runtime_memory
```

El tamaño del archivo **no debe usarse** como equivalente al consumo de
memoria durante la inferencia.

**No introducir todavía** (pertenecen a la capa de compatibilidad):

- VRAM required;
- RAM required;
- CPU required;
- total runtime memory;
- estimated inference memory.

### 3.7 Capabilities — semántica del identificador `code_generation`

`ModelCapabilities` (B8.1, `app/model_domain.py`) fija cinco identificadores
—`text_generation`, `code_generation`, `vision`, `embeddings`, `tool_use`— y su
representación ternaria `True/False/None` (B8.0 §5, §8). Esta sección fija la
**semántica normativa** del identificador `code_generation`, que hasta ahora
existía como identificador sin límites operativos definidos.

**Decisión B8.1 — definición normativa:**

```text
code_generation = the capability to produce, complete, transform, or modify
                  source code through content generation.
```

La definición es **agnóstica respecto del sujeto**: describe la capacidad, no
qué runtime, modelo o backend la posee. Esta sección **no** afirma que ningún
runtime, modelo o backend soporte `code_generation`.

**Incluye explícitamente:**

- generación de código desde una instrucción (`produce`);
- code completion (`complete`);
- code infilling (`complete` sobre un tramo parcial);
- fill-in-the-middle / FIM (`complete`/`transform` sobre prefijo y sufijo);
- transformación generativa de código (`transform`);
- corrección o refactorización generativa de código (`modify`).

**No incluye por sí sola:**

- explicar código, o analizarlo sin producir código;
- ejecutar código;
- ejecutar comandos;
- usar herramientas (`tool_use`);
- manipular repositorios;
- comportamiento autónomo de agente de software.

**Reglas de no-inferencia (evidencia, no solapamiento semántico):**

Estas reglas rigen la **propagación de evidencia entre identificadores**, en la
línea de B9.4 §18 y B9.6.0 §17-§18. No declaran disjunción semántica entre
capacidades: que un runtime produzca texto que resulte ser código no crea por sí
mismo ninguna afirmación de `code_generation`.

- `tool_use` no implica `code_generation`;
- `text_generation` no implica `code_generation`;
- que el nombre de un modelo contenga «Coder» no implica `code_generation`;
- soportar un lenguaje de programación no implica `code_generation`;
- ejecutar código no implica `code_generation`;
- que otro runtime soporte `code_generation` no implica que este lo soporte.

**Regla de evidencia para runtime:** una afirmación «runtime → SUPPORTS →
`code_generation`» requiere evidencia explícita de que el runtime proporciona
una operación, interfaz o funcionalidad documentada capaz de producir,
completar, transformar o modificar código (B9.6.0 §7). Ninguna otra capacidad,
nombre de modelo, formato o vendor sustituye esa evidencia.

**Alcance de esta sección:** fija únicamente `code_generation`. La semántica de
los otros cuatro identificadores y la ampliación de la taxonomía (audio,
reranking, speech, …) permanecen abiertas (§8).

## 4. Runtime memory vs storage size

**Decisión arquitectónica:** el consumo de memoria durante la ejecución no es
una propiedad fija y aislada del modelo. Conceptualmente depende de:

```text
model + artifact + quantization + context + runtime + backend
        + offloading + configuration
```

Por lo tanto, una futura representación **no debe reducirlo** a una cifra
contexto-independiente:

```text
memory_required = 20 GB     ← INVÁLIDO como propiedad del modelo/artefacto
```

La futura **Compatibility Engine** será la responsable de estimar/analizar la
viabilidad de ejecución considerando modelo + artefacto + hardware + runtime +
configuración. El dominio del modelo solo aporta los insumos factuales
(`storage_size`, `parameters`, `active_parameters`, `max_context`, …).

---

## 5. UNKNOWN mediante `None`

**Decisión de B8.0:**

```text
None == información desconocida
```

Ejemplos:

```text
parameters        = None
source            = None
vision            = None
quantization_bits = None
```

`None` **no significa** necesariamente "el atributo no existe"; significa:

```text
CastleArq no tiene información suficiente para afirmarlo.
```

Esta decisión mantiene coherencia con la filosofía de evidencia ya usada en
B2/B7 (`FunctionalCheck.passed ∈ {True, False, None}`):
`None` nunca se interpreta como un valor afirmativo ni negativo.

## 6. Separación de responsabilidades

```text
Model                → describe qué es el modelo
ModelArtifact        → describe una variante concreta del modelo
Hardware             → describe qué hardware tiene el usuario
Runtime              → describe qué puede ejecutar
Compatibility Engine → interpreta todos esos datos
```

Consecuencia directa: **`Model` NO debe contener** campos de conclusión:

```text
compatible
can_run
recommended_gpu
recommended_vram
recommended_ram
```

Estos son resultados calculados posteriormente por la Compatibility Engine a
partir del modelo, el artefacto, el hardware y el runtime. Mezclarlos en el
dominio rompería la separación interpretar/detectar que sostiene B1–B7.

---

## 7. Alcance: fuera de B8.0 explícitamente

B8.0 **no** implementa:

- model discovery;
- Hugging Face API;
- filesystem scanning;
- model downloading;
- model installation;
- model execution;
- Ollama integration;
- llama.cpp integration;
- LM Studio integration;
- compatibility analysis;
- VRAM estimation;
- RAM estimation;
- inference benchmarking;
- model security verification;
- source trust evaluation;
- evidence chains;
- automatic system modification.

Todo ello pertenece a bloques posteriores.
